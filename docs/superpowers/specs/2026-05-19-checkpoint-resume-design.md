# Checkpoint-based Ingest Resume

Date: 2026-05-19

## Problem

Ingest pipeline has no resume mechanism. When an LLM call fails mid-ingest (rate limit, quota exhaustion, network error), all progress is lost. Re-running starts from scratch, which wastes tokens and can trap the user on a single large document that never completes within a quota window.

Additionally, the current `generate_pages_node` only processes the first 5 chunks (`chunks[:5]`), silently discarding the rest. Large documents lose content beyond ~20,000 tokens.

## Approach

Checkpoint files (JSON) track per-batch progress. Each batch is 5 chunks, processed sequentially with one LLM call each. Resume skips completed batches.

## Checkpoint Data Structure

Path: `.wiki-checkpoints/<source-path-slug>.json`

Source path slug is the file path with `/` replaced by `-`, safe for filenames (e.g. `data/web/arxiv.org/00f556a3.md` becomes `data-web-arxiv.org-00f556a3.md.json`).

```json
{
  "source": "data/web/arxiv.org/00f556a3.md",
  "source_title": "Attention Is All You Need",
  "total_chunks": 12,
  "batch_size": 5,
  "completed_batches": [0, 1],
  "generated_titles": ["BERT", "Transformer", "Attention Mechanism"]
}
```

### Lifecycle

| Event | Action |
|---|---|
| Ingest starts | Write initial checkpoint (`completed_batches: []`) |
| Each batch completes (LLM + pages written to disk) | Append batch index and generated titles to checkpoint |
| All batches done | Delete checkpoint file |
| `update_links` runs | No checkpoint needed (idempotent) |

## Modified Ingest Pipeline

### Current (linear, no resume)

```
extract -> chunk -> generate_pages (one shot, chunks[:5]) -> write -> update_links
```

### New (batch loop with checkpointing)

```
extract -> chunk -> [batch loop] -> update_links
```

Batch loop:
1. Read checkpoint, skip completed batches
2. Build prompt including list of already-generated page titles from previous batches
3. Call LLM to generate pages for this batch
4. Write pages to wiki directory
5. Update checkpoint (append batch index + titles)

### Batch atomicity

Within a batch, LLM call + page writes + checkpoint update are treated as one unit. Checkpoint is only updated after pages are successfully written. If any step fails, the checkpoint remains at the previous state and the batch is retried on resume.

### Cross-batch linking

Each batch's LLM prompt includes the titles of pages generated by previous batches:

> "The following wiki pages already exist: BERT, Transformer, Attention Mechanism"

This lets the LLM generate `[[wikilinks]]` to existing pages across batches. `update_links` then adds reverse links.

## Error Handling

### LLM call failure (rate limit, network error)

- Checkpoint not updated for the failed batch
- Completed batches unaffected (pages on disk)
- Resume retries the failed batch
- If all fallback providers fail, stop and preserve checkpoint

### Corrupt checkpoint file

- Log warning, treat as no checkpoint, start from scratch

### Source file modified after checkpoint created

- Compare source file modification time against checkpoint creation time
- If source is newer, delete checkpoint and start fresh

### Wiki pages manually deleted between runs

- No special handling. Checkpoint tracks "processed", not "pages exist"
- `update_links` simply has fewer links to process
- To fully regenerate, user deletes the checkpoint file manually

## CLI Changes

| Command | Behavior |
|---|---|
| `wiki ingest <source>` | Auto-detect and resume from checkpoint |
| `wiki ingest <source> --fresh` | Ignore checkpoint, start from scratch |
| `wiki ingest-all` | Process each file sequentially, auto-resume per file |
