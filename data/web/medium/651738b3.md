## Why are built-in prompts of evaluation frameworks off the mark & how to write your own.

It may sound counter-intuitive, but we use AI to evaluate AI.

Human evaluators are costly. Often, they are experts in their field and busy cracking other things. Getting them to evaluate AI-generated responses is next to impossible.

Also, you don’t stop evaluating LLMs. It’s a continuous process. You make changes to the system, the model, prompts, pipeline, etc., and you must evaluate them every time.

But unlike software projects, LLM outputs aren’t deterministic. You can’t programmatically assess their accuracy, relevancy, etc. This leaves us with only one choice — use LLMs to evaluate LLMs.

But it’s not different from any other LLM project. The difference is your prompt is now called an evaluation prompt.

You don’t have to write it. If you’re using libraries like [Deepeval](<https://deepeval.com/docs/getting-started>), you get built-in prompts. But their generic prompt is only a starting point for most projects (if you’re serious about them.)

So, you write them.

## Why should you write your evaluation prompt?

Writing evaluation prompts gives you more control.

Slight changes to the generic prompts can dramatically improve evaluations. I often re-prompt ChatGPT with a **marginal change and get better outputs**.

Have you used different LLM models before? Have you changed models in ChatGPT, or have you used different Chatbots (Gemini, Claude)? Have you tried the same prompt on them?

If you have, you’d know that the same **prompt behaves differently across models**.

Also, when you write your prompt, you can give more **specific steps to think** rather than autogenerated thinking.

These make the generic prompts not necessarily the best for your preferred model. So write them.

But if you’re to write them, how would you approach it?

## What makes a good evaluation prompt?

Evaluation prompts aren’t different from prompts for our regular application. The following is trivial.

> Evaluate the RESPONSE for accuracy in answering the QUESTION, using the CONTEXT as the source of truth.

But it’s far from perfect. You can’t expect a helpful response using this prompt.

Here are a few things you can do to help the LLM evaluate better.

### Binary labels are beautiful; three are helpful, but the rest aren’t.

LLMs _don’t_ remember past predictions, so they can’t maintain consistency unless earlier responses are fed back to the model.

Imagine you ask an LLM to score the accuracy of an answer on a 0–100 scale. You receive a score of 60. Then, you ask for the accuracy of another answer, and you get 50. However, it doesn’t mean the former is more accurate. The LLM evaluated these answers independently and doesn’t know why it assigned a score of 60 to the first and a score of 50 to the second.

But if you ask the LLM to label the answers as “accurate” or “inaccurate,” its responses could be (mostly) correct. Expecting precision in LLM responses is not a good decision.

Even humans do well if given a binary classification task.

But there are times when the LLM doesn’t get enough information to decide. Without a third option, the evaluator would still put the answer into one of the two buckets. So, having three labels, such as “accurate,” “inaccurate,” and “unknown,” would be smarter.

So, here’s a better version of the prompt we saw earlier.

> Evaluate the RESPONSE for accuracy in answering the QUESTION, using the CONTEXT as the source of truth. Return one of the following labels: ‘Accurate,’ ‘Not Accurate,’ or “Unknown.”

### Clearly define labels and borderline cases.

What is accuracy?

If you’re answering as a machine learning engineer, you’d say “percentage of total predictions that are correct.” But if you’re a thermometer manufacturer, accuracy means the closeness of a value to the real value.

Likewise, asking an LLM to classify as “accurate” or “inaccurate” is vague.

You should define what “accurate” means in clear terms.

For instance, state that “toxic” means “containing harmful or disrespectful words.” This is better than simply asking the model to classify toxic comments.

**But borderline cases are interesting.**

At times, the input falls under both buckets. For example, a word that can be disrespectful in one context but not in another may be in the input.

Take the word “boy.”

“You better do as you’re told, boy.”

In the above sentence, “ _boy”_ is not just age-related. It’s a **power move**. It strips the adult of his status.

But it has a positive connotation in “You’re my boy!”

Though the word “boy” rarely confuses everyday language, an LLM might get into tricky situations. We need to instruct how it should behave in such cases.

We may say something like, “When unsure, label them as ‘inaccurate.’” Now, the model would know how to handle them.

Here’s a modified version of our evaluation prompt:

> Evaluate the RESPONSE for accuracy in answering the QUESTION, using the CONTEXT as the source of truth. Return one of the following labels: ‘Accurate’ or ‘Not Accurate.’ _A response is “_ accurate _” if the context contain the exact value. lable them “_ inaccurate” _otherwise. If context has confusing information err to the side of_ ‘Not accurate.’

### Teach the difference between 3 and 4 when scoring is needed.

I’ve already mentioned that LLMs perform poorly on scoring tasks (or whenever precision is needed). But they are sometimes what we need.

But if this is what we want, we should be extra careful in the prompt.

We should define the difference between the scores. We need clear instructions on why the LLM would evaluate something to 3 but not 2 or 4.

This would become formidable when the score range increases. Thus, vow for a smaller range, like a 5-point Likert scale, and clearly explain when to pick each option.

Here’s a little trick if you still need a wider range.

Do the evaluation several times and average the scores. A mean or median value would be more appropriate when precision is your priority.

### To evaluate multiple dimensions, split them into multiple evaluations

Often, we don’t stop with one single metric.

For instance, accuracy alone won’t tell whether a retrieval augmented generation (RAG) app performs well. We need additional metrics, such as relevancy and faithfulness scores.

However, LLM evaluations are best when AI is given a single task to focus on. They get mixed up if we ask to generate all the metrics in a single prompt.

Simplify evaluation — one at a time.

Split the tasks. Whenever you need to evaluate several dimensions, consider them as individual tests. Each should have its evaluation prompt.

Need an overall score? Aggregate the individual values.

For instance, if you’ve evaluated for accuracy, relevancy, and faithfulness. You can take the sum or average of the three scores. You can also do a weighted average if you want some metric to have more influence on the overall score.

Splitting the evaluation helps reviewers understand the scores, especially if you’re evaluating online systems and find that the combined score drops suddenly; you know exactly where to look.

### Label some responses yourself for the LLM to learn from.

If you’re interested in prompt engineering, you’d know what few-shot learning is. It’s a powerful technique to teach the model to behave in a specific way by showing examples.

Few-shot learning has proven to be a powerful technique for influencing LLM outputs. It is a fast and effective alternative to advanced techniques like fine-tuning, which costs a fortune.

You can read more about this method in _“Language Models are Few-Shot Learners.”_ ([Brown et al., 2020](<https://arxiv.org/abs/2005.14165>)).

But there are a few things to be aware of.

First is skewness. Smaller models may get confused when they see more negative examples than positive ones (or vice versa)

If your examples are primarily about a single class, the model responses could be biased towards this class. In other words, if you provide 99 examples of what an offensive comment is and one example it is not, the model would predict most of your comments as offensive even though they aren’t. This is common for all machine learning classification tasks not specific to LLMs.

They also get confused when the examples are sorted (positives are given first, and negatives are given later). Prompt format and example ordering can impact few-shot results. You can read more about it in the paper _Calibrate Before Use: Improving Few-Shot Performance of Language Models.”_([Zhao et al., 2021](<https://arxiv.org/abs/2102.09690>))

### Make use of Chain of Thought Reasoning.

While few-shot learning is powerful, it is suited for structured problem-solving. For complex tasks, a zero-shot chain of thought may be better.

You can read about **Zero-Shot-CoT** in _“Chain-of-Thought Prompting” by_[Wei et al. (2022)](<https://arxiv.org/abs/2201.11903>) and in _“Large Language Models are Zero-Shot Reasoners_ ” by [Kojima et al. (2022)](<https://arxiv.org/abs/2205.11916>)

Newer reasoning models are exceptional in solving convoluted problems. Besides the final answer, you can retrieve and store their thinking process. This makes troubleshooting convenient.

## Other things that improve LLM-as-a-judge

We discussed prompting extensively. An unambiguous and detailed prompt is a must for evaluations. But besides the prompt, we can do a few other things to improve the process.

### Set the temperature low.

Temperature sets the randomness in AI-generated responses. Setting it to 0 would result in consistent output while setting it to 1 (some models even allow up to 2) makes the responses more random.

You may set it high for tasks demanding creativity. But for evaluations? They should be consistent.

Thus, it is set to a low value.

It doesn’t have to be 0. The model should have some freedom to make decisions.

### Experiment with models

I’ve already mentioned that prompts behave differently across models. And not every model is trained with evaluation in mind. Therefore, finding the model that best evaluates your data requires a systematic approach.

I would first start with a powerful model (like o3 or DeepSeek R1) and establish a baseline performance.

Take a sample of your question-and-answer pair and manually evaluate it. I’d do the same with a powerful model. Then, I can compare how well it does against my manual data. This is my baseline.

Now, I can switch to a smaller or different model. Chances are the performance drops. But could you afford the difference in favor of cost and latency?

## Final thoughts

There are situations where a human can’t do all the evaluation for AI-generated content.

Think about a chatbot that discusses sensitive information with the user. Or any AI-powered app that takes a user input and generates an AI response. It’s next to impossible.

However, using an LLM to judge AI-generated content saves a lot of time and money. The evaluation prompt makes or breaks this process.

Writing an evaluation prompt becomes essential. The generic ones in the evaluation framework are merely a starting point.

I hope these tips will help you when you build evaluation systems in the future.
