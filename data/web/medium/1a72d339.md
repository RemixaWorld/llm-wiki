In our previous discussion on Self-RAG, we mentioned its on-demand retrieval feature, which determines whether document retrieval is necessary based on the user’s query. If retrieval isn’t needed, the system directly returns results generated by the LLM (Large Language Model). This approach not only enhances system performance but also improves the user experience. In Self-RAG, on-demand retrieval is achieved through a specially trained LLM. However, in advanced RAG (Retrieval Augmented Generation) retrieval, we can use **query routing** to achieve this functionality. Query routing allows us to easily implement logic akin to If/Else statements in code. Today, we will explore the principles and implementation methods of query routing, and understand its usage in real-world projects through code examples.

## Query Routing

Query routing is an intelligent query distribution feature in RAG that selects the most suitable processing method or data source from multiple options based on the semantic content of the user’s input. Query routing can significantly enhance the relevance and efficiency of RAG retrieval, making it suitable for complex information retrieval scenarios, such as distributing user queries to different knowledge bases. The flexibility and intelligence of query routing make it a critical component in building efficient RAG systems.

### Types of Query Routing

Based on the principles of query routing implementation, we can categorize it into two types:

* **LLM Router** : By constructing effective prompts, LLM determines the intent of user queries. Existing implementations include LlamaIndex Router, among others.
* **Embedding Router** : By using an Embedding model, user queries are transformed into vectors, and intent is determined through similarity retrieval. Existing implementations include Semantic Router, among others.

Let’s delve into the implementation principles of these two types of query routing.

## LLM Router

Using LLM to determine user intent is currently a common routing method in RAG. First, all categories of the query are listed in the prompt, and then LLM classifies the query. Finally, the appropriate processing method is selected based on the classification result.

The LLM application framework [LlamaIndex](<https://www.llamaindex.ai/>) employs an LLM Router. In LlamaIndex, several query routing implementations exist, such as the `RouterRetriever`, `RouterQueryEngine`, and `RouterComponent` . Their fundamental principle is similar: initialize with a selector and a list of tool components, use the selector to get the index of the tool component, choose the corresponding tool component based on the index, and finally execute the tool component's processing logic. Here is an example code for `RouterQueryEngine`:

```python from llama_index.core.query_engine import RouterQueryEnginefrom llama_index.core.selectors import LLMSingleSelectorfrom llama_index.core.tools import QueryEngineTool# initialize toolslist_tool = QueryEngineTool.from_defaults( query_engine=list_query_engine, description="Useful for summarization questions related to the data source",)vector_tool = QueryEngineTool.from_defaults( query_engine=vector_query_engine, description="Useful for retrieving specific context related to the data source",)# initialize router query engine (single selection, llm)query_engine = RouterQueryEngine( selector=LLMSingleSelector.from_defaults(), query_engine_tools=[ list_tool, vector_tool, ],)query_engine.query("<query>") ```

* First, we construct two tools, `list_tool` and `vector_tool`, which are used for summarization queries and vector queries, respectively. `list_tool` uses `SummaryIndex` to build the retrieval engine, while `vector_tool` uses `VectorStoreIndex`.
* Next, we initialize `RouterQueryEngine`, passing in the selector and tool list.
* The selector here is `LLMSingleSelector`, which uses LLM to determine user intent and return a single selection result.
* Finally, the `query_engine.query` method is called with the user query, and `RouterQueryEngine` selects the appropriate tool based on the query and executes it.

* First, the selector derives a selection result based on the user’s query.
* The data is extracted from the selection result to obtain the tool component index.
* The component from the tool list is selected and executed based on the index.

LlamaIndex provides four kinds of selectors, as shown in the diagram below:

These four selectors use LLM to determine user intent, which can be divided into single-result selectors and multiple-result selectors. Single-result selectors return only one choice, while multiple-result selectors return several choices, merging them into a final result.

Based on parsing results, they can also be classified into text result selectors and object result selectors. Text result selectors use LLM’s completion API to generate text-type selection results formatted as `<index>. <reason>`, where `index` is the selection index, and `reason` is the rationale behind the selection. Object result selectors use LLM's Function Calling API to parse the selection result into a Python object. The default object is `SingleSelection`, defined as follows:

```python class SingleSelection(BaseModel): """A single selection of a choice.""" index: int reason: str ```

Examples of the two parsing results are as follows:

``` # Text selector2. Useful for questions related to oranges# Object selectorSingleSelection(index=2, reason="Useful for questions related to oranges") ```

When using a text result selector, further processing is required, such as extracting the index from the result. Object result selectors do not need extra processing, as the properties of the object can directly retrieve the result.

Let’s also examine the prompt template for the Selector:

``` DEFAULT_SINGLE_SELECT_PROMPT_TMPL = ( "Some choices are given below. It is provided in a numbered list " "(1 to {num_choices}), " "where each item in the list corresponds to a summary.
" "---------------------
" "{context_list}" "
---------------------
" "Using only the choices above and not prior knowledge, return " "the choice that is most relevant to the question: '{query_str}'
") ```

* This is the default prompt template for `LLMSingleSelector`.
* `{num_choices}` indicates the number of choices.
* `{context_list}` is the textual description of the tool component list, including the index and description.
* `{query_str}` is the user query.

A key aspect of using LLM Router is constructing effective prompts. If the LLM is sufficiently powerful, the prompts do not need to be very precise to achieve the desired effect. However, if the LLM isn’t strong enough, the prompts must be continually adjusted to obtain satisfactory results. During the author’s experience with LlamaIndex Router, it was found that while using OpenAI’s `gpt-3.5-turbo` model, the `LLMSingleSelector` occasionally failed to parse correctly. In contrast, the `PydanticSingleSelector` was relatively stable.

Once the selection index is obtained, it can be used to select the tool component, as shown in the `RouterQueryEngine` code snippet:

```python class RouterQueryEngine(BaseQueryEngine): def _query(self, query_bundle: QueryBundle) -> RESPONSE_TYPE: ...... result = self._selector.select(self._metadatas, query_bundle) selected_query_engine = self._query_engines[result.ind] final_response = selected_query_engine.query(query_bundle) ...... ```

* In the `_query` method of `RouterQueryEngine`, the selection result is first obtained through the selector.
* Based on the index in the selection result, the corresponding retrieval engine is chosen from `_query_engines`.
* Finally, the retrieval engine’s `query` method is invoked to generate the final result.

### Advantages and Disadvantages

* **Advantages** : Simple method, easy to implement.
* **Disadvantages** : Requires a relatively powerful LLM to correctly interpret user intent. If the selection result needs to be parsed into objects, the LLM must also support Function Calling capabilities.

## Embedding Router

Another approach to query routing involves using an Embedding model to vectorize user queries, followed by classifying the queries through vector similarity, which then determines the appropriate processing method.

[Semantic Router](<https://github.com/aurelio-labs/semantic-router>) is a routing tool built on this principle. It aims to provide ultra-fast AI decision-making capabilities, utilizing semantic vectors for rapid decisions to improve the efficiency of LLM applications and AI Agents. Semantic Router is very straightforward to use, as demonstrated in the following example code:

```python import osfrom semantic_router import Routefrom semantic_router.encoders import CohereEncoder, OpenAIEncoderfrom semantic_router.layer import RouteLayer# we could use this as a guide for our chatbot to avoid political conversationspolitics = Route( name="politics", utterances=[ "isn't politics the best thing ever", "why don't you tell me about your political opinions", "don't you just love the president", "they're going to destroy this country!", "they will save the country!", ],)# this could be used as an indicator to our chatbot to switch to a more# conversational promptchitchat = Route( name="chitchat", utterances=[ "how's the weather today?", "how are things going?", "lovely weather today", "the weather is horrendous", "let's go to the chippy", ],)# we place both of our decisions together into single listroutes = [politics, chitchat]# OpenAI Encoderos.environ["OPENAI_API_KEY"] = "<YOUR_API_KEY>"encoder = OpenAIEncoder()rl = RouteLayer(encoder=encoder, routes=routes)rl("don't you love politics?").name# politicsrl("how's the weather today?").name# chitchat ```

* First, we define two Routes: `politics` and `chitchat`, each containing multiple example utterances.
* Then, an Encoder is created, here using OpenAI’s Encoder to generate vectors via OpenAI’s Embedding model.
* Finally, a RouteLayer is created with the Encoder and Route list as input.
* The RouteLayer method is invoked with the user query to obtain a classification result. **Note** : Not every user query will match a preset classification result. If the user query doesn’t fall within a predefined category, the classification result might be empty.

The default Embedding model for OpenAI Encoder is `text-embedding-3-small`, which outperforms the previous OpenAI `text-embedding-ada-002` model and is also more cost-effective. Additionally, Semantic Router supports other Encoders, such as Huggingface Encoder, which uses the [sentence-transformers/all-MiniLM-L6-v2](<https://huggingface.co/sentence-transformers/all-MiniLM-L6-v2>) model by default. This sentence-transformer model maps sentences and paragraphs into a 384-dimensional vector space, suitable for tasks like classification or semantic search.

### Advantages and Disadvantages

* **Advantages** : Requires only an Embedding model, which is more efficient and resource-conserving than LLM Router.
* **Disadvantages** : Requires the pre-loading of example utterances. If the examples are insufficient or not comprehensive enough, the classification performance may be suboptimal.

## Practical Application of Query Routing

Let’s now integrate LlamaIndex and Semantic Router to create a query router that distributes user queries to various tool components. These components include engaging in chitchat with the LLM, retrieving documents using the RAG process to generate answers, and conducting web searches using the Bing search engine.

First, we define a tool component for chitchat with the LLM, using LlamaIndex’s [Pipeline](<https://docs.llamaindex.ai/en/stable/examples/pipeline/query_pipeline/>) feature to build a query pipeline. For more details on query pipeline functionality, you can refer to my previous article.

Here is the example code:

```python from llama_index.llms.openai import OpenAIfrom llama_index.core.query_pipeline import QueryPipeline, InputComponentllm = OpenAI(model="gpt-3.5-turbo", system_prompt="You are a helpful assistant.")chitchat_p = QueryPipeline(verbose=True)chitchat_p.add_modules( { "input": InputComponent(), "llm": llm, })chitchat_p.add_link("input", "llm")output = chitchat_p.run(input="hello")print(f"Output: {output}")# Display resultOutput: assistant: Hello! * Here, we use OpenAI’s `gpt-3.5-turbo` model to construct an LLM.
* Then, a `QueryPipeline` is built, adding `input` and `llm` modules. The `input` module is an input component with a default input parameter key named `input`.
* Next, a connection is established between the two modules.
* Finally, the `run` method is invoked with the user query to obtain a response.

Next, let’s add a base RAG tool component by similarly creating a query pipeline. For this, we’ll use the Wikipedia article on [The Avengers](<https://en.wikipedia.org/wiki/Avenger>) movie plot as our test document. Here’s the sample code:

```python from llama_index.core import SimpleDirectoryReader, VectorStoreIndexfrom llama_index.core.response_synthesizers.tree_summarize import TreeSummarizedocuments = SimpleDirectoryReader("./data").load_data()index = VectorStoreIndex.from_documents(documents)retriever = index.as_retriever(similarity_top_k=2)rag_p = QueryPipeline(verbose=True)rag_p.add_modules( { "input": InputComponent(), "retriever": retriever, "output": TreeSummarize(), })rag_p.add_link("input", "retriever")rag_p.add_link("input", "output", dest_key="query_str")rag_p.add_link("retriever", "output", dest_key="nodes")output = rag_p.run(input="Which two members of the Avengers created Ultron?")print(f"Output: {output}")# Display resultOutput: Tony Stark and Bruce Banner. ```

* The initial part involves the usual LlamaIndex retrieval engine construction process, using `SimpleDirectoryReader` to load test documents and `VectorStoreIndex` to construct a retriever.
* A query pipeline is created, adding `input`, `retriever`, and `output` modules. The `output` module is a tree summarize component.
* Connections are added among the three modules, with the `output` module utilizing the output from both the `input` and `retriever` modules.
* Finally, the `run` method is called with the user query to generate a response.

Next, let’s add a tool component that uses the Bing search engine. Again, we’ll create a query pipeline, but this time we need to employ a custom module. Here’s the example code:

```json web_p = QueryPipeline(verbose=True)web_p.add_modules( { "input": InputComponent(), "web_search": WebSearchComponent(), })web_p.add_link("input", "web_search") ```

* The web search tool is relatively simple, consisting of only two modules: `input` and `web_search`.
* The `WebSearchComponent` is a custom module that we'll explore in detail.

Before implementing this custom module, we need to create a Bing Search Service on Azure and obtain an API Key. For detailed steps, you can refer to Microsoft’s [official documentation](<https://learn.microsoft.com/en-us/bing/search-apis/bing-web-search/overview>). Then, install LlamaIndex’s Bing query tools library: `pip install llama-index-tools-bing-search`. Once done, we can start implementing the custom module, as shown below:

```python import osfrom typing import Dict, Anyfrom llama_index.core.query_pipeline import CustomQueryComponentfrom llama_index.tools.bing_search import BingSearchToolSpecfrom llama_index.agent.openai import OpenAIAgentclass WebSearchComponent(CustomQueryComponent): """Web search component.""" def _validate_component_inputs(self, input: Dict[str, Any]) -> Dict[str, Any]: """Validate component inputs during run_component.""" assert "input" in input, "input is required" return input @property def _input_keys(self) -> set: """Input keys dict.""" return {"input"} @property def _output_keys(self) -> set: return {"output"} def _run_component(self, **kwargs) -> Dict[str, Any]: """Run the component.""" tool_spec = BingSearchToolSpec(api_key=os.getenv("BING_SEARCH_API_KEY")) agent = OpenAIAgent.from_tools(tool_spec.to_tool_list()) question = kwargs["input"] result = agent.chat(question) return {"output": result} ```

* Let’s focus on the core method `_run_component` within the custom component.
* A `BingSearchToolSpec` object is created first, with the Bing search engine's API Key passed as an argument. Here, the API Key is stored in the `BING_SEARCH_API_KEY` environment variable.
* We use LlamaIndex’s Agent feature, creating an `OpenAIAgent` object and passing in the Bing search tool.
* Finally, the user’s query is obtained using `kwargs["input"]` and passed to the `agent.chat` method to get the search results, which are then returned.
* For more information on how to use the Bing search tool, you can refer to [its documentation](<https://llamahub.ai/l/tools/llama-index-tools-bing-search?from=>).

After creating the three tool components, we need to create a routing module. We’ll implement this routing module using Semantic Router by defining several Routes, as demonstrated in the following code:

``` chitchat = Route( name="chitchat", utterances=[ "how's the weather today?", "how are things going?", "lovely weather today", "the weather is horrendous", "let's go to the chippy", ],)rag = Route( name="rag", utterances=[ "What mysterious object did Loki use in his attempt to conquer Earth?", "Which two members of the Avengers created Ultron?", "How did Thanos achieve his plan of exterminating half of all life in the universe?", "What method did the Avengers use to reverse Thanos' actions?", "Which member of the Avengers sacrificed themselves to defeat Thanos?", ],)web = Route( name="web", utterances=[ "Search online for the top three countries in the 2024 Paris Olympics medal table.", "Find the latest news about the U.S. presidential election.", "Look up the current updates on NVIDIA's stock performance today.", "Search for what Musk said on X last month.", "Find the latest AI news.", ],) ```

* Here, we define three Routes, each targeting different types of queries.
* The `chitchat` Route consists of example utterances for casual conversations, corresponding to the `chitchat` tool component.
* The `rag` Route includes example queries related to the Avengers movie plot, aligning with the `rag` tool component.
* The `web` Route consists of web search-related queries with many keywords like `Search` and `Find`, corresponding to the `web` tool component.

Next, let’s create a custom routing module using Semantic Router to implement query routing, as shown below:

```python from llama_index.core.base.query_pipeline.query import ( QueryComponent, QUERY_COMPONENT_TYPE,)from llama_index.core.bridge.pydantic import Fieldclass SemanticRouterComponent(CustomQueryComponent): """Semantic router component.""" components: Dict[str, QueryComponent] = Field( ..., description="Components (must correspond to choices)" ) def __init__(self, components: Dict[str, QUERY_COMPONENT_TYPE]) -> None: """Init.""" super().__init__(components=components) def _validate_component_inputs(self, input: Dict[str, Any]) -> Dict[str, Any]: """Validate component inputs during run_component.""" return input @property def _input_keys(self) -> set: """Input keys dict.""" return {"input"} @property def _output_keys(self) -> set: return {"output", "selection"} def _run_component(self, **kwargs) -> Dict[str, Any]: """Run the component.""" if len(self.components) < 1: raise ValueError("No components") if chitchat.name not in self.components.keys(): raise ValueError("No chitchat component") routes = [chitchat, rag, web] encoder = OpenAIEncoder() rl = RouteLayer(encoder=encoder, routes=routes) question = kwargs["input"] selection = rl(question).name if selection is not None: output = self.components[selection].run_component(input=question) else: output = self.components["chitchat"].run_component(input=question) return {"output": output, "selection": selection} ```

* In the constructor function `__init__` of the custom module, a dictionary is passed with keys representing Route names and values corresponding to the respective tool components.
* In the `_output_keys` method, two output keys are returned: one for the output result and one for the selection result.
* In the `_run_component` method, the tool component parameters are first validated to ensure the presence of the `chitchat` tool component, as queries that can't be classified need to be dispatched to the `chitchat` tool component.
* Semantic Router is used to determine the user’s query intent, obtaining a selection result `selection`.
* The appropriate tool component is then chosen and executed based on the selection result.
* If the selection result is empty, the `chitchat` tool component is chosen and executed.
* Finally, the output result and selection result are returned.

Finally, we add all the tool components and the routing module into a separate query pipeline, as demonstrated below:

```json p = QueryPipeline(verbose=True)p.add_modules( { "router": SemanticRouterComponent( components={ "chitchat": chitchat_p, "rag": rag_p, "web": web_p, } ), }) ```

* The newly created query pipeline contains only one module, `router`, which is our custom routing module `SemanticRouterComponent`.
* Within the routing module, we pass the three previously defined query pipelines, indicating that different user intents trigger different query pipelines.
* Since there’s only one module, no connection setup is needed.

Let’s execute this pipeline and observe how it performs:

``` output = p.run(input="hello")# Selection: chitchat# Output: assistant: Hello! How can I assist you today?output = p.run(input="Which two members of the Avengers created Ultron?")# Selection: rag# Output: Tony Stark and Bruce Banner.output = p.run(input="Search online for the top three countries in the 2024 Paris Olympics medal table.")# Selection: web# Output: The top three countries in the latest medal table for the 2024 Paris Olympics are as follows:# 1. United States# 2. China# 3. Great Britain ```

As observed, our query router functions effectively, selecting different tool components based on the distinct user query intents and providing corresponding results.
