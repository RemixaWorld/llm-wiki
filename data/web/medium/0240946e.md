In the ever-evolving landscape of artificial intelligence, **retrieval-augmented generation (RAG)** has been a significant leap forward, especially in addressing factual inaccuracies in large language model (LLM) outputs. RAG enables models to retrieve relevant external knowledge, thereby improving the accuracy and contextual relevance of their responses. However, even RAG has its limitations. It often retrieves documents indiscriminately, without evaluating whether the retrieved information meaningfully contributes to answering the query. This can result in cluttered or even misleading outputs.

To address these limitations, researchers have introduced **Self-Retrieval-Augmented Generation (Self-RAG)** , an advanced strategy that enhances RAG by incorporating **self-reflection** and **self-grading** into the retrieval and generation processes. In this article, I’ll be implementing my own take on Self-RAG, focusing on two key improvements: **self-correction** through relevance assessment of retrieved documents, and **self-reflection** by checking for hallucinations and evaluating the relevance of the generated responses.

I’ve slimmed down the approach described in the original paper to optimize for **reduced latency and costs** , making this version more efficient while still maintaining accuracy and reliability.

## What is Self-RAG?

**Self-Reflective Retrieval-Augmented Generation (Self-RAG)** is a framework that augments traditional RAG by adding a self-assessment mechanism, allowing the system to critically evaluate both the retrieved documents and the generated responses. In conventional RAG, the retrieval process is often indiscriminate. Documents are retrieved without assessing their true relevance to the query, and no reflection occurs on whether the generated response is aligned with the retrieved information.

In my approach to Self-RAG, I focus on two primary functions:

1. **Self-Correction by Assessing Relevance of Chunks** :
At each step of retrieval, the system will assess the relevance of the retrieved chunks. By actively checking whether the chunks are useful for answering the question, the system avoids clutter and ensures that only high-quality, relevant data is passed to the generation process.
2. **Self-Reflection by Checking for Hallucinations and Relevance** :
After generating a response, the system will evaluate the response for hallucinations, ensuring that all key claims are supported by the retrieved documents. This reduces the likelihood of generating unsupported or factually incorrect content. Additionally, the relevance of the response to the query is graded, ensuring the output is both factually accurate and contextually appropriate. If the generated response is **not fully supported** by the retrieved documents or is flagged as irrelevant, the system will initiate an **additional web search** to gather more information. The results of this web search will then be **fed back into the generation process** , allowing the model to refine its response with higher-quality data.

This streamlined approach focuses on minimizing latency and computational costs by avoiding unnecessary document retrievals and adding lightweight checks for hallucinations and relevance. The result is an efficient yet powerful Self-RAG framework that retains the core benefits of reflection and correction without the overhead of more complex implementations.

### Retriever

The **retriever** plays a central role in our Self-RAG system by fetching relevant text chunks from the vectorstore. These chunks contain the information that will be used to generate responses to the user’s questions. The retriever’s job is to scan the vectorstore for document embeddings that are most relevant to the query and return them for further processing.

To set this up, we first initialize the retriever from the vectorstore:

``` retriever = vectorstore.as_retriever() ```

This line ensures that our vectorstore, which contains the preprocessed and vectorized documents, is ready to handle retrieval queries efficiently.

Next, we define the `retrieve` function, which takes in the current **state** (which includes the user’s question) and returns the most relevant documents:

```python def retrieve(state: Dict[str, Any]) -> Dict[str, Any]: print("---RETRIEVE---") question = state["question"] documents = retriever.invoke(question) return {"documents": [doc.page_content for doc in documents], "question": question} ```

### Websearch

In cases where the initial retrieval of documents from the vectorstore does not provide sufficient information or relevant content, we can turn to **web search** as an additional step in the Self-RAG process. By performing a web search, we ensure that the system has access to the latest and most comprehensive information, which can be particularly helpful when dealing with time-sensitive or specialized queries that are not fully covered by the vectorstore.

For this purpose, we will use **TavilySearch** , a tool designed to fetch information from the web based on the user’s query. The results are returned as text chunks, which can then be processed in the same way as the documents retrieved from the vectorstore.

Here’s the implementation of the **web_search** function:

```python def web_search(state: Dict[str, Any]) -> Dict[str, Any]: print("---WEB SEARCH---") question = state["question"] documents = state["documents"] docs = TavilySearchResults(k=3).invoke({"query": question}) web_results = "
".join([d["content"] for d in docs]) documents.append(web_results) return {"documents": documents, "question": question, "web_search": "Yes"} ```

Key steps in the websearch function:

1. **Input** : The function accepts the current **state** , which includes the user’s question and the retrieved documents (if any) from the vectorstore.
2. **Perform the Web Search** : Using the **TavilySearchResults** method, we perform a web search based on the user’s query. This retrieves three relevant chunks of information from the web (`k=3`), which can be adjusted depending on how much information we want to retrieve.
3. **Combine and Append Results** : The search results are combined into a single string (`
` is used to separate chunks), and then appended to the list of documents previously retrieved. This ensures that the web search results are integrated into the response generation process.\
4. **Output** : The function returns the updated list of documents, along with the original question and a flag (`"web_search": "Yes"`) indicating that a web search was performed. This flag can be useful later in the pipeline for decision-making purposes.

### Grade Documents

An essential part of the **self-correction** mechanism in Self-RAG is grading the relevance of the retrieved text chunks. Not every document retrieved from the vectorstore will be useful or relevant to the user’s query. To ensure that only meaningful data is passed on to the generation process, we implement a grading step where each document is evaluated for relevance.

This grading process helps filter out irrelevant information, improving the accuracy and focus of the final response. The key to this step is using a **retrieval grader** , powered by a large language model (LLM), that assesses whether each document contains keywords or content related to the user’s question.

First, we define a **prompt template** that instructs the LLM to act as a grader, assigning a simple binary score (`yes` or `no`) based on whether the document is relevant to the question. The test does not need to be overly stringent; the goal is to quickly filter out erroneous or irrelevant retrievals.

``` retrieval_grader_prompt = PromptTemplate( template="""You are a grader assessing relevance of a retrieved document to a user question. If the document contains keywords related to the user question, grade it as relevant. It does not need to be a stringent test. The goal is to filter out erroneous retrievals. Give a binary score 'yes' or 'no' score to indicate whether the document is relevant to the question. Provide the binary score as a JSON with a single key 'score' and no preamble or explanation. Here is the retrieved document: {document} Here is the user question: {question}""", input_variables=["question", "document"],) ```

Next, we combine the **retrieval_grader_prompt** with the LLM and a JSON output parser to create a **retrieval grading chain** :

``` retrieval_grader = retrieval_grader_prompt | model | JsonOutputParser() ```

This retrieval_grader chain will be used to assess each document retrieved by the system.

Next, the `grade_documents` function processes each document retrieved from the vectorstore (or web search) and filters out those that are deemed irrelevant. Here’s the code:

```python def grade_documents(state: Dict[str, Any]) -> Dict[str, Any]: print("---CHECK DOCUMENT RELEVANCE TO QUESTION---") question = state["question"] documents = state["documents"] filtered_docs = [] # Iterate through each document and assess its relevance for doc in documents: score = retrieval_grader.invoke({"question": question, "document": doc}) # Only keep documents marked as relevant if score["score"].lower() == "yes": print("---GRADE: DOCUMENT RELEVANT---") filtered_docs.append(doc) else: print("---GRADE: DOCUMENT NOT RELEVANT---") return {"documents": filtered_docs, "question": question} ```

Key steps in the function:

1. **Input (State)** : The function accepts the current **state** , which includes the user’s question and the documents retrieved in previous steps (from either the vectorstore or the web search).
2. **Grading Process** : For each document, the **retrieval grader** is invoked. The model assesses whether the document is relevant to the question and returns a score in JSON format (`yes` for relevant, `no` for irrelevant).
3. **Filtering** : If a document is graded as relevant (`yes`), it is appended to the list of **filtered documents**. Irrelevant documents are discarded.
4. **Output** : The function returns the updated list of filtered documents, which will be passed on to the next steps in the Self-RAG process, as well as the original question.

### Generate

Once relevant chunks of text have been retrieved and graded, the next step in the Self-RAG process is to **generate a response** for the user. This is where the system takes the retrieved documents and formulates an accurate, informative, and well-structured reply based on the user’s query.

To accomplish this, we define a **prompt template** that sets clear rules for how the response should be generated. The goal is to simulate a professional, knowledgeable assistant that delivers precise answers based on the retrieved content, without introducing any fabrications.

Here’s how we define the **answer prompt** :

``` answer_prompt = PromptTemplate( template="""You are a scientific research assistant and engage in a professional and informative conversation with a person. **RULES** - Use a neutral, objective, and respectful tone. - Never fabricate information. Use only the information provided in the context. - Answer from the perspective of a neutral and independent researcher. - Avoid phrases like "according to the website" or "based on the documentation" or "in the given context." - Do not end an answer with "for further information contact..." - Be precise, but feel free to be creative with your explanations while remaining professional. - Use markdown formatting for your output, but do not use headings or titles. - Do not ask follow-up questions. Question: {question} Context: {context} Answer:""", input_variables=["question", "context"],) ```

Once the prompt is defined, we can combine it with the LLM (in this case, Claude 3.5 Sonne**t**) and a string output parser, creating a **retrieval-augmented generation (RAG) chain** :

``` rag_chain = answer_prompt | model | StrOutputParser() ```

Now, we define the function that will invoke this RAG chain to generate a response:

```python def generate(state: Dict[str, Any]) -> Dict[str, Any]: print("---GENERATE---") question = state["question"] documents = state["documents"] # Generate an answer using the retrieved documents as context answer = rag_chain.invoke( {"context": "

".join(documents), "question": question} ) return {"documents": documents, "question": question, "answer": answer} ```

How the function works:

1. **Input** : The function accepts the current **state** , which contains the user’s question and the documents retrieved in the previous steps (from the vectorstore or websearch).
2. **Context Building** : The retrieved documents are combined into a single string, with each chunk separated by a newline. This serves as the **context** for generating the response.
3. **Generate the Answer** : The `rag_chain.invoke()` method is called, which feeds the question and context into the model, generating a precise answer that aligns with the factual content from the documents.
4. **Output** : The function returns the generated answer along with the documents and question.

### Hallucination Grader

In language models, hallucinations refer to confidently generated responses that are not factually grounded in the retrieved data. This can lead to misleading answers, especially if the generated response isn’t fully supported by the documents provided. To address this, the **hallucination grader** evaluates the answer and ensures that it is grounded in facts and directly relevant to the user’s query. If the hallucination grader detects that the answer is irrelevant or contains hallucinations, it triggers a fallback mechanism: sending the query to a web search to retrieve more accurate information.

The **hallucination_grader_prompt** is designed to evaluate whether the generated answer is fully supported by the retrieved documents. The model assigns a binary score (`yes` or `no`) based on whether the response is grounded in the facts.

``` hallucination_grader_prompt = PromptTemplate( template="""You are a grader assessing whether an answer is grounded in / supported by a set of facts. Give a binary score 'yes' or 'no' score to indicate whether the answer to the question is grounded in / supported by a set of facts. Also, make sure that the answer actually addresses the question. Provide the binary score as a JSON with a single key 'score' and no preamble or explanation. Here is the question: {question} Here are the facts: {documents} Here is the answer: {answer}""", input_variables=["answer", "documents", "question"],) ```

Once the hallucination grader prompt is defined, we can combine it with the model and a JSON output parser to create a **hallucination_grader chain**. This chain evaluates whether the generated answer is factually grounded.

``` hallucination_grader = hallucination_grader_prompt | model | JsonOutputParser() ```

Next, the `grade_answer_v_documents_and_question` function processes the generated response, checks if it is fully supported by the retrieved documents, and decides whether additional steps like a web search are required.

```python def grade_answer_v_documents_and_question(state: Dict[str, Any]) -> str: print("---CHECK HALLUCINATIONS---") # If a web search has already been performed, we skip the hallucination check if state['web_search'] == "Yes": return 'useful' # If no web search was performed yet, grade the generated answer for hallucinations else: score = hallucination_grader.invoke( {"documents": state["documents"], "answer": state["answer"], "question": state["question"]} ) print('hallu score', score) # If the answer is supported by facts, mark it as useful if score["score"] == "yes": return "useful" # If the answer is not supported (detected as a hallucination), send the query to web search else: print("---ANSWER NOT SUPPORTED, INITIATING WEB SEARCH---") return "websearch" ```

Key steps in the function:

1. **Input (State)** : The function accepts the **state** , which includes the user’s question, retrieved documents, and the generated response.
2. **Avoiding Redundant Checks** : If a web search has already been performed, the function skips the hallucination check to avoid a loop and returns the response as **useful**.
3. **Grading the Response** : If no web search was performed, the hallucination grader evaluates whether the generated answer is supported by the facts in the retrieved documents.
4. **Decision Process** : If the response is factually grounded, the function returns **useful**. If the response is not supported by the documents (i.e., it contains hallucinations or is irrelevant), the function triggers a **web search** to gather more information and improve the response.

### Define the AI Agent Graph

Now that we’ve defined the core components — retrieving, grading, and generating and grading responses — it’s time to assemble these building blocks into a cohesive system. To effectively manage the flow of tasks, we structure the AI agent using a stateful graph. This allows for dynamic decision-making at each step, ensuring that the agent can adjust its actions based on the input and evolve as it processes information. The AI agent graph is built using nodes (representing tasks), edges (which define the logical flow between tasks), and conditional edges (allowing the system to adapt and redirect based on specific conditions).

**State Definition**

The **state** stores key parameters that persist throughout the AI agent’s workflow. These parameters are passed between the nodes as the agent processes the user’s question, retrieves relevant information, and generates and grades the answer. The **state** includes the following parameters:

* **question** : The original query posed by the user.
* **answer** : The final generated response to the user’s question.
* **web_search** : A flag to indicate whether a web search has been performed. This helps avoid unnecessary loops in the workflow.
* **documents** : A list of relevant text chunks retrieved either from the vectorstore or through web search.

Here’s how we define the **state** :

```python # Define the Stateclass GraphState(TypedDict): question: str answer: str web_search: str documents: list[str] ```

This state will be maintained and updated as the AI agent processes the query, allowing the agent to remember past decisions and adapt dynamically.

**Workflow Definition**

The workflow represents the entire sequence of tasks (nodes) the AI agent will perform, as well as the transitions between those tasks (edges). Each node in the workflow represents a specific task (such as document retrieval or generating an answer), while edges define the logical connections between these tasks.

**Nodes** are the tasks or actions that the agent performs. Here, we define four key nodes:

1. **websearch** : This node performs a web search if the initial retrieval fails or if the generated answer is unsupported.
2. **retrieve** : This node retrieves relevant documents from the vectorstore based on the user’s query.
3. **grade_documents** : This node filters and grades the retrieved documents to ensure only relevant content is used.
4. **generate** : This node generates a response based on the retrieved and graded documents.

Here’s how we define and add the nodes to the workflow:

``` # Define the LangGraph workflowworkflow = StateGraph(GraphState)# Add Nodesworkflow.add_node("websearch", web_search)workflow.add_node("retrieve", retrieve)workflow.add_node("grade_documents", grade_documents)workflow.add_node("generate", generate) ```

**Edges** define how the nodes are connected and the order in which tasks are performed. In this workflow, edges represent the sequence of actions, starting from document retrieval, through grading and response generation, and optionally performing a web search if needed.

Here’s how we define and add the edges:

``` # Add Edgesworkflow.add_edge(START, "retrieve")workflow.add_edge("retrieve", "grade_documents")workflow.add_edge("grade_documents", "generate")workflow.add_edge("websearch", "generate") ```

This setup ensures that the agent first retrieves documents, grades them, generates a response, and — if needed — performs a web search to supplement the information.

**Conditional edges** introduce decision points in the workflow, allowing the system to dynamically decide which node to proceed to next based on the input or output from the previous node. In this case, we add a conditional edge after the **generate** step. If the generated answer is deemed irrelevant or unsupported (detected as a hallucination), the agent will initiate a web search. If the answer is useful and factually grounded, the workflow will terminate.

```json # Add Conditional Edge: this edge decides if the answer is relevant, if not a websearch will be performedworkflow.add_conditional_edges( "generate", grade_answer_v_documents_and_question, { "not supported": "websearch", "useful": END, },) ```

This conditional edge helps maintain the accuracy and reliability of the AI agent’s responses by incorporating an additional web search step when needed.

After defining all the nodes, edges, and conditional logic, we **compile the workflow**. This step ensures that the entire process is connected and ready to execute:

``` # Compile the workflowcompiled_workflow = workflow.compile() ```

Once compiled, the AI agent can seamlessly move through the various stages of retrieval, grading, and response generation, dynamically adapting when it encounters unsupported answers by triggering a web search.
