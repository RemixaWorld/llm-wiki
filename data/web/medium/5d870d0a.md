Recently i worked on a project where the goal was to fine-tune a small language model using domain-specific data for a client. after exploring a few approaches, i decided to go with RAFT — retrieval-augmented fine-tuning — to get the best of both retrieval and supervised learning.

For this, i used unsloth to fine-tune a qwen3–4b model. the workflow was pretty straightforward — first i generated the training data from the client’s files, then cleaned and structured it, applied a chat-style template, and finally started the fine-tuning process.

We ended up with strong results — especially after fine-tuning the contextual embedding model for the domain and also the Re-ranker alongside it. i’ve covered those parts in earlier posts, and i’ll link to them at the end of this one. here, the focus is on the generation side of things — how we built and shaped the data to actually teach the model what it needs to know.

### RAFT: Adapting Language Model to Domain Specific RAG

Press enter or click to view image in full size

[RAFT](<https://arxiv.org/abs/2403.10131>) — short for retrieval-augmented fine-tuning — is a method that combines the strengths of retrieval-augmented generation with supervised fine-tuning. instead of just training a model on static data, raft introduces relevant documents (and sometimes irrelevant ones) during training, helping the model learn how to ground its answers in actual context. this not only improves accuracy but also reduces hallucinations, especially in domain-specific tasks. it’s like teaching a model to reason with notes in hand — and know when to trust them.

### Qwen3

Press enter or click to view image in full size

[Qwen3](<https://huggingface.co/Qwen>) is the latest generation of open‑source language models from Alibaba, spanning compact versions like 0.6b and 4b all the way up to massive moes with 235b parameters. it introduces a hybrid reasoning design, letting the model dynamically switch between a “thinking” mode — for complex tasks like math, coding, or logic — and a “non‑thinking” mode for faster, general responses . beyond just reasoning, qwen3 supports long context windows (up to ~128k tokens), multilingual understanding across 119 languages, and both dense and mixture‑of‑experts architectures — a powerful foundation for fine‑tuning with systems like peft , trl , unsloth...

### Unsloth

Press enter or click to view image in full size

Unsloth is an open‑source fine‑tuning library that makes adapting LLMs dramatically faster and more efficient. by replacing key PyTorch operations with custom Triton GPU kernels, it delivers roughly 2× faster training and slashes memory usage by up to 70%, all without losing accuracy .

It’s fully compatible with Hugging Face, peft and trl workflows, supports LoRA/QLoRA on Nvidia GPUs from entry-level T4s to high-end H100s, and works smoothly even in free Colab/Kaggle environments . that combination of speed, efficiency, and open‑source flexibility makes unsloth a great match for more experimental pipelines like RAFT and qwen3 fine‑tuning.

### Generating the RAFT training dataset

In this step, we prepare the dataset for retrieval-augmented fine-tuning using llama-index’s `RAFTDatasetPack`.

```python import osfrom llama_index.packs.raft_dataset import RAFTDatasetPackfrom llama_index.llms.google_genai import GoogleGenAIfrom llama_index.embeddings.google_genai import GoogleGenAIEmbeddingGOOGLE_API_KEY = "xxxxxx-xxxxxxxxxx" os.environ["GOOGLE_API_KEY"] = GOOGLE_API_KEYllm = GoogleGenAI(model="gemini-2.5-flash-preview-05-20")embed_model = GoogleGenAIEmbedding(model_name="text-embedding-004")file_path = "/path/to.txt" # or md or pdf .. raft_dataset = RAFTDatasetPack(file_path , llm=llm , embed_model=embed_model , num_questions_per_chunk=3 , num_distract_docs=3 , chunk_size=2048)dataset = raft_dataset.run() ```

As we saw above, a Gemini 2.5 model handles the question generation while Google's embedding API creates vector representations. the dataset is built from a source file (txt, md, or pdf), where each chunk is paired with generated questions and distractor documents to simulate retrieval scenarios. the final output is a structured dataset ready for supervised fine-tuning.

### Formatting and saving the dataset

After generating the initial RAFT dataset, we convert it to a Hugging Face–compatible format.

```python import datasetsdf = dataset.to_pandas()# Combine 'user' and 'assistant' columns into a new 'messages' column as list of dictionariesdf['messages'] = df.apply(lambda row: [{'content': row['instruction'], 'role': 'user'}, {'content': row['cot_answer'], 'role': 'assistant'}], axis=1)dataset = datasets.Dataset.from_pandas(df)# Optional (save the dataset)output_path = "data"dataset.save_to_disk(output_path)dataset.to_json(output_path + ".jsonl") ```

Eeach data point is reshaped into a chat-style structure with `user` and `assistant` messages to match instruction-tuning standards. finally, the dataset is saved both to disk and as a `.jsonl` file for flexibility in downstream training or inspection.

### Loading the base model with unsloth

Here we load the `qwen3-4b-128k` model using unsloth’s optimized `FastLanguageModel` wrapper.

```python from unsloth import FastLanguageModelimport torchmodel, tokenizer = FastLanguageModel.from_pretrained( model_name = "unsloth/Qwen3-4B-128K", max_seq_length =4096 , # Context length - can be longer, but uses more memory load_in_4bit = True, # 4bit uses much less memory load_in_8bit = False, # A bit more accurate, uses 2x memory full_finetuning = False, # We have full finetuning now! # token = "hf_...", # use one if using gated models) ```

The model is configured for efficient fine-tuning with 4-bit quantization, keeping memory usage low while supporting long context windows up to 4k tokens. this setup is ideal for instruction-tuning on custom datasets.

### Applying the chat template

To prepare the dataset for instruction tuning, we define and apply a custom chat template that formats each example using Qwen-style role tags.

```python import reimport randomfrom multiprocessing import cpu_count# Set chat templateDEFAULT_CHAT_TEMPLATE = "{% for message in messages %}
{% if message['role'] == 'user' %}
{{ '<|user|>
' + message['content'] + eos_token }}
{% elif message['role'] == 'system' %}
{{ '<|system|>
' + message['content'] + eos_token }}
{% elif message['role'] == 'assistant' %}
{{ '<|assistant|>
' + message['content'] + eos_token }}
{% endif %}
{% if loop.last and add_generation_prompt %}
{{ '<|assistant|>' }}
{% endif %}
{% endfor %}"tokenizer.chat_template = DEFAULT_CHAT_TEMPLATESYSTEM_PROMPT = """You are a helpful question answerer who can provide an answer given a question and relevant context. """def apply_chat_template(example, tokenizer): messages = example["messages"] # We add an empty system message if there is none if messages[0]["role"] != "system": messages.insert(0, {"role": "system", "content": SYSTEM_PROMPT}) example["text"] = tokenizer.apply_chat_template(messages, tokenize=False) return examplecolumn_names = list(dataset.features)raw_datasets = dataset.map(apply_chat_template, num_proc=cpu_count(), fn_kwargs={"tokenizer": tokenizer}, remove_columns=column_names, desc="Applying chat template",) ```

As we saw earlier, each interaction includes a `user` message and an `assistant` response — here, we also insert a `system` prompt to guide the assistant’s behavior. the final output is a clean, model-ready text field built with `tokenizer.apply_chat_template`, applied efficiently in parallel using all available CPU cores.

### Configuring LoRA fine-tuning with SFTTrainer

In this section, we set up LoRA-based fine-tuning using unsloth and `trl`'s `SFTTrainer`.

```python from trl import SFTTrainer, SFTConfigraw_datasets = raw_datasets.train_test_split(test_size=0.1)# create the splitstrain_dataset = raw_datasets["train"]eval_dataset = raw_datasets["test"]model = FastLanguageModel.get_peft_model( model, r = 32, # Choose any number > 0! Suggested 8, 16, 32, 64, 128 target_modules = ["q_proj", "k_proj", "v_proj", "o_proj", "gate_proj", "up_proj", "down_proj",], lora_alpha = 32, # Best to choose alpha = rank or rank*2 lora_dropout = 0, # Supports any, but = 0 is optimized bias = "none", # Supports any, but = "none" is optimized # [NEW] "unsloth" uses 30% less VRAM, fits 2x larger batch sizes! use_gradient_checkpointing = "unsloth", # True or "unsloth" for very long context random_state = 3407, use_rslora = False, # We support rank stabilized LoRA loftq_config = None, # And LoftQ)trainer = SFTTrainer( model = model, train_dataset = train_dataset, eval_dataset = eval_dataset, args = SFTConfig( dataset_text_field = "text", per_device_train_batch_size = 2, gradient_accumulation_steps = 4, # Use GA to mimic batch size! warmup_steps = 5, # num_train_epochs = 1, # Set this for 1 full training run. max_steps = 30, learning_rate = 2e-4, # Reduce to 2e-5 for long training runs logging_steps = 1, optim = "adamw_8bit", weight_decay = 0.01, lr_scheduler_type = "linear", seed = 3407, report_to = "none", # Use this for WandB etc ),)tokenizer.pad_token = tokenizer.eos_token ```

The model is wrapped with `get_peft_model`, targeting key projection layers and using a low-rank adaptation strategy to reduce training overhead. we split the dataset into train and test, then configure the trainer with modest training steps, gradient accumulation, and 8-bit optimization for efficiency. gradient checkpointing is enabled using unsloth’s optimized backend to support longer sequences with minimal memory usage. this setup balances speed, stability, and adaptability to domain-specific data.

### Launching the fine-tuning process

``` train_result = trainer.train() ```

Finally, we kick off the supervised fine-tuning with `trainer.train()`. as we’ve set everything up earlier — from data preparation to model optimization — this step runs the actual training loop, adapting the base Qwen3 model to the target domain using the LoRA configuration and our formatted dataset. the result is a more context-aware, efficient model tuned for domain-specific tasks.

### Testing the fine-tuned model

As a final step, we test the fine-tuned model using a structured prompt that includes both system guidance and a user query.

```python messages = [ {"role" : "system", "content" : SYSTEM_PROMPT}, {"role" : "user", "content" : "<Context> \+ Question"}]text = tokenizer.apply_chat_template( messages, tokenize = False, add_generation_prompt = True, # Must add for generation enable_thinking = False, # Disable thinking)from transformers import TextStreamer_ = model.generate( **tokenizer(text, return_tensors = "pt").to("cuda"), max_new_tokens = 256, # Increase for longer outputs! temperature = 0.7, top_p = 0.8, top_k = 20, # For non thinking streamer = TextStreamer(tokenizer, skip_prompt = True),) ```

We reuse the chat template and set `add_generation_prompt=True` to trigger generation. thinking mode is disabled for a faster, simpler response. the output is streamed in real-time using `TextStreamer`, allowing us to quickly verify the model’s behavior on domain-specific inputs.
