## The Evolution of AI Memory: From Goldfish to Proactive Collaborators

Most AI systems today suffer from what can be called “goldfish memory” — they forget everything as soon as a conversation ends. While this limitation might suffice for simple, single-session tasks, it falls drastically short for applications that demand continuity, personalization, or nuanced workflows. Imagine a social media manager who can’t recall your last campaign strategy or a chatbot that forgets your preferences after every interaction. It’s not just inefficient; it’s holding AI back from reaching its full potential.

LangGraph is changing the game. By introducing **long-term memory** , LangGraph transforms AI agents into intelligent, proactive collaborators. Unlike short-term memory, which is scoped to a single session and excels at maintaining immediate context, long-term memory enables agents to store, recall, and learn from information across multiple conversations. This isn’t just about remembering — it’s about evolving. AI agents powered by LangGraph’s long-term memory can adapt to user preferences, incorporate feedback, and refine their behavior to provide increasingly relevant and efficient support.

Here’s how LangGraph achieves this leap forward:

* **Cross-Thread Persistence** : Agents no longer “reset” after every interaction. They maintain context across sessions, enabling seamless continuity in workflows.
* **Personalization** : By remembering user preferences and feedback, AI agents can tailor their responses and strategies to individual needs.
* **Streamlined Efficiency** : Forgetting isn’t just inconvenient; it’s costly. Long-term memory eliminates repetitive tasks, reduces redundant interactions, and accelerates decision-making.

At the core of LangGraph’s memory system is a **persistent document store** — a deceptively simple yet powerful tool that stores data as JSON documents. This framework supports flexible namespacing, allowing developers to organize memories by context, user, or application. Coupled with content-based filtering, agents can quickly retrieve the most relevant information, making every interaction feel intelligent and informed.

But the real magic lies in how LangGraph seamlessly blends short-term and long-term memory. **Short-term memory** , powered by **checkpointers** , keeps agents sharp and focused within a single session. **Long-term memory** , on the other hand, enables them to carry knowledge forward, transforming static tools into dynamic systems that grow and adapt over time.

### Memory Management

Effective memory management is the backbone of the AI agent’s ability to store and recall information, adapt to user inputs, and provide a seamless experience. To achieve this, the agent uses structured schemas defined with **Pydantic** , ensuring consistency, validation, and scalability.

The AI agent organizes memory into structured schemas to store and manage information effectively. These schemas include definitions for both individual memory items and collections of memories:

```python from pydantic import BaseModel, Fieldclass Memory(BaseModel): content: str = Field(description="The main content of the memory. For example: User expressed interest in learning about French.")class MemoryCollection(BaseModel): memories: list[Memory] = Field(description="A list of memories about the user.") ```

**Memory Class** : Represents a single memory item, containing a `content` field to store specific pieces of information, such as:

* `“User expressed interest in learning about French.”`
* `“User prefers posting on Instagram and LinkedIn.”`

**MemoryCollection Class** : Aggregates multiple memory objects into a list, representing the full set of the user’s memories. For instance:

```json { "memories": [ {"content": "User expressed interest in learning about French."}, {"content": "User prefers content in a casual tone."} ]} ```

By structuring memory this way, the agent ensures data is easy to validate, update, and query, forming a robust foundation for managing long-term information.

In this tutorial, the AI agent relies on three key memory components: the **User Profile Memory** , the **Content Calendar** , and the **Guidelines Prompt**. These components are structured to ensure consistency and validation, making it easier for the AI to adapt dynamically to user inputs.

* **User Profile Memory** : The agent builds a detailed understanding of your preferences over time, including your preferred platforms and the tone and style of your content. The `Profile` class represents a single memory that the AI agent can dynamically update.

```python class Profile(BaseModel): """This is the profile of the user you are chatting with""" name: Optional[str] = Field(description="The user's name", default=None) location: Optional[str] = Field(description="The user's location", default=None) target_audience: Optional[str] = Field(description="Target audience for content creation.", default=None) preferred_platforms: list[str] = Field(description="User's preferred platforms for posting content.", default_factory=list) ```
* **Content Calendar** : It maintains a centralized calendar to track your content pipeline, including ideas, deadlines, statuses, and drafts, ensuring nothing is forgotten. Unlike the `Profile` class, the `ContentCalendar` class represents a memory collection rather than a single memory. This means it can hold multiple items (i.e., a list of memory objects) that the AI agent can add to or update dynamically.

```python class ContentCalendar(BaseModel): """Represents an item in the content calendar""" title: str = Field(description="The title or topic of the content.") platform: Optional[str] = Field(description="The platform where the content will be posted (e.g., Instagram, Blog).", default=None) deadline: Optional[datetime] = Field(description="The deadline for posting the content.", default=None) status: Literal["idea", "draft", "review", "posted"] = Field(description="The current status of the content.", default="idea") tags: list[str] = Field(description="Tags or topics associated with the content.", default_factory=list) idea: str = Field(description="General idea of the content item", default=None) ```
* **Guidelines Prompt** : The agent refines its behavior based on user feedback, maintaining a set of guidelines that shape the content creation process. These guidelines are updated dynamically, ensuring the agent aligns with the user’s evolving needs.

``` CREATE_GUIDELINES = """Reflect on the following interaction.Based on this interaction, update your guidelines for content creation. Use any feedback from the user to update how they like to brainstorm, organize, or track content.Your current instructions are:<guidelines>{guidelines}</guidelines>""" ```

These memory components will be used to store long-term information that is gathered by interacting with the AI Agent.

### How Trustcall Tracks and Updates Memory

With the memory components in place to store information, we also need a system to dynamically update and add memories. For this, we use **Trustcall** , a framework designed for structured updates to JSON schemas. Trustcall enables the AI to manage memory efficiently and transparently by providing two key capabilities: validation and incremental updates. It self-corrects validation failures to maintain consistency with the defined schema and applies precise updates only where needed, avoiding the need to overwrite entire data structures.

To monitor how Trustcall updates memory components, we implement a custom **Spy** class. Acting as a listener, the Spy captures detailed information about tool calls made by Trustcall during its execution. By attaching the Spy to the Trustcall extractor, we gain visibility into every change applied to the memory schemas. Here’s how it is implemented:

```python from trustcall import create_extractorfrom langchain_openai import ChatOpenAI# Inspect the tool calls made by Trustcallclass Spy: def __init__(self): self.called_tools = [] def __call__(self, run): # Collect information about the tool calls made by the extractor. q = [run] while q: r = q.pop() if r.child_runs: q.extend(r.child_runs) if r.run_type == "chat_model": self.called_tools.append( r.outputs["generations"][0][0]["message"]["kwargs"]["tool_calls"] )# Initialize the spyspy = Spy()# Initialize the modelmodel = ChatOpenAI(model="gpt-4o", temperature=0)# Create the profile extractorprofile_extractor = create_extractor( model, tools=[Profile], tool_choice="Profile",)# Create the content extractorcontent_extractor = create_extractor( model, tools=[ContentCalendar], tool_choice="ContentCalendar", enable_inserts=True).with_listeners(on_end=spy) ```

In this example, the **Spy** class is attached as a listener to the `content_extractor`, which updates the **ContentCalendar** memory component. Since the **ContentCalendar** represents a memory collection consisting of multiple JSON documents, the Spy ensures transparency and traceability by capturing details of all updates. However, the `profile_extractor` does not require a Spy listener because the **Profile** memory component is a single JSON document. Updates to the profile are simpler and less complex, making detailed monitoring unnecessary.

The **Spy** class plays a critical role in providing visibility into Trustcall’s operations. It ensures that every memory update is monitored, enabling developers to track and validate changes. The Spy is initialized with an empty list (`called_tools`) to store details of tool calls made during execution. When the Trustcall extractor processes user input, it generates an execution trace—a record of all actions performed during the process. This trace includes both the parent operation and any additional steps (child runs) triggered during execution. The Spy systematically explores both parent and child runs using a queue, ensuring that every tool call is captured.

For each step in the execution, the Spy inspects outputs from the chat model (`run_type == "chat_model"`) to extract details about the tool calls. These details are appended to the `called_tools` list for further analysis. By integrating the Spy as a listener to the Trustcall extractor, we ensure that it captures real-time information about memory updates.

By combining **Trustcall** for structured memory updates with the **Spy** class for detailed monitoring, the AI agent achieves a balance of efficiency, precision, and transparency. This setup ensures that all changes to memory components are traceable, fostering trust and accountability in the agent’s ability to evolve and adapt over time.

### Reformatting Spy Output: Extracting and Presenting Tool Call Information

To better understand and use the information captured by the **Spy class** , we will define a custom function, `extract_tool_info`, to process and reformat the output from `spy.called_tools`. This reformatted data can also be integrated into prompts for a language model, providing more context for informed responses.

```python def extract_tool_info(tool_calls, schema_name="Memory"): """Extract information from tool calls for both patches and new memories. Args: tool_calls: List of tool calls from the model schema_name: Name of the schema tool (e.g., "Memory", "ToDo", "Profile") """ # Initialize list of changes changes = [] for call_group in tool_calls: for call in call_group: if call['name'] == 'PatchDoc': changes.append({ 'type': 'update', 'doc_id': call['args']['json_doc_id'], 'planned_edits': call['args']['planned_edits'], 'value': call['args']['patches'][0]['value'] }) elif call['name'] == schema_name: changes.append({ 'type': 'new', 'value': call['args'] }) # Format results as a single string result_parts = [] for change in changes: if change['type'] == 'update': result_parts.append( f"Document {change['doc_id']} updated:
" f"Plan: {change['planned_edits']}
" f"Added content: {change['value']}" ) else: result_parts.append( f"New {schema_name} created:
" f"Content: {change['value']}" ) return "

".join(result_parts) ```

This function processes tool calls made by the Trustcall extractor, differentiating between updates to existing documents (`PatchDoc`) and the creation of new memory items. For updates, it extracts details like the document ID, planned edits, and new values, while for new memory items, it captures their full content. The output is formatted into a readable string, making it easy to review changes or include them in prompts for further interactions with a language model.

### **Analyze User Input — content_generAItor**

When the AI Agent receives a new message from the user, the `**content_generAItor**` function becomes central to managing memory updates. It processes the latest user input, integrates it with existing memory components—such as the **user profile** , **content calendar** , and **guidelines** —and determines the appropriate memory type to update. To ensure clarity and consistency, the agent employs a Pydantic schema, `**UpdateMemory**` which explicitly defines the type of memory to be updated. This structured approach helps maintain a seamless and organized workflow for managing and evolving the agent’s memory.

```python class UpdateMemory(TypedDict): """ Decision on what memory type to update """ update_type: Literal['user', 'content_calendar', 'guidelines']def content_generAItor(state: MessagesState, config: RunnableConfig, store: BaseStore): user_id = config["configurable"]["user_id"] # Retrieve memories profile_memories = store.search(("profile", user_id)) user_profile = profile_memories[0].value if profile_memories else None calendar_memories = store.search(("content_calendar", user_id)) content_calendar = "
".join(f"{item.value}" for item in calendar_memories) guidelines_memories = store.search(("guidelines", user_id)) guidelines = guidelines_memories[0].value if guidelines_memories else "" # Prepare the system message system_msg = MODEL_SYSTEM_MESSAGE.format( user_profile=user_profile, content_calendar=content_calendar, guidelines=guidelines ) # Generate a response response = model.bind_tools([UpdateMemory], parallel_tool_calls=False).invoke( [SystemMessage(content=system_msg)] + state["messages"] ) return {"messages": [response]} ```

The `MODEL_SYSTEM_MESSAGE` prompt used by `content_generAItor` is crucial for orchestrating this workflow. It acts as a blueprint, clearly defining the agent’s role and reasoning process. Let’s break it down:

**1\. Defining the Agent’s Role**

``` You are a helpful content creation assistant. ```

This section sets the context for the assistant’s behavior, emphasizing its collaborative and organizational role.

**2\. Structuring the Agent’s Memory**

``` You maintain three types of memory:1. The user's profile (general preferences for content creation).2. A content calendar with ideas, deadlines, statuses, and drafts.3. Guidelines for creating content based on user feedback. ```

By explicitly defining the memory types, the prompt ensures the agent can organize information effectively.

**3\. Dynamically Injecting Context**

``` Here is the current User Profile:<user_profile>{user_profile}</user_profile>Here is the current Content Calendar:<content_calendar>{content_calendar}</content_calendar>Here are the current content creation guidelines:<guidelines>{guidelines}</guidelines> ```

This section pulls in the current state of the user’s memory, ensuring the agent’s responses are contextualized and informed.

**4\. Reasoning and Decision-Making**

``` Here are your instructions for reasoning about the user's messages:1. Reason carefully about the user's messages as presented below. 2. Decide whether any of the your long-term memory should be updated:- If personal information was provided about the user, update the user's profile by calling UpdateMemory tool with type `user`- If content creations are mentioned, update the ContentCalendar list by calling UpdateMemory tool with type `content_calendar`- If the user has specified preferences for how to update the ContentCalendar list, update the instructions by calling UpdateMemory tool with type `guidelines` ```

**5\. User-Friendly Feedback**

``` 3\. Tell the user that you have updated your memory, if appropriate: - Do not inform the user about updates to the user profile. - Inform the user about updates to the ContentCalendar. - Do not mention updates to guidelines. ```

This ensures the agent communicates updates naturally, without overwhelming the user.

**6\. Prioritizing Content Calendar Updates**

``` 4\. Err on the side of updating the ContentCalendar list. No need to ask for explicit permission. ```

This instruction ensures the agent prioritizes updates to the Content Calendar, maintaining a proactive approach to content management.

**7\. Responding Naturally**

``` 5\. Respond naturally to the user after a tool call was made to save memories, or if no tool call was made. ```

By ensuring natural responses, the agent maintains a seamless and conversational interaction with the user.

### **Determine the Update Type**

Using the `route_message` function, the agent determines whether the input requires an update to the:

* **User Profile** : Personal preferences like platforms or target audience.
* **Content Calendar** : Ideas, deadlines, or statuses of content projects.
* **Guidelines** : Feedback shaping the content creation process.

```python def route_message(state: MessagesState, config: RunnableConfig, store: BaseStore) -> Literal[END, "update_content_calendar", "update_guidelines", "update_profile"]: """Reflect on the memories and chat history to decide whether to update the memory collection.""" message = state['messages'][-1] if len(message.tool_calls) == 0: return END else: tool_call = message.tool_calls[0] if tool_call['args']['update_type'] == "user": return "update_profile" elif tool_call['args']['update_type'] == "content_calendar": return "update_content_calendar" elif tool_call['args']['update_type'] == "guidelines": return "update_guidelines" else: raise ValueError ```

### **Invoke the Appropriate Tool**

With the **content_generAItor** node routing user inputs and the **route_message** function determining the appropriate next steps, the workflow transitions seamlessly to the **tool nodes**. These nodes are specialized functions responsible for updating distinct memory components. Whether it’s refining the user profile, managing the content calendar, or adapting content creation guidelines, tool nodes ensure that every interaction contributes to the agent’s growth and alignment with user needs. By processing chat history, invoking Trustcall for structured updates, and saving results to memory, these nodes form the operational core of the AI social media manager. Below, we break down the implementation and purpose of the key tool nodes: `update_profile`, `update_content_calendar`, and `update_guidelines`.

**1\. Updating the User Profile**

The `update_profile` function ensures the agent maintains an up-to-date understanding of user preferences, such as platforms, tone, and target audience.

```python def update_profile(state: MessagesState, config: RunnableConfig, store: BaseStore): """Reflect on the chat history and update the memory collection.""" # Get the user ID and define the namespace user_id = config["configurable"]["user_id"] namespace = ("profile", user_id) # Retrieve existing profile memories existing_items = store.search(namespace) tool_name = "Profile" existing_memories = ([(item.key, tool_name, item.value) for item in existing_items] if existing_items else None) # Format the instruction and merge with chat history TRUSTCALL_INSTRUCTION_FORMATTED = TRUSTCALL_INSTRUCTION.format(time=datetime.now().isoformat()) updated_messages = list(merge_message_runs(messages=[SystemMessage(content=TRUSTCALL_INSTRUCTION_FORMATTED)] + state["messages"][:-1])) # Extract updates and save to the store result = profile_extractor.invoke({"messages": updated_messages, "existing": existing_memories}) for r, rmeta in zip(result["responses"], result["response_metadata"]): store.put(namespace, rmeta.get("json_doc_id", str(uuid.uuid4())), r.model_dump(mode="json")) tool_calls = state['messages'][-1].tool_calls return {"messages": [{"role": "tool", "content": "updated profile", "tool_call_id": tool_calls[0]['id']}]}# Trustcall promptTRUSTCALL_INSTRUCTION = """Reflect on the following interaction. Use the provided tools to retain any necessary memories about the user.System Time: {time}""" ```

**Process Overview** :

1. **Retrieve Existing Profile Data** : The function queries the memory store to retrieve the current profile data using the `("profile", user_id)` namespace. This ensures that updates are applied with a clear context of the user’s existing preferences, such as platforms, tone, and target audience.
2. **Format and Process Messages** : A formatted instruction is created using the `TRUSTCALL_INSTRUCTION` template, which includes the current system time. The instruction is merged with the chat history using `merge_message_runs`, generating an updated message set ready for processing.
3. **Process Updates with Trustcall** : The `profile_extractor` invokes Trustcall to analyze the updated messages and identify changes needed for the user profile. Trustcall validates and extracts structured updates, ensuring consistency with the schema.
4. **Save and Summarize Updates** : The function saves the updated profile data back into the memory store. Each update is stored under a unique identifier (`json_doc_id`), ensuring traceability. This ensures the user profile remains accurate and aligned with the latest input.
5. **Return Feedback** : The function generates a response confirming the update to the profile. This response includes information about the changes, maintaining transparency and closing the feedback loop for the interaction.

### 2\. Updating the Content Calendar List

The `update_content_calendar` function is responsible for managing the content calendar, tracking content-related tasks such as ideas, deadlines, and statuses. It ensures the calendar evolves dynamically based on user inputs, leveraging Trustcall for structured updates and the Spy class for monitoring changes.

```python def update_content_calendar(state: MessagesState, config: RunnableConfig, store: BaseStore): user_id = config["configurable"]["user_id"] namespace = ("content_calendar", user_id) existing_items = store.search(namespace) tool_name = "ContentCalendar" existing_memories = [(item.key, tool_name, item.value) for item in existing_items] if existing_items else None TRUSTCALL_INSTRUCTION_FORMATTED = TRUSTCALL_INSTRUCTION.format(time=datetime.now().isoformat()) updated_messages = merge_message_runs([SystemMessage(content=TRUSTCALL_INSTRUCTION_FORMATTED)] + state["messages"][:-1]) # Initialize the spy for visibility into the tool calls made by Trustcall spy = Spy() content_extractor = create_extractor(model, tools=[ContentCalendar], tool_choice=tool_name, enable_inserts=True).with_listeners(on_end=spy) result = content_extractor.invoke({"messages": updated_messages, "existing": existing_memories}) for r, rmeta in zip(result["responses"], result["response_metadata"]): store.put(namespace, rmeta.get("json_doc_id", str(uuid.uuid4())), r.model_dump(mode="json")) tool_calls = state['messages'][-1].tool_calls # Extract the changes made by Trustcall and add the the ToolMessage returned to task_mAIstro content_calendar_update_msg = extract_tool_info(spy.called_tools, tool_name) return {"messages": [{"role": "tool", "content": content_calendar_update_msg, "tool_call_id":tool_calls[0]['id']}]} ```

**Process Overview** :

1. **Retrieve Existing Entries** : The function queries the memory store to retrieve the current content calendar items, providing context for the updates.
2. **Format and Process Messages** : It prepares a formatted instruction using `TRUSTCALL_INSTRUCTION` and merges it with the current chat history to generate updated messages.
3. **Monitor Updates with Trustcall and Spy** : The `content_extractor` invokes Trustcall to apply the updates, while the Spy class tracks tool calls, capturing detailed information about the changes made to the content calendar.
4. **Save and Summarize Updates** : The updated calendar items are saved back into the memory store. Additionally, the function extracts a summary of the changes using `extract_tool_info`, providing traceability and transparency.
5. **Return Feedback** : The function generates a response containing the update summary, ensuring that the changes are clearly communicated and logged.

### 3\. Updating Content Creation Guidelines

The `update_guidelines` function refines the agent’s behavior by updating content creation guidelines based on user feedback.

```python def update_guidelines(state: MessagesState, config: RunnableConfig, store: BaseStore): user_id = config["configurable"]["user_id"] namespace = ("guidelines", user_id) existing_memory = store.get(namespace, "content_guidelines") system_msg = CREATE_INSTRUCTIONS.format(guidelines=existing_memory.value if existing_memory else None) new_memory = model.invoke([SystemMessage(content=system_msg)] + state["messages"][:-1] + [HumanMessage(content="Please update the guidelines.")]) store.put(namespace, "content_guidelines", {"memory": new_memory.content}) tool_calls = state['messages'][-1].tool_calls return {"messages": [{"role": "tool", "content": "updated guidelines", "tool_call_id":tool_calls[0]['id']}]} ```

**Process Overview** :

1. **Retrieve Existing Guidelines** : The function queries the memory store to access the current content creation guidelines using the `("guidelines", user_id)` namespace. If no existing guidelines are available, it initializes the process with a default empty state.
2. **Format and Process Messages** : A system message is prepared using the `CREATE_INSTRUCTIONS` template, incorporating the existing guidelines (if available). This ensures that the updated guidelines are informed by prior user feedback. The system message is then merged with the latest chat history.
3. **Generate Updated Guidelines** : The model processes the prepared messages and generates a refined set of guidelines based on the conversation. This step dynamically adapts the content creation process to reflect the user’s evolving needs and preferences.
4. **Save and Persist Updates** : The refined guidelines are stored back in the memory store under the key `"content_guidelines"`. This ensures that the updated set of instructions is retained for future interactions, maintaining alignment with the user’s expectations.
5. **Return Feedback** : A response is generated to confirm that the guidelines have been updated successfully. This feedback provides traceability and reassures the user that their inputs have been incorporated into the agent’s behavior.

## Graph Compiling: Where It All Comes Together

The AI social media manager’s functionality culminates in the graph-compiling process, where all nodes and edges are connected into a unified system. By combining the **content_generAItor** , **route_message** , and specialized tool nodes, the graph defines the end-to-end workflow for processing user inputs, updating memory components, and looping back to the next interaction. Here’s how it all comes together:

### Building the Graph

The **StateGraph** is initialized using the `MessagesState` class, which acts as a centralized state tracker for user interactions. This setup enables the dynamic flow of tasks and decisions within the AI agent's workflow. Each node in the graph represents a distinct task, and the flow between these tasks is orchestrated by defining edges, ensuring smooth transitions and a logical progression of interactions.

``` # Graph setupbuilder = StateGraph(MessagesState)# Add nodes to the graphbuilder.add_node(content_generAItor) # Central node for generating responsesbuilder.add_node(update_profile) # Node for updating the user profilebuilder.add_node(update_content_calendar) # Node for updating the content calendarbuilder.add_node(update_guidelines) # Node for refining content guidelines# Define the flow between nodesbuilder.add_edge(START, "content_generAItor") # Start at the content generatorbuilder.add_conditional_edges("content_generAItor", route_message) # Route based on user inputbuilder.add_edge("update_profile", "content_generAItor") # Return to generator after profile updatebuilder.add_edge("update_content_calendar", "content_generAItor") # Return after calendar updatebuilder.add_edge("update_guidelines", "content_generAItor") # Return after guidelines update ```

**Main Node:** The `content_generAItor` node serves as the central hub of the graph. It processes user input, retrieves the relevant memory components (e.g., user profile, content calendar, and guidelines), and determines the next action. This node encapsulates the core logic for routing the flow of the conversation and ensuring that responses are both contextual and informed.

**Tool Nodes:** The graph includes specialized nodes for updating specific memory components:

* `**update_profile**`: Updates the user profile with new preferences or details provided during the interaction.
* `**update_content_calendar**`: Manages and updates tasks related to content creation, such as ideas, deadlines, or statuses.
* `**update_guidelines**`: Refines content creation guidelines based on user feedback to ensure the agent aligns with user expectations.

Each of these nodes executes its task and then loops back to the `content_generAItor` to continue the workflow seamlessly.

**Edges** define the transitions between nodes, ensuring that the flow of tasks is logical and consistent:

* **Start at the Generator** : The workflow begins at the `content_generAItor`, which processes the initial user input.
* **Conditional Routing** : The `route_message` function dynamically determines which tool node to invoke based on the type of update needed (e.g., `update_profile`, `update_content_calendar`, or `update_guidelines`).
* **Looping Back** : After completing a task at a tool node, the flow returns to the `content_generAItor`, ensuring continuity and readiness for the next user input.

To manage information effectively, the graph integrates two memory systems:

* **Across-thread Memory** : Managed by `InMemoryStore`, this long-term memory system enables the agent to persist information across sessions, ensuring continuity over time.
* **Within-thread Memory** : Powered by `MemorySaver`, this short-term memory system tracks context within a single conversation, providing immediate responsiveness.

``` # Memory storesacross_thread_memory = InMemoryStore()within_thread_memory = MemorySaver() ```

### Compiling the Graph

The graph is compiled by linking the defined nodes, edges, and memory systems into a unified workflow:

``` # Compile the graphgraph = builder.compile(checkpointer=within_thread_memory, store=across_thread_memory) ```

This step ensures that each component functions cohesively, with memory updates seamlessly integrated into the workflow.
