In today’s data-driven world, businesses heavily depend on their data to make informed decisions, from defining business strategies to managing supply chains. Quality of the data is crucial to ensure the accuracy of the analyses and avoid unnecessary costs. However, data often comes in different formats and conventions and can be plagued with issues like missing or duplicate values. As a result, data scientists spend a considerable amount of time and resources on data preparation.

Data preparation involves several operations collectively known as preparators. These preparators are combined into a pipeline for exploring, cleaning, and transforming raw data into usable datasets. In fact, it’s estimated that data scientists spend up to 80% of their time on data preparation.

There are many libraries available for data preparation, but choosing the right one can be a daunting task. The dataframe has become the go-to data structure for constructing pipelines and developing libraries due to its simplicity. It’s a two-dimensional data structure made up of rows and columns.

**Pandas** is the most widely used library for manipulating dataframes. Its popularity is so great that it’s even credited for the popularity of Python itself. However, despite its success, Pandas has some limitations. It’s not designed to work efficiently with large datasets as it operates in a single-threaded manner and lacks support for cluster deployment.

To address these limitations, alternative libraries have been developed. But these libraries come with their own set of features which can make it difficult for data scientists to choose the most suitable solution.

In this blog, I want to discuss about perfromance comparison of Pandas and its popular alternatives like PySpark, Modin (with both Dask and Ray engine), Polars, CuDF, Vaex, and DataTable based on a research study. You can read the full research article [here](<https://arxiv.org/pdf/2312.11122v2>)

The study evaluates these libraries based on four essential stages in the pipelines: input/output (I/O), exploratory data analysis (EDA), data transformation (DT), and data cleaning (DC). These findings are particularly useful for those who are using Pandas in their workflow but want to replace it with a more efficient library that has the same interface.

## Understanding Alternate Dataframe Libraries:

Different dataframe libraries use different combinations of these features. Let’s take a look at some popular ones.

### PySpark

PySpark is the Python API for Apache Spark, which allows working with distributed collections of objects partitioned across a cluster. PySpark dataframes can be seen as relational tables that support lazy evaluation. PySpark has two APIs: Spark SQL, which combines SQL queries with Spark programs; and Pandas on Spark, which distributes Pandas workloads across multiple nodes.

Read more on PySpark [here](<https://github.com/apache/spark>)

### Modin

Modin is a Python library that offers a parallel alternative to Pandas. It uses 15 core operators to simplify Pandas functions and build its own Pandas-like API. Modin can switch between different partition schemes depending on the operation. Each partition is then processed independently by the execution engine: Dask or Ray.

Read more on Modlin [here](<https://modin.readthedocs.io/en/latest/>)

### Polars

Polars is a Python library written in Rust and built on top of arrow2. It has developed its own Domain Specific Language (DSL) for transforming data and supports both eager and lazy execution. The lazy strategy allows queries to run in batches, reducing the load on memory and CPU.

Read more on Polars [here](<https://pola.rs/>)

### CuDF

CuDF is part of the NVIDIA RAPIDS framework. It runs general-purpose data science pipelines on GPUs, leveraging their computational power for accelerating data processing. CuDF uses parallelization to execute operations simultaneously across all available GPU cores.

Read more on CuDF [here](<https://docs.rapids.ai/api/cudf/legacy/user_guide/>)

### Vaex

Vaex is a Python library designed to handle extremely large tabular datasets. It achieves memory optimization through streaming algorithms, memory-mapped files, and a zero-copy policy. Vaex supports multithreading for faster computation on multi-core CPUs.

Read more on Vaex [here](<https://vaex.readthedocs.io/en/latest/>)

### DataTable

DataTable is a Python package that supports column-oriented data storage, optimizing data access and processing. DataTable enables memory-mapping of data on disk, allowing the seamless processing of out-of-memory datasets. DataTable incorporates multithreaded data processing and offers efficient algorithms for sorting, grouping, and joining operations.

Read more on DataTable [here](<https://datatable.readthedocs.io/en/latest/>)

## Dataframe Libraries and Features:

Dataframe libraries are powerful tools for managing and manipulating data. Five key features make these libraries highly efficient:

* **Multithreading:** This makes the most of your hardware resources by speeding up the execution of dataframe operations.
* **GPU acceleration:** This taps into the parallel computing capabilities of graphics processing units to boost the performance of dataframe operations.
* **Resource optimization:** This involves strategies for managing memory efficiently, reducing the strain on resources and improving performance.
* **Lazy evaluation:** This holds off on executing operations until a specific output operation is called, allowing for query optimization techniques.
* **Deploy on cluster:** This distributes dataframe processing across a machine cluster, leveraging parallel computing.

### Data Preparation Pipelines

For each dataset, researchers chose the top-voted Kaggle notebook that tackled a related challenge and focused on the data prep part. Across these notebooks, there were 27 key “preparators” that fall into four main stages:

1. **Input/Output (I/O)** : These handle loading and saving data from various sources like databases, CSV files, or even web APIs.
2. **Exploratory Data Analysis (EDA)** : Tools that help explore data, spot patterns, or catch errors.
3. **Data Transformation (DT)** : Things like joining tables, encoding categories, and aggregating data to make it analysis-ready.
4. **Data Cleaning (DC)** : Fixing missing data, correcting errors, and kicking outliers to the curb to ensure clean, reliable results.

### Exploratory Data Analysis (EDA): Who’s Fastest?

In the EDA stage, **Polars** steals the show for most datasets except Patrol, where **CuDF** takes the lead. A few tasks dominate the runtime: finding missing values, spotting outliers, searching patterns, and sorting data. Here’s what stood out:

* **Polars** shines in finding missing values and outliers, speeding things up by up to 10^4x compared to Pandas. It uses Arrow arrays to handle metadata efficiently.
* **DataTable** outperforms Polars on Patrol when locating missing values, thanks to binary search-based filtering, making it lightning fast.
* **Vaex** is unbeatable at pattern searching. It’s up to 1,000x faster than Pandas and 10x faster than CuDF. Its columnar data structure gives it an edge in this task, though it struggles with row-wise operations like spotting outliers, where it’s surprisingly slower than Pandas.

For sorting values, **CuDF** and **Polars** are top performers, while **SparkSQL** gains momentum as datasets grow. **Modin** , however, trips up on sorting in the Athlete dataset, where it defaults back to Pandas, making it 100x slower.

**Big Takeaways from EDA Performance:**

1. **Polars** dominates for dense datasets like Taxi but slows on string-heavy datasets like Patrol.
2. **Vaex** rocks at column-based tasks but stumbles on row-based ones.
3. **Modin** can be blazingly fast thanks to multithreading but has weak spots in some operations.

In short, while Pandas holds steady as a reliable choice, newer libraries like Polars and Vaex show serious potential when speed is critical. It all boils down to the dataset type and the task at hand.

### Data Transformation (DT): Who Wins the Speed Race?

When it comes to transforming data, different libraries shine on different datasets. Here’s the breakdown:

* **CuDF** is the champ on Loan and Patrol datasets, blazing through tasks like categorical encoding and grouping, often 100x faster than its closest competitors, Polars and Modin.
* **Polars** and **SparkSQL** take the lead on the Athlete and Taxi datasets, leveraging lazy evaluation to boost speed.
* **Vaex** dominates column-wise tasks like creating new columns, being 1,000x faster than CuDF, but it hits a speed bump with row-based operations like grouping or pivoting.

Interestingly, **SparkPD** lags behind due to the overhead of translating Pandas operations into Spark plans, while **Modin** shines on larger datasets thanks to its multithreading prowess.

### Data Cleaning (DC):

Data cleaning is where **CuDF** flexes its muscles, outperforming everyone on most datasets except Taxi, where **Vaex** takes the crown, with **Modin** and **Polars** close behind.

* On smaller datasets like Athlete and Loan, **deduplicating rows** is the most time-consuming task, making up 70% of the total runtime. Pandas holds up well, but CuDF edges it out on Athlete.
* On larger datasets like Patrol, CuDF crushes it, being over 1000x faster than Pandas for tasks like removing empty rows and changing date formats.
* Vaex’s performance on Taxi is stellar, outperforming CuDF in several tasks, especially on dense data.

### Performance Results:

### CuDF: Great on GPU, Not Ideal for Big Data on Limited Hardware

CuDF relies heavily on GPU memory, so if the dataset fits, it’s lightning-fast. But that’s the catch, once GPU resources are maxed out, it struggles with massive datasets, making it less suitable for machines with limited GPU power.

### SparkSQL: The Scaling Champion

**SparkSQL** wins the scalability crown. It’s the only library that can handle full datasets on a laptop, thanks to its clever use of **disk spillover,** when memory runs out, it shifts data to disk, keeping things running smoothly.
Meanwhile, **SparkPD** struggles with overhead from converting between Pandas and Spark dataframes, often running into out-of-memory (OOM) errors on laptops.

### DataTable, Modin, and Ray: Efficient and Resource-Smart

* **DataTable** is a memory-efficient champ, especially on Patrol, using fewer resources and avoiding the need to split the dataframe, which helps dodge errors related to data exchange.
* **ModinR** (powered by Ray) outshines its Dask-based sibling by scaling more efficiently across all machine configurations. Ray’s **distributed task scheduling** is key, spreading tasks efficiently and minimizing memory overhead. This makes Modin on Ray a robust option for large-scale data processing.
* **Dask** on the other hand, uses a centralized scheduler, which increases memory use and leads to OOM issues more frequently.

### Polars: Fast but Hits a Wall on Big Data

Polars excels with smaller datasets due to its **in-memory execution model** , but this becomes a bottleneck for large datasets. Since it requires everything to fit in RAM, it struggles to scale on bigger datasets, especially compared to disk-backed solutions like SparkSQL.

### Pandas: The Scalability Bottleneck

As expected, **Pandas** struggles the most. It’s the only library that couldn’t complete the pipeline on the Taxi dataset, even on a server configuration. While Pandas is a reliable workhorse for small to medium datasets, scalability is not its strong suit.

For large datasets or resource-constrained environments, SparkSQL’s disk spillover and Modin’s Ray-powered distributed approach offer the best scalability. CuDF dazzles with GPU power but isn’t ideal without hefty GPU resources. And while Pandas and Polars shine in simpler setups, they fall short when data scales. Choose your library wisely, based on your data size and machine power!

## Key Takeaways from the Research Study: Choosing the Right Dataframe Library

The evaluation results from the research highlights Panda’s well-known limitations, but here’s the catch: despite a slew of alternatives, there’s no one-size-fits-all solution for working with tabular data on a single machine.

> The best choice depends on factors like dataset size, machine configuration, and the type of operations you need to perform.

To help you choose the right library, let’s answer a few key questions:

### 1\. Does Your Dataset Fit in GPU Memory?

If you’ve got a GPU with enough memory to handle your dataset, **CuDF** is a top performer. It’s fast, Pandas-compatible, and ideal for GPU-accelerated workflows. But beware, CuDF doesn’t have an optimizer, so for full data pipelines, libraries like **Polars** or **SparkSQL** may outperform it by skipping unnecessary steps.

### 2\. Are You Running an Entire Pipeline or Just One Stage?

* **For I/O tasks** , **DataTable** is the speed king. It’s blazing fast at reading and writing data, though it lacks mature support for other operations and has low Pandas compatibility.
* **For Exploratory Data Analysis (EDA)** , **Polars** shines as the top performer.
* **For Data Transformation (DT) and Data Cleaning (DC)** , **SparkSQL** is a reliable choice, excelling as the best CPU-only solution for running entire pipelines efficiently.

### 3\. What’s the Size of Your Dataset?

**Small Datasets (Under 500k Rows):** Here, most libraries perform similarly. **Polars** is often recommended for its speed, but **Pandas** might still be the simplest option — especially if the performance boost isn’t worth learning a new API or rewriting your existing pipeline.

**Medium Datasets (2 to 19 Million Rows):** If your data is dense with lots of numeric columns (like a 5% sample of Taxi), **Vaex** is a solid choice for column-wise operations — though it’s not Pandas-compatible. For sparse datasets with many nulls (like Loan), **Polars** and **SparkPD** perform well. If your data contains many string columns (like 25% of Patrol), **SparkSQL** is your best bet.

**Large Datasets (Over 20 Million Rows):** When you’re dealing with big data, **SparkSQL** is the go-to library, thanks to its disk spillover capability and scalability. If your pipeline involves heavy column operations, especially with lots of string columns and null values (like Patrol), **Vaex** is an excellent option. Plus, it’s easy to use — no need to set up a PySpark environment.

## Final Thoughts

There’s no magic bullet when it comes to dataframe libraries. Your best choice depends on your dataset’s characteristics, the hardware at your disposal, and the complexity of your data pipeline. Whether you’re sticking with Pandas for simplicity or leveraging SparkSQL for big data, understanding the strengths and weaknesses of each library will help you pick the right tool for the job.
