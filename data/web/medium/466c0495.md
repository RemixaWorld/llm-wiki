## Vocabulary and Tokenizer

Before diving into the embeddings and encodings, it’s essential to understand a foundational step that happens much earlier: building the vocabulary. While modern language models often rely on byte-pair encoding (BPE), sentencepieces, or even byte-level tokenization, in the original attention paper, the authors used **word-level tokenization**. For clarity and alignment with that paper, we’ll stick with words as our basic tokens.

It’s important to note that vocabulary creation is **model-agnostic**. That is, it happens independently of any specific model architecture like Transformers. The **tokenizer** is responsible for building this vocabulary — it reads raw text and creates a mapping from tokens (e.g., words) to unique IDs. It doesn’t know anything about how the tokens will later be processed by a neural network.

**Think of it like building a dictionary** : you’re just collecting and indexing words. Whether the dictionary is later used for a poem, an essay, or a legal document doesn’t matter at this stage. Let’s take a simple example to see how this works. Given the sentence:

> _“I love cats I like dogs”_

A tokenizer using word-level granularity would assign unique IDs like this:

![Figure 2: Vocabulary.](https://miro.medium.com/v2/resize:fit:300/1*fI6JBhnxIIKwSyCIwvzJYQ.png)

Now we have our vocabulary — each word is associated with a unique integer ID. In the next steps, we’ll see how these IDs are used as inputs to the Transformer model.

## Input embeddings

As you can see in **Figure 1** , everything starts with the input. The model begins by processing this input — but computers don’t understand words or images directly. They only understand **numbers**. (Yes, I know you’ve probably heard this sentence a hundred times already 😄).

![Figure 3: Input embeddings.](https://miro.medium.com/v2/resize:fit:158/1*rAKfaCdpwouhjO4NhWJWvw.png)

So, our first task is to convert these inputs — like the sentence _“I like dogs”_ — into numerical representations that a machine can work with.

In **modern terminology** , the process of converting raw text into tokens is called **tokenization** , and the result is often referred to as **token embeddings**. However, it’s important to clarify:

* **Tokenization** creates a mapping between text and token IDs based on a vocabulary.
* **Embeddings** map those token IDs into continuous **vector representations** using a trainable **embedding matrix**.

These are separate processes. Tokenization is static and vocabulary-based, while the embedding is dynamic and dependent on model parameters like the number of dimensions.

Recall the vocabulary we built earlier. It contains 5 words:

![Figure 4: Vocabulary.](https://miro.medium.com/v2/resize:fit:300/1*fI6JBhnxIIKwSyCIwvzJYQ.png)

If our input sentence is **“I like dogs”** , the tokenizer would convert this into: **[0, 3, 4]**. These are just token IDs — but they’re not enough. The model doesn’t work with discrete IDs, it needs **vectors** with a defined number of **dimensions**. That brings us to a very important concept: **Dimensions.**

### What Are Dimensions?

Dimensions in an embedding vector represent **abstract features** that the model can learn from data. They’re not explicitly interpretable. You might imagine them as measuring concepts like _“sweetness”_ or _“loveliness”_ , but in reality, **neural networks don’t tell you what each dimension means**.

All you need to know is:

* The **more dimensions** you use (with enough data and training), the **richer** and **more informative** the representations can become.
* The **embedding dimension** is a model hyperparameter. You choose it (e.g., 4, 128, 512) before training.

I would highly recommend watching [this part](<https://www.youtube.com/watch?v=wjZofJX0v4M&t=747s>) of 3Blue1Brown video, later on it also explains human understandable version of how the directions of vectors encodes meaning inside it. One of the most eye-opening part was when they explained plurality concept and how the dot products dimension “plurality” was giving postive results with plural words.

### Embedding Matrix

Let’s say our model uses **4 dimensions**. Then we create an **embedding matrix** with the shape:

``` (5, 4) → (vocabulary size, embedding dimension) ```

Example:

``` [ [0.2, 0.1, 0.4, 0.3], # "I" [0.6, 0.9, 0.1, 0.0], # "love" [0.3, 0.7, 0.8, 0.5], # "cats" [0.5, 0.2, 0.6, 0.1], # "like" [0.1, 0.3, 0.2, 0.4], # "dogs"] ```

Where do these floating-point numbers come from?

They’re **learnable parameters** — randomly initialized at the beginning of training and **updated during backpropagation**.

### **Resulting Embeddings**

Each **row** in this matrix corresponds to a token from our vocabulary. So, the sentence _“I like dogs”_ becomes:

``` [ [0.2, 0.1, 0.4, 0.3], # I [0.5, 0.2, 0.6, 0.1], # like [0.1, 0.3, 0.2, 0.4], # dogs] ```

Now we’ve successfully **embedded the sentence** into vectors.

At the beginning of this article, we briefly mentioned that RNNs suffer from a lack of parallelism, while Transformers — and especially LLMs — do not. But maybe you haven’t yet seen _how_ parallelism actually plays out. So let’s unpack that.

### Parallelism

Are Input Embeddings (the starting point of everything) Parallelized in Transformers? **Yes. Absolutely.** Transformers process input embeddings entirely in parallel — during both training and inference.

Let’s go back to our simple example: “I like dogs”, _For simplicity, let’s assume the token IDs are [0, 1, 2] — matching their row positions in the embedding matrix_

``` # Tokenized to IDs:input_ids = [0, 1, 2]# Example embedding matrix:embedding_matrix = np.array([ [0.2, 0.1, 0.4, 0.3], # "I" [0.5, 0.2, 0.6, 0.1], # "like" [0.1, 0.3, 0.2, 0.4], # "dogs"]) ```

Now, when we fetch the embeddings where the real paralel processing starts:

``` input_embeddings = embedding_matrix[input_ids] ```

That one line retrieves all embeddings at **once**. No loops. No delays. This is made possible by _vectorized operations_ — powerful tools offered by libraries like NumPy, PyTorch, and TensorFlow.

**How Is This Parallelization Achieved?** This parallelism isn’t driven by Python threads or `for` loops. Instead, it’s powered by **matrix operations** that execute on the **CPU or GPU** , depending on where your data resides.

**Wait… Doesn’t Python Run on the CPU?** Yes. And here’s the twist: _Python code doesn’t run directly on GPUs. It talks to libraries (like PyTorch or TensorFlow), which call into_** _C++ and CUDA_** _under the hood. That’s where the real GPU magic happens._

**What Actually Happens Behind the Scenes**

Let’s walk through what happens when you run the following code:

```python import torchx = torch.tensor([1.0, 2.0, 3.0], device='cuda')y = x * 2 ```

Here’s the breakdown of what’s going on under the hood:

1. Python runs your script → on the **CPU**
2. PyTorch calls into its C++ backend → still on the **CPU**
3. The C++ backend launches a CUDA kernel → initiated by the **CPU**
4. The CUDA kernel executes the actual computation → on the **GPU**
5. Results are returned to PyTorch → handled again by the **CPU**

In this architecture, the **CPU acts like a conductor** , orchestrating operations and telling the GPU what to do. The **GPU is the orchestra** , performing the actual mathematical computations — **in parallel and at high speed**.

This is precisely why **NVIDIA’s stock prices are soaring** and **GPUs are seen as strategic assets**. They’re like tiny professors, built specifically to do math incredibly fast. And in today’s world, whoever can compute fast can **learn from data faster** — which translates directly into power in AI.

## Positional Encoding

Now that we’ve covered word/input/token embeddings and how parallelism works, we can move on to the next topic: encoding the positions of words in a sentence.

![Figure 7: Positional Encoding](https://miro.medium.com/v2/resize:fit:295/1*NHn8b_OUoOLYFT9rXlkmpA.png)

I deliberately explained parallelism right before this section, because at first, the idea of keeping track of word order while processing everything in parallel felt like a contradiction. How can a model understand the **sequence** of words when there’s no step-by-step processing like in RNNs? Let’s unpack the problem first. Consider the two sentences:

> _“The dog chased the cat”
>  “The cat chased the dog”_

Both use the same words, but the meaning is reversed. That reversal is caused entirely by word **order**. So, clearly, a language model needs to know _where_ a word appears in a sentence — not just _what_ the word is. At first, you might think of a simple fix:

> _“Let’s add position information directly to the embedding.”_

For example, for the sentence “I like dogs”, we could assign raw positions `[0, 1, 2]` and add those to the embeddings. But there’s a problem: this doesn’t scale. As the position numbers get larger — say, 1000 or beyond — the added values can dominate the embeddings and destabilize the training process. If you remember backpropagation, extreme values can lead to exploding gradients, which we absolutely want to avoid.

Some alternative methods (like learning a separate embedding for each position) have been explored, but they come with their own limitations — such as poor generalization to longer sequences or unnecessary parameter overhead. So we need something better.

**What Problems Are We Trying to Solve?**

Before diving into how Transformers actually solve the problem, let’s clarify **what we want from a good positional encoding system** :

1. **Each position should have a unique encoding**
Every position in the input sequence (e.g., 1st word, 2nd word, etc.) should be **unique**. This helps the model understand the structure of the sentence.
2. **It should capture relative distance between words**
The model should be able to tell _how far apart_ two words are. This is important for learning grammatical dependencies and syntactic patterns. _(Remember how in the embeddings section we talked about the direction between vectors — like how “cats” shared a “plurality” direction with other plural words? Similarly, the direction between position encodings can carry useful relational information.)_
3. **It should generalize to sequences longer than what the model saw during training**
We don’t want a system that breaks when a sentence is slightly longer than the training data. A good encoding method should extend naturally to unseen lengths.
4. **It should be deterministic and not learned**
If possible, we want the position encodings to be computed from a fixed rule rather than learned from data. This avoids unnecessary parameters and speeds up training.

### **Binary encoding**

Ok now we know what needs to be done. But before diving into more advanced positional encoding techniques like sinusoidal encoding, let’s begin with a simpler and more familiar concept: **binary encoding**. This is foundational in computer science — used in CPUs, memory addressing, and low-level protocols — because computers fundamentally operate using just two symbols: `0` and `1`.

Now imagine a basic task: we want to assign a **unique position identifier** to each word in a sentence. To keep things simple, let’s assume our sentence has a maximum length of **16 words**.

To represent 16 positions (0 through 15), we need **4 bits** , since: 2⁴ = 16

This gives us the following positional encodings:

``` Position 0 → [0, 0, 0, 0] Position 1 → [0, 0, 0, 1] Position 2 → [0, 0, 1, 0] Position 3 → [0, 0, 1, 1] ... Position 15 → [1, 1, 1, 1] ```

To better understand how each bit (dimension) behaves across positions, consider the diagram below:

![Figure 8: visual representation of binary encoding](https://miro.medium.com/v2/resize:fit:700/1*SIs24eTpae76cBDBEssDOw.png)

Each row corresponds to a bit (dimension), and each column corresponds to a position from 0 to 15 (shown in binary). Notice how:

* The **top row** flips every position: 0, 1, 0, 1…
* The next row flips every 2 positions
* Then every 4, the **bottom row** which flips once halfway through

Now let’s use this in an example to encode our sentence.**** “I like dogs”

**Step 1** : Token Embeddings

We assumed 4-dimensional embeddings for simplicity. Here are the pretrained token embeddings:

``` "I" → [0.2, 0.1, 0.4, 0.3] "like" → [0.5, 0.2, 0.6, 0.1] "dogs" → [0.1, 0.3, 0.2, 0.4] ```

**Step 2** : Binary Position Vectors (4-bit for 16-token support)

``` Position 0 → [0, 0, 0, 0] Position 1 → [0, 0, 0, 1] Position 2 → [0, 0, 1, 0] ```

**Step 3** : Add Positional Vector to Token EmbeddingWordToken

![Figure 9: binary encoding example](https://miro.medium.com/v2/resize:fit:700/1*UcDT1xT5JTEYY9mwOvjFuA.png)

**Why Binary Encoding Works?**

1. **Deterministic and Unique:** Each position has a **unique** binary vector, computed using a simple, deterministic formula:

``` Binary(p) = [ floor(p / 2^(n-1)) % 2, floor(p / 2^(n-2)) % 2, ..., floor(p / 2^0) % 2] ```

For 4-bit encoding, this maps:

* Position 0 → [0, 0, 0, 0]
* Position 1 → [0, 0, 0, 1]
* Position 2 → [0, 0, 1, 0]

**2\. Gradient-Friendly (mostly):** Because values are either 0 or 1, binary vectors **don’t introduce very large magnitudes**. This helps preserve **relatively** **stable gradient flow** during back-propagation. Therefore there is little risk of exploding gradients.

**Why Binary Encoding Falls Short?**

While binary encoding offers deterministic and unique representations, it comes with several critical drawbacks that make it unsuitable as a positional encoding method for Transformers:

**1\. Discontinuity and Lack of Smoothness.** Binary encodings change abruptly. Take position 7 (`0111`) and position 8 (`1000`) as an example. Only one bit flips, but the overall binary vectors are drastically different — one has three 1s, the other has just 1. When these vectors are added to token embeddings, the resulting representations jump in value rather than change smoothly. This sudden shift disrupts the model's ability to learn smooth positional patterns.

**2\. No Sense of Relative Distance.** Binary encodings fail to capture _how far apart_ two positions are. For instance, position 7 and 8 are adjacent, but their binary representations differ in every bit. The model receives no clue that they are next to each other — just that they are different. This makes it harder for the model to generalize sequential relationships based on distance.

**3\. Limited Generalization to Longer Sequences.** Binary encoding is fixed to a predefined maximum sequence length. With 4 bits, you can represent only 16 positions (0–15). If your model later encounters a sequence of length 32, you’d need to jump to 5-bit encodings — effectively changing the input dimensionality. This breaks compatibility and prevents smooth generalization to longer sequences during inference.

**4\. Gradient Noise from Abrupt Changes.** Although binary values (0 or 1) seem gradient-safe, their **abrupt transitions** between positions (e.g., from 7 → 8 flipping multiple bits) cause sharp changes in the input. This disrupts the smooth input-output relationship needed for stable learning and introduces **gradient noise** — making optimization harder, biased and less predictable, especially for nearby positions that should behave similarly.

**How Do We Solve the Problems of Binary Encoding?**

When I was trying to understand how Transformers fix the shortcomings of binary encoding, the real _aha!_ moment came when I imagined following illustration:

![Figure 10: From binary jumps to smooth sinusoidal curves](https://miro.medium.com/v2/resize:fit:700/1*IPXRwLJ4TahUs-hFFssSiQ.png)

Instead of abrupt jumps between 0 and 1, we now have smooth transitions. If you look closely, you’ll notice the curves are sinusoidal — we’ve essentially replaced jagged binary steps with flowing sine and cosine waves.

Let’s draw a new graph — this time with sinusoidal lines. Here’s what that might look like:

![Figure 11: Sinusoidal curves across positions](https://miro.medium.com/v2/resize:fit:459/1*BTBm2rhFSSJkG0PBTU4NHw.png)

What immediately stands out is that each position still has a unique signature. But unlike binary encoding (which needed multiple “bit flips” to express position), sinusoidal encoding achieves the same with just a few continuous waves. It’s both compact and smooth.

**Making Sinusoidal Encoding Deterministic**

Now, how do we ensure that this encoding is consistent and mathematically sound? That’s where the original paper’s magic formula comes in:

![image](https://miro.medium.com/v2/resize:fit:648/1*29P38e222RV-lSxQ0yzt6w.png)

This formula makes sure that:

* The encoding is **deterministic** (you get the same result every time).
* The waves vary across **different frequencies** , depending on the embedding dimension.
* Sine and cosine are used together to create **interleaved patterns** , ensuring maximum positional diversity.

### Sinusoidal Positional Encoding

Let’s revisit the four problems we discussed earlier and see how sinusoidal encoding addresses each:

🔹 **Fixes Discontinuity:**
Sine and cosine functions change gradually. Each new position causes a smooth shift in vector values. No sharp binary jumps. This smoothness leads to better gradient flow and more stable training.

🔹 **Captures Relative Position:**
Thanks to periodicity and smooth gradients, the difference between positions becomes meaningful. For instance,

![image](https://miro.medium.com/v2/resize:fit:424/1*ILBSCSMVtPVuxWGOQ0o7bA.png)

This means: _The model can learn how far apart two positions are just by subtracting their encodings._ With binary, position 7 (0111) and 8 (1000) had no relation — now, the difference is predictable and informative.

🔹 **Generalizes to Any Sequence Length:**
You don’t need more bits for longer sentences. The formula works for position 10 or 10,000 — no architecture changes, no retraining. The model can encode positions it has never seen before.

🔹 **Stable Optimization (No Gradient Noise):**
Since sinusoidal encoding is fixed and not learned, it adds no trainable parameters. The values remain within a smooth, bounded range, helping prevent exploding gradients or erratic updates. Training becomes faster and more stable.

In short, sinusoidal encoding is elegant, effective, and perfectly aligned with the Transformer’s goal: process sequences in parallel without losing positional meaning.

Before we wrap up positional encoding, it’s worth noting that the sinusoidal method from the _“Attention Is All You Need”_ paper is no longer the most widely used approach. These days, **Rotary Position Embeddings (RoPE)** have become more popular in modern architectures. That said, new research is still building on ideas — for example, this recent paper: [arXiv:2410.06205](<https://arxiv.org/pdf/2410.06205>).

But for now, having a solid understanding of how positional encoding was originally introduced — and how it enables parallel processing — is more than enough.
