**Problem Statement: How do we choose the right document from thousands of our documents to retrieve information from in a RAG system?**

In this article, we demonstrate how you can create an Automated File Directory through Knowledge Table, simply by running a set of pre-set queries against a set of your documents, and saving it as a Knowledge Graph, so that you can direct natural language queries to the right filtered set of documents, reducing the search space, and increasing the accuracy of retrieval.

When trying to build RAG systems for Enterprise systems, we must account for the fact that enterprises have a messy collection of tens of thousands of documents that they want to consider in their enterprise memory systems.

If we categorize RAG processes into two separate steps, we can imagine two steps. First identifying which document is most relevant to a query, and then parsing the content within the filtered list of documents for the final information we want to retrieve. This can be seen illustrated in the diagram below.

![image](https://miro.medium.com/v2/resize:fit:1000/1*fwXtYrEv4X2c7CEw08hBhg.png)

We can see that we will first need intelligent document parsing and tagging systems that can help create contextual tags for each document. Thankfully, this is a task that LLMs are fantastic at. In the below example demo, we take a set of 10 Samsung product catalogs. We then run a number of pre-set questions that constitute the schema for our metadata. These questions include ‘What is the Product discussed?’, ‘What is the model discussed?’, ‘What category does this Product fail into?’, ‘What is a description of this Product?’, etc. Each cell value then constitutes metadata that we tie to the specific document, based on the output of the question.

We can see that when we are generating this metadata, we can set pre-set rules for what an exhaustive list of classification can look like. It should be emphasized that even though there is a UI/UX component to this process, this entire process can be done programmatically. This is so developers can stream large sets of documents and data without necessarily having to fiddle with the UI.

Once we create the document metadata in the knowledge table, we export the manual metadata to triples and create a graph of documents using our SDK.

```python from whyhow import WhyHowclient = WhyHow(api_key="<whyhow-api-key>", base_url="https://api.whyhow.ai")graph_id = client.create_graph_from_knowledge_table( file_path="./path/to/triples.json", workspace_name="manuals", graph_name="manual graph")# Print the created graph IDprint(f"Created graph with ID: {graph_id}") ```

This constructs a Manual Graph of all the file metadata, and can be queried to quickly understand high level context about each product. As part of the graph creation, we are also adding information about the manual as a property in each node so that we can correlate metadata back to a source document.

![https://app.whyhow.ai/public/graph/670db00d38be68140d16784c](https://miro.medium.com/v2/resize:fit:1000/0*uYZR63KDw2XYRzkT)

We also create a dedicated graph of each specific manual in the knowledge table that we can query for product-specific questions. For example, here is a graph of the Galaxy S23 user manual as can be seen below.

![https://app.whyhow.ai/public/graph/670da68d38be68140d16783e](https://miro.medium.com/v2/resize:fit:1000/0*yDU06rzWEO-EN-gF)

Answering a question about products is a two step multi-agent process that leverages two kinds of graphs, the graph or all manuals, and individual product-specific graphs. First, we query the manuals graph to find the most relevant manuals for answering a given question.

```python def get_docs(q: str): # query = "Which files should I look at to answer this question: " + q query_response = client.graphs.query_unstructured( graph_id="<manual-graph-id>", query=query ) return query_response ``` ```python def query_specific_graph(graph: str, query: str): # look up graph id answer = client.graphs.query_unstructured(graph_id="<graph_id>", query=query) return answer.answer ```

When we ask “Which 2023 devices have biometric capabilities?”, the first agent retrieves manuals of products that were made in 2023, in this case, the manuals for a Samsung washer, a Samsung notebook computer, and a Samsung smartphone. We then parse the response, and for each product that was returned by the first query, we then run a query against that product’s dedicated graph.

```json query = "Which 2023 devices have biometric capabilities?"manuals = get_docs(query)for node in manuals.nodes: if node["label"] == "Product": doc_property = node['properties'].get('document') relevant_docs.append(doc_property)answers = []for doc in relevant_docs: answer = query_specific_graph(doc, query) answers.append({"answer":answer, "source": node["name"]}) ```

We concatenate all the responses into an array, keeping track of the source documents, and then we pass it into a final agent whose job is to summarize the responses and produce a final answer. In this case, two of the three products have biometric capabilities and the answer reflects that.

```python def get_final_answer(answers: list, query: str): prompt = f""" Answer the following query using the information provided in the data below. Explain your answer. Query: {query} Data: {answers} """ print(f"Prompt: {prompt}") response = openai_client.chat.completions.create( model="gpt-4o-mini", messages=[ {"role": "user", "content": prompt}, ], max_tokens=512, ) return response.choices[0].message.content ```

We can also query using other types of metadata. For example, if we ask the question “Which biometric capabilities do phones have?”, our search will reveal three types of “phones” (rather than three products from the year “2023”), the Samsung Galaxy S21, S22, and S23. Each product-specific graph is queried and you can generate a completely different type of answer.
