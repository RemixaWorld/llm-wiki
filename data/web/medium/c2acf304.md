Let’s be honest — retrieval-augmented generation is great but it’s not magic. you can have solid retrievers and even fancy re-rankers and still end up feeding your llm a mess of irrelevant context. that means longer prompts slower inference and worse answers .

If you’ve worked with rag in practice you’ve seen it — top-ranked passages still carry fluff. sentence-level noise that adds nothing useful and just burns tokens .

That’s where provence comes in — a smarter sentence-level pruning method that filters out the junk before it reaches your language model .

## What is provence?

Press enter or click to view image in full size

**Provence** is a sentence-level context pruning method designed to improve retrieval-augmented generation pipelines by removing irrelevant information from retrieved documents. it’s built on top of a re-ranker architecture (specifically deberta-v3) and introduces a dual-head model: one head re-ranks passages as usual, while the other performs token-level pruning by predicting which parts of a passage are useful for answering a given question.

This makes provence extremely efficient — you get both re-ranking and pruning in a single forward pass. it’s a drop-in enhancement for rag systems that want to clean up noisy inputs before sending them to a language model.

## How was it trained?

Press enter or click to view image in full size

To train **provence** , the authors created silver labels using llama-3. for each question, they retrieved passages and then used llama-3–8b to generate answers. from there, they automatically identified which sentences in the retrieved context were actually used by the model. this allowed them to build a training set without manual annotation, capturing sentence-level relevance in a way that reflects how llms consume context. training data came from a mix of [ms-marco](<https://microsoft.github.io/msmarco/>) and natural questions, with variable-length passages and title prepending to simulate real-world document structures.

Press enter or click to view image in full size

The model architecture is based on deberta-v3 with two heads: a pruning head that produces token-level binary masks, and a re-ranking head that scores passage relevance using the bos token. during training, the model optimizes both pruning accuracy and reranker fidelity using a combined loss — binary cross-entropy for pruning and mean squared error (mse) for distillation from the original reranker. this ensures that pruning performance improves without sacrificing reranking quality. during inference, the pruning head outputs token-wise probabilities that are thresholded (typically at 0.1 or 0.5) to decide which sentences to keep.

## The Results

Press enter or click to view image in full size

Results show that provence consistently achieves high compression (removing 50–80% of input) with minimal or no drop in answer quality across benchmarks like natural questions, hotpotqa, tydi qa, and popqa.

In some cases, it even improves answer quality by removing misleading or irrelevant context. the pruning is robust — it works regardless of where the relevant sentence appears in the passage, and it dynamically adapts to the number of sentences needed. ablation studies show that the unified architecture (re-ranking + pruning) and the use of llm-generated labels are key to its performance. most importantly, because pruning is fused with re-ranking, there’s almost no additional latency — which makes it practical for real-time or production-grade rag systems.

In short, provence helps llms read less and answer better. it’s a smart, efficient way to clean up context without complicating your pipeline — and it’s available open-source on hugging face if you want to try it today. in fact, that’s exactly what we’ll do in this blog post. in the **code time** section, we’ll walk through how to plug provence into a simple rag pipeline using only free tools — no fancy infrastructure or paid apis needed.

## Code time :

### Setup and data download :

We install the required libraries from the `llama-index` ecosystem — including neo4j vector support, google embeddings, and cohere re-ranker.

Then we create a local `data` directory and download a sample text file to use as our input data.

### Models and api setup :

Here we import components from `llama-index` for embeddings, vector store, and re-ranking.

```python from llama_index.embeddings.google_genai import GoogleGenAIEmbeddingfrom llama_index.postprocessor.cohere_rerank import CohereRerankimport torchfrom transformers import AutoModelimport osGOOGLE_API_KEY = "xxxxxxxxxxx"COHERE_API_KEY = "xxxxxxxxxxxxxx"os.environ["GOOGLE_API_KEY"] = GOOGLE_API_KEYos.environ["COHERE_API_KEY"] = COHERE_API_KEYembed_model = GoogleGenAIEmbedding(model_name="text-embedding-004") ```

We set our `google` and `cohere` api keys as environment variables, then initialize the **embedding model** with `text-embedding-004` — from google’s genai suite. these will be used for creating vector embeddings of our text.

### Vector store setup with neo4j

This block connects to a **neo4j vector database** using your credentials and uri.

```python from llama_index.vector_stores.neo4jvector import Neo4jVectorStoreNEO4J_USERNAME = "neo4j"NEO4J_PASSWORD = "xxxxx"NEO4J_URI = "neo4j+s://xxxxx.databases.neo4j.io"EMBED_DIM = 768neo4j_vector = Neo4jVectorStore(NEO4J_USERNAME, NEO4J_PASSWORD, NEO4J_URI, EMBED_DIM, hybrid_search=True) ```

We specify the embedding dimension (`768`) to match the embedding model, and enable `hybrid_search`, which lets us combine vector similarity with keyword-based scoring — improving retrieval quality. this store will hold our document embeddings for fast and relevant search.

### Document loading and indexing

Here we load our data from the `./data` folder using `SimpleDirectoryReader`, then split it into chunks of **512** tokens with **50** tokens of overlap for better semantic continuity.

```python # load documentsfrom llama_index.core import StorageContext , VectorStoreIndex, SimpleDirectoryReaderfrom llama_index.core import SettingsSettings.chunk_size = 512Settings.chunk_overlap = 50documents = SimpleDirectoryReader("./data").load_data()storage_context = StorageContext.from_defaults(vector_store=neo4j_vector)index = VectorStoreIndex.from_documents( documents, storage_context=storage_context , embed_model=embed_model) ```

We create a `storage_context` that points to our neo4j vector store, and build a `VectorStoreIndex` using the loaded documents and the embedding model. this step prepares our data for retrieval.

### Context pruning pipeline with provence

This class defines a full **retrieval + reranking + pruning pipeline**. it starts by retrieving documents using your vector index, **optionally** reranks them with **cohere’s reranker** , then prunes each one using the **provence model**.

```python from llama_index.core.schema import NodeWithScoreclass ContextPruningPipeline: def __init__(self, index, top_n=15, similarity_top_k=10, use_reranker=False): self.retriever = index.as_retriever(similarity_top_k=similarity_top_k) self.top_n = top_n self.use_reranker = use_reranker # initialize Cohere reranker only if requested if use_reranker: from llama_index.postprocessor import CohereRerank self.reranker = CohereRerank(top_n=top_n, model="rerank-v3.5") else: self.reranker = None # load Provence model and move to gpu if available self.device = torch.device("cuda" if torch.cuda.is_available() else "cpu") self.provence = AutoModel.from_pretrained( "naver/provence-reranker-debertav3-v1", trust_remote_code=True ).to(self.device) def prune_contexts(self, question: str, docs: list[str]) -> list[dict]: results = [] for doc in docs: output = self.provence.process(question, doc) results.append({ "pruned_context": output["pruned_context"], "reranking_score": float(output["reranking_score"]), }) return results def run(self, query: str) -> list[NodeWithScore]: # step 1 retrieve retrieved_nodes = self.retriever.retrieve(query) # step 2 optional reranking if self.reranker: retrieved_nodes = self.reranker.postprocess_nodes( nodes=retrieved_nodes, query_str=query ) # step 3 prune with Provence and wrap in NodeWithScore pruned_nodes = [] for node in retrieved_nodes: output = self.provence.process(query, node.get_content()) pruned_text = output["pruned_context"].strip() score = float(output["reranking_score"]) if pruned_text: pruned_node = NodeWithScore( node=node.node, score=score, ) pruned_node.node.text = pruned_text pruned_nodes.append(pruned_node) return pruned_nodes ```

First we initialize the retriever, load the `provence` model (using `AutoModel.from_pretrained`) and move it to gpu if available. reranking is optional.

The `run` method does three steps:

1. retrieve documents based on similarity
2. optionally rerank them for relevance
3. use provence to prune each document’s content down to only the relevant sentences

Each pruned result is returned as a `NodeWithScore` — ready for llm input. this setup ensures that only the most relevant, clean context reaches your model.

### Run the pipeline on a question

Here we create an instance of the `ContextPruningPipeline`, specifying that we want to retrieve the top 15 most similar chunks and keep the top 5 after reranking.

``` pipeline = ContextPruningPipeline(index, top_n=5 , similarity_top_k=15) ```

Then we run the full pipeline on the query `"what did the author do growing up?"`.

``` query = "What did the author do growing up?"results = pipeline.run(query) ```

This will retrieve relevant chunks, optionally rerank them, prune them with **provence** , and return a cleaned-up list of high-quality context nodes.

## !! NOTES !! :

In a real-time rag pipeline, you have a couple of options — you can use a re-ranker like cohere first and then apply provence to prune the context, or you can skip the re-ranker and rely on provence directly. while provence isn’t quite as strong as dedicated re-rankers in ranking quality, it’s extremely fast and still good enough for many cases, especially when latency is critical. for speed-focused applications, this trade-off can be well worth it.

You could also deploy provence as a separate api — especially on a gpu-powered machine with a solid inference engine — to keep pruning fast and modular.

Just keep in mind that the model used here, `naver/provence-reranker-debertav3-v1`, is released under a **cc-by-nc-4.0** license, which means it's not allowed for commercial use.

However the authors have been transparent in their [paper](<https://arxiv.org/abs/2501.16214>), and it contains everything we need to understand the architecture and even train our own version if needed.
