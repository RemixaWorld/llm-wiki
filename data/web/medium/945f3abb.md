### **The Architecture:**

![created by author M K Pavan Kumar (in relation with the title architecture)](https://miro.medium.com/v2/resize:fit:700/1*6tgRQqAR4WdaFfSbwGcnwQ.png)

The architecture consists of two main workflows: a model deployment pipeline and a client-serving system. The deployment pipeline (n8n), shown at the top of the diagram, starts with a scheduled trigger that initiates the process. It connects to AWS S3 to list and download model files, aggregates them, and finally writes them to a local file system. This automated pipeline ensures that models are consistently updated and available for serving.

The heart of this architecture lies in its flexible model tracking system. The MLflow model tracking server, represented in the diagram, maintains multiple active model versions (V1, V2, V3, V4, up to Vn). This is where the real power of the system shines — different clients can simultaneously use different model versions according to their specific needs or requirements. For instance, while Client 1 might be using V1 for their production workload, another client could be using V3 for their use case, all served from the same infrastructure.

The integration between LlamaIndex and Qdrant isn’t just a simple logging mechanism — it represents a fully decoupled vector search infrastructure that’s seamlessly tracked within MLflow. When a model version is logged, its corresponding vector store, built using LlamaIndex and persisted in Qdrant, is also captured as part of the MLflow artifacts. This design choice is particularly powerful because it allows clients to fetch not just the model, but also the complete vector index required for their queries.

The beauty of this decoupling becomes apparent in production scenarios. Clients don’t need to rebuild or maintain their own vector indices — they can simply retrieve the pre-built index associated with their chosen model version from MLflow. This separation of concerns between indexing and querying brings several advantages: it reduces computational overhead on the client side, ensures consistency in vector search results across different deployments, and allows for independent scaling of indexing and querying operations. Think of it as a “vector index as a service” that’s version-controlled alongside your models.

What makes this architecture truly beautiful is its ability to maintain backward compatibility while enabling forward progression. Clients aren’t forced to upgrade to the latest model version simultaneously — they can migrate at their own pace while the system continues to serve their current version reliably. This flexibility is crucial in enterprise environments where different clients may have varying requirements, testing cycles, or regulatory constraints.

The system’s decoupled nature ensures that model updates and version management don’t impact the serving layer’s availability. Each version operates independently, and the MLflow tracking server acts as a central hub that manages these versions efficiently. This approach significantly reduces the operational complexity of managing multiple model versions in production while ensuring reliable service for all clients.

The `model_indexing.py`

```python from llama_index.core import Settings, SimpleDirectoryReader, StorageContext, VectorStoreIndexfrom llama_index.embeddings.ollama import OllamaEmbeddingfrom llama_index.llms.ollama import Ollamafrom llama_index.vector_stores.qdrant import QdrantVectorStorefrom dotenv import load_dotenv, find_dotenvimport qdrant_clientimport mlflowimport osload_dotenv(find_dotenv())Settings.llm = Ollama(model=os.environ.get('LANGUAGE_MODEL'), base_url=os.environ.get('OLLAMA_URL'))Settings.embed_model = OllamaEmbedding(model_name=os.environ.get('EMBED_MODEL'), base_url=os.environ.get('OLLAMA_URL'))Settings.chunk_size = int(os.environ.get("CHUNK_SIZE"))Settings.chunk_overlap = int(os.environ.get("CHUNK_OVERLAP"))documents = SimpleDirectoryReader(input_dir='data', required_exts=['.pdf']).load_data(show_progress=True)client = qdrant_client.QdrantClient(url=os.environ.get('QDRANT_URL'), api_key=os.environ.get('QDRANT_API_KEY'))vector_store = QdrantVectorStore(client=client, collection_name=os.environ.get('COLLECTION_NAME'))storage_context = StorageContext.from_defaults(vector_store=vector_store)index = Noneif not client.collection_exists(collection_name=os.environ.get('COLLECTION_NAME')): index = VectorStoreIndex.from_documents(documents=documents, storage_context=storage_context, show_progress=True)else: index = VectorStoreIndex.from_vector_store(vector_store=vector_store)mlflow.models.set_model(index) ```

This script sets up a methodology to process documents, embed them using a specific language model, and store the embeddings in a Qdrant vector database for efficient retrieval. Here’s a breakdown of the functionality:

1. **Configuration and Settings** : The code initializes settings for the language model (LLM) and embedding model using environment variables. These settings include the model type, base URL for the service, and chunking parameters for splitting documents into manageable segments.
2. **Document Loading** : It uses the `SimpleDirectoryReader` to load and process documents from a specified directory, targeting PDF files. The documents are read and prepared for embedding and storage, with progress indicators to track the operation.
3. **Vector Store Setup** : A Qdrant vector store is established using the `QdrantClient`. It connects to the Qdrant database using a URL and API key from environment variables. This serves as the backend for storing and retrieving vector embeddings of document data.
4. **Index Creation or Retrieval** : The script checks whether a specified collection exists in the Qdrant database. If it doesn’t, a new index is created by embedding the loaded documents and storing them in the vector store. If the collection exists, it reuses the existing vector store to initialize the index.
5. **Model Registration** : Finally, the script registers the constructed or loaded index as a model in MLflow, enabling model versioning, tracking, and further deployment in workflows.

replace with your own logic file_name = os.path.basename(file_path) file_size = os.path.getsize(file_path) print(f"Processing {file_name} (Size: {file_size} bytes)") mlflow.set_tracking_uri('http://127.0.0.1:3000') mlflow.set_experiment(experiment_name='llamaindex-qdrant-rag-9') mlflow.llama_index.autolog() with mlflow.start_run(): model_info = mlflow.llama_index.log_model( "model_indexing.py", artifact_path="index", engine_type="query", # chat, query & retrieve input_example="your query here", # Infers signature registered_model_name="my_llama_index_vector_store", # Stores an instance in the model registry ) print("MLflow version:", mlflow.__version__) print(f"model_uri = {model_info.model_uri}") print("Tracking URI:", mlflow.get_tracking_uri()) print("Artifact URI:", mlflow.get_artifact_uri()) except Exception as e: print(f"Error processing file {file_path}: {str(e)}")def watch_folder(path): """Set up folder watching""" event_handler = FolderWatcher() observer = Observer() observer.schedule(event_handler, path, recursive=False) observer.start() try: while True: time.sleep(1) except KeyboardInterrupt: observer.stop() print("Folder watching stopped") observer.join()if __name__ == "__main__": # Replace with your folder path folder_to_watch = "./data" print(f"Starting to watch folder: {folder_to_watch}") watch_folder(folder_to_watch) ```

This script implements a folder watcher that monitors a specific directory for changes, such as file creation or modification. It is designed to trigger specific actions when new files are added or existing files are updated. The watcher is powered by the `watchdog` library, which listens for filesystem events and allows custom handlers to process these events.

The `process_file` method is where the actual logic for handling files resides. It takes the file path as input, extracts metadata like the file name and size, and prints this information for logging purposes. This method then integrates with MLflow for tracking and managing the machine learning workflow. Specifically, it sets the MLflow tracking URI and selects an experiment named "llamaindex-qdrant-rag-9." The `mlflow.llama_index.autolog()` function is used to enable automatic logging for LlamaIndex operations.

Within an MLflow run, the script logs a model using `mlflow.llama_index.log_model`. It specifies a Python script ("model_indexing.py") as the model artifact and sets additional parameters like the engine type (`query`), an input example, and a registered model name ("my_llama_index_vector_store"). The model logging process registers the model with MLflow, providing a URI for future access and storing related artifacts. The method concludes by printing the MLflow version, tracking URI, and artifact URI for debugging and confirmation.
