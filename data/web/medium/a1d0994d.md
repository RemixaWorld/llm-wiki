Modern LLMs have superpowers like a 2M token context window and hundreds of billions of parameters. However, the solution to inject private data remains the same — RAGs.

But if you put poor-quality documents as context, you get poor answers. Garbage in, garbage out!

The model itself has little impact on the final output of the RAG. In RAGs, small LLMs like Llama 3.2 3B can do pretty much the same job as O3. A larger model’s reasoning abilities may be helpful for complex tasks like AI agents. But for RAGs? You’ll often get satisfied with smaller ones.

However, RAGs have two bottlenecks. If you get any of them wrong, your app could be trashed.

One is chunking. We break the document into smaller chunks and store them in a database for retrieval. The chunks must be small enough to exclude noise and large enough to capture one main idea. If done correctly, you can retrieve high-quality data from the database to answer users’ questions.

## Does Reranking matter?

Usually, when we retrieve chunks for RAGs, we use vector search. Vector databases can efficiently compute the cosine similarity of our input to the vector versions of the documents in the databases. They then fetch the top n results.

You don’t have to use a vector database to retrieve information, but this is the most popular one.

However, vector similarity doesn’t warrant that the documents are semantically similar.

Consider some examples. Two documents might use the same word with different meanings:

``` Document A: "The bank by the river collapsed during the flood."Document B: "The bank announced it would collapse multiple branches to cut costs." ```

These documents might have high vector similarity due to shared terms like “bank” and “collapse,” but they discuss entirely different concepts (e.g., a riverbank vs. a financial institution).

Here’s another one,

``` Document A: "Machine learning models require significant computational resources for training."Document B: "Military training exercises require significant resources and planning." ```

The similar structure and shared terms (“training,” “resources”) might create high vector similarity despite discussing unrelated domains.

These retrieved documents are irrelevant to answering the user’s query, and distance-based searches don’t account for this. Therefore, we need a more intelligent second-level reranking.

This is where reranking models come in.

Reranking models are a special kind of LLMs. They specialize in ranking a given set of documents against an input query by their relevancy. Therefore, they need some special abilities.

## How Rerank Works?

Reranking, as its name suggests, takes many search results and reorders by their relevance to the given input query. Here’s an example:

```python # Import necessary librariesfrom typing import Listimport bs4from dotenv import load_dotenvfrom langchain.retrievers import ContextualCompressionRetrieverfrom langchain.retrievers.document_compressors import CohereRerankfrom langchain_chroma import Chromafrom langchain_community.document_loaders import WebBaseLoaderfrom langchain_core.documents import Documentfrom langchain_core.output_parsers import StrOutputParserfrom langchain_core.prompts import ChatPromptTemplatefrom langchain_core.runnables import RunnablePassthroughfrom langchain_openai import ChatOpenAI, OpenAIEmbeddingsfrom langchain_text_splitters import RecursiveCharacterTextSplitter# Load environment variablesload_dotenv()# Initialize OpenAI embeddings and LLMembeddings = OpenAIEmbeddings()llm = ChatOpenAI(model="gpt-4o-mini")# Scrape Django documentation and split it into manageable chunksloader = WebBaseLoader( web_paths=("https://docs.djangoproject.com/en/5.1/topics/security/",), bs_kwargs=dict(parse_only=bs4.SoupStrainer(id="docs-content")),)docs = loader.load()splitter = RecursiveCharacterTextSplitter( chunk_size=1000, chunk_overlap=200, length_function=len)chunks = splitter.split_documents(docs)# Create a vector database from the document chunksvector_db = Chroma.from_documents( documents=chunks, embedding=embeddings, persist_directory="./chroma_db")# Set up the standard retrieverstandard_retriever = vector_db.as_retriever( search_type="similarity", search_kwargs={"k": 10})# Set up the Cohere rerankercohere_compressor = CohereRerank()cohere_retriever = ContextualCompressionRetriever( base_compressor=cohere_compressor, base_retriever=standard_retriever)# Set up prompt templateprompt = ChatPromptTemplate.from_template( """You are a helpful assistant that provides information about the Django framework.Answer the question based on the provided context. If you don't know the answer,say so honestly and suggest checking the Django documentation.Context:{context}Question:{question}Answer:""")# Helper function to format documents for the promptdef format_docs(docs): return "

".join([doc.page_content for doc in docs])# Create different RAG chains to compare performancestandard_rag_chain = ( { "context": lambda query: format_docs( standard_retriever.get_relevant_documents(query) ), "question": RunnablePassthrough(), } | prompt | llm | StrOutputParser())cohere_rag_chain = ( { "context": lambda query: format_docs( cohere_retriever.get_relevant_documents(query) ), "question": RunnablePassthrough(), } | prompt | llm | StrOutputParser())# Test and compare the different approachestest_question = "What are Django's best practices for preventing SQL injection attacks?"print("
--- Standard Similarity Search ---")response1 = standard_rag_chain.invoke(test_question)print(response1)print("
--- Cohere Reranking ---")response2 = cohere_rag_chain.invoke(test_question)print(response2) ```

We have a workflow to read and index Django’s security docs in this. We then create an RAG chain that answers user queries by retrieving relevant information from the indexed db.

The second method is a RAG chain with Reranking. Notice that we’ve used a **Contextual Compression Retriever** instead of the regular retriever. This does the extra magic.

The example only illustrates the implementation. Sure, both methods would produce the same results for a small webpage like this as the source. However, in real-world applications where you must scan hundreds of thousands of documents, the first method is often insufficient to produce quality answers.

But if you’ve implemented this in your projects, your chances of improving your RAG are only about 50%. If you speak to people who’ve implemented this, this would be the answer.

There are various reasons for this. Reranking is a powerful technique, not a silver bullet, that can magically fix everything. But I found a fix that could make reranking work for most cases.

## Fixing the major reranking issue

We introduced reranking to fix poorly performing distance-based retrieval in vector stores. However, reranking itself doesn’t help if your data contains too many copies of the same information.

To understand this, let’s consider an example.

Let’s say you retrieve information to the query “What indoor plants are good to grow under low light conditions.” Now, suppose you’ve retrieved the following information:

``` 1\. Pothos grow under low light conditions and it's a good indoor plant.2. Houseplants are usually a good option to grow under low light.3. Pothos is an indoor plant that needs little light. 4. Pothos can tollarate low light conditions. You can grow them indoors. 5. Lettuces can grow under low light condition, but their yiled would be low. Not good for indoor without a grow light. ```

Did you notice that there are three duplicates of Pothos? If you rerank this, the ranks wouldn’t be very accurate because of these duplicates.

For unstructured data, you can’t tell if duplicates are talking about different things. Therefore, removing them entirely can harm the final results.

I recently came across a[ paper that introduced the dartboard method](<https://arxiv.org/html/2407.12101v1>). This method can improve the relevance of the context by removing redundant documents from the context we retrieve.

Let’s take a peek at its implementation and discuss how it works.

```python # ALl other code remains the same...# Create a class to perform dartboard rerankingclass DartboardRanker: def __init__( self, embedding_model, relevance_weight=0.7, diversity_weight=0.3, ): self.embedding_model = embedding_model self.relevance_weight = relevance_weight self.diversity_weight = diversity_weight self.cohere_reranker = CohereRerank() def rerank(self, docs: List[Document], query: str, k: int = 5) -> List[Document]: """Rerank documents using the dartboard technique.""" if len(docs) <= 1: return docs # Use Cohere reranker for relevance scoring # First get relevance-reranked documents reranked_docs = self.cohere_reranker.compress_documents(docs, query) # Since compress_documents just returns reordered docs without scores, # we'll create artificial relevance scores based on position # Higher position = higher relevance num_docs = len(reranked_docs) relevance_scores = np.array( [(num_docs - i) / num_docs for i in range(num_docs)] ) # Get embeddings for diversity calculation doc_texts = [doc.page_content for doc in reranked_docs] doc_embeddings = self.embedding_model.embed_documents(doc_texts) # Calculate diversity scores using cosine similarity similarity_matrix = cosine_similarity(doc_embeddings) mean_similarities = np.mean(similarity_matrix, axis=1) diversity_scores = 1 - mean_similarities # Normalize diversity scores if max(diversity_scores) > min(diversity_scores): diversity_scores = (diversity_scores - min(diversity_scores)) / ( max(diversity_scores) - min(diversity_scores) ) else: diversity_scores = np.ones_like(diversity_scores) # Combine scores using dartboard technique combined_scores = (self.relevance_weight * relevance_scores) + ( self.diversity_weight * diversity_scores ) # Sort documents by combined score sorted_indices = np.argsort(-combined_scores) # Descending order # Return top k documents return [reranked_docs[i] for i in sorted_indices[: min(k, len(reranked_docs))]]# Create the dartboard rankerdartboard_ranker = DartboardRanker( embedding_model=embeddings, relevance_weight=0.7, diversity_weight=0.3)# Function to retrieve with dartboard techniquedef retrieve_with_dartboard(query): # First get docs with standard retriever initial_docs = standard_retriever.get_relevant_documents(query) # Then apply dartboard reranking reranked_docs = dartboard_ranker.rerank(initial_docs, query, k=5) return reranked_docsdartboard_rag_chain = ( { "context": lambda query: format_docs(retrieve_with_dartboard(query)), "question": RunnablePassthrough(), } | prompt | llm | StrOutputParser())print("
--- Dartboard Technique (Relevance + Diversity) ---")response3 = dartboard_rag_chain.invoke(test_question)print(response3) ```

If you study the code carefully, in addition to the relevant score, we calculate another one called the diversity score. This score is used to find how unique the information is compared to all other retrieved contexts.

If a document is similar to most other documents in the collection, it will receive a low diversity score. However, if the information is unique, it will receive a higher diversity score.

The entire process of retrieval now has three steps.

1. Standard retriever fetches relevant documents from the vector store based on distance scores.
2. The Reranker model reorders them and fetches only the semantically relevant information.
3. The dartboard technique removes copies of the same information appearing multiple times.

Now, our context for the LLM is smaller and more relevant. With little noise, your RAGs will respond with high-quality accuracy.

## Final Thoughts

RAGs are everywhere. I’d say it’s GenAI’s predominant application area.

However, RAGs can be improved in many ways. One primary weakness is poor retrieval if information is retrieved using distance-based matrices. A fix for this is Reranking. Models such as Cohere’s Reranker can help for a degree. But sometimes, these models alone won’t take us to the best they can.

The dartboard technique is another layer in the retrieval stack, effectively filtering out redundant information from the retrieved context.
