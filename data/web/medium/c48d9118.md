Classification problems are everywhere. From identifying spam messages to recommending us the next YouTube video, we constantly rely on systems that classify data to make our lives easier, often without even realizing it.

Traditional machine learning excels at this type of thing. Train a model with enough example data and it will learn to classify effectively.

However, in my own experience, there’s a set of real-world problems, where having a classification model would be ideal, but training one just isn’t practical. Whether you lack enough data or the complexity isn’t worth the effort, training a custom model doesn’t always make sense.

That’s where _Large Language Models_ (LLMs) like GPT, Claude, etc. come in. These powerful, general-purpose models can be adapted to a wide range of tasks using prompts, without the need for retraining. LLMs are ideal for situations where building a traditional classification model isn’t practical for the following reasons:

* **General Knowledge** : LLMs are trained on vast, diverse data, allowing them to classify text across various domains without domain-specific training. This makes them perfect for use cases where you lack sufficient labeled data or need broad contextual understanding.
* **Flexibility** : Unlike rigid traditional models, LLMs don’t require retraining when new categories or criteria emerge. You can simply modify the prompt to handle changes, making them ideal for dynamic environments where the classification needs to evolve over time.

## LLM as a classifier

How do you get the LLM to classify your data?—With a prompt. The prompt should roughly resemble something like this:

```python # InstructionHey LLM, you are a classifier.Choose the most appropriate class and output only your classification.There are these classes:{classes}# SolveThis is the input to be classified:{input} ```

Given a prompt like this, the LLM will operate as a classification model. This is called _zero-shot prompting_. Results here will vary depending on your use case, which generally falls into two categories:

**In training distribution (category 1):**

* _LLM can perform your task well out of the box_ : Both the classes and the input are common enough in the LLM’s training dataset that the concepts are generally understood
*  _Example_ : Classifying customer reviews into categories like “Positive”, “Neutral”, “Negative”. The boundaries between these categories are well reflected in the training data.

**Out of training distribution (category 2):**

* _LLM cannot perform your task well out of the box:_ Either the classes or the input are too unique or proprietary, meaning the concepts wouldn’t be reflected in the LLM’s training data.
* _Example_ : Classifying expenses into personalized categories like “Needs”, “Wants”, “Travel”. Such distinctions are personal and wouldn’t be reflected in the LLM’s training data.

If your use case is category 1, then you will likely see excellent performance from the most advanced LLMs with zero-shot prompting.

If your use case is category 2, then the bad news it that even the most advanced LLMs will struggle to accurately classify your input with zero-shot prompting. The good news is, we can improve the results.

## Better classification through retrieval

To address performance issues, especially when tasks fall outside the LLM’s training distribution, we can improve classification by augmenting the prompt with retrieval. This approach is called _Retrieval Augmented Classification_ ([RAC](<https://arxiv.org/abs/2202.11233>)), a method that integrates retrieval with classification to improve the LLM’s decision-making.

Incorporating retrieval into your classification pipeline transforms the LLM from a simple zero-shot classifier to a more contextually informed one. This works by retrieving relevant information from a pre-indexed dataset and feeding it into the prompt. This additional data can narrow the scope of the problem, making it easier for the LLM to correctly classify the input.

### How RAC improves classification

**Enhancing context with similar examples** :

By retrieving similar examples from your dataset, you provide the LLM with more context about the specific input. This contextual information is crucial, especially when the classification involves nuanced or domain-specific distinctions.

For example, if you’re classifying transactions into categories like “Needs”, “Wants”, and “Travel” retrieving previous transactions that have been labeled similarly can guide the LLM toward the right classification by showing it how similar data points were categorized in the past.

**Altering the prompt with retrieved data** :

In a retrieval-augmented setup, the prompt includes the relevant retrieved examples, which help the LLM better understand the decision boundaries between classes. A retrieval-enhanced prompt might look like this:

```python # InstructionHey LLM, you are a classifier.Consider the previously labeled examples when making your classification.Choose the most appropriate class and output only your classification.There are these classes:{classes}Here are some examples of previously labeled data:{retrieved_examples}# SolveThis is the input to be classified:{input} ```

The core idea being that classification becomes easier and more accurate when the LLM has similar examples to guide its decisions.

### How to implement retrieval

To implement RAC, you’ll need to set up a retrieval system. Retrieval can be implemented in different ways, depending on what’s best suited for your use case. Some options include:

* **Vector search with embeddings** : This involves converting your data into embeddings and using a vector database to find the most similar examples based on their semantic meaning. This is especially powerful for unstructured data like text because it captures semantic meaning.
* **Keyword search** : If your data lacks semantic meaning and doesn’t need the power of embeddings, a simple keyword search can do the job.
* **Hybrid search** : You can combine the benefits of vector and keyword search by using a hybrid approach.

While there are options, vector search is probably the easiest way to integrate retrieval into your pipeline, especially with fully managed services like Pinecone that handle the infrastructure for you. With Pinecone, this process is as simple as making a few API calls.

Regardless of retrieval strategy, the retrieval system must be capable of doing 2 things:

1. **Index your data**
2. **Retrieve similar data**

To tie it all together, a full RAC pipeline looks like:

1. **Data indexing** : You index your labeled examples.
2. **Input** : You send the input data to the retrieval system.
3. **Retrieval** : The system fetches relevant examples from your pre-indexed data.
4. **Augmentation** : These examples are passed to the LLM in the prompt.
5. **Classification** : The LLM uses both the input and the retrieved examples to classify the data more accurately.

It’s as simple as that. Once retrieval is in place, your LLM is no longer flying blind — it is now informed with relevant context, which means better results.

## A case study: personal transaction classification

### Transaction data overview

I worked with a set of my own personal transaction data, categorized into labels like:

``` \- Assets:Discover:Main:Needs:Monthly- Assets:Discover:Main:Needs:Groceries- Assets:Discover:Main:Needs:Gas- Assets:Discover:Main:Needs:Other- Assets:Discover:Main:Wants:Monthly- Assets:Discover:Main:Wants:Other- Assets:Discover:Furniture- Assets:Discover:FutureWants- Assets:Discover:Travel ```

This task falls into the out of training distribution category. These classes are my own personal budget categories, meaning that this data likely differs from anything the LLM has seen in training.

Each transaction represents a real-world expense that I wanted to automatically classify into these categories for budgeting purposes. Labeled examples are JSON objects consisting of 4 fields, example:

```json { "vendor": "AMAZON PRIME", "day": "04", "amount": "16.04", "from_account": "Assets:Discover:Main:Needs:Monthly"} ```

Unlabeled examples (AKA test data) lack a `from_account`, example:

```json { "vendor": "SPOTIFY", "day": "09", "amount": "11.76",} ```

I had 130 labeled transactions and 57 unlabeled transactions.

To evaluate how well different approaches worked for this classification task, I ran several experiments using zero-shot prompting, vector retrieval K-Nearest Neighbors, and RAC to evaluate the classification accuracy of `from_account` on the 57 unlabeled transactions.

For my retrieval system, I uploaded the 130 labeled transactions to Pinecone’s serverless vector database using OpenAI embeddings and cosine similarity as the measure of embedding distance.

### Evaluation: z** _ero-shot_**

I began by testing the zero-shot capabilities of two models: GPT 4o-mini and GPT 4o.

* **GPT 4o-mini** : Achieved an accuracy of **38%**. This was expectedly low, as GPT 4o-mini struggled to map my personalized categories without any additional context or learning from examples.
* **GPT 4o** : Performed better, achieving an accuracy of **63%**. This improvement can be attributed to GPT 4o’s more advanced understanding of language and broader knowledge base.

These results highlight the limitations of zero-shot prompting for domain-specific classification tasks. While GPT 4o could handle generic categories fairly well, personalized categories significantly hindered its performance.

### Evaluation: KNN with vector retrieval

In this experiment, I used the retrieval system to find the K most similar transactions from the vector database and classified the unlabeled transaction based on the mode `from_account`. In other words, what is the most common `from_account` in the set of retrieved similar transactions? This method relied solely on the retrieval system and didn't utilize any LLM calls.

* **KNN** : This method increased the accuracy to **64%**. While the improvement was not drastic compared to GPT 4o’s zero-shot performance, it demonstrated that simply retrieving similar transactions without any classification model could yield better results than an LLM working without context.

This approach works well for more frequently occurring categories where similar historical transactions provide strong classification guidance. However, for more personalized categories or those with less data, this approach struggled, as the nearest neighbors were often insufficiently distinct to capture the correct classification.

### Evaluation: RAC

Next, I implemented RAC, combining vector retrieval with LLM classification. In this setup, I used vector embeddings to retrieve similar historical transactions and then fed this retrieved context into the LLM to assist in making a more informed classification decision.

* **GPT 4o-mini with RAC** : Accuracy jumped to **85%**. This significant improvement shows how powerful contextual retrieval can be. By providing the model with relevant examples before asking it to classify the transaction, the LLM was able to handle the nuanced distinctions between categories like “Needs” vs “Wants” much better than in the zero-shot scenario.
* **GPT 4o with RAC** : Interestingly, the accuracy here reached **76%** , lower than GPT 4o-mini’s performance in this setup. While GPT 4o benefited from retrieval, it didn’t show the same leap in performance as GPT 4o-mini. This was unexpected. This could be due to GPT 4o’s tendency to rely more on its inherent knowledge base, which, in this case, led to overconfidence in certain predictions.

RAC demonstrated its strength, especially in cases where zero-shot LLMs struggled to classify accurately. The additional context provided by vector retrieval helped disambiguate transactions that were harder to categorize based purely on the transaction description.

RAC demonstrates a practical solution for low-data and highly personalized classification tasks, offering a flexible and effective alternative to traditional custom model training.

Moving forward, there’s potential for further optimization with improving data quality, retrieval techniques, and prompting to further improve classification accuracy.

### Things to know

**Cost Efficiency:**

One of the major advantages of RAC is its affordability. With LLM API calls costing fractions of a cent and services like Pinecone offering generous free tiers, the cost of running RAC is minimal. You don’t need to invest time or money in training a custom model or managing complex infrastructure, making RAC accessible for personal projects or small-scale deployments.

**Accuracy vs. Human Oversight:**

In this case study, I achieved **85% accuracy** using GPT 4o-mini with RAC, which is certainly useful but not perfect. In practice, this means that while RAC can automate a large portion of the classification work, some human oversight may still be required, particularly for edge cases or critical decisions.

To handle this, I recommend incorporating a mechanism that allows the model to “opt out” when it’s uncertain about a classification. One practical solution is to introduce an additional class: `UNKNOWN`.

By prompting the LLM to return an `UNKNOWN` label when it's not confident in its classification, you create a more robust system. This allows you to focus human effort only on the transactions that the model is unsure about, while automating the bulk of the process.

## Conclusion

As discussed, LLMs are a viable solution for situations where training your own classification model isn’t practical. RAC enhances LLMs’ classification power in situations where zero-shot LLMs fall short. By combining the broad knowledge and language understanding of LLMs with the specificity of retrieved examples, RAC bridges the gap between general-purpose models and domain-specific tasks.

In this case study, RAC significantly improved classification accuracy, particularly for personalized categories that zero-shot LLMs struggled with. The additional context provided by retrieval allows the LLM to make more informed decisions, effectively solving the issue out of training distribution data.

The ease of implementing RAC with tools like Pinecone and the affordability of LLM API calls make it accessible even for smaller projects. While no system is perfect, RAC offers a pragmatic balance between automation and accuracy.
