# The RAG Layer Nobody Talks About

##  _Retrieval gets all the attention. But what happens between retrieval and generation is where systems quietly succeed or fail._

The retrieval worked perfectly.

Five chunks returned, relevance scores above 0.85, exactly the policy documents the user needed. The answer was right there in chunk three.

But the response missed key details. Not a hallucination exactly. More like the model skimmed instead of reading.

You debug the retriever. Tune the embedding model. Adjust chunk sizes. But retrieval was never the issue.

The issue was elsewhere: how those chunks were assembled into a prompt. What order they appeared. How much context surrounded them. Whether the model could actually _use_ what you retrieved.

This is the layer nobody warns you about: what happens _between_ retrieval and generation. Your vector database hands off relevant chunks. Your LLM produces a response. The bit in the middle, the augmentation layer, decides whether your retrieval actually matters.

## Position Still Matters

> LLMs don’t read context uniformly.

[Stanford and Meta researchers found this out in 2023](<https://arxiv.org/pdf/2307.03172>). They buried a critical fact at different positions within retrieved documents and measured accuracy. The results? A U-shaped curve. Models attended strongly to what came first (primacy) and what came last (recency). The middle got neglected.

**This has gotten better.** GPT-4o and Claude 3.5 Sonnet don’t struggle with position as much as GPT-3.5-Turbo did. The effect hasn’t vanished. It’s reduced, not eliminated. The architectural cause remains: transformer attention mechanisms, through quirks of softmax normalization and [“attention sinks”](<https://arxiv.org/abs/2309.17453>), still allocate disproportionate weight to early tokens.

So: put your best chunks first. It costs nothing and hedges against position effects. Works regardless of which model you’re using.

## What Actually Happens After Retrieval

Most RAG tutorials show a clean diagram:

> Query → Retriever → LLM → Response

The arrow between Retriever and LLM hides an entire processing pipeline.

That arrow hides a lot:

> Your retriever returns candidates, typically the top 20–50 chunks ranked by embedding similarity. Those raw results have problems. Some chunks overlap, repeating the same information. Some contradict each other. Some matched on keywords but don’t actually answer your question. Feeding them directly to the LLM wastes tokens and introduces noise.
>
> The processing pipeline transforms those raw candidates into optimized context. It filters by relevance threshold. It removes near-duplicates. It reranks using models that understand query-document relationships better than embedding similarity alone. It handles contradictions. It expands promising chunks to include surrounding context. Then, finally, it assembles everything into a prompt structure the LLM can actually use.

Skip any of these steps and you’re leaving quality on the table.

_The hidden pipeline between retrieval and generation: 50 candidates narrow to 4–6 optimized chunks through filtering, reranking, and deduplication._

**Reranking** is where the biggest gains show up. Vector similarity is fast but shallow. It compares compressed representations of documents, sacrificing nuance for speed. Cross-encoder rerankers process your query and each document together through full transformer attention, capturing relationships that embeddings miss.

The pattern that works: retrieve broadly (top 50 candidates), rerank precisely (keep top 5). [Pinecone’s benchmarks](<https://www.pinecone.io/learn/series/rag/rerankers/>) show this two-stage approach improves retrieval quality by 14–30% over vector search alone. Production systems consistently show similar numbers.

Press enter or click to view image in full size

_Bi-encoders retrieve fast but shallow. Cross-encoders rerank slow but deep. Combining both gives you speed and precision._

For reranking models, [Cohere Rerank](<https://docs.cohere.com/docs/rerank>) handles most use cases well. It’s multilingual, which helps if your docs aren’t all in English. For self-hosted deployments, BAAI’s [bge-reranker-v2-m3](<https://huggingface.co/BAAI/bge-reranker-v2-m3>) offers comparable quality without API costs.

**Deduplication** solves a problem you might not notice until it costs you. Chunking strategies that use sliding windows create overlap. Retrieve five chunks and three might contain the same paragraph. That’s not just wasted tokens. Repetition can bias the model toward over-emphasizing repeated content.

Maximal Marginal Relevance (MMR) handles this well. The idea: each new chunk you add should be relevant, but also different from what you’ve already picked. No point including three chunks that say the same thing.

**Contradiction handling** is harder. When your retriever returns chunks that disagree, what should the model do? Systems often confidently cite the wrong source because it appeared first in the context.

For temporal contradictions, the fix is metadata. Include timestamps and filter older content when newer content covers the same ground. [LlamaIndex](<https://docs.llamaindex.ai/>) has an `EmbeddingRecencyPostprocessor` that does this automatically.

For authority conflicts, weight your sources. Official documentation should override user-generated content. Primary sources should beat summaries. Explicit metadata labeling lets you implement these preferences in your pipeline.

When legitimate ambiguity exists, the honest approach is presenting both perspectives with clear attribution. Forcing a false consensus produces confident-sounding responses that mislead users.

## The Token Budget Nobody Teaches You

Context windows have limits. You know this. Budgeting within those limits is the part nobody teaches.

A 128K context window sounds enormous until you account for everything competing for space. Your system prompt needs room. The user’s query takes tokens. You need to reserve capacity for the response itself. What’s left is your actual budget for retrieved context.

A reasonable allocation: 1,500 tokens for system prompt, 500 for user query, 4,000 reserved for output. On a 128K model, that leaves around 122,000 tokens for context. Plenty, right?

In theory, yes. In practice, more isn’t always better. Even with improved long-context models, there’s a point of diminishing returns where additional chunks add noise rather than signal. The model has to sift through more content to find what’s relevant.

_Token allocation reality: just because you can fill 128K doesn’t mean you should. Quality over quantity._

The sweet spot tends to be 4–6 chunks for most queries. Beyond that, each additional chunk competes for relevance with chunks already included. Unless the new chunk contains genuinely unique information, it dilutes rather than enriches.

When you need more context than fits, compression beats truncation.

Microsoft’s [LongLLMLingua](<https://arxiv.org/pdf/2310.06839>) achieves 4x compression while improving accuracy by 21% on question-answering benchmarks. It scores token importance using perplexity and preserves query-relevant content while discarding filler. The compressed context contains less text but more signal.

The alternative, [RECOMP](<https://arxiv.org/pdf/2310.04408>), offers both extractive compression (selecting key sentences) and abstractive compression (generating summaries). Either approach beats naive truncation, which discards content based on position rather than importance.

Compression works best when dealing with long documents where the relevant information is scattered. For typical retrieval scenarios with well-chunked content, staying within 4–6 high-quality chunks works better than compressing larger sets.

## Prompt Architecture That Actually Works

How you structure the final prompt matters more than most tutorials acknowledge.

The basic architecture has two layers: a persistent system prompt that establishes rules, and a dynamic user prompt that injects query-time context. Mixing these layers causes inconsistency. Keep them separate.

Your system prompt should define:

* Role and persona (“You are a technical support assistant for…”)
* Grounding rules (“Answer only using the provided context. If the context doesn’t contain the answer, say so.”)
* Format specifications (“Cite sources using [1], [2] notation”)
* Refusal patterns (“Do not answer questions about competitor products”)

This prompt stays constant across queries. The rules apply universally.

Your user prompt should contain:

* Retrieved context, clearly delimited
* The actual user query
* Any query-specific instructions

The delimiter choice affects parsing accuracy. XML tags outperform markdown and plain text for Claude and models trained on structured data. I use `<context>`, `<document>`, and `<query>` as boundaries.

The source metadata enables citation. The page numbers let users verify. The clear structure helps the model parse content from instructions.

What metadata should you include? Source titles, yes. Timestamps for time-sensitive content, yes. Page numbers if you want citations, yes.

What should you exclude? Internal relevance scores, file system paths, encoding information, debug data. These consume tokens without helping generation. If the metadata doesn’t help the _model_ reason better, leave it out.

## The Failures That Don’t Show Up in Logs

Good retrieval metrics don’t guarantee good responses. Watch for failure modes that happen after retrieval succeeds.

**Citation hallucination** is sneaky. The response sounds authoritative, includes bracketed citations, and is completely wrong about which source said what. The facts might be correct. The attributions aren’t.

This happens because citation accuracy and factual accuracy are independent. The model can extract correct information from context while misremembering (if that word even applies to LLMs) which chunk it came from. Production systems need validation that traces specific claims to specific sources.

**Context poisoning** is what I call it when low-relevance chunks crowd out good ones. Your retriever returns ten chunks. Seven are so-so. Three are exactly what you need. Those seven dilute the signal, not through position, but through volume. The model tries to use everything instead of finding the best parts.

Tighter relevance thresholds help. So does capping your chunk count. If you’re unsure, go with fewer good chunks over more mediocre ones.

**Temporal staleness** shows up when your index lacks freshness signals. The retriever returns a policy document from 2022 because it matches the query terms perfectly. That policy got replaced in 2024. But your pipeline doesn’t know that.

Metadata-based filtering catches this, but only if you index timestamps and query with recency awareness. For fast-moving domains, consider freshness as a ranking factor alongside relevance.

**Reasoning fragmentation** kills multi-hop queries. The user asks a question that requires connecting facts from multiple chunks. Each chunk retrieves successfully. The model fails to synthesize them because they’re semantically distant in the prompt, lacking bridging context.

Hierarchical chunking helps here. LlamaIndex’s sentence window retrieval embeds individual sentences for precise retrieval but expands to surrounding paragraphs at query time. The bridging context comes along for free.

## What Actually Works

After building production RAG systems, these patterns hold up:

**Retrieval** : Hybrid search combining BM25 keyword matching with dense embeddings, merged via Reciprocal Rank Fusion. This catches queries that either approach alone would miss. [Anthropic’s research on Contextual Retrieval](<https://www.anthropic.com/news/contextual-retrieval>) showed hybrid approaches reduce retrieval failures by 67%.

**Reranking** : Cohere Rerank for cloud deployments, bge-reranker for self-hosted. Always rerank. The latency cost is worth it.

**Deduplication** : MMR with lambda around 0.6. You want relevance, but you also want variety.

**Chunk count** : 4–6 for most queries. Go higher only when you genuinely need to synthesize across multiple sources.

**Position strategy** : Best chunks go first. Supporting context fills the middle. Summary at the end if you have room. Use both ends of the prompt.

**Prompt structure** : XML tags for context delimitation. Source and timestamp metadata included. Internal pipeline data excluded.

**Evaluation** : Separate retrieval metrics (precision, recall) from generation metrics (faithfulness, groundedness). When responses fail, you need to know which component failed.

This isn’t the only valid approach. But it stops you from debugging the wrong layer.

## The Layer That Earns Its Keep

Most RAG discussions focus on retrieval. Makes sense. If you don’t retrieve the right chunks, nothing downstream can save you.

But retrieval is a solved problem compared to augmentation. Vector databases are mature. Embedding models are good and getting better. Reranking is becoming standard. The retrieval layer has clear best practices and measurable benchmarks.

The augmentation layer, the space between retrieval and generation, is younger and messier. Position effects, compression strategies, prompt architecture, failure modes that don’t show up in retrieval metrics. Systems that look identical on paper diverge here in production.

When your RAG system underperforms, resist the instinct to blame the retriever first. Check where you’re placing chunks in your prompt. Check whether you’re including too much context. Check whether your prompt structure helps or hinders the model’s ability to parse relevant information.

The retrieval might be fine. It’s what happens next that determines whether the model actually uses what you found.
