In the practical development of Retrieval-Augmented Generation (RAG), numerous detailed challenges often arise. While a demo can be created in just three days, optimizing its performance may require up to three months.

This article discusses three practical challenges encountered during the development of an RAG system and presents corresponding mitigation ideas, hoping to assist others in the field. The Three practical challenges are:

* File Incremental Updates for RAG and GraphRAG
* Numerical Reasoning
* Short Follow-Up Type Query

## File Incremental Updates for RAG and GraphRAG

This section is divided into five parts.

* The background of file incremental updates
* Solution
* Implementation method
* Discussion of file incremental updates in GraphRAG
* Personal thoughts and reflections

### Background

A common scenario involves storing users’ PDF files in the server’s `uploads` directory. A scheduled task then scans this directory to build a knowledge base from the PDF files found there.

Initially, we adopted a **file-level incremental update** strategy. This process involves generating a hash fingerprint for each file when scanning the directory and checking whether it already exists.

If the fingerprint does not exist, it signifies a new file. We will then perform pasring, chunking, and vectorizing for this file before incorporating it into the vector store.

Figure 1: When content is added to flo.pdf, if we adopt a file-level incremental update strategy, it will lead to redundant content in the vector store(bottom right). Image by author.

However, this method has a drawback. As shown in Figure 1, suppose we have already added the file `flo.pdf` to the vector store. If we later add minor content to this file, its new hash fingerprint will not match any of the existing fingerprints.

Consequently, we treat the updated file as a new file and redo the following steps. This results in unnecessary computational effort and duplicated content for the unchanged sections. During retrieval, if the duplicated chunk is recalled, it will squeeze out the space for other relevant information, thereby reducing the effectiveness of the RAG system.

### Solution

How can this problem be resolved?

For incremental updates, we should continue to rely on hash fingerprints for identification. However, hashing should no longer apply to entire files, but should focus on specific storage levels, such as individual chunks, nodes, or documents, depending on the terminology and storage structure.

If we focus on the chunk level, the main logic is shown below.

* By checking the hash value associated with each chunk, determine if the chunk’s storage needs to be updated.
* If the chunk does not exist, add it to the dictionary `deduped_chunks_to_upsert`.
* If the chunk exists but the chunk hash value does not match, remove the old chunk and its associated node from the vector store, then add the new chunk to the dictionary `deduped_chunks_to_upsert`.
* If the chunk exists and the chunk hash value matches, skip the update.
* Uniformly update the contents within the dictionary `deduped_chunks_to_upsert`.

### How to Implement

Both [Langchain](<https://python.langchain.com/docs/how_to/indexing/>) and [LlamaIndex](<https://docs.llamaindex.ai/en/stable/examples/ingestion/ingestion_gdrive/>) offer related functionalities. When implementing our own solution, we don’t have to fully adopt their code, but we can learn from their ideas.

First, we look at LangChain’s approach. It uses a `RecordManager` to track document writes into the vector store. During the indexing process, hashes are computed for each document, and the following information is stored in the `RecordManager`:

* The document hash (which includes both page content and metadata).
* The right time.
* The source ID, should be included in each document’s metadata to help determine the document’s source.

[The usage](<https://python.langchain.com/docs/how_to/indexing/>) is as follows.

```python from langchain.indexes import SQLRecordManager, index......res = index( [doc1], record_manager, vectorstore, cleanup="incremental", source_id_key="source",)print(res) ```

The code above executes specific tasks through the [index function](<https://github.com/langchain-ai/langchain/blob/e8e5d67a8d8839c96dc54552b5ff007b95992345/libs/core/langchain_core/indexing/api.py#L191>). The main idea is similar to before: filtering out duplicate objects that need to be inserted based on their hash values.

The [pipeline.run function](<https://github.com/run-llama/llama_index/blob/v0.11.15/llama-index-core/llama_index/core/ingestion/pipeline.py#L452>) is called the [_handle_upserts function](<https://github.com/run-llama/llama_index/blob/v0.11.15/llama-index-core/llama_index/core/ingestion/pipeline.py#L397>), which follows a logic similar to the one I described earlier.

```python def _handle_upserts( self, nodes: Sequence[BaseNode], store_doc_text: bool = True, ) -> Sequence[BaseNode]: """Handle docstore upserts by checking hashes and ids.""" assert self.docstore is not None doc_ids_from_nodes = set() deduped_nodes_to_run = {} for node in nodes: ref_doc_id = node.ref_doc_id if node.ref_doc_id else node.id_ doc_ids_from_nodes.add(ref_doc_id) existing_hash = self.docstore.get_document_hash(ref_doc_id) if not existing_hash: # document doesn't exist, so add it deduped_nodes_to_run[ref_doc_id] = node elif existing_hash and existing_hash != node.hash: self.docstore.delete_ref_doc(ref_doc_id, raise_error=False) if self.vector_store is not None: self.vector_store.delete(ref_doc_id) deduped_nodes_to_run[ref_doc_id] = node else: continue # document exists and is unchanged, so skip it if self.docstore_strategy == DocstoreStrategy.UPSERTS_AND_DELETE: # Identify missing docs and delete them from docstore and vector store existing_doc_ids_before = set( self.docstore.get_all_document_hashes().values() ) doc_ids_to_delete = existing_doc_ids_before - doc_ids_from_nodes for ref_doc_id in doc_ids_to_delete: self.docstore.delete_document(ref_doc_id) if self.vector_store is not None: self.vector_store.delete(ref_doc_id) nodes_to_run = list(deduped_nodes_to_run.values()) self.docstore.set_document_hashes({n.id_: n.hash for n in nodes_to_run}) self.docstore.add_documents(nodes_to_run, store_text=store_doc_text) return nodes_to_run ```

### Incremental Updates for GraphRAG

Recently, GraphRAG has become a popular improvement of the RAG method. However, [its incremental updates have not yet been implemented](<https://github.com/microsoft/graphrag/issues/741>).

The main reason lies in handling advanced data structures like communities and knowledge graphs, which is more complex than ordinary processes.

The third-party implementation [nano-GraphRAG](<https://github.com/gusye1234/nano-graphrag>) offers an incremental update feature. Its main process is in the [ainsert function](<https://github.com/gusye1234/nano-graphrag/blob/v0.0.8/nano_graphrag/graphrag.py#L251>). The core idea is to use the MD5 hash values of documents and chunks as keys. During insertion, only new chunks are added. Nano-GraphRAG automatically loads the previous graph from the working directory, and new entities and relationships are incorporated into the current graph.

```python async def ainsert(self, string_or_strings): await self._insert_start() try: if isinstance(string_or_strings, str): string_or_strings = [string_or_strings] # ---------- new docs new_docs = { compute_mdhash_id(c.strip(), prefix="doc-"): {"content": c.strip()} for c in string_or_strings } _add_doc_keys = await self.full_docs.filter_keys(list(new_docs.keys())) new_docs = {k: v for k, v in new_docs.items() if k in _add_doc_keys} if not len(new_docs): logger.warning(f"All docs are already in the storage") return logger.info(f"[New Docs] inserting {len(new_docs)} docs") # ---------- chunking inserting_chunks = get_chunks( new_docs=new_docs, chunk_func=self.chunk_func, overlap_token_size=self.chunk_overlap_token_size, max_token_size=self.chunk_token_size, ) _add_chunk_keys = await self.text_chunks.filter_keys( list(inserting_chunks.keys()) ) inserting_chunks = { k: v for k, v in inserting_chunks.items() if k in _add_chunk_keys } if not len(inserting_chunks): logger.warning(f"All chunks are already in the storage") return logger.info(f"[New Chunks] inserting {len(inserting_chunks)} chunks") if self.enable_naive_rag: logger.info("Insert chunks for naive RAG") await self.chunks_vdb.upsert(inserting_chunks) # TODO: no incremental update for communities now, so just drop all await self.community_reports.drop() # ---------- extract/summary entity and upsert to graph logger.info("[Entity Extraction]...") maybe_new_kg = await self.entity_extraction_func( inserting_chunks, knwoledge_graph_inst=self.chunk_entity_relation_graph, entity_vdb=self.entities_vdb, global_config=asdict(self), ) if maybe_new_kg is None: logger.warning("No new entities found") return self.chunk_entity_relation_graph = maybe_new_kg # ---------- update clusterings of graph logger.info("[Community Report]...") await self.chunk_entity_relation_graph.clustering( self.graph_cluster_algorithm ) await generate_community_report( self.community_reports, self.chunk_entity_relation_graph, asdict(self) ) # ---------- commit upsertings and indexing await self.full_docs.upsert(new_docs) await self.text_chunks.upsert(inserting_chunks) finally: await self._insert_done() ```

However, with each insertion, nano-GraphRAG still recalculates the communities and generates a new community report. Incremental updates for communities have not yet been implemented.

### Other Ideas

I have thought of several other ideas, which I will share for your reference.

* **Semantic Strategy** : By using NLP techniques (such as semantic embeddings, BERT, etc.), semantic changes in document chunks can be detected, rather than relying solely on changes in the text. If the semantics of a chunk differ significantly from the previous version, an update is triggered. Otherwise, even if there are minor textual modifications, reindexing the chunk is unnecessary.
* **Chunk-level updates combined with knowledge graphs** : In certain fields like medicine and law,, chunks can be mapped to entities or relationships in a knowledge graph. When a chunk in a document changes, the relationships in the knowledge graph can intelligently identify related chunks, enabling joint updates of those related chunks. By leveraging knowledge graphs, updates are not limited to chunks with textual changes, but can also be triggered based on semantic and relational changes, making this approach suitable for complex documents and scenarios with deep semantic connections.

Additionally, the timing of updates is also crucial. In most real-world applications, it may be necessary to combine multiple strategies. For example, use real-time stream processing and message queues for “hot data,” such as news reports, that is frequently accessed and updated while using batch updates and delayed processing for “cold data,” such as academic papers, that is less frequently accessed. By separating hot and cold data and applying a hybrid update strategy, we can maintain high system performance while ensuring timely and accurate updates.

## Numerical Reasoning

In actual development, users frequently ask questions like: ‘What is the population growth rate for City A in 2022?’

For queries like this, the potential retrieval chunks and tables are as follows:

``` batch_retrieval_results:["City A had a steady population increase over the past decade.", "The estimated population in 2021 was 1.2 million."]batch_tables:["Year | Population", "2021 | 1,200,000", "2022 | 1,230,000"] ```

Previously, I directly input the query and retrieval results into the LLM, but the results were unsatisfactory. This is because LLMs have limitations in numerical computations, it is challenging for them to directly obtain an answer based on retrieval results alone, some calculations are necessary.

Recently, I recently read [a paper](<https://arxiv.org/pdf/2408.05141v3>) presenting a novel idea that I tested and found quite effective.

This method introduces a Numerical Calculator to address these weaknesses. Employing Python-based computations, this external tool efficiently extracts and computes values directly from tables and textual data. It ensures accuracy in arithmetic operations and prevents the production of incorrect values.

I analyzed [the core code of this method](<https://gitlab.aicrowd.com/shizueyy/crag-new/-/blob/main/models/rag_llama_batch_with_calculator.py?ref_type=heads#L382>) and produced the following flowchart.

Figure 3: The core process of Numerical Calculator. Image by author.

For example, based on previous retrieval results, we can use the following formatted prompt to obtain a Python expression.

``` # References- City A had a steady population increase over the past decade.- The estimated population in 2021 was 1.2 million.------## Table references### Table 1:Year | Population2021 | 1,200,0002022 | 1,230,000------**Remember your rules**:1. The expression **MUST** be a valid Python expression.2. The expression **MUST** be useful to answer the question.3. If you think no expression is needed, you **MUST** answer with empty string.4. The output should be succinct, you **MUST** do reasoning in your heart without outputing the reasoning.5. You **MUST NOT** output any other words except the valid Python expression.6. You **MUST NOT** output the expression that need the user to input anything.Question: What is the population growth rate for City A in 2022?Using the references listed above and based on the question, generate a valid Python expression for me: ```

For instance, the generated expression might calculate the population growth rate from 2021 to 2022, as follows:

``` (1230000 - 1200000) / 1200000 * 100 ```

With this Python expression, numerical reasoning for this query is no longer a problem.

## Short Follow-Up Type Query

As is widely known, the shorter the user’s query, the more difficult it is to process.

In actual development, we often encounter scenarios like the following: for example, a user might first ask, “How many times has Brazil won the World Cup?” and then immediately follow up with, “What about France?”, as shown in Figure 4.

Figure 4: A common scenario of Short Follow-Up Type Query. Screenshot by author.

The last query, ‘What about France?’ is vague. Using this query directly to retrieval could lead to irrelevant results. We need to rewrite this query to reflect what the user is actually asking.

The final question should be rewritten to reflect a more specific inquiry, similar to: ‘How many times has France won the World Cup?’ This rephrasing makes the new query meaningful and precise.
