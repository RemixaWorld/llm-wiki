And as models get bigger, training and inferring them becomes more and more expensive; both in terms of time and money. So, if we can make the attention mechanism faster and more efficient, we can train and infer larger models in less time and with less money and can even train models that were previously infeasible to train.

## 2\. Attention Briefly Explained

The attention mechanism is a key component of the Transformer architecture introduced by Vaswani et al. in “Attention is All You Need” (2017). On a high level, attention allows the model to dynamically focus on different parts of the input sequence while ignoring others when processing a certain token. A token is a single element in the input sequence, which can be a word, a patch of pixels, or even a node in a graph.

For each token in the input sequence an attention score is computed with respect to all other tokens in the sequence.

Originally, attention was introduced to process sequences of text, but it has since been applied to a wide range of tasks and data modalities, such as images, videos, and graphs, becoming a general-purpose mechanism for capturing dependencies between elements in a sequence.

To gain some intuition, let’s have a look on the following example:

Very simplified, I like to imagine attention as a mechanism to ask questions to the data, and the attention score as the answer to that question. The higher the attention score, the more important the information is for the current token. Multi-head attention (MHA) is then basically asking multiple questions at the same time for the same token, and then combining the answers. More on this later.

Equipped with this intuition, let’s have a look a look at the Transformer encoder architecture and the attention mechanism in more detail.

The encoder of a transformer consists of a stack of various identical stages. Each stage consists of two substages: a multi-head self-attention (MHA) and multi-layer perceptron (MLP).

The MHA substage implements multiple parallel attention heads which are then concatenated and linearly transformed to the expected hidden dimension.

The key takeaway here is that the attention mechanism materializes _NxN_ matrices in intermediate results, while the output we are interested in is only of shape _Nxd_ , where _N_ is the sequence length and _d_ the hidden dimension. This is the reason for the prominent claim of the Transformer’s quadratic work and memory complexity of _O(N²)_ with respect to the sequence length _N_. And while this example mentions typical values for _N=4,096_ (back at that time), the paper scales it up to _N=65,536_ , which would result in intermediate results of 4.29 billion values!

## 3\. Modern GPUs and CUDA Device Architecture

### 3.1. GPU Architecture

Let’s start by comparing the architecture of a CPU and a GPU. A CPU consists of a few cores optimized for sequential processing. In contrast, a GPU has a massively parallel architecture consisting of thousands of smaller, more efficient cores designed for handling multiple tasks simultaneously. Both CPUs and GPUs have a hierarchy of memories with varying sizes and speeds. This is very crucial for later when talking about how flash attention achieves its massive speedup.

Press enter or click to view image in full size

Figure 6: Comparison between CPU and GPU architecture. Image by

[Sascha Kirch](<https://medium.com/u/5c38dace9d5e?source=post_page---user_mention--5a9f2407d739--------------------------------------->)

.

> This general-purpose GPU architecture together with the CUDA programming language were introduced by Nvidia’s Tesla architecture in 2006, and many of its core concepts are still present in modern GPUs. I highly recommend checking out the [Whitepaper about the Tesla architecture](<https://www.cs.cmu.edu/afs/cs/academic/class/15869-f11/www/readings/lindholm08_tesla.pdf>) by Nvidia.

The GPU architecture is built around the Streaming Multiprocessor (SM), which consists of multiple CUDA and Tensor cores, shared memory and registers. Each SM can execute multiple blocks of threads in parallel. Threads within a block can communicate with each other using shared memory, while threads in different blocks cannot.

A little spoiler what this allows us to do: We have now so many threads, in fact thousands of them, that we can parallelize heavy computations like matrix multiplications and convolutions, by assigning each thread to a small part of the computation over a small chunk of data.

### 3.2. CUDA Programming Model

Nvidia GPUs are programmed using the CUDA programming model, an extension of the C++ programming language. It allows developers to write CUDA kernels, which are small functions that are executed by each of the threads. These threads are organized in blocks, which are then organized in a grid.

Press enter or click to view image in full size

Figure 7: CUDA Thread hierarchy. Image by

[Sascha Kirch](<https://medium.com/u/5c38dace9d5e?source=post_page---user_mention--5a9f2407d739--------------------------------------->)

.

This thread hierarchy is a neat feature of CUDA, because is mimics the shape of the data we are working with, i.e. vectors, matrices and tensors. Furthermore, each thread knows its position in the grid and block, which allows us to calculate the position in the data structure we are working with.

We can also map the CUDA Programming Model to the GPU architecture, to see at which level of the hierarchy the data is stored and how it is accessed by the threads.

Figure 8: CUDA Programming model vs. GPU architecture. Image by

[Sascha Kirch](<https://medium.com/u/5c38dace9d5e?source=post_page---user_mention--5a9f2407d739--------------------------------------->)

.

To be able to introduce the concept of kernel fusion in FlashAttention, we need to understand how the CPU interacts with the GPU, and how the data is flowing. Let’s start with the heterogeneous programming model, which simply means we use different devices to execute our code, i.e. CPU and GPU.

Press enter or click to view image in full size

Figure 9: Heterogeneous programming model using CPU and GPU. Image by

[Sascha Kirch](<https://medium.com/u/5c38dace9d5e?source=post_page---user_mention--5a9f2407d739--------------------------------------->)

.

The CPU performs serial code execution and is responsible for transferring data between host and device, and to launch the kernels. The GPU on the other hand executes these kernels in parallel by launching multiple threads inside a grid of thread blocks on the device. The results are read back to the CPU, which then continues its serial processing and eventually starts another kernel. The key takeaway here is that in a naive implementation, each kernel requires transferring data to and from the device. And to put it into the context of our attention mechanism, these sequentially executed kernels could be the matrix multiplication, scaling, masking, SoftMax and dropout.

Zooming in on the data flow of a single kernel execution, we can see how the data is flowing between the CPU and the GPU, and how the cores (threads) are accessing the data in the GPU Memory (global memory).

.

Puh, that was a lot of information. So let’s look into an example to make it more clear. The most prominent example is matrix multiplication, which is a key operation in deep learning.

### 3.3. Matrix Multiplication in CUDA

As you surely know, to multiply two matrices _A_ and _B_ , we take the dot product of each row of matrix _A_ with each column of matrix _B_. In a naive (and extremely inefficient) implementation we could replicate this algorithm in CUDA by assigning each thread with the task to calculate one element of the resulting matrix _C_.

Press enter or click to view image in full size

Figure 11: Matrix Multiplication. Image by

[Sascha Kirch](<https://medium.com/u/5c38dace9d5e?source=post_page---user_mention--5a9f2407d739--------------------------------------->)

inspired by [Simon Boehm](<https://siboehm.com/articles/22/CUDA-MMM>).

Note how computing an entire row of the resulting matrix _C_ requires a single row of matrix _A_ and all columns of matrix _B_.

Again, we must take a little detour to how a kernel is executed and on different bandwidths of memory. Every time we launch a kernel, the thread block grid is constructed, the kernel is loaded into the cores, and the data is loaded from the global memory into the registers of the processors. The kernel is then executed, and the result is stored back in the global memory. Generally speaking, the larger the memory, the farther away it is from the processor, and the slower it is. So, the global memory is the largest but slowest memory in the hierarchy, and the registers of the individual cores are the smallest but fastest memory in the hierarchy.

To give you an idea (because 1.5 TB/s of an A100 doesn’t sound too bad after all), let’s see what the absolute minimum of numbers is we need to load to multiply two matrices of size _NxN_ , with _N=4096_. We assume values are in float32 format, which means each element is 4 bytes.

* We need to read _4096x4096_ elements from matrix _A_ and _4096x4096_ elements from matrix _B_ : _2x4096x4096x4 bytes = 134MB_.
* we need to store _4096x4096_ elements in matrix _C_ : _4096x4096x4 bytes = 64MB_.

If we now follow the naive implementation of matrix multiplication, we are actually loading the entire matrix _B_ for each row of matrix _A_. This means we are loading _4096x4096_ elements _4096_ times, which is _134MB x 4096 = 549GB_ , which is quite some traffic 😅. And that’s only for our small context window of _N=4096_ tokens…

**❓So, knowing all this, what are the tricks to make computations on a GPU faster and more efficient?**

### 3.4. Optimizations for Kernel Execution

As you have probably guessed, our main concern is to reduce the number of reads and writes to the global memory, because it is the slowest memory in the hierarchy and our cores are often waiting for data to be loaded.

There are several techniques to achieve this including:

* **Shared memory** — Keeping frequently used data close to the core.
* **Block Tiling** — Re-using data that has already been loaded to compute multiple outputs.
* **Kernel fusion** — Avoid writing and reading intermediate results.

> Note that we will cut some corners here to keep it simple while building the foundation we need to understand the contribution of FlashAttention. If you are interested in a more detailed explanation of matrix multiplication in CUDA and which optimizations can be applied, I recommend reading [this amazing and illustrative blog post](<https://siboehm.com/articles/22/CUDA-MMM>) by Simon Boehm.

But for now, let’s talk about the beforementioned optimizations, and how they can be applied to matrix multiplication.

**Shared Memory**

> Keeping frequently used data close to the core.

The first thing we do is to exploit the different memory levels in the hierarchy. Shared memory is a small, fast memory that is shared between threads in a block (Across all cores within a single Streaming Multiprocessor). As stated in the FlashAttention Paper for the A100 GPU the bandwidth of the global memory (40GB) is 1.5TB/s while for shared memory (20MB) it is 19TB/s.

We know that threads in a block can communicate with each other using shared memory and that blocks can be executed in parallel on different Streaming Multiprocessors.

Press enter or click to view image in full size

Figure 12: Usage of shared memory in matrix multiplication. Image by

[Sascha Kirch](<https://medium.com/u/5c38dace9d5e?source=post_page---user_mention--5a9f2407d739--------------------------------------->)

inspired by [Simon Boehm](<https://siboehm.com/articles/22/CUDA-MMM>).

So, for each block we process, we load the data from the global memory into the shared memory, and then the threads in the block can access the data from the shared memory. When processing the next block, we repeat this process.

**Block Tiling**

> Re-using data that has already been loaded to compute multiple outputs.

The next thing we do is to compute more than one element of the resulting matrix _C_ in a single thread. This is called tiling, and it is a common technique to reduce the number of reads and writes to the global memory. The basic idea is to re-use data in a thread that has already been loaded into registers from the shared memory for multiple computations.

Press enter or click to view image in full size

Figure 13: Block tiling in matrix multiplication. Image by

[Sascha Kirch](<https://medium.com/u/5c38dace9d5e?source=post_page---user_mention--5a9f2407d739--------------------------------------->)

inspired by [Simon Boehm](<https://siboehm.com/articles/22/CUDA-MMM>).

To be clear, we are still performing the same number of computations, we are simply reading less data from memory re-using what we have already loaded. This means we spent less time waiting for data but more time on computing. We improved what is called the _Arithmetic Intensity,_ which is the ratio of the number of operations to the number of memory accesses.

**Kernel Fusion**

> Avoid writing and reading intermediate results.

Finally, we can fuse multiple kernels into a single kernel to avoid writing intermediate results into global memory, just to read them again in the next kernel.

Press enter or click to view image in full size

Figure 14: How kernel fusion influences wall time and memory consumption. Image by

[Sascha Kirch](<https://medium.com/u/5c38dace9d5e?source=post_page---user_mention--5a9f2407d739--------------------------------------->)

.

Important side note: Kernels can only be fused if they operate on the same block-tile of data. This is important to keep in mind when we talk about the attention mechanism later.

## 4\. Attention on Modern GPUs

### 4.1. Why Attention is so Slow and Resource Intensive

As you might have guessed by now, we write and read too much data to and from the global memory.

Let’s have another look on the attention mechanism and the shapes of the matrices involved, but this time through the lens of the GPU architecture and CUDA programming model.

Press enter or click to view image in full size

Figure 15: Reads and writes for each kernel of the attention layer. Image by

[Sascha Kirch](<https://medium.com/u/5c38dace9d5e?source=post_page---user_mention--5a9f2407d739--------------------------------------->)

.

There are several observations we can make here:

1. We have 3 input matrices (_Q_ , _K_ and _V_), each of size _Nxd_ , and one output matrix _O_ of size _Nxd_.
2. The attention mechanism materializes huge _NxN_ matrices in intermediate results that all need to be stored and then read again when executing the next kernel.
3. Some operations like matrix multiplication and SoftMax, reuse the same data of their respective inputs for a single element in the output.
4. Other operations such as Dropout and masking are applied element-wise.

As you can see there are a lot of those expensive reads and writes from and to global memory, and the worst part is that we are not even interested in them since those are intermediate results.

So, let’s see how we can apply the beforementioned optimizations to the attention mechanism. Or better, let’s see why we can’t apply them (before diving into FlashAttention to see how they did it).

### 4.2. How Could We Improve the Attention Mechanism?

The big issue with the attention mechanism is that we have to materialize _NxN_ matrices in intermediate results, which we then have to write and read from the global memory. So why not simply fusing the involved kernels together to avoid writing and reading intermediate results?

This is a great idea, but there are two problems with it:

1. Not all those kernels operate on the same block-tile of data, which is required for kernel fusion as mentioned earlier.
2. We need the intermediate results in the backward pass to calculate the gradients.

Slowing down a bit, let’s have a look at the first problem. How is the SoftMax function even implemented applied in practice? Let’s have a look on our _NxN_ matrices

Press enter or click to view image in full size

Figure 16: How the SoftMax is computed in the attention mechanism. Image by

[Sascha Kirch](<https://medium.com/u/5c38dace9d5e?source=post_page---user_mention--5a9f2407d739--------------------------------------->)

.

First, note how the SoftMax is applied per row and not on the entire matrix! Second, and more importantly, to compute a single element of the SoftMax matrix _P_ , we need to read all elements of the corresponding row of the input matrix _S_.

Now, recall that the matrix multiplication kernel applies block tiling and a sliding window to load inputs into shared memory to compute partial sums. This is not compatible with the SoftMax function, because we need all elements of the row to compute a single element in the output.

> What is the intuition behind applying the SoftMax function per row? Each row of those NxN is concerned with a single token in the input sequence. Computing the SoftMax per row, results in a score that represent how much each of the other tokens in the sequence “attend” to the current token. In other words, how important is the other token for the current token to solve the task at hand.

Let’s assume for a second, that we could apply the SoftMax function on the same block-tile of data as the matrix multiplication kernel. This would allow us to fuse the kernels together and avoid writing and reading intermediate results. But we still have the second problem: We need the intermediate results in the backward pass to calculate the gradients.

To train our models, we usually feed them with a batch of data, calculate the loss with respect to some target, and then apply backpropagation to update the parameters of our model, so the next time we feed it with data, it performs better (hopefully). Applying the chain rule, we can compute the gradients for each of the individual operations in the model. Let’s extract a single simplified attention mechanism from the entire model:

So, we need to keep the intermediate results in memory, which means we have to write them to the global memory and read them again in the backward pass. Exactly what we wanted to avoid in the first place. So, we are back to square one…
