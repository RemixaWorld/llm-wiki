Retrieval-Augmented Generation (RAG) is a well-known technique for adding large amounts of external knowledge to an LLM. If the external knowledge that you want to include is limited in size and does not change much, **Cache-Augmented Generation (CAG)** or **Context Caching** might be of interest to you.

In this article, we will implement a local chatbot in Python that uses an `llms.txt` file to efficiently answer questions.

## RAG vs. CAG

In RAG, documents are chunked into smaller pieces, transformed into vector embeddings, and stored in a vector database. When a user asks a question, the vector database is searched for matches, which are then appended to the user’s question in the form of context. The LLM can then use the provided context to better answer the question.

![An overview of the RAG pipeline. For documents storage: input documents -> text chunks -> encoder model -> vector database. For LLM prompting: User question -> encoder model -> vector database -> top-k relevant chunks -> generator LLM model. The LLM then answers the question with the retrieved context.](https://miro.medium.com/v2/resize:fit:700/0*lmVzNAOAdCC0JKWM.jpeg)

RAG is very useful when we have a lot of data and if the data is expected to change over time.

However, if the similarity search fails and no matches or odd matches are retrieved, the LLM has no chance. _Garbage in, garbage out._

Another drawback is that we have to perform the database search every time a user asks a question, and the LLM has to process the context again each time. If we only have a few documents, this seems very inefficient.

With the advent of long context LLMs with 128K and more tokens, a new paradigm called CAG is now trending. The figure below shows the conceptual difference between RAG and CAG.

![RAG vs. CAG: RAG has to process the knowledge source during inference. CAG uses offline preloading instead.](https://miro.medium.com/v2/resize:fit:660/1*I4X-yhZli26oRcxiy6QN8g.png)

If we have limited input data (the knowledge source) and the data is not expected to change much, we can just preprocess the data once and store it on disk. We can then use this cached knowledge and add it to the context of the LLM every time a user asks a question.

Because Transformer-based LLMs rely on self-attention at their core, which is computed using Queries `Q`, Keys `K`, and Values `V` matrices, this cache is often referred to as **KV** **cache**.

![The attention math formula is based on the matrices Q, K, and V.](https://miro.medium.com/v2/resize:fit:551/1*PfKfbOKI4rS0YaRYXfSXdw.png)

## Context Caching

Instead of implementing the offline KV caching of the knowledge source yourself, it is easier to use so-called context caching or prompt caching. LLM providers such as Google, DeepSeek, and OpenAI already use context caching to save costs.

In context caching, the LLM framework automatically stores the KV cache from previous queries. The stored KV cache is automatically used when it matches the new query.

To use context caching with locally deployed open-source LLMs, we can use vLLM’s **Automatic Prefix Caching (APC)** feature. In vLLM, the KV cache consists of blocks of tokens. A single block can be cached, or multiple blocks can be cached together as a “prefix” [4].

![Context caching with vLLM’s KV-blocks [4]](https://miro.medium.com/v2/resize:fit:700/1*ds-WkVOkZnvLh-M1tYRN0w.png)

### When to Use CAG / Context Caching?

Context caching reduces the cost of repetitive queries that contain repetitive content with high token usage.

You should consider using CAG / context caching for use cases such as:

* Chatbots with extensive system prompts
* Repeated queries with large documents as context
* Multiple queries with large images or videos as context
* Coding LLMs that use a large codebase as context
* Multi-round conversations with an LLM with a long chat history

## Providing an AI-friendly Knowledge Source

The idea of caching is to efficiently provide our LLM with a fixed knowledge source that contains all the information that our chatbot needs.

In its simplest form, the knowledge source is just a very long string that we can save as a text file. However, I suggest that we use a file called`llms.txt`.

The /llms.txt file is a proposal by Jeremy Howard to help LLMs use a web page at inference time [5].

The idea is that search engines and LLMs with Internet access will be able to use the human- and LLM-readable `llms.txt` file, which contains all the necessary information in a concise, clear language.

Here is my example `llms.txt` file for a sample restaurant website called Bob’s Burger, that wants to implement a chatbot for their website.

``` # Bob's Burger> The best burgers in town## FAQQuestion: Who are you?I am a chatbot from Bob’s BurgerQuestion: Do you have vegetarian options?Yes, we have a veggie burgerQuestion: When are you open?We are open Tuesday through Saturday from 8am to 11pm.## ContactEmail: burger@mail.comPhone: +123456789## Menu| Item | Price || -------------- | ----------- || Cheeseburger | 10 || Veggie Burger | 8 |## Drinks| Item | Price || -------------- | ----------- || Iced Tea | 4 || Coke | 3 | ```

This file must contain all the information the LLM should know. The FAQ section acts as a training example for in-context learning. Here we can “train” our chatbot to give the answers we want.

## Running an LLM Locally With CAG / Context Caching

First, we need to install vLLM with `pip install vllm~=0.8.2`.

To start the OpenAI-compatible API server, we can simply use the `vllm serve `command:

``` vllm serve google/gemma-3-1b-it --api-key token-abc123 --enable-prefix-caching ```

Alternatively, we can also use Docker with the `vllm-openai` image:

``` docker run --runtime nvidia --gpus all \ -v ~/.cache/huggingface:/root/.cache/huggingface \ --env "HUGGING_FACE_HUB_TOKEN=<secret>" \ -p 8000:8000 \ --ipc=host \ vllm/vllm-openai:latest \ --model google/gemma-3-1b-it \ --api-key token-abc123 \ --enable-prefix-caching ```

This will start a **vLLM server** with the configured API key and **with context caching (APC) enabled**. All API calls will then try to use the available context cache.

If you want to use gated models from Hugging Face, you need to create a user access token in your HF account. One way to provide the credentials to your shell is to issue the command `huggingface-cli login` and then paste in your token. Another is to set the environment variable `HUGGING_FACE_HUB_TOKEN=<secret>`.

## Implementing the Chatbot User Interface With Streamlit

I use `streamlit` for the frontend user interface, `pymupdf4llm`to process files, and `openai` to talk to the LLM model.

Let’s install these three dependencies first:

```python pip install streamlit~=1.44.0 pymupdf4llm~=0.0.19 openai~=1.69.0 ```

We start our application with the necessary package imports, the title of our application and we define the OpenAI client.

```python import htmlimport osimport pymupdf4llmimport streamlit as stfrom openai import OpenAI# Constant for default valuesDEFAULT_MAX_TOKENS = 512DEFAULT_TEMPERATURE = 0.1st.title("LLM Chatbot CAG Assistant")@st.cache_resourcedef init_client() -> OpenAI: """Initialize the OpenAI client""" return OpenAI( base_url="http://localhost:8000/v1", api_key="token-abc123", )client = init_client() ```

In the Streamlit app, we will use `st.file_uploader()` to dynamically upload input data. For this, we need a helper function to save a file to disk:

```python def save_file(uploaded_file) -> str: """Save uploaded file (UploadedFile) to the 'files' directory.""" files_dir = os.path.join(os.path.dirname(__file__), "..", "files") os.makedirs(files_dir, exist_ok=True) # Create the directory if it doesn't exist file_path = os.path.join(files_dir, uploaded_file.name) with open(file_path, "wb") as f: f.write(uploaded_file.getbuffer()) return file_path ```

Using the `save_file` helper function, we write a function that takes an uploaded file (for example PDF, TXT, or Markdown) and uses `pymupdf4llm` to convert it to the AI-friendly Markdown format.

```python def process_uploaded_file(uploaded_file) -> str | None: """Process the uploaded file and extract context.""" try: file_path = save_file(uploaded_file) markdown = pymupdf4llm.to_markdown(file_path) return html.escape(markdown) # Escape HTML to prevent injection except Exception as e: st.error(f"Error processing file: {e}") return None ```

Now we can build the LLM input prompt given a user question `question` and the resulting `context` from a processed file:

```python def build_prompt(question: str, context: str | None) -> str: """Construct the prompt for the chatbot.""" if context: return ( "Answer the following question using the context provided from an internal, " "confidential document. Do not repeat anything from the context. " "Do not provide harmful or illegal advice.

" f"Context: {context}

" f"Question: {question}" ) else: return f"Answer the following question: {question}" ```

We will store chat messages from the user and the LLM in the `st.session_state.messages` variable. The `get_chat_messages` function returns a list with the system message, the last user message with the LLM’s response, and the current user message. This is the input for the LLM API call in `get_response`:

```python MODEL = "google/gemma-3-1b-it"def get_chat_messages(prompt: str, context: str) -> list[dict]: """Prepare the chat messages for the API call.""" recent_messages = st.session_state.messages[-3:-1] system_message = { "role": "system", "content": "You are a helpful and friendly assistant.", } user_message = {"role": "user", "content": build_prompt(prompt, context)} return [system_message] + recent_messages + [user_message]def get_response(messages: list[dict], temperature: float, max_tokens: int) -> str: """Call the OpenAI API to get a response.""" try: completion = client.chat.completions.create( model=MODEL, messages=messages, temperature=temperature, max_completion_tokens=max_tokens, ) return completion.choices[0].message.content except Exception as e: st.error(f"Error fetching response: {e}") return "I'm sorry, I couldn't process your request." ```

With all these functions, we can finally write the Streamlit frontend. On the side, we define a sidebar with `st.sidebar` where we put variable parameters and the file uploader. In the middle of the frontend, we have the chat interface. All messages are stored in `st.session_state.messages` and the user enters his questions in `st.chat_input`:

```json # Constants for default valuesDEFAULT_MAX_TOKENS = 512DEFAULT_TEMPERATURE = 0.1with st.sidebar: max_completion_tokens = st.number_input( "max_completion_tokens", 128, 8192, DEFAULT_MAX_TOKENS ) temperature = st.number_input("temperature", 0.0, 2.0, DEFAULT_TEMPERATURE) uploaded_file = st.file_uploader( "Upload file for context", type=["pdf", "txt", "md", "markdown"], accept_multiple_files=False, ) doc_context = process_uploaded_file(uploaded_file) if uploaded_file else None# Initialize chat historyif "messages" not in st.session_state: st.session_state.messages = []# Display chat messages from history on app rerunfor message in st.session_state.messages: with st.chat_message(message["role"]): st.markdown(message["content"])# Accept user inputif prompt := st.chat_input("Ask me anything!"): prompt = prompt.strip() # Add user message to chat history st.session_state.messages.append({"role": "user", "content": prompt}) # Display user message in chat message container with st.chat_message("user"): st.markdown(prompt) # Get assistant response with st.chat_message("assistant"): messages = get_chat_messages(prompt, doc_context) answer = get_response(messages, temperature, max_completion_tokens) st.markdown(answer) # Add assistant response to chat history st.session_state.messages.append({"role": "assistant", "content": answer}) ```

With this app, we can upload a file and the chatbot will use it to answer any questions.

## Conclusion

If your use case involves repetitive queries with a limited and mostly unchanging knowledge source, Cache-Augmented Generation (CAG) / Context Caching might be for you.

Instead of using a sophisticated RAG system, we can simply add the knowledge source in the form of a very long string to the LLM’s context. To make this more efficient by avoiding repetitive computations, the KV cache can be stored and reused in subsequent queries.

For this purpose, I used vLLM to deploy a local LLM with automatic context caching (a feature called APC).
