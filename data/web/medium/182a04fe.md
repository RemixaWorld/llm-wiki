A critical term that often appears in generative AI and LLM discussions, especially when the topic of optimization comes up, is **‘Semantic Caching’**. Despite the existence of open frameworks like GPT Cache, LangChain, etc., this concept requires attention. For developers working with Language Models, latency and cost present significant challenges. High latency can harm the user experience, while rising costs can impede scalability.

Consider the following scenario: A GenAI application that you have developed gains substantial traction, processing numerous API calls daily. You notice that users often pose similar queries — queries that have been addressed before. However, each interaction with the LLM incurs costs for redundant tokens, leading to a suboptimal user experience.

This is where the utility of Semantic Cache becomes clear. It allows for a cached response for repetitive semantically-similar queries, eliminating the need to resort to your AI provider. This results in cost savings and latency reduction.

Semantic caching offers several key benefits for LLMs.

1. By storing precomputed semantic representations, query resolution is sped up, resulting in faster response times and more efficient resource use. For example, for our document question-answering RAG pipeline (covered later in the post), retrieval time without caching is approximately `6504 ms`. With semantic caching, this is reduced to about `1919 ms`(a `3.4x`gain). For exact match queries, the improvement is even more substantial, with retrieval time reduced to `53 ms`(a `123x`gain). These numbers are based on the experimentation we will be setting up later in this blog post. We will dive into this in greater detail later, exploring the implementation and benefits of semantic caching in question-answering systems.
2. A significant advantage of reducing computational demands is the consequent decrease in operational costs. This is particularly relevant in the context of completion APIs such as `Gemini 1.0 Pro`, which typically calculate charges based on both input and output characters. Such a cost structure can be burdensome for applications with high usage. As a contrast, `text-embedding`APIs from Vertex AI present a markedly lower cost structure. As of `June 2024`, the charges for the text embedding API amount to `$0.000375`per `1,000`characters for text output. In comparison, completion APIs are notably more expensive. Specifically, `Gemini 1.0 Pro`charges `$0.000125`per `1,000`characters for text input and an additional `$0.000375`per `1,000`characters for text output, amounting to a combined cost of `$0.0005`per `1,000`characters. It is important to note that these figures exclude the costs associated with indexing the embeddings and conducting the semantic match using GCP services like Vertex AI Vector Search and Memorystore. However, these expenses are expected to diminish with economies of scale, when contrasted with the primary cost component, which is the cost of embedding text.
3. Furthermore, semantic caching increases throughput**** by effectively managing larger query volumes, thereby preventing performance bottlenecks under high loads. Rate limits, imposed by managed LLM services to regulate resource consumption, can pose challenges for high-throughput applications. Embedding APIs, however, generally offer substantially higher rate limits than their completion counterparts. As of `June 2024`, the text-embedding API from Vertex AI allows for `1,500`requests per minute (RPM), a stark contrast to the `360`RPM limit of Gemini Pro 1.0, illustrating the greater scalability afforded by embedding APIs.

This combination of benefits makes semantic caching an essential optimization strategy for scaling and improving the efficiency of LLM applications or pipelines.

## The Evolution of Caching - Transitioning from Standard to Semantic

Caching is a key technique that enhances an LLM or any application’s speed and computational efficiency. Traditional caching methods store and quickly retrieve pre-generated responses for repeated queries for LLM generative AI, significantly reducing computational load and response time. However, in the ever-changing realm of human language, exact query matches are rare. This is where semantic caching comes into play.

Semantic caching works by interpreting and leveraging the underlying semantics of queries. It identifies and fetches cached responses that semantically relate to the input query, thereby increasing the chances of cache hits and improving response times and resource utilization. This approach is particularly beneficial in scenarios where users phrase similar queries differently, for example, let’s say financial report searches. Semantic caching can rapidly and accurately respond to such queries by avoiding redundant computations, thus enhancing the performance of LM applications.

It signifies a transition from traditional keyword-based caching to a method that takes into account the semantic intent or context of queries. For example, given two prompts with different phrasing but the same intent — “ _Show me the annual financial report_ ” and “ _I need the yearly financial statement_ ” — semantic cache recognizes the identical intent and provides a similar response, something traditional cache cannot do.

In the later sections, we will learn how to leverage both standard and semantic forms of caching in a unified architecture and learn how to implement all of this in a step-by-step manner in Google Cloud.

## Standard Cache Setup

Next, let’s see how to set up a standard cache to capture question-answer pairs. We can leverage this for our end-to-end overall architecture. For this task, we will use Memorystore.

[Google Cloud Memorystore](<https://cloud.google.com/memorystore?hl=en>) is a fully managed in-memory data store service that excels at caching data to improve the performance and responsiveness of real-time applications. By storing frequently accessed data in memory, Memorystore offers sub-millisecond latency and high availability. It supports Redis and Memcached protocols, scaling seamlessly to handle growing workloads while integrating smoothly with other GCP services.

Setting up this cache is relatively straightforward via the GCP console. Make sure you have enabled the necessary APIs to set this up. For our exercise, we can essentially set up a basic instance without any replicas and with minimal memory of 4GB.

![image](https://miro.medium.com/v2/resize:fit:700/1*D-8-Bo5U1joqF3RSJehPGw.png)

Let’s also populate this cache with question-answer pairs. We’ll use the same set of questions from the ground truth test set that we previously used to create your semantic index. But now, instead of encoding the question, we’ll create a unique hash of the question. This hash will serve as the key, and the actual raw question (text) will serve as the value for insertion into the cache.

Next, use the same hash id for the question, but add an ‘ans:’ prefix to the hash. Use this as a key to insert the relevant answer. This process is illustrated in the figure below.

![image](https://miro.medium.com/v2/resize:fit:700/1*jPAD8AO7NPpCkDJ5fORKRQ.png)

You can execute `[load.py](<https://github.com/arunpshankar/VertexAI-Semantic-Caching/blob/main/src/redis/load.py>)`located in the `[src/redis](<https://github.com/arunpshankar/VertexAI-Semantic-Caching/tree/main/src/redis>)`directory to pre-load the standard cache with question and answer pairs.

When connecting to Memorystore on Google Cloud Platform, it’s often necessary to use port forwarding to securely access the Redis cloud instance from a local machine. This process involves setting up a small virtual machine, which acts as a bridge between your local environment and the remote Memorystore service. Here’s how you can set it up:

First, create a new compute instance in your Google Cloud project by running the following command:

``` $ gcloud compute instances create 'redis-forwarder' --machine-type=f1-micro --zone=us-central1-a --project=your-project-id ```

Replace `your-project-id` with your actual Google Cloud project ID. This instance will act as your forwarder.

Next, establish a secure SSH connection with the instance and forward your local port to the Memorystore Redis instance:

``` $ gcloud compute ssh redis-forwarder --zone=us-central1-a -- -N -L 6379:[Memorystore_IP]:6379 ```

Replace `[Memorystore_IP]` with the IP address of your Memorystore Redis instance. This command maps your local port `6379`to the Memorystore Redis instance’s port `6379`, enabling you to interact with your Redis database as if it were running locally.

This approach of using port forwarding is crucial for maintaining a secure connection and ensuring that your data transactions are protected, particularly when accessing cloud resources from a local development environment.

## Connecting the Dots — Orchestrating the end-to-End Workflow

If you have come this far, you should have successfully set up all requisite elements to construct a comprehensive end-to-end workflow for implementing semantic caching within the scope of a document question-answering system. This holistic workflow can be subdivided into two primary pathways: one focusing on exact match and the other on semantic match.

### Exact Match

Consider a scenario where the system might encounter the same search query (question) again from the same user or a different user. This is usually the case when your search queries are short and there’s a high chance of recurrence. In this scenario, rather than going through the regular process of encoding your search query and doing semantic matching against the document indexes, we can directly retrieve the answer from the standard cache if the new incoming query exactly matches the queries already available in the cache. The figure below illustrates this process.

According to the figure, the user starts with a question. We then compute a hash of the question and check if the hash key exists in the standard cache. If it does, we reuse the same hash with an “ans:” prefix to generate a new hash ID that can be used to pull the answer directly from the cache. If the key doesn’t exist, we revert to the next mechanism of finding a semantic match candidate for the incoming query, which will be discussed next.

![Exact Match using Standard Cache](https://miro.medium.com/v2/resize:fit:700/1*_FMFGvijzP3DIHxCc7a_5g.png)

### Semantic Match

Now, let’s explore the overall workflow that shows how semantic matching integrates with the previously discussed exact match scenarios. We’ll break down how everything works together, step by step, as illustrated in the figure below.

![Semantic Caching — End-to-end Workflow](https://miro.medium.com/v2/resize:fit:1000/1*l1sWenhXYZFZIW5H9II21w.png)

1. The user submits a question to the system.
2. The question is then encoded using the text embedding model into a `1x768`dimensional embedding.
3. We match the incoming question against the semantic index we previously created to find the most similar questions along with a confidence score. For our use case, we use cosine distance to measure the similarity between two questions (represented as vectors). It is calculated as 1 minus the cosine similarity. Values range from 0 (identical) to 2 (exactly opposite), with lower values indicating greater similarity or smaller distance. The confidence score is computed as 1 minus the cosine distance.
4. We set the decision threshold based on the confidence score to a high value of 0.98. Depending on whether this condition passes or fails, we take one of two different paths.
5. If the condition is met, we know that the incoming question (query) from the user is semantically very similar to the top-matching question in our semantic index. We then use the hash ID of this top-matching question to check if this key already exists in the Memorystore standard cache.
6. We use the hash id of the question to check the standard cache for a mapping key-value pair entry. If found, we return the retrieved answer to the user. If the key is not found, it indicates an error as the key is found in the semantic index but the mapping key-value pair is not present in the standard cache. We can use error handling mechanisms to track these misses. An offline batch process can recompute the answers for such queries and remediate the error by inserting them into the standard cache. Alternatively, this can also be done online by simply routing the flow back to step 7, which would be a native semantic search using the document (page) semantic index instead of the index created for past questions.
7. When the incoming question does not meet the conditional threshold for semantic similarity, we take the incoming question vector, match it against our document (page) index, and find the top 3 matching pages. We then retrieve these pages as text.
8. Next, we pass the retrieved context, along with the incoming query, to Gemini 1.0 Pro. This generates a relevant answer grounded in the text of these pages. The answer is then returned to the user.
9. Regardless of whether the incoming question returns a top match that meets the confidence threshold, we still upsert the query into the semantic index for past queries.
10. Similarly, for both cases of the threshold check — whether it passes or fails — we store the generated answer. The incoming question is also added to the standard cache. `**Note:**`The question’s hash serves as the connecting link between the two entries — the encoded question in the semantic index and the key-value pair in the standard cache.

The module `[qa.py](<https://github.com/arunpshankar/VertexAI-Semantic-Caching/blob/main/src/run/qa.py>)`in the `src/run`package illustrates the complete workflow combined together in one working orchestration.

## Enhancements and Additions

Next, let’s examine some enhancements we can make to the architecture. These could include things that can be implemented differently or improvements to the current state of affairs. We also propose additional exercises to better elucidate things.

* Currently, we handle user queries (questions) in two ways: as an exact match or as semantically similar. We could also introduce a third category called lexically or syntactically similar. This would capture similar queries that differ only by a limited set of punctuation, stop words, or minor variations that do not affect the meaning. These can be easily checked and routed to an exact match against the standard cache avoiding the longer semantic matching path. We could implement a normalization cleaning step to standardize this before hashing. However, this largely depends on the nature of the incoming questions. The challenge lies in differentiating between these two categories and devising the constraints and rules for matching. `**Note:**`In our setup, anything other than an exact match is treated as a semantic match.
* Adding an additional LLM entity extraction and check can ensure accuracy for numeric and time periods related to the incoming query. For example, we need to ensure that we don’t categorize questions like “What is Google’s operating income in billions at the close of March 2021?” and “What is Google’s operating income in billions at the close of March 2022” as semantically similar. By incorporating an entity recognition step facilitated by Gemini (LLM), we can execute a pre-matching step. Here, we extract the time period and compare it against the time period of the top match to validate if it is truly similar or not. This helps prevent semantically similar queries that are sometimes very different based on numeric entities, such as time periods.
* In our existing architecture, when storing the question and the relevant pre-existing answer (retrieved from the standard cache) — instead of directly mapping the question’s hash to the answer, we can map it to the hash of the answer. This approach requires hashing the answer as well. To find an answer, we can now map the question hash ID to the answer hash ID. This allows us to avoid storing duplicate entries for answers. This also empowers us for better explainability. We can examine the logs and traces to see how different queries map to the same answer. `**Note:**` This is not implemented in the current architecture for simplicity’s sake.
* With our current setup, we hard-code the threshold confidence based on trial and error. Ideally, to determine this cutoff, we could examine the quality of the routed answers as a pre-warm exercise. This involves starting with a test set of queries, which are held out and not included in the standard cache or the semantic index created for past questions. These queries are run through the system with a fixed value (usually high, let’s say 0.9), to capture the corresponding answers. We can then compare these answers to the expected answer either manually or using an LLM of choice to arrive at an evaluation metric and success criteria. Afterwards, we dynamically increment the threshold and repeat the exercise, after clearing the standard cache and semantic index of the test candidates. This way we arrive at a threshold that is more aligned to what we are looking for.
* To optimize cache efficiency in scenarios where memory is constrained and billions of queries need to be managed, leveraging TTL (time to live) adjustments based on cache hits is a strategic approach. By dynamically modifying the TTL of Redis keys according to their access frequency, you can prioritize the retention of frequently accessed keys while allowing less utilized keys to expire, thus managing memory more effectively. This requires implementing a monitoring system that records each key’s cache hits. By maintaining a hit counter for each key and adjusting TTLs based on these metrics, we can ensure that memory allocation aligns with the real-time demand and access patterns of the data. This allows you to focus on your data flow and business logic without worrying about complex cleanup tasks. The counter can also provide us with insights for further enhancements.
