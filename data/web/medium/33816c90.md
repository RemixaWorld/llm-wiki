A few months ago, I was scouring the web with one question in mind: **Is it possible to control the flow of a conversation with an LLM like ChatGPT?**

Like you, I couldn’t find an answer to this. This left me with two choices: either figure it out on my own or wait for GCP, AWS, and others to come up with a solution through their cloud offerings.

> _Fun fact: Spoke to engineers at both Google and Amazon to see if this was even on their roadmap and was quite disappointed._

So, I decided to take matters into my own hands. And guess what? I did it — or at least I’ve got a work-in-progress that’s good enough to share. So sit tight and let's see how to add some structure to these overly creative (at times) LLMs.

## **The Problem: Flexibility vs Control**

To make sure we’re on the same page, the issue here is having a conversation flow that might be as simple as a series of questions or as complex as having branching logic, and you want to present this to your user in a chat interface. A few years ago, the go-to approach would have been to use a chatbot framework like **Dialogflow** , **Amazon Lex** , or even a tool like **Typeform**.

However, these have shortcomings. The conversations don’t feel natural, and mind you, the bar for “natural” has skipped quite significantly since LLMs came into the mix. Plus, these older systems often aren’t smart enough. If you ask a clarifying question, most at times the bot just treats your question as an answer and move on to the next prompt, making the interaction frustrating and less intuitive.

## **A Solid Foundation**

The very first thing to do is to define the conversation flow structure. By this, I’m not just talking about the sequence of questions and how they connect — I consider that to be Step 0. What I mean is selecting a chatbot framework like AWS Lex and using it to design your flow. Most of these frameworks offer simple drag-and-drop interfaces that allow you to map out the entire conversation, making it easier to structure and manage the interaction.

As we discussed earlier, these frameworks excel at providing structure. So, let’s use that strength. Any of these bot frameworks — like Lex, **IBM Watson** , **RASA** , or others — will work well, as long as you can interact with the bot programmatically. Now, we have a very rigid conversation flow, which we’ll refer to as “the bot” from here on. The next step is refining our bot by integrating an LLM. The big question is — how do we do that?

## **Infusing Intelligence with LLMs**

Though I said, “add in an LLM”, what we really need is an [**AI Agent**](<https://zapier.com/blog/ai-agent/>). Which is essentially an LLM with some tools in its arsenal (pun intended). The idea is to position this Agent between the user and the rigid bot we designed earlier, allowing it to mediate between the user and the bot.

The Agent acts as an Orchestrator, handling three key tasks:

* Receives input from the user.
* Decides whether to respond directly or forward the input to the bot.
* Passes information from the bot back to the user.

Now, let’s shift our focus to the Agent. There are several frameworks available today for creating AI agents, including **OpenAI assistants** , Langchain, **CrewAI** , and others. My current favorite is [**LangGraph**](<https://langchain-ai.github.io/langgraph/>), which is built on top of Langchain. I prefer LangGraph because, in my experience, it offers the most control. And as you’ve probably noticed, we’re on a mission to gain as much control as possible. However, LangGraph has a bit of a learning curve, and this isn’t a course on LangGraph, so I’ll explain things in a way that applies to any Agent framework.

For our orchestrator agent, we’ll use GPT-4o and equip it with one tool: a function that wraps the Python code used to call the Lex bot via the SDK.

```python @tool("lex_bot", return_direct=True)def lex_bot(text: str, session_id: Optional[str] = None) -> str: """Returns the bot prompt.""" next_prompt = bot.get_bot_response(text, session_id) return next_prompt ```

Now here is where LangGraph displays its might. Let’s see step by step how everything comes together in the graph. To reiterate, the flow works like this: Messages from the user first go to the LLM. The LLM then decides whether to respond directly or forward the message to the bot. If the message is sent to the bot, the bot responds directly to the user.

### Triggering the Conversation Flow Starts

When using rigid bot frameworks, you typically create a conversation flow that is triggered by specific keywords. In my case, the trigger phrase was “Hello Code xyz,” which my app automatically sent when a user opened a chat.

This setup meant that for the first message sent to the LLM, I needed to ensure that the LLM would always forward it to the bot instead of trying to respond on its own. Fortunately, LangGraph offers a feature called **Forced-Tool Calling**. Since our bot functions as our tool, I was able to make sure that the first message was always directed to the bot. The bot’s response was then forwarded back to the user, as illustrated in the flow chart.

### Reasoning

For subsequent messages, the flow starts with the LLM deciding how to respond. The key factor here is your LLM’s **System Prompt**. While a basic prompt like, “ _You are a smart orchestrator facilitating communication between a user and a Lex bot,_ ” will get you some results, the trick is to tweak the system prompt to fit your specific use case.

For instance, one critical issue I aimed to solve was making sure that when a user asked a clarification question, the LLM would respond directly without triggering the bot. To achieve this, I modified my prompt accordingly.

``` DECISION_AND_RESPONSE_PROMPT = """You are a smart orchestrator facilitating communication between a user and a Lex bot. Do not make any reference of the bot to the user.Follow these guidelines:- Clarifying QuestionsIf the Lex bot asks the user a question, and the user responds with a clarifying question, address the user's query directly.- DO NOT RESPOND TO ANY QUESTIONS FROM THE USER THAT ARE NOT RELATED TO THE CONVERSATION. Politely tell them you have no idea.""" ```

### Explicit Direction

The Conversation Start trigger we discussed is one example of the explicit control that LangGraph permits us to implement. Another thing I found useful is that Langraph allows bot responses to go directly to the user without passing back through the LLM. This is particularly beneficial because it saves on unnecessary token usage, which was exactly what I needed in my situation. If your case is different and you prefer the responses to go through the LLM, LangGraph allows for that too, you just have to make a simple tweak to the graph.

### Memory

Last but not least, you’ll need to address the memory aspect for everything to function smoothly. When a message come in from the user through the agent and the response is sent back, that completes a run. However, when the user replies, the agent has no way of remembering the previous interaction (run), which is why memory is essential.

LangGraph does offer documentation on persistence, but I found it somewhat confusing and complex. Instead, I implemented memory by serializing the agent’s state (the history of messages) after each run. I stored this serialized data in a database (I used Redis cache) with a session_id. For subsequent interactions, the agent reads from this stored data, allowing it to recall previous conversations.

```python def llm_bot(llm_bot_input: str, user_id: str, lex_bot: LexBot) -> dict: global bot bot = lex_bot workflow = StateGraph(AgentState) workflow.add_node("agent", call_model) workflow.add_node("action", call_tool) workflow.set_entry_point("agent") workflow.add_conditional_edges( "agent", should_continue, {"continue": "action", "end": END} ) workflow.add_edge("action", END) app = workflow.compile() system_message = SystemMessage(content=DECISION_AND_RESPONSE_PROMPT) user_input = HumanMessage(content=llm_bot_input) messages = get_llm_memory(user_id) inputs = { "messages": loads(messages) + [user_input] if messages else [system_message, user_input] } output = app.invoke(inputs, {"configurable": {"session_id": user_id}}) print("STATE:") pprint(output) print("END STATE") store_llm_memory(dumps(output.get("messages")), user_id) if output.get("messages")[-1].type == "function": return json.loads(output.get("messages")[-1].content) return {"messages": [{"content": output.get("messages")[-1].content}]} ```

## **Optimising the Intelligent Bot**

By now, you should have a solid understanding of how to put together an intelligent chatbot by combining a traditional rigid bot with an AI agent. However, as I mentioned earlier, this is still a work in progress. My hope in sharing this is that it sparks ideas for further improvements or perhaps inspires you to develop something even better.

In the meantime, here are a few improvements I made and suggest you consider:

**Memory Optimization**

For longer conversation flows, the conversation history can start to get quite large, leading to two issues: increased LLM costs and the agent forgetting the System Prompt, which is key as it serves as the reasoning engine. The solution I went for, is to keep just the system prompt along with the last 10 messages for every call to the LLM. This keeps the system prompt close to the current interaction, improving accuracy and reducing token usage.

**Guardrails**

Of course, you don’t want someone using your bot as ChatGPT. To prevent users from misusing your bot as a general-purpose Q&A, it’s important to implement guardrails. These safeguards help maintain the bot’s intended purpose and reduce off-topic interactions. A simple instruction in your System prompt is a solid start.
