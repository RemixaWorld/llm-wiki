### Introduction

In this article, we will discuss different ways to extract data from documents. We will compare OCR+LLM with Claude 3 vision and explore fast OCR transformers and cloud-native OCRs. Additionally, we will provide a code example for implementing OCR as a simple API using docTR. Lastly, we will talk about Groq and how it can be used to give us the best inference speed for LLM.

Will be using this [repo](<https://github.com/enoch3712/Open-DocLLM>), from the previous articles.

### The use case: Document scan to save time

### OCR transformers designed for Speed

The new era of OCR is based on transformers, usually from Huggingface trained to run on Tensorflow/Pytorch in CPU/GPU. Here are some of the best mentions:

1. [**DocTR**](<https://mindee.github.io/doctr/using_doctr/using_models.html>)\- This OCR tool is also optimized for high-speed performance on both CPU and GPU. It offers a user-friendly approach where only three lines of code are needed.
2. [**TrOCR**](<https://github.com/microsoft/unilm/tree/master/trocr>)\- Is also a pre-trained transformer, that offers several models. Supported by Microsoft.
3. [**PaddleOCR**](<https://github.com/PaddlePaddle/PaddleOCR>)\- It is optimized for speed and can process large volumes of images in real time. With an average CPU processing time of only 41 milliseconds per image​
4. [MMOCR](<https://github.com/open-mmlab/mmocr>)
5. [Surya](<https://github.com/VikParuchuri/surya>)

As you can see there are plenty. I ran it in performance mode and I got 50ms, and in some cases, you would be able to go down to 20ms in GPU. I tested some of the cloud-native OCRs you have:

1. **Azure Form Recognizer** : Best performance time of about 3 seconds, it's always around that value. The best in terms of overall speed of the solutions
2. **Amazon Textract** : Amazon Textract typically processes documents in a few seconds per page, usually 3–4. Not much different than **Azure Form Recognizer.** The products are quite similar, and there is not much difference between performance and cost.
3. **Google Cloud Vision API and Document AI** : Highly efficient, solid, and similar to both.
4. **Abby Cloud OCR:** A developer's favorite. It is faster than all of these alternatives and gives you a representation of the page in terms of location, **would be perfect to use in this context if it suits you**.

These products are now mature. They have the same price and the same offers.

Before LLM’s, these cloud AI services used to be the way to go. They offer you a template to train your type of documents (e.g. invoice, medical record) so you can classify and extract the information. **But comes with a hefty price and vendor lockout of the box**. Now with LLM’s, we only require a basic read or a simple layout template scan that will cost you a fraction of the other models. Once that's done, we can extract the necessary information with the LLM, which will handle the bulk of the work. This method works efficiently and eliminates the need for any additional steps and will be better in terms of cost and results.

### Code example OCR

Let's split our code into microservices. The OCR will be a simple fast API in a docker container, so we can deploy in different environments and tweak as much as we need in terms of configuration.

Press enter or click to view image in full size

Different services of the stack

I will choose docTR (Document Text Recognition) for this example as it is the easiest one to implement and run. To get started with testing, I have created a simple docTR folder on the repo with a docker container that is ready to run. You can start testing straight away with docker using the following code:

```python from fastapi import FastAPI, File, UploadFilefrom fastapi.responses import JSONResponsefrom doctr.io import DocumentFilefrom doctr.models import ocr_predictorfrom PIL import Imageimport ioimport osapp = FastAPI(title="OCR Service using docTR")@app.post("/ocr/")async def perform_ocr(file: UploadFile = File(...)): image_data = await file.read() # Attempt to load the image directly from the BytesIO object doc = DocumentFile.from_images(image_data) model = ocr_predictor(pretrained=True) result = model(doc) extracted_texts = [] for page in result.pages: for block in page.blocks: for line in block.lines: line_text = ' '.join([word.value for word in line.words]) extracted_texts.append(line_text) return JSONResponse(content={"ExtractedText": extracted_texts})if __name__ == "__main__": import uvicorn uvicorn.run(app, host="0.0.0.0", port=8001) ```

The code is simply:

1. An endpoint that receives a file.
2. Calls the docTR standard model.
3. Run the OCR, and get all the text into an Array.

The docker container installs all the dependencies:

```python # Use an official Python runtime as a parent image, suitable for TensorFlowFROM tensorflow/tensorflow:latest# Set the working directory in the containerWORKDIR /app# Install system dependencies required for OpenCV and WeasyPrintRUN apt-get update && apt-get install -y \ libgl1-mesa-glx \ libpango-1.0-0 \ libpangocairo-1.0-0 \ libgdk-pixbuf2.0-0 \ libffi-dev \ shared-mime-info# Install FastAPI and UvicornRUN pip install fastapi uvicorn python-multipart aiofiles Pillow# Copy the local directory contents into the containerCOPY . /app# Install `doctr` with TensorFlow supportRUN pip install python-doctr[tf]# Expose the port FastAPI will run onEXPOSE 8001# Command to run the FastAPI server on container startCMD ["uvicorn", "app:app", "--host", "0.0.0.0", "--port", "8001", "--workers", "4"] ```

There are already containers available that you can use. These containers have much smaller and slimmer models that you can test and use for your experimentation purposes. **This way, you can have something right away without feeling lost. ### OCR+Groq

The Groq code is what you are expecting:

```python from groq import Groqdef send_request_to_groq(content: str) -> str: client = Groq(api_key=API_KEY_GROQ) completion = client.chat.completions.create( model="gemma-7b-it", messages=[ { "role": "system", "content": "You are an API server that receives content from a document and returns a JSON with the defined protocol" }, { "role": "user", "content": content } ], temperature=1, max_tokens=1024, top_p=1, stream=False, #Needs to be false response_format={"type": "json_object"}, # just like in OpenAI API stop=None, ) return completion.choices[0].message.content ```

The thing that surprises me the most is the “response_format”, it's an amazing feature other providers don't have. **So huge props to the Groq team!**

The final code is the controller. Is the same as the “extract” endpoint, just calls Groq, so it becomes **“/extract_fast”. You should change the OCR result according to what you are using.**

When it comes to scanning documents and extracting data, using only visual tools may not be enough.
