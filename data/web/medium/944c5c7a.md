### Application UI— Streamlit

There are a couple of obvious options for the webapp UI for our application: Flask and Streamlit.

[**Flask**](<https://flask.palletsprojects.com/en/stable/>)**** is a powerful — yet lightweight — open-source Python web application framework that gives us a high level of control and flexibility over our application UI and functionality. But there is a bit of a learning curve. In addition to understanding Flask concepts like routing from URLs to Python code, you also have to be familiar with frontend content creation, e.g. using HTML, CSS and Javascript; and the concept of using Jinja2 to create reusable frontend templates. You can jump-start a lot of this effort by using a tool like [Boostrap-Flask](<https://bootstrap-flask.readthedocs.io/en/stable/>).

_But there’s an easier way…_

[**Streamlit**](<https://streamlit.io/>)**** is an open-source Python framework designed for creating and sharing data-driven web applications quickly and easily. It is particularly popular among data scientists and machine learning engineers, for turning Python data applications (like our Jupyter notebook) into web-based interactive applications.

> Streamlit allows us to create our web app using **pure Python**. We don’t need to write any frontend using HTML / CSS / Javascript, since Streamlit generates this for us. Streamlit makes it very easy to create UI widgets from our Python code.

The look-and-feel options of Streamlit applications are limited. Although it provides basic theming and styling, Streamlit applications will all tend to look fairly similar.

The needs of my video processing application are simple, and I’m happy with the UI styling limitations. So… **I’m going to use Streamlit!**

### Docker Containers

Containers are lightweight, isolated environments containing everything needed to run an application. They are abstracted from the host hardware and the host OS. And as a result, there are loads of benefits of running containerised applications:

* Super lightweight and therefore both very fast and very cheap to run.
* They package up all your applications dependencies. Thus they eliminate painful environment configuration.
* Portable and agnostic of the hosting environment (e.g. your laptop, VMs in your data centre, or your favourite cloud). Thus: build once, run anwwhere.
* They are isolated from other applications, avoiding dependency conflicts and other related challenges.
* There’s a massive ecosystem of pre-canned container images available. Run them as they are, or use these images as a base for your own images.
* They are easily built and deployed as part of a CI/CD pipeline.

The typical workflow for containers is:

![Docker container workflow](https://miro.medium.com/v2/resize:fit:700/1*aoB0LV3ZAsv3i-kD_N-nNw.png)

1. Create our application.
2. Write a Dockefile that we will use to create a container image for our application.
3. Build the container image.
4. Push the container image to an image registry.
5. “Pull” the image and run our application — in one or more containers.

### Container Image Hosting — Google Artifact Registry (GAR)

GAR is Google’s general-purpose artifact management service that can store and manage a wide range of software artifacts, such as container images and language packages. (It is the successor to the Google Container Registry.)

GAR provides automatic vulnerability scanning of our artefacts, and it’s trivial to deploy from GAR to Google Cloud services such as Google Kubernets Engine (GKE) and Cloud Run.

### Container Hosting Runtime — Google Cloud Run

Cloud Run is Google’s serverless container runtime environment, intended for hosting of stateless containers that respond to web requests or other events. Cloud Run automatically scales, and can scale down to 0 when not in use. You only pay for what you’re using.

![Cloud Run for container hosting](https://miro.medium.com/v2/resize:fit:700/1*ZlhYH5NWCV4-qd6aZ-ZWyA.png)

We can easily deploy to Cloud Run using a container image stored in a registry, such as Google Artifact Registry.

### CI/CD — GitHub and Google Cloud Build

We will push our application code to a git repo in GitHub. There are various ways we can create a CI/CD pipeline to build, test and deploy our applications. For example, we can use GitHub Actions — as I’ve described in my article [Create a CI/CD Pipeline using GitHub Actions and Google Cloud](</google-cloud/create-a-ci-cd-pipeline-using-github-actions-and-google-cloud-9be20ff50e97>).

![Options for building a CI/CD pipeline that deploys to Google Cloud](https://miro.medium.com/v2/resize:fit:700/0*sbRr9m6maiU6I5SX.png)

But here we will use Google Cloud Build: a fully-managed, cloud-native, serverless CI/CD service. It can integrate directly with various source repos, including Google Source Repositories, GitHub and BitBucket. We can use Cloud Build to set up an automated CI/CD pipeline, such that code changes we commit to GitHub will automatically be deployed to Google Cloud Run.

### Load Balancing — Google Cloud External Application Load Balancer (ALB)

Google’s load balancers are fully-managed, software-defined, serverless, scalable, and highly available. We use ALBs to:

* Provide a stable and public frontend IP address, in order to reach private backend services.
* Distribute load amongst autoscaling backends.
* Automaticly route of requests to backends that are closest to the user.
* Proxy (hide) the backends from the users.
* Use any external domain name.
* Provide managed SSL certificates, to ensure encrypted traffic between users and Google Cloud with HTTPS.
* Provide easy integration with Google Cloud Armor, for capabilities such as DDoS protection, and web application firewalling.
* Provide easy integration with Google Cloud CDN, for caching of content close to users.
* Provide easy integration with Google Cloud Identity-Aware Proxy (IAP).

### Zero Trust Access — Google Cloud Identity-Aware Proxy (IAP)

IAP lets you control access to your application before requests even reach your application resources.

It allows us to authenticate a user, and then determine whether the user is authorised to access the requested resource, such as our Cloud Run application.

![Using IAP to restrict access to Cloud Run applications](https://miro.medium.com/v2/resize:fit:700/1*omFvSvD9ITzsf4n1xXI1oQ.png)

### Multimodal Generative AI Model — Google Vertex AI Gemini 1.5 Flash

Multimodal generative AI models can process input from multiple modalities at the same time, such as text, images, audio and video.

Gemini 1.5 Flash is Google’s multimodal model designed for high-volume, cost-effective applications. It is fast and efficient, with lower cost than Gemini 1.5 Pro.

### Creating and Running a Local Docker Container

Now we want to containerise our application with Docker. The `docker build` command reads from the `Dockerfile` in order to build our container image. Here is our `Dockerfile`:

```python FROM python:3.12EXPOSE 8080WORKDIR /appCOPY . ./RUN pip install -r requirements.txtENTRYPOINT ["streamlit", "run", "app.py", "--server.port=8080", "--server.address=0.0.0.0"] ```

Explaining how Docker works is beyond the scope of this article. But a brief explanation of what’s going on here:

1. We’re loading the `Python` base container image.
2. The container will expose the application on port 8080.
3. We set the working directory inside the container to `/app`. All subsequent commands run from this directory.
4. We copy the contents from the local directory into the container `/app` directory.
5. We install the Python dependencies that are specified in `requirements.txt`. I.e. these requirements are baked into our image at the point we build the image.
6. We define the `ENTRYPOINT` — i.e. the command that runs whenever a container from this image is launched.

Let’s go ahead and build the image:

``` docker build -t $SERVICE_NAME:$VERSION . ```

It builds pretty quickly:

![Building the container in local dev environment](https://miro.medium.com/v2/resize:fit:673/1*kkrrht2-q7w1gkcQhJ-K-w.png)

And now we can run the container locally:

``` # Run as a local container.# We need to pass environment variables to the container# and the Google Application Default Credentials (ADC)docker run --rm -p 8080:8080 \ -e PROJECT_ID=$PROJECT_ID -e REGION=$REGION \ -e LOG_LEVEL=$LOG_LEVEL \ -e GOOGLE_APPLICATION_CREDENTIALS="/app/.config/gcloud/application_default_credentials.json" \ --mount type=bind,source=${HOME}/.config/gcloud,target=/app/.config/gcloud \ $SERVICE_NAME:$VERSION ```

There’s some interesting stuff going on in this `docker run` command:

* The `--rm` parameter ensures that the container is deleted after it has run. But you might prefer to just leave the container running.
* We use the `-e` parameter in several places to set environment variables inside the container environment. This is how we pass in the environment variables from our host environment.
* One of these environment variables is `GOOGLE_APPLICATION_CREDENTIALS`, i.e. a variable that tells Google where to find the ADC credentials used by Google APIs within our application. We set this to point to a local credentials file _inside_ our container.
* Finally, we use the `mount` flag in order to mount our host environment `.config/gcloud` directory to `/app/.config/glcoud` _inside_ the container. This is how we actually make our ADC credentials available to the container itself.

It starts up **super-fast from the container!** The browser application is available almost instantly.

![Starting our container locally](https://miro.medium.com/v2/resize:fit:700/1*AmtNjfmz6TTcKy2CqBL2nw.png)

### 2 — Add the Application (HTTPS) Load Balancer

In this step we add an external HTTPS load balancer for our Cloud Run application. The LB allows us to:

* Present a fixed IP address which is Internet-accessible.
* Bind a custom domain name to our IP address.
* Integrate user authentication with IAP.

This diagram shows the typical components of a Google Cloud application load balancer:

![Google application load balancer](https://miro.medium.com/v2/resize:fit:700/1*bn-TGs2FTma2EUzQbKM2bQ.png)

We could set up the LB through the Cloud Console. But here — as usual — I’ll present the steps to do this through the terminal, using the gcloud CLI.

```bash # Define env varsexport SVC_LB_IP="lb-ip"export SVC_CERT="lb-cert"export SERVERLESS_NEG="$SERVICE_NAME-serverless-neg"export BACKEND_SERVICE="$SERVICE_NAME-backend-service"export URL_MAP="lb-url-map"export TARGET_HTTP_PROXY="lb-target-proxy"export FORWARDING_RULE="lb-forwarding-rule"# Create global static external IP addressgcloud compute addresses create $SVC_LB_IP \ --network-tier=PREMIUM \ --ip-version=IPV4 \ --global# Check it and get the IP address# We'll create a DNS A record pointing to this IP address latergcloud compute addresses describe $SVC_LB_IP \ --format="get(address)" \ --global ```

Our IP address has been created. We will use this IP address as the frontend of our load balancer.

![External IP address created](https://miro.medium.com/v2/resize:fit:511/1*SclvsWRO7PlsxPhPoQyk3g.png)

If you’re going to use your **own domain name** , now is a good time to set up your **DNS “A” record**. This is a record that maps the domain name (from your DNS provider) to the IP address you’ve just created. The exact process for setting up your DNS record will vary depending on who provides your domain name.

Next: our HTTPS LB requires an **SSL certificate**. Run the commands below to create a managed SSL certificate:

``` # Create a managed SSL certificategcloud compute ssl-certificates create $SVC_CERT \ --description="video-intel-alb-cert" \ --domains=$DOMAIN_NAME \ --global# Check the status of the certificategcloud compute ssl-certificates list --global ```

At this point we can see the certificate is in PROVISIONING phase:

![Provisioning the SSL certificate](https://miro.medium.com/v2/resize:fit:700/1*n95tNEb8DvLKotvNohIcoQ.png)

For the certificate to become `ACTIVE`, the Google-managed SSL certificate must be associated with a load balancer; specifically the load balancer's target proxy.

![SSL certificate is assoicated with the LB target proxy](https://miro.medium.com/v2/resize:fit:700/1*djn12h0UgIinQv5gjZeRJg.png)

Continue with the LB creation steps:

``` # Create a serverless NEG for the serverless Cloud Run servicegcloud compute network-endpoint-groups create $SERVERLESS_NEG \ --region=$REGION \ --network-endpoint-type=serverless \ --cloud-run-service=$SERVICE_NAME# Create ALB backend servicegcloud compute backend-services create $BACKEND_SERVICE \ --load-balancing-scheme=EXTERNAL \ --global# Add the serverless NEG as a backend servicegcloud compute backend-services add-backend $BACKEND_SERVICE \ --global \ --network-endpoint-group=$SERVERLESS_NEG \ --network-endpoint-group-region=$REGION# Create URL map to route incoming requests to the backend servicegcloud compute url-maps create $URL_MAP \ --default-service $BACKEND_SERVICE# Create a target HTTPS proxy to route requests to your URL mapgcloud compute target-https-proxies create $TARGET_HTTP_PROXY \ --ssl-certificates=$SVC_CERT \ --url-map=$URL_MAP# Create a forwarding rule to route incoming requests to the proxygcloud compute forwarding-rules create $FORWARDING_RULE \ --load-balancing-scheme=EXTERNAL \ --network-tier=PREMIUM \ --address=$SVC_LB_IP \ --target-https-proxy=$TARGET_HTTP_PROXY \ --global \ --ports=443 ```

We can now recheck the SSL certificate, and we should see it is active:

``` # Check the status of the certificategcloud compute ssl-certificates list --global ```

![SSL certificate now active](https://miro.medium.com/v2/resize:fit:1000/1*AqzBQyGaAl9N-SOENPT7Bg.png)

We can check the load balancer in the console:

![Load balancer created](https://miro.medium.com/v2/resize:fit:1000/1*OPrldy7-mEbOkQGEbGUgwQ.png)

### 3 — Make Our Cloud Run Service Accessible Via the Load Balancer

By default, Cloud Run services are publicly accessible from the Internet, through an `app.url`. Previously we restricted access to authenticated and authorised identities. (Remember our “Forbidden” message.) But the service itself can still be reached directly from the Internet, bypassing the load balancer. We want to restrict direct access, such that access is only possible via the load balancer, like this:

![image](https://miro.medium.com/v2/resize:fit:700/1*C9cMwumZaAtuQ3NZHN6JkA.png)

We can do this by changing the [Cloud Run Ingress setting](<https://cloud.google.com/run/docs/securing/ingress>). There are three options:

* **All** — the default, and least restrictive
* **Internal** — the most restrictive
* **Internal and Cloud Load Balancing** — as with “Internal”, but also allows access via an external load balancer.

We want to use “Internal and Google Cloud Load Balancing”. This is what the Google documentation says about this setting:

![Configuring Ingress for Internal and Cloud Load Balancing](https://miro.medium.com/v2/resize:fit:700/1*x6Pm47mKPbgMZ_Eov_pjpw.png)

Let’s apply this setting:

``` gcloud run services update $SERVICE_NAME \ --ingress internal-and-cloud-load-balancing \ --region=$REGION ```

### 4 — Configure Identity-Aware Proxy (IAP)

Lastly, we’ll **setup Identity-Aware Proxy**. We start by creating an **IAP service account** that the load balancer will use in order to invoke requests to the Cloud Run service:

```bash # The name of the IAP service accountexport IAP_SA="service-$PROJECT_NUMBER@gcp-sa-iap.iam.gserviceaccount.com"# Enable the IAP APIgcloud services enable iap.googleapis.com# Create the IAP service accountgcloud beta services identity create --service=iap.googleapis.com --project=$PROJECT_ID# Grant the invoker permission to the service accountgcloud run services add-iam-policy-binding $SERVICE_NAME \ --member="serviceAccount:$IAP_SA" \ --region=$REGION \ --role="roles/run.invoker" ```

Then we need to **enable IAP on the load balancer backend**. This is how we ensure that the IAP credentials are used when invoking the Cloud Run service.

``` gcloud compute backend-services update $BACKEND_SERVICE --global --iap=enabled ```

If you open IAP in the Google Cloud Console, you will see the message: _“Before you can use IAP, you need to configure your OAuth consent screen.”_

![Configure Identity-Aware Proxy](https://miro.medium.com/v2/resize:fit:700/1*sBdugT0Bw6VmmY-sjYD0YQ.png)

Clicking on this takes us to the Google Auth Platform App Information (previously OAuth consent) screen:

![image](https://miro.medium.com/v2/resize:fit:700/1*TxOwIOcP7b-UGGpUCPvPig.png)

Our application doesn’t actually need any scopes. But if you wanted to make certain data — like your email address — available to your application, you can add the scopes here:

![Adding scopes](https://miro.medium.com/v2/resize:fit:700/1*5JTKLF5O-8sEtaUwfiFW3Q.png)

### 5 — Grant Access to Our Users

Okay, we’re nearly done! We just need to allow our users access access via IAP. We do this by granting the `IAP-secured web app user` role to the users or groups we want to give access to. We can do that in the Cloud Console:

![image](https://miro.medium.com/v2/resize:fit:700/1*DI3e0slVtksj--ZkZ2ocNQ.png)

Finally **grant IAP-secured Web App User to users or groups**.

![image](https://miro.medium.com/v2/resize:fit:700/1*sw3FVAkLmUVkueP5HRZlqQ.png)

Alternatively, we can do it in the terminal:

``` gcloud projects add-iam-policy-binding $PROJECT_ID \ --member="group:gcp-devops@$MY_ORG" \ --role="roles/iap.httpsResourceAccessor" ```

## Performance Optimisation?

I’ve set the maximum number of Cloud Run instances to 1, so:

* There will be 0 instances if there’s no demand
* Otherwise, 1 instance.

But there are changes we could make to improve performance:

1. If we want to avoid a slow initial _cold start_ time, we can set the minimum number of instances to 1. This will result in an “always-on” container. But — of course — we have to pay whilst it is running.
2. Alternative, to reduce cold start time, we can configure [Cloud Run startup CPU boost](<https://cloud.google.com/blog/products/serverless/announcing-startup-cpu-boost-for-cloud-run--cloud-functions>). Here Google Cloud dynamically allocates more CPU to our Cloud Run container during startup, which can dramatically improve our startup time. And, because this extra CPU is only allocated for those infrequent cold starts, it’s generally going to be more cost effective than keeping an instance running all the time. Here’s how we do it:

``` gcloud beta run services update $SERVICE_NAME" \ --region=$REGION --cpu-boost ```

We can verify in the Cloud Console:

![Startup CPU boost for Cloud Run](https://miro.medium.com/v2/resize:fit:700/1*DXarT2pjCNRcoIKMZU10SQ.png)
