This article will mainly discuss three practical challenges of RAG and the corresponding mitigation ideas.

## Irregular Query and Short Query

In real-world production environments, user queries frequently lack standardization; many are semantically incomplete, poorly articulated, or convey multiple intentions. Additionally, the shorter the user query, the harder it is to handle.

For example, queries like “recommend hotel”, “Tell me football news and today’s weather”, or “benefits of apple” are difficult for RAG system to handle.

There are three approaches to mitigate this:

* **Intent Analysis** : Identify one or more user intents to narrow the search scope.
* **Keyword Extraction** : Determine the keywords of the query and retrieve based on them.
* **Clarification and Inquiry** : Proactively ask the user questions to obtain more information. For example, for the query “benefits of apple,” the RAG system can ask, “Do you mean the fruit or the technology company?”

### **Intent Analysis**

As illustrated in Figure 1, intent analysis involves classifying a user’s query into one or more predefined intents, thereby narrowing the search scope. It is actually a traditional NLP technique.

As shown in Figure 4, the purpose of using keyword extraction in RAG is to extract keywords from user queries and documents to facilitate retrieval.

In Figure 4, we see two dashed boxes: the red dashed box represents the original chunks obtained through keyword retrieval, and the blue dashed box represents the original chunks obtained through ordinary retrieval.

After obtaining these two dashed boxes, we can perform re-ranking or other post-processing approaches. It is clear that keyword retrieval can assist ordinary retrieval.

The current question is how to obtain the keywords from the original chunks or the user query. There are three methods as follows.

* TF-IDF: First, perform tokenization and stopword removal. Then, calculate the inverse document frequency (IDF) for each token and the TF-IDF score for each token. Finally, rank the words based on the calculated TF-IDF scores. The higher the ranking of the token, the more important it is in the document.
* Training models or using existing models, like [KeyBERT](<https://github.com/MaartenGr/KeyBERT>): Directly extract keywords to form the final keyword list.

### Clarification and Inquiry

Clarification and inquiry is an important strategy, especially when dealing with vague, incomplete, or ambiguous user queries. By proactively clarifying and asking questions, RAG system can gather more information, better understand the user’s intent, and provide more targeted responses.

For example, if a user directly asks, “recommend hotel”, we can gather information about the user’s preferred location, price range, and other preferences through clarification and inquiry, thereby providing a more accurate response.

Clarification and inquiry is a technique from the traditional dialogue systems field.

If we don’t use an LLM, clarification and inquiry mainly includes the following steps:

* First, detect ambiguous or unclear parts of the user’s input. This can be achieved through keyword extraction, by identifying common ambiguous or unclear words. Alternatively, it can be done using intent analysis technology, to analyze the input’s meaning and context.
* Generate a clarification or inquiry response, which can be done through predefined templates or by using generative models.
* Processing the user’s subsequent input, and updating understanding and task execution based on the new input.

On the contrary, if using an LLM, we can include in the prompt: “If you cannot answer the user’s query based on the background knowledge, then you can follow up with the user with questions, limited to 4 questions.”

### Summary

It’s worth mentioning that the three methods introduced above aren’t isolated; they can be combined.

For example, intent analysis can be achieved through keyword extraction, and clarification and inquiry can be combined with intent analysis.

## Structured Data

We know that unstructured data, especially PDF files, contains a wealth of information. Therefore, I have written [a series of articles on parsing PDF files](<https://medium.com/@florian_algo/list/document-intelligence-and-pdf-parsing-2334780a5667>).

As shown in Figure 7, in actual production environment, it is rare to complete an entire business process using only unstructured data. Generally, it is necessary to integrate information from the company’s existing relational databases and even Excel files into the RAG process.

Figure 7: Unstructured data and structured data in RAG, structured data is equally important. Image by author.

There are three ways to integrate structured data into RAG process:

* Consider each row of every table in the relational database as a chunk, and then perform embedding. However, this approach ignores the overall information of the table and disrupts the relevance within the table, often leading to poor results during retrieval.
* Instead of vectorizing the information of each row of the table, embed the metadata, such as table descriptions, view descriptions, and field information. After vectoring the user’s query, use the embedding to find the corresponding table, view, or field. Then use some pre-written SQL functions for querying. This method involves more workload when writing the SQL functions in advance, but the execution is relatively stable compared to the other methods.
* [Text2SQL](<https://paperswithcode.com/task/text-to-sql/latest>), as shown in Figure 8, uses an LLM to convert the user’s question into an SQL statement. It then sends the database query results to LLM to generate the final answer. This approach is relatively elegant and works well for simple queries. However, if the user’s query is more complex, the results can be unstable.

Press enter or click to view image in full size

Figure 8: An example of Text2SQL. Source: [Query Construction](<https://blog.langchain.dev/query-construction/>).

Note: To generate accurate SQL queries, it’s necessary to provide the LLM with an accurate description of the database. A common Text2SQL prompt is roughly as follows: provide the LLM with a `CREATE TABLE` description for each table, which include column names, their types, etc followed by three example rows in a `SELECT` statement.

## About Private Deployment

In the actual application of RAG, some clients have high data confidentiality requirements, necessitating private deployment within the enterprise.

There are three points to note:

* Selection of model parameters: If the main function of the LLM is induction and generation, a smaller scale such as 7B or 13B is acceptable. If there are high requirements for knowledge reasoning, logical reasoning, multi-step reasoning, etc., then more parameters are better, such as 33B or 70B.
* If the client is in an environment without external internet access, it’s necessary to download all dependencies of Python libraries like PyTorch and Transformers in advance. Container technologies (e.g., Docker) can simplify environment configuration and management.
* To improve inference speed and reduce resource consumption, we can perform [model quantization](<https://medium.com/@florian_algo/model-quantization-1-basic-concepts-860547ec6aa9>). Additionally, to ensure efficient request processing and response, choose an efficient LLM service framework to deploy RAG system. If some open-source frameworks do not meet your needs, write the necessary modules yourself.
