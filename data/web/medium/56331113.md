## TL;DR

Fine-tuning large language models with **Quantized LoRA (QLoRA)** allows efficient updates to original model weights but may initially reduce accuracy when merging LoRA weights with quantized base weights. The solution is to **first dequantize these layers** , ensuring that merging preserves the model’s fine-tuned performance. This approach maintains accuracy after merging LoRA weights, while keeping the model lightweight for resource-efficient inference.

## The Story

When fine-tuning a **Large Language Model (LLM)** , the goal is to adjust the weights to better capture patterns in your data. However, full fine-tuning of a model with a vast number of parameters can be challenging due to high computational costs, significant memory requirements, and the risk of overfitting — especially with limited data.

So, you’re thinking about fine-tuning an LLM on your own data. Maybe you want it to master specific patterns in your domain, or perhaps you have a downstream task in mind where you need the model to outperform off-the-shelf alternatives.

You’ve chosen the model, prepared the data, and fired up your GPU machine, all set to start coding and training. But there’s a catch: your resources aren’t unlimited, and time is ticking.

You need an efficient way to fine-tune without compromising too much on performance.

That’s when you stumble upon **LoRA** (Low-Rank Adaptation). With LoRA, you can avoid training the entire model’s weights, focusing instead on a more resource-friendly approach to fine-tuning.

You give it a shot, but soon you encounter the dreaded **Out of Memory (OOM)** error. You start looking for an alternative, and that’s when you find **QLoRA ,** an approach that follows LoRA’s efficiency but also quantizes model weights, allowing them to fit comfortably on a single machine while fine-tuning.

Problem solved!

Or so you thought.

After training with QLoRA, you run your evaluation and see great results. You save the model; merging the LoRA weights with the original ones to consolidate the learned adaptations into a single, unified model. This merging step is crucial, it ensures that the final model is ready for deployment or storage without relying on the extra LoRA modules. When you reload it and run another evaluation, the results are shocking. Accuracy has deteriorated, no matter whether you load it at higher or lower precision.

If this sounds familiar, or if you’re exploring a similar path, read on. This article will guide you through the exact steps needed to maintain the accuracy you saw during fine-tuning with QLoRA, all while achieving a much lighter memory footprint than the original model.

## Brief introduction to fine-tuning with LoRA

**Low-Rank Adaptation (LoRA)** , [introduced in 2021](<https://arxiv.org/pdf/2106.09685>) proposed an efficient alternative to full fine-tuning. Instead of updating all model weights during fine-tuning, LoRA modifies only a small subset of parameters while preserving model performance.

The core concept involves freezing the pre-trained model’s original weights and injecting trainable low-rank decomposition matrices into the selected layers. Only these new matrices are trained, reducing both memory and computational load.

For example, consider the `mistral-7b-instruct-v0.1` model, which is our focus in this article (though these methods apply to other models as well). When you load this model from HuggingFace and examine its architecture (Figure 1), you’ll notice multiple linear layers (in yellow).

![Figure 1 : Mistral-7B-Instruct-v0.1 structure prior to fine-tuning](https://miro.medium.com/v2/resize:fit:700/1*Lx5IKzUOVt9CS7s0ao-u3A.png)

Each linear layer represents a matrix W of shape ℝᵐ * ⁿ, where 𝓂 is the input features to the layer and 𝓃 is the output feature. LoRA decomposes this matrix into two smaller matrices, A and B, whose dimensions are determined by the rank 𝓇, a hyperparameter chosen by the user. This rank 𝓇 is much smaller than 𝓂 or 𝓃, allowing the dimensions of new matrices to be just a fraction of the original size, and therefore significantly reducing the resources required for training.

For illustration and simplicity, let’s apply LoRA to a single linear layer, `q_proj` using [PEFT](<https://github.com/huggingface/peft>). As shown in Figure 1 (in blue and green colours), you’ll see that `q_proj` now includes additional components:

* `lora_dropout`
* `lora_a`, and
* `lora_b`

`lora_b`

The original `q_proj` layer, has `in_features=4096`and `out_features=4096`, giving it a shape of (4096, 4096).

![Figure 2: Mistral-7B-Instruct-v0.1 structure after adding LoRA layers using PEFT](https://miro.medium.com/v2/resize:fit:700/1*iDqAKo5VDMdZvZS5Nb6dKw.png)

With a LoRA operation of rank 16, the dimensions of `lora_a` and `lora_b` are adapted as follows:

* `lora_a` has `in_features = 4096` and `out_features = 16`.
* `lora_b` has `in_features = 16` and `out_features = 4096`.

When `lora_a` is multiplied by `lora_b`, the resulting tensor dimension is (4096, 4096), matching the original `q_proj` layer’s shape. This match is intentional to ensure compatibility with the original model architecture. While LoRA does not explicitly use Singular Value Decomposition (SVD), it is inspired by the principles of low-rank approximation, where high-dimensional tensors can be approximated by the product of smaller, low-rank tensors.

Why employ this approach?

In short, it significantly reduces the number of trainable parameters, focusing training updates on `lora_a`, `lora_b`, and `lora_dropout` while keeping the original model layers frozen. Once the LoRA operation completes, the combined product of `lora_a`, `lora_b`, and `lora_dropout` is added back to `q_proj` as a low-rank update. Since this update shares the same (4096, 4096) dimension as the original matrix W, it integrates seamlessly.

You can refer to our earlier post and the merge and unload section of this post to understand this better.

## Introduction to Quantization in LLM

### Introduction to quantization

Quantization reduces the precision of base model weights while striving not to lose too much accuracy. Typically, models are stored in **FP32** (32-bit floating-point format). With quantization, one can save the models in FP16, BF16, INT8, NF4 .., etc. Each of these formats offer a trade-off between precision and memory efficiency, with lower-bit formats generally consuming less memory but potentially sacrificing some model accuracy.

### Types of quantization

**Post-Training Quantization (PTQ)**

PTQ is applied after a model has been fully trained. It involves converting the model’s weights and activations to lower precision formats without the need to retraining the model while its weights are quantized. This method is straightforward to implement but may result in some performance degradation:

**Quantization-Aware Training (QAT)**

QAT incorporates quantization effects during the training process. **QLoRA** is in this category. This approach allows the model to adapt to the reduced precision, often resulting in better performance compared to PTQ.

_Why quantization?_

Quantization offers two key benefits: smaller model size and reduced memory usage.

**_Smaller Model Size:_** Quantized models take up less space, making them easier to store, transfer, and deploy across devices.

**_Reduced Memory Consumption:_** Lower precision formats reduce memory needs during both training and inference, enabling models to run on devices with limited memory.

It’s important to note that quantization may also lead to longer inference times despite reduced memory usage. For a deeper look into this trade-off, you can refer to benchmark results like those provided by [LitGPT](<https://github.com/Lightning-AI/litgpt/blob/main/tutorials/quantize.md>), which show the effects of quantization on both memory usage and inference speed. We also observed the longer inference speed with quantized models.

### QLoRA: Balancing Efficiency and Accuracy

Quantizing LoRA fine-tuning (QLoRA) offers a way to fine-tune large language models by combining LoRA’s efficiency in training a subset of parameters with the quantization of base weights, which saves memory during fine-tuning.

Lets get back to how our model structure would look like when fine-tuning with QLoRA (Figure 4):

![Figure 4 : Mistral-7B-Instruct-v0.1 structure after fine tuning with QLoRA prior to merging.](https://miro.medium.com/v2/resize:fit:700/1*uwJ7d8203EmCVTxrEhNUqw.png)

Focusing on the blue lines, each layer contains a `base_layer` quantized at 4 bits (indicated by the `Linear4bit` module), as well as `lora_A` and `lora_B` layers that remain in high precision (indicated by the `Linear` modules in green). This structure allows efficient training while maintaining precision where it matters for LoRA updates.

In many cases, you might expect a drop in model performance during fine-tuning due to the lower precision of weights in the forward pass. However, after fine-tuning, inference results should ideally be consistent, whether or not the LoRA weights are merged back into the base weights. In the non-merged model, inputs pass through both the base and LoRA layers, while in the merged model (after removing the LoRA layers in a process called “unloading”), inputs pass through a single layer with combined weights, theoretically yielding identical outputs. Unfortunately, this isn’t always the case. In the following sections, we’ll explore why incorrectly merge the LoRA weights can sometimes lead to unexpected accuracy drops and how to address this issue.

## Merge and unload

If we use this model directly for inference, the input tokens would be embedded and passed through multiple layers of the transformer, including both the quantized base layers and the LoRA layers. The final layer would produce output embeddings for each token, which would then be processed to generate the predicted tokens. This process, followed by decoding, yields the final text output.

However, for streamlined inference, we want to “merge and unload” the LoRA layers. In this step, we merge the LoRA layers (`lora_A` and `lora_B`) into the base layer via a linear transformation and then remove (or “unload”) the LoRA layers, as they’re no longer needed for inference.

```python import torchimport logginglogging.basicConfig(level=logging.INFO)logger = logging.getLogger(__name__)def calculate_lora_weights( rank: int, lora_alpha: float, lora_A: torch.Tensor, lora_B: torch.Tensor) -> torch.Tensor: """ Computes the LoRA (Low-Rank Adaptation) weights by scaling the matrix product of LoRA A and B matrices. Args: rank (int): The rank (r) used in LoRA. lora_alpha (float): Scaling factor for LoRA. lora_A (torch.Tensor): LoRA A matrix. lora_B (torch.Tensor): LoRA B matrix. Returns: torch.Tensor: The scaled LoRA weights. """ scaling_factor = lora_alpha / rank logger.debug(f"Calculating LoRA weights with scaling factor: {scaling_factor}") return (lora_B @ lora_A) * scaling_factordef merge_lora_weights( base_layer: torch.nn.Module, finetuned_layer: torch.nn.Module, rank: int, lora_alpha: float,) -> torch.nn.Module: """ Merges the base pretrained weights with LoRA weights into the finetuned layer. Args: base_layer (torch.nn.Module): The base pretrained layer. finetuned_layer (torch.nn.Module): The LoRA finetuned layer. rank (int): The rank (r) used in LoRA. lora_alpha (float): Scaling factor for LoRA. Returns: torch.nn.Module: The finetuned layer with LoRA weights merged. """ logger.info("Merging LoRA weights into the finetuned layer.") # Extracting input/output features and weights input_features = finetuned_layer.lora_A.default.in_features output_features = finetuned_layer.lora_B.default.out_features logger.debug(f"Input features: {input_features}, Output features: {output_features}") lora_A_weight = finetuned_layer.lora_A.default.weight lora_B_weight = finetuned_layer.lora_B.default.weight logger.debug(f"LoRA A shape: {lora_A_weight.shape}, LoRA B shape: {lora_B_weight.shape}") # Calculate the LoRA weight matrix lora_weights = calculate_lora_weights(rank, lora_alpha, lora_A_weight, lora_B_weight) # Merge LoRA weights with base weights pretrained_dtype = finetuned_layer.base_layer.weight.data.dtype with torch.no_grad(): logger.info("Adding LoRA weights to the pretrained base layer.") base_weight = finetuned_layer.weight finetuned_layer.weight.data += lora_weights.to( device=base_weight.data.device, dtype=pretrained_dtype ) logger.info("LoRA weights successfully merged.") return finetuned_layerdef unload_model(model: torch.nn.Module) -> torch.nn.Module: """ Unloads the model to free resources or return a reduced state. Args: model (torch.nn.Module): The input model to be unloaded. Returns: torch.nn.Module: The unloaded model. """ logger.info("Unloading the model.") return model.unload() ```

## The incorrect way to merge Base model weights with LoRA layers

The previous code demonstrates a common but incorrect approach to merging LoRA layers, which results in a discrepancy in model quality between pre-merge and post-merge states.

In theory, merging LoRA layers with the base model should not impact inference quality, as it is fundamentally a linear transformation. However, many developers rely on off-the-shelf `merge_and_unload` functions, such as [Hugging Face's implementation](<https://huggingface.co/docs/peft/main/en/package_reference/lora#peft.LoraModel.merge_and_unload>). While these functions follow the same merging logic—adding the _A_ _* B_ LoRA adjustments back into the `base_layer` weights—using them directly on a quantized model can lead to degraded quality in the fine-tuned model compared to inference with the unmerged layers.

### The Problem with Basic Merging on Quantized Models

What’s happening here is that we’re merging high-precision LoRA adjustments into a 4-bit quantized base layer. To illustrate why this approach is problematic, let’s walk through a simple example.

First, let’s generate a random float32 number, which we’ll call 𝒮:

```python import numpy as nps = np.float32(np.random.uniform(-1, 1))print("S:", s) ```

Suppose 𝒮 equals `-0.22289008`.

Next, let’s quantize 𝒮 to 4-bit precision, like what we need to do in model quantization.

We will follow a Uniform Quantization where the range of an input sequence is divided into number of equally spaced zones. That’s a straight forward normalization and scaling of the 𝒮 using the following formula.

* 𝓎ₙ is the quantized sequence
* 𝓍ₙ is the input sequence
*  _L_ is the levels of quantization calculated as 2ᵇ where _b_ is the number of bits used for quantization.

Assuming our quantization range is -1 to 1, with 4-bit quantization (16 levels ( ²⁴)), we will have:

``` quantization_levels = 16min_val, max_val = -1.0, 1.0quantized_s = np.round((s - min_val) / (max_val - min_val) * (quantization_levels - 1))print("Quantized S:", quantized_s) ```

After quantization, Quantized 𝒮 is `6.0`, which represents the quantized version of a scaler value of the base model’s weight.

Now, let’s assume we have a second float32 value, _G_ , resulting from fine-tuning with LoRA:

``` g = np.float32(np.random.uniform(-1, 1))print("G:", g) ```

Suppose _G_ equals `0.8382505.`

Using a basic merge approach, we would add _G_ (in its high-precision format) directly to the quantized 𝒮 (`6.0`), resulting in a merged weight of `6.8382505`. This result, however, fails to capture the true weight adjustment accurately because it combines values of very different precisions.

## Correct Merging: Dequantization-First Approach

To handle this correctly, we should first dequantize (the reverse process of quantization) 𝒮 back to its original float32 precision before merging as follow:

``` dequantized_s = (quantized_s / (quantization_levels - 1)) * (max_val - min_val) + min_valprint("Dequantized S:", dequantized_s) ```

For this randomly generated numbers, the dequantized 𝒮 would be approximately `-0.1999996`.

Now, when we merge 𝒮 and _G_ , we get `0.6382509`, a significant difference from the basic merge result of `6.8382505`

Let’s explore how this dequantization-first approach applies to a model with a frozen, 4-bit quantized base layer and high precision, float32, LoRA layers, as shown in Figure 5 below.

![Figure 5 : Mistral-7B-Instruct-v0.1 structure after fine tuning with QLoRA prior to merging](https://miro.medium.com/v2/resize:fit:700/1*KzGKeBP8lHiKr6fGbtXbFw.png)

In this model, we need to iterate over its layers and, when we come across a quantized to 4-bit layer, dequantize it back to float32. For our model, the specific layer requiring this dequantization is highlighted in the yellow box in the figure.

**Steps in the Dequantization-First Approach:**

1. **Identify Quantized Layers** : Loop through each layer and check if it’s a quantized layer, as indicated by the `bnb.nn.Linear4bit` instance.
2. **Dequantize Weights** : For each quantized layer, retrieve its quantization information from `quant_state` and use `bnb.functional.dequantize_4bit` to convert the 4-bit weights to a higher precision.
3. **Create a New Layer with Dequantized Weights** : Initialize a new `torch.nn.Linear` layer with the same input and output sizes as the original 4-bit layer, then assign the dequantized weights to this new layer.
4. **Replace the Old Layer** : Use `_get_submodules` from `peft.utils` to locate the parent module of the target layer, then replace the old quantized layer with the new high-precision module.

```python import bitsandbytes as bnbfrom peft.utils import _get_submodulesimport torchimport copyimport loggingfrom typing import Unionlogging.basicConfig(level=logging.INFO)logger = logging.getLogger(__name__)def dequantize_model( model: torch.nn.Module, dtype: torch.dtype = torch.float32, device: str = "cuda") -> torch.nn.Module: """ Converts all Linear4bit layers in the given model to standard PyTorch Linear layers with dequantized weights. Args: model (torch.nn.Module): The input model containing quantized layers. dtype (torch.dtype): The target data type for the dequantized weights (default: torch.float32). device (str): The target device for the new layers (default: "cuda"). Returns: torch.nn.Module: The model with Linear4bit layers replaced by standard Linear layers. """ logger.info("Starting dequantization process for the model.") layer_count = 0 # To count how many layers are dequantized with torch.no_grad(): for module_name, module_instance, in model.named_modules(): if isinstance(module_instance, bnb.nn.Linear4bit): logger.info(f"Dequantizing layer: {module_name}") # Deep copy the quantization state to preserve original module properties quantization_state: dict = copy.deepcopy(module_instance.weight.quant_state) logger.debug(f"Quantization state for layer {module_name}: {quantization_state}") # Dequantize the 4-bit weights and convert them to the desired dtype dequantized_weights: torch.Tensor = bnb.functional.dequantize_4bit( module_instance.weight.data, quant_state=quantization_state, quant_type="nf4" ).to(dtype) logger.debug(f"Dequantized weights shape for layer {module_name}: {dequantized_weights.shape}") # Create a new Linear layer with the dequantized weights new_linear_layer: torch.nn.Linear = torch.nn.Linear( in_features=module_instance.in_features, out_features=module_instance.out_features, bias=False, dtype=dtype ) new_linear_layer.weight = torch.nn.Parameter(dequantized_weights) new_linear_layer.to(device=device, dtype=dtype) # Replace the original module with the new one in the model parent_module: torch.nn.Module target_module: Union[torch.nn.Module, None] target_name: str parent_module, target_module, target_name = _get_submodules(model, module_name) setattr(parent_module, target_name, new_linear_layer) logger.info(f"Replaced {module_name} with dequantized Linear layer.") layer_count += 1 logger.info(f"Dequantization process completed. Total layers dequantized: {layer_count}") return model ```

After running this function, the base model will be fully dequantized, allowing it to be merged with the high-precision LoRA layers accurately.

Inspecting the model structure post merging and unloading, we would see LoRA layers disappearing with base layers appear in an unquatized as shown in Figure 6.

Once merged, the model can be saved and reloaded at either high or low precision, preserving the quality achieved during fine-tuning.

## Summary

Quantized LoRA (QLoRA) enables efficient fine-tuning of large models on limited resources by combining quantized base weights with LoRA adjustments. Directly merging LoRA adjustments into quantized layers can reduce accuracy due to precision mismatches. The solution is a **dequantize-first approach** , dequantizing base weights first, then merge LoRA updates, preserving accuracy without sacrificing memory efficiency. This method maintains fine-tuned performance and makes QLoRA ideal for resource-constrained environments.
