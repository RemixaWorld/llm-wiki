## Quick Recap: What Happens in the Forward Pass

As we covered in the [previous article](</@chris.p.hughes10/inside-openais-gpt-oss-how-production-moe-really-works-cfa5f6a23caa>), MoE replaces the standard feed-forward network (FFN) in a transformer with a router plus multiple expert FFNs:

```sql # Standard transformer FFNoutput = ffn(x) # All tokens use same network# MoE replacementscores = softmax(router(x)) # [batch, num_experts] - each token's affinity to each expertgate_weights, indices = topk(scores, k) # Select top-k expertsoutput = sum(gate_weights[i] * experts[indices[i]](x) for i in range(k)) # Weighted sum of selected expert outputs ```

The router is just a simple linear layer that learns which experts are good at which types of inputs. The `topk` operation selects the best k experts per token, and the outputs get combined using the softmax-normalized gate weights.

Now, let’s talk about training.

## The Key Insight

**The cross-entropy loss doesn’t change at all.** You’re still predicting next tokens exactly as you would with a dense model. The MoE-specific components are _auxiliary losses_ that get added on top:

![image](https://miro.medium.com/v2/resize:fit:691/1*ZINDPMwDPqJldNGWJkisAQ.png)

The primary learning objective — minimizing cross-entropy between predictions and targets — remains identical to dense transformer training. Everything MoE-specific is auxiliary.

## But Wait — How Can Gradients Flow?

This was my main point of confusion. If `topk` is non-differentiable, how does anything learn at all?

The answer lies in understanding exactly where gradients _do_ and _don’t_ flow:

![image](https://miro.medium.com/v2/resize:fit:1000/1*v_vr2XeCzroWMOJqcWhOxA.png)

The key insight is: **gradients flow through the expert selection probabilities and the selected expert FFN parameters — not through the selection itself.**

The expert selection probabilities (softmax outputs) ARE differentiable. The `topk` operation just masks some of them to zero, but the non-zero gates still pass gradients to their experts _and_ back to the router.

Let me make this concrete. Recall that the expert combination step looks like:

``` # From OpenAI's gpt-oss (simplified)t = torch.einsum("bec,be->bc", expert_outputs, expert_weights) ```

During the backward pass:

* **Selected experts** receive gradients, weighted by their probability values
* **The router** receives gradients through the expert probabilities
* **Non-selected experts** receive NO gradient — this is the problem we need to solve!

The discrete selection means you can’t ask “what if I’d picked expert 3 instead of expert 2?” But you _can_ still optimize the experts you did pick, and the router learns from the relative scores of the selected experts.

## The Collapse Problem: Why Auxiliary Losses Exist

Without any intervention, here’s what happens during MoE training:

1. Early in training, the router randomly assigns tokens to experts
2. Some expert (say, expert 0) happens to perform slightly better on a few tokens
3. The router learns to send more tokens to expert 0
4. Expert 0 gets more gradient updates, becomes even better
5. The router sends even MORE tokens to expert 0
6. **Positive feedback loop** : Eventually, 90%+ of tokens go to 1–2 “favourite” experts
7. Other experts receive almost no gradients → they “die”

The result? You’ve paid for 128 experts but only 2 are actually being used. This is called **expert collapse** or **routing collapse**.

Here’s what this looks like in practice:

![image](https://miro.medium.com/v2/resize:fit:700/1*YMQp60-IeMDUE36ds8wCVQ.png)

This is why auxiliary losses exist — not to change what the model learns, but to prevent this degenerate collapse during training.

## The Load Balancing Loss: How It Works

The most common auxiliary loss comes from the [Switch Transformer paper](<https://arxiv.org/abs/2101.03961>) (Fedus et al., 2022):

![image](https://miro.medium.com/v2/resize:fit:376/0*E7mdLID_4hVk3kds.png)

Where:

* `α` = balancing coefficient (typically 0.01)
* `N` = number of experts
* `fᵢ` = fraction of tokens actually routed to expert _i_ (hard assignment)
* `Pᵢ` = mean router probability for expert _i_ (soft probability)

If we break down the intuition, we can think of the terms as follows:

* `fᵢ` : “How many tokens did expert _i_ actually receive?”
* `Pᵢ` : “How much did the router _want_ to send to expert _i_?”
* `fᵢ `·`Pᵢ` : Penalizes experts with both high allocation AND high probability

The magic is in the gradient. Taking the derivative with respect to `Pᵢ`:

![image](https://miro.medium.com/v2/resize:fit:232/1*2qaWkF3VcCqLAfFouhsLwA.png)

**The gradient is proportional to how overloaded each expert is.**

* **Overloaded experts** → strong downward pressure on their router probabilities
* **Underloaded experts** → less pressure (or upward pressure from softmax normalization)

This creates a self-correcting feedback loop that counteracts the collapse tendency.

## Concrete Example

Let’s trace through a simple example with 4 experts and 8 tokens:

``` Router probabilities (Pᵢ = mean across tokens):Expert 0: 0.4 Expert 1: 0.3 Expert 2: 0.2 Expert 3: 0.1Actual routing (fᵢ = fraction of tokens routed):Expert 0: 0.5 Expert 1: 0.375 Expert 2: 0.125 Expert 3: 0.0 (4) (3) (1) (0 tokens!)Load balancing loss contribution per expert:Expert 0: 0.4 × 0.5 = 0.20 ← highest penalty (overloaded)Expert 1: 0.3 × 0.375 = 0.11Expert 2: 0.2 × 0.125 = 0.025Expert 3: 0.1 × 0.0 = 0.0 ← no penalty (but also no tokens!)Total: L_balance = 4 × (0.20 + 0.11 + 0.025 + 0.0) = 1.34 ```

The gradient will push hardest against Expert 0’s routing probability, encouraging the router to spread load more evenly.

## Real Implementation: HuggingFace Mixtral

Let’s look at how this is actually implemented. Here’s the load balancing loss function from [HuggingFace’s Mixtral implementation](<https://github.com/huggingface/transformers/blob/main/src/transformers/models/mixtral/modeling_mixtral.py>):

```python def load_balancing_loss_func( gate_logits: torch.Tensor, num_experts: int, top_k: int = 2) -> float: """ Computes auxiliary load balancing loss as in Switch Transformer. Implements equations (4)-(6) from the paper. """ if gate_logits is None: return 0 if isinstance(gate_logits, tuple): # Concatenate across all MoE layers gate_logits = torch.cat(gate_logits, dim=0) # Get routing decisions routing_weights = torch.softmax(gate_logits, dim=-1) # [tokens, num_experts] _, selected_experts = torch.topk(routing_weights, top_k, dim=-1) # [tokens, top_k] # Create expert mask: which experts were selected? expert_mask = torch.nn.functional.one_hot( selected_experts, num_classes=num_experts ) # [tokens, top_k, num_experts] # For each token, was expert i selected? (collapse top_k dimension) expert_mask = torch.max(expert_mask, dim=-2).values.float() # [tokens, num_experts] # f_i: fraction of tokens routed to each expert tokens_per_expert = torch.mean(expert_mask, dim=0) # [num_experts] # P_i: mean router probability for each expert router_prob_per_expert = torch.mean(routing_weights, dim=0) # [num_experts] # L = N * Σ(f_i * P_i) return torch.sum(tokens_per_expert * router_prob_per_expert) * num_experts ```

Compare this to the forward pass code we examined in the [previous article ](</@chris.p.hughes10/inside-openais-gpt-oss-how-production-moe-really-works-cfa5f6a23caa?sk=1be245eef1ef39db070fb860b9574d10>)— the routing logic is nearly identical, but here we’re computing statistics across all tokens rather than processing them through experts.

And here’s how it integrates into the training loop:

```python class MixtralForCausalLM(MixtralPreTrainedModel): def forward(self, input_ids, labels=None, output_router_logits=True, ...): # Standard forward pass through the model outputs = self.model( input_ids, output_router_logits=output_router_logits, ... ) # 1. STANDARD CROSS-ENTROPY LOSS (unchanged!) logits = self.lm_head(outputs.last_hidden_state) loss = F.cross_entropy( logits.view(-1, self.config.vocab_size), labels.view(-1) ) # 2. ADD AUXILIARY LOAD BALANCING LOSS if outputs.router_logits is not None: aux_loss = load_balancing_loss_func( outputs.router_logits, self.config.num_local_experts, self.config.num_experts_per_tok ) # Combine with small coefficient (typically 0.01) loss = loss + self.config.router_aux_loss_coef * aux_loss return loss ```

Notice how clean this is: the cross-entropy loss computation is identical to any dense model. The MoE-specific part is just an additive term.

## The Auxiliary Loss Dilemma

Here’s the tricky part — the auxiliary loss creates a fundamental trade-off:

* Too small α → experts collapse (not enough balancing pressure)
* Too large α → hurts model performance (balancing overwrites task signal)

The Switch Transformer paper recommends `α = 0.01` based on sweeping from `10⁻¹` to `10⁻⁵`. But finding the right balance is model and data dependent.

This trade-off motivated DeepSeek’s alternative approach…

## DeepSeek’s “Auxiliary-Loss-Free” Balancing

[DeepSeek V3](<https://arxiv.org/abs/2412.19437>) introduced a clever alternative that avoids the auxiliary loss dilemma entirely.

### The Problem with Auxiliary Losses

Recall the dilemma: auxiliary losses add gradients that compete with the task loss. Set α too high and you hurt model quality; set it too low and experts collapse. You’re always trading off.

### The Key Insight

What if we could influence _which_ experts get selected without adding any gradients to the loss function?

DeepSeek’s solution: **add a bias term to routing scores, but update it outside of backpropagation.**

```sql Standard routing: scores = sigmoid(x @ expert_centroids) → select top-k → outputDeepSeek routing: scores = sigmoid(x @ expert_centroids) biased_scores = scores + bias → select top-k → output ↑ Updated by simple rule, NOT by gradients ```

The bias makes overloaded experts less attractive (negative bias) and underutilized experts more attractive (positive bias). But critically:

1. **Selection** uses the biased scores (so load balancing happens)
2. **Gate weights** use the original unbiased scores (so gradients are clean)
3. **Bias updates** happen outside backprop (so no interference with task loss)

### How the Bias Update Works

After each batch, check how balanced the expert loads are:

``` # Pseudocode for bias updatefor each expert i: actual_load = (tokens routed to expert i) / total_tokens target_load = 1 / num_experts # e.g., 1/256 = 0.39% if actual_load > target_load: bias[i] -= γ # Expert is overloaded → make it less attractive else: bias[i] += γ # Expert is underused → make it more attractive ```

This is just a simple control loop — no gradients, no loss function, no hyperparameter balancing act.

Here’s a simplified implementation illustrating the core idea:

```python class DeepSeekMoERouter: def __init__(self, num_experts, gamma=0.001): self.expert_biases = torch.zeros(num_experts) # b_i for each expert self.gamma = gamma # update rate def forward(self, x, expert_centroids, top_k): # Compute affinities scores = torch.sigmoid(x @ expert_centroids.T) # [batch, num_experts] # Add biases for routing decision scores_with_bias = scores + self.expert_biases # Route based on BIASED scores _, selected = torch.topk(scores_with_bias, k=top_k, dim=-1) # But use UNBIASED scores for gating weights! gate_weights = scores.gather(-1, selected) # Important: no bias here gate_weights = gate_weights / gate_weights.sum(dim=-1, keepdim=True) # Update biases based on load (no gradient!) with torch.no_grad(): expert_counts = torch.bincount(selected.flatten(), minlength=len(self.expert_biases)) expert_load = expert_counts.float() / expert_counts.sum() target_load = 1.0 / len(self.expert_biases) self.expert_biases += self.gamma * (target_load - expert_load) return gate_weights, selected ```

### Confession From the DeepSeek Paper

Despite calling it “auxiliary-loss-free,” DeepSeek V3 still uses a small auxiliary loss! [From the paper](<https://arxiv.org/abs/2412.19437>):

_“We also incorporate a complementary sequence-wise balance loss… with a very small hyperparameter”_

Why? Batch-level balancing doesn’t guarantee sequence-level balance. At inference time, you can’t control what sequences arrive — if one sequence overwhelmingly favours certain experts, you get load imbalance even with batch-level balancing.

The honest answer: balancing is hard, and even clever approaches need backup mechanisms.

### Why This Works

The bias only affects the _discrete selection_ of which experts to use. It doesn’t affect the _continuous gate weights_ that get multiplied with expert outputs. Since gradients flow through gate weights (not through selection), the task loss gradients remain completely uncontaminated.

## Z-Loss: Stability for Router Softmax

One more auxiliary loss worth knowing: the **router Z-loss** from [ST-MoE](<https://arxiv.org/abs/2202.08906>):

```python def compute_router_z_loss(router_logits): """ Penalize large router logits for numerical stability. """ # log(sum(exp(logits)))² - keeps softmax denominator near 0 logsumexp = torch.logsumexp(router_logits, dim=-1) return torch.mean(logsumexp ** 2) ```

This keeps the softmax denominator (the log-sum-exp) close to 0, preventing numerical instability.

Why does this matter? Router softmax can produce very large logits, leading to:

* Numerical overflow/underflow
* Training spikes
* Unstable gradients

From training logs in several papers, removing Z-loss causes sporadic validation loss spikes where “the model just kind of goes crazy for a couple iterations.”

### **Is z-loss widely used?**

It’s recommended and commonly implemented in MoE frameworks, but adoption in production models is mixed. Qwen3 and Mixtral use auxiliary losses for stability (likely including z-loss or similar mechanisms). However, DeepSeek V3 moved away from _all_ auxiliary losses — including z-loss — in favour of their bias-based balancing approach; achieving “remarkably stable” training on 14.8T tokens without any irrecoverable loss spikes.

This suggests z-loss is a useful tool for stability, but not strictly necessary if you have other mechanisms (like careful FP8 precision handling, QK normalization, and bias-based balancing) in place.

## Putting It All Together

Here’s a simplified implementation demonstrating a complete training step; showing how all the losses combine:

```python def train_moe_step(model, batch, config): # Forward pass with router logits outputs = model( input_ids=batch['input_ids'], labels=batch['labels'], output_router_logits=True ) # 1. PRIMARY TASK LOSS (unchanged from dense models!) task_loss = outputs.loss # Cross-entropy # 2. LOAD BALANCING LOSS balance_loss = load_balancing_loss_func( outputs.router_logits, num_experts=config.num_experts, top_k=config.top_k ) # 3. OPTIONAL: Z-LOSS FOR STABILITY z_loss = compute_router_z_loss(outputs.router_logits) # 4. COMBINE total_loss = ( task_loss + config.balance_loss_coef * balance_loss # typically 0.01 + config.z_loss_coef * z_loss # typically 0.001 ) # Standard backward and optimize total_loss.backward() optimizer.step() return { 'task_loss': task_loss.item(), 'balance_loss': balance_loss.item(), 'z_loss': z_loss.item(), 'total_loss': total_loss.item() } ```

## Summary: What to Remember

![image](https://miro.medium.com/v2/resize:fit:700/1*rk9RzhgBcN2mwQ0dVBAhww.png)

Key takeaways:

1. **Cross-entropy is unchanged** — MoE doesn’t modify the primary learning objective
2. **Gradients flow through gate weights, not selections** — The `topk` is non-differentiable but doesn't block learning
3. **Auxiliary losses are regularizers** — They shape routing behaviour without directly supervising it
4. **Balancing is critical but tricky** — Too much hurts performance, too little causes collapse
5. **DeepSeek’s approach is elegant** — Separating selection from optimization avoids gradient interference
6. **Real implementations are messier** — Look at HuggingFace code to see edge cases around attention masks, multiple layers, etc.
