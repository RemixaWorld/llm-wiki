Microsoft recently released Phi-4-mini to the open-source, a 3.8-billion-parameter model with a focus on text understanding and generation. It is claimed that Phi-4-mini performs on par with models double its size on certain tasks, particularly in mathematics and coding. In our earlier study, we too compared the generation performance of Phi-4-mini against a few bigger models, including Phi-4 and DeepSeek-R1 7B in a _GraphRAG_ setup [1]. GraphRAG involves the use of knowledge graphs (KG) as a source of context or factual information for LLMs, and Phi-4-mini was found to perform well in comparison to those bigger models. It was only left behind on certain deeper reasoning questions.

During that study, it was observed that Phi-4-mini constructed KGs were far simpler than the other models. Its graphs were mostly disjointed. To further improve the utility of this model, enhancing the quality of KG construction may produce more relevant context to support its generation. This is especially crucial when the model is applied to a niche domain, whose information was not used during its training.

In this article, we will adopt the LlamaIndex framework and explore the options to customize the KG extraction and retrieval pipelines for Phi-4-mini as the language model of choice in a local GraphRAG setup. As for the domain of application, we will explore its viability in generating responses on the usage of the REST API service of a network performance monitoring (NPM) appliance. To host the KGs for this setup, Neo4j is an ideal choice. Not only it is an enterprise-grade graph DBMS, it boasts an intuitive interface with great visualizations enabling quick and insightful views into our data with absolute ease.

Let’s start by taking a closer look at the technology stack.

## 1.0 Technology Stack

For this study, it is performed on a MacBook M4 Pro (16 GPUs) with 24 GB RAM running MacOS Sequioa. The version of Python used was 3.12.9.

To store and query our KGs, the Neo4j graph DBMS is a natural choice. Its production-grade nature, exceptional ease of use and unparalleled visualization capability will provide us the front seat to appreciate and highlight the focus of this study. In [an earlier work](</local-llm-generated-knowledge-graphs-powered-by-local-neo4j-4111c5234993#b768>), the installation and setup of Neo4j was described in detail. The same steps were adopted here to setup the most recent release, Neo4j 2025.01.0.

As a best practice, we will create a virtual environment and activate the environment, as per below:

Similar to our other recent work, the AI framework `LlamaIndex` is chosen, as it has the full spectrum of modules and tools for data ingestion, indexing, retrieval and querying. It includes module `PropertyGraphIndex`, which simplifies KG construction from unstructured text as well as for retrieval. To enable Neo4j as a graph store, module `Neo4jPropertyGraphStore` and a Python driver for Neo4j, named `neo4j`, are used.

The `llama-cpp-python` package, which provides Python bindings for the `llama.cpp` libraries, will be used to host a local LLM. As for the language model, the quantized 8-bit [Phi-4-mini Instruct](<https://huggingface.co/microsoft/Phi-4-mini-instruct>) is adopted.

## 2.0 Customizing KG Extractors and Retrievers

To support the question-answering system workflow, it will involve the ingestion pipeline that includes the KG extractor, the KG query engine with the retrievers as well as LLM prompting with the retrieved context.

Let’s start by importing all the required libraries:

```python from llama_index.core import ( PropertyGraphIndex, SimpleDirectoryReader, StorageContext, Settings,)from llama_index.llms.llama_cpp import LlamaCPPfrom llama_index.embeddings.huggingface import HuggingFaceEmbeddingfrom llama_index.graph_stores.neo4j import Neo4jPropertyGraphStorefrom llama_index.core.indices.property_graph import ( SimpleLLMPathExtractor, LLMSynonymRetriever, VectorContextRetriever,)import re ```

This is followed by the instantiation of the `LlamaCPP` object with the path of our local model. We will also instantiate `HuggingFaceEmbedding` embeddings model. To allow this LLM and embeddings model to be used globally by LlamaIndex modules, let’s assign class `Settings` property `llm` to this LLM instance and property `embed_model` to the `HuggingFaceEmbedding` object. We then proceed to setup a graph store backed by the Neo4j database by instantiating a `Neo4jPropertyGraphStore` object. The following code listing captures these steps.

```json # load a local modelmodel_path='./models/Phi-4-mini-instruct.Q8_0.gguf'llm = LlamaCPP( model_path=model_path, temperature=0.0, max_new_tokens=2000, context_window=5096, model_kwargs={"n_gpu_layers": -1}, verbose=False)embed_model = HuggingFaceEmbedding()# associate the llm and embeddings model objects to Settings attributesSettings.llm = llmSettings.embed_model = embed_modelSettings.chunk_size = 512# initialize to the graph database connectionurl = "bolt://localhost:7687"username = "neo4j"password = "password"database = "neo4j"graph_store = Neo4jPropertyGraphStore( username=username, password=password, url=url, database=database,) ```

### 2.1 KG Construction

KG construction in LlamaIndex is achieved by employing one or more `kg_extractors` on each chunk, and attaching entities and relationships as metadata to each node. By default two extractors are used, which includes module `SimpleLLMPathExtractor`[2]. This extractor uses a LLM to parse single-hop paths from short sentences to generate triplets of _“subject, relationship, object”._ To ensure it works optimally, let’s tune the prompt per Phi-4-mini format as well as cater for our domain of application.

Here is the extraction prompt:

``` extract_prompt = ( "Some text is provided below. Given the text, extract up to " "{max_paths_per_chunk} " "knowledge triplets in the form of subject, predicate, object.
" "Avoid stopwords.
" "---------------------
" "Example:" "Text: Alice is Bob's mother." "Triplets:
Alice, is mother of, Bob
" "Text: API requests must include an Authorization header with an access token preceded by " "word 'Bearer', which expires after 15 minutes.
" "Triplets:
" "API request, requires, Authorization header
" "Authorization header, contains, access token
" "Access token, preceded by, word 'Bearer'
" "Access token, expires after, 15 minutes
" "---------------------
" "Text: {text}
" "Triplets:
")ep = f'<|system|>You are a helpful AI assistant.<|end|><|user|>{extract_prompt}<|end|><|assistant|>' ```

When this is used against Phi-4-mini, it typically produces a numbered list to triplets. To ensure the triplets are in the expected form for KG construction, let’s define function `parse_fn` to help with the response parsing:

```python def parse_fn(response_str: str) -> list[tuple[str, str, str]]: # separate into lines lines = response_str.split("
") # remove preceding line numbers lines = list(set([re.sub(r'^\d*\\.\s*','',line) for line in lines])) # list of lists with 3 elements initially capitalized triplets = [[item.strip().capitalize() for item in line.split(',')] for line in lines if line.count(',') == 2] return triplets ```

The first comprehension in this function produces a list of strings without any preceding numbers or whitespaces. Phi-4-mini sometimes generates a lot of duplicate triplets, and by using the `set` conversion and back helps to address that. The list of triplets are formed by splitting on a comma for any string with exactly two commas. Each element of the triplet is stripped of whitespaces and initially capitalized. With the prompt wrapped in Phi-4-mini format and the parsing function, we can complete `kg_extractor` instantiation as per below:

``` kg_extractor = SimpleLLMPathExtractor( extract_prompt=ep, parse_fn=parse_fn,) ```

With this extractor, the ingestion pipeline can now be defined as shown next:

``` kg_index = PropertyGraphIndex.from_documents( documents, max_triplets_per_chunk=10, kg_extractors=[kg_extractor], property_graph_store=graph_store,) ```

Let’s proceed with customizing the context retrieval and querying pipeline.

### 2.2 KG Retrieval and Querying

By default, LlamaIndex uses two modules to assist with context retrieval from KGs, namely modules `LLMSynonymRetriever` and `VectorContextRetriever`. The former informs its retrieval based a LLM generated list of keywords or synonyms, which is a good candidate for tuning per our LLM of choice.

Here is the retrieve prompt, based on the default LlamaIndex retrieve prompt, specified per Phi-4-mini format:

``` retrieve_prompt = ( "Given some initial query, generate synonyms or related keywords up to {max_keywords} in total, " "considering possible cases of capitalization, pluralization, common expressions, etc.
" "Provide all synonyms/keywords separated by '^' symbols: 'keyword1^keyword2^...'
" "Note, result should be in one-line, separated by '^' symbols." "----
" "QUERY: {query_str}
" "----
" "KEYWORDS: ")rp = f'<|system|>You are a helpful AI assistant.<|end|><|user|>{retrieve_prompt}<|end|><|assistant| ```

This prompt would produce a list of synonyms delimited by ‘^’ in a single line, and with Phi-4-mini, at times it responds with many duplicates as mentioned earlier. To help with parsing the response, let’s define the parsing function as per below:

```python def parse_fn_r(output: str) -> list[str]: matches = list(set(output.strip().split("^"))) return [x.strip().capitalize() for x in matches if x.strip()] ```

This function helps to split the keywords, remove any duplicates and whitespaces as well as initially capitalize them for consistency to be used for KG retrieval as part of `LLMSynonymRetriever`, as shown further:

``` synonym_retriever = LLMSynonymRetriever( kg_index.property_graph_store, include_text=True, synonym_prompt=rp, output_parsing_fn=parse_fn_r, max_keywords=10, # the depth of relations to follow after node retrieval path_depth=2,) ```

Since the Neo4j database also supports vector queries, let’s use `VectorContextRetriever` to retrieve nodes based on their vector similarity, and then to fetch the paths connected to those nodes, as our second retriever:

``` vector_retriever = VectorContextRetriever( kg_index.property_graph_store, include_text=True, similarity_top_k=2, path_depth=1,) ```

As the retrievers are ready, lets define the query engine to include them:

``` kg_keyword_query_engine = kg_index.as_query_engine( sub_retrievers=[synonym_retriever,vector_retriever],) ```

With the definition of the query engine, it’s time to complete the querying pipeline:

``` query = 'State the REST api version of AppResponse that should be used to handle decryption of TLS traffic using DH ciphers.'llm_prompt = f'<|system|>You are a helpful AI assistant.<|end|><|user|>{query}<|end|><|assistant|>'response = kg_keyword_query_engine.query(llm_prompt)print(f'Query: {query}
Response: {response.response}') ```

We are now ready for experimentation. How does such customization effect the constructed KGs? Let’s find out!

## 4.0 Closing Thoughts

Microsoft released Phi-4-mini, a small language model targeted toward resource constrained environments. For a small model, it boasts a good generative performance. To adopt a public model such as Phi-4-mini to a niche domain, some level of adaptation is necessary. GraphRAG is a popular approach where documents are ingested and represented as knowledge graphs, and later retrieved to serve context to ground a model’s generation performance as well as minimize its hallucinations. To handle these graphs efficiently, we adopted Neo4j graph DBMS. As a positive side-effect, Neo4j web UI supports a rich query language along with exceptional visualizations to allow insightful views of this data.

In this article, we looked at how to customize LlamaIndex ingestion as well as retrieval pipelines to support Phi-4-mini. For the ingestion pipeline, we adapted the extract prompt and response parsing function of module `SimpleLLMPathExtractor`, and for retrieval, we modified the same aspects of `LLMSynonymRetriever` in a similar fashion. With the former change, the resulting knowledge graphs were a lot more connected with meaningful entities and relationships related to the domain. With these better quality graphs, the quality of retrieval and the quantity of relevant source nodes found to support generation were consistently better.

With this GraphRAG setup, Phi-4-mini was found to generate complete curl commands for accessing the REST API service of a NPM appliance rather ably. Even though the generative performance improved with the customization, the model was not able to completely avoid hallucinations.
