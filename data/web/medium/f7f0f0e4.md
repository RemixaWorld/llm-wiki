Reading Tables with RAG

As I have explained in my articles about search (articles [1](<https://medium.com/p/055b4b940fb2>) and [2](<https://medium.com/p/ba5d0805ded9>)), many enterprise use cases for LLMs are search problems. This search problem is solved through Retrieval-Augmented Generation, where we deliver data to a Large Language Model while they’re answering a question.

We know that the [RAG system](<https://www.kommunicate.io/blog/rag-in-customer-service-chatbot/>) can be inefficient in several cases. For example, if your corpus is sufficiently large with many values, it will need help to give you accurate results. This is because we offer the data we get from RAG to Large Language Models with their context-based limitations.

This becomes more challenging with tables. Let’s say you have a table of 200 rows and 200 columns. You’re dealing with 40,000 units of data, which can be computationally expensive. In an enterprise use case, this is a small table.

So, as scale increases, you see diminishing returns. RAG systems are optimized for text retrieval, so structured data becomes a different proposition altogether.

In this article, we’re going to talk about the RAG process, the problem with table-based RAG, and some new innovative approaches that can help your [AI chatbot](<https://www.kommunicate.io/product/generative-ai-chatbot/>) systems asses tables.

## What is RAG?

Retrieval Augmented Generation is a process where the relevant answer to a question is supplied to an LLM when answering a question. This is beneficial for two reasons:

1. **Up-to-date Data —** The RAG systems can collect current data from your CRM systems and other places and provide up-to-date data to the LLM.
2. **Targeted & Specific Answers— **Because these chatbots get relevant, targeted information, your customers also get relevant, targeted answers.
3. **Contextual Information** — When your customers ask a question about your business, they want contextual answers to their questions. This is possible with the RAG system, which supplies relevant information during inference.

So, we know why we use RAG. Let’s discuss how it works.

## How does RAG Work?

Press enter or click to view image in full size

The RAG Process

Retrieval-augmented generation works in three steps:

1. **Document Processing —** Documents are chunked into small pieces of information and then [embedded](<https://www.kommunicate.io/blog/vector-embeddings/>) and stored in a vector store.
2. **Query Processing —** The same embedding model encodes the user’s question, and then a retriever searches the vector store for documents relevant to the query. These matching documents are then ranked by relevance.
3. **Response Generation —** The retriever model adds relevant documents to the context window for the LLM. The LLm answers the question based on the user query and supplied documents.

While the RAG process seems intuitive, there are several points where it could fail, mainly when you deal with tables within documents.

## Why does RAG Struggle with Tables?

Ultimately, the RAG system supplies data to an LLM to help it answer a user question. In the case of tables, this becomes complex because:

1. **Context Window Limitations —** Most enterprise businesses opt for Small Language Models for their specificity and fast responses. While this is beneficial, it also creates a smaller context window through which an LLM can get data.
Now, even a tiny 200*200 table would have 40000 elements and cross the GPT 3.5 Turbo limit of 4000 tokens by some distance.
2. **Lost-in-the-Middle —** The latest models have bigger context windows. For example, GPT 4-o-Mini has a 128k context window. But, when you provide a lot of data to an LLM for answering, it needs help comprehending everything. This creates a [**lost-in-the-middle**](<https://arxiv.org/abs/2307.03172>)**** problem where LLMs don’t use the middle part of a dataset when answering questions.
3. **Text-Centric Approach —** RAG, as an information-retrieval system, has been designed for text, so it struggles with numerical and categorical data usually available on tables.
4. **Table Structure —** Existing methods can’t parse the intricate table structures, especially with larger tables.
5. **Inefficient Encoding of Rows and Columns —** Encoding entire tables is very expensive. If you want to compress the tables, they can lose their semantic meaning, mainly if the table contains numeric values.

So, we need help. Many official documents and websites use tables to convey information, but RAG can’t process them well.

## [Helping RAG Read Tables: CORAG](<https://arxiv.org/abs/2411.00744>)

Let’s understand the table in the RAG problem more intuitively here:

For a corpus of text, C, you have n chunks, which can be divided into n number of tokens, and you set the number of tokens.

When someone asks a question, the RAG system will feed the LLM x amount of ranked chunks. The language model will be able to answer the question correctly if these chunks are:

1. Fitting into the computational cost constraint
2. Maximally relevant to the query

So, the problem becomes an **optimal chunking optimization** problem and can be defined with.

Here, U is the utility score, the cost is the current cost of the encoding, and B is the cost constraint. So, the idea is to find the maximum utility of a chunk combination that doesn’t surpass the cost constraints.

Here, we need an algorithm that lets us sample every path and choose the path that a reranker model thinks is the most beneficial. This is done using a Monte Carlo Tree Simulation where

* **Exploration** is encouraged using the Upper Confidence Bound algorithm.
* **Cost Control** is implemented to prevent selecting combinations that exceed our budgets.

Additionally, they also add a configuration module that determines:

* The number of iterations
* Cost assigned
* How much to explore?

Since this configuration module helps you determine the parameters for the MCTS search, we need to understand that.

## Determining the Configuration

The configuration agent is trained with joint loss functions that help it understand different domains of questions. For example, it will know that “How to make salad dressing” and “Who is the President-Elect for U.S.A.?” are different questions.

They do this using different re-rankers where positive pairs are query embeddings where the same re-ranker is optimal and are paired together and vice-versa.

And then during inference:

1. **Query Embeddings:** Your user’s questions are embedded.
2. **Feature Mapping** — These embedded queries are passed through a 3-layered network. This network is then used to predict the re-ranker and the MCTS configuration parameters.

## [Helping RAG Read Tables: Table RAG](<https://www.semanticscholar.org/reader/07205fbe57ab05c561faaa5d16d5e59e48b85bfc>)

Let’s take a table and try to understand its components. Usually, when someone asks a question to a table, they want the answer from a particular column or cell.

TableRAG tries to optimize this operation by changing how tables are encoded.

This takes place in three parts:

1. **Query Division** — Each user query is divided into two parts. First, we find the category or schema it wants to evaluate to find the particular column we want to encode, and then we find the particular value the question wants to evaluate and find a particular cell.
2. **Schema Retrieval** — First, the model fetch takes your query and finds the column names that correspond to it. These column names are then matched to the query to determine relevance.
Each time the schema is retrieved, it has the column name (Self-explanatory), data type (integer, decimal, or categorical), and examples (maximum and minimum for numerical values, three most frequent terms for categorical ones).
3. **Cell Retrieval —** The schema from the first step is used to find column-value pairs. These are then matched with the encoded queries, and the top-K retrieval results for each query are chosen.

This immediately reduces the complexity of the operation. Your retriever is not searching a matrix that spans the entirety of your table; it’s doing a basic search through an array. Also, this creates specific benefits.

## Benefits and Results

Distinct cell identification has two major benefits in the context of RAG:

1. Your language models can now accurately detect the presence of specific keywords.
2. These specific cells are now contextually associated with the column names.

## Parting Words

As enterprises increasingly rely on RAG systems for their AI applications, handling tabular data efficiently becomes crucial. While effective for text, the traditional RAG approach faces significant challenges when dealing with tables — from context window limitations to inefficient encoding of rows and columns. However, recent research has provided promising solutions to these challenges.

CORAG addresses the fundamental optimization problem in RAG by using Monte Carlo Tree Simulation to intelligently select and combine chunks of information while maintaining cost constraints. Its configuration module adapts to different queries, resulting in more accurate answers with lower computational costs.

TableRAG takes a different but complementary approach by reimagining how tables are processed. Splitting queries and implementing a two-step retrieval process — first for schema, then for specific cells — it significantly reduces computational complexity while improving accuracy. This method shows particular promise for enterprise applications where large tables are common.

These advancements suggest that the future of RAG systems lies not in treating all data uniformly but in developing specialized approaches for different data structures. As organizations deal with increasingly complex and varied data formats, such targeted solutions will become essential for building efficient and accurate AI systems.
