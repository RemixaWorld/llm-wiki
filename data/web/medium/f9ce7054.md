Imagine this scenario:

> You’re part of a generative AI team at a company with access to every major LLM on the market. You’ve even fine-tuned and deployed a few models locally for proprietary use cases.
>
> But every month, your team’s cloud budget is getting wrecked.
>

>
> Worse, you discover that every team is building their own wrappers for each LLM API. Swapping one model for another (say, Fireworks AI → DeepSeek) isn’t as easy as flipping a switch — it means rewriting code, debugging new interfaces, and adjusting prompts.

“I can’t be the only person facing this,” you think — and you’re absolutely right.

## About LiteLLM

Born out of the illustrious [Y Combinator program](<https://www.ycombinator.com/>), **LiteLLM** is a lightweight, powerful abstraction layer that **unifies LLM API calls** across providers — whether you’re calling OpenAI, Anthropic, Mistral, Ollama, or your own local GGUF models.

It also supports **cost tracking, admin dashboards** , model fallback, caching, and more — making it easy to run GenAI systems at scale.

Even better? It’s open-source, comes with a Python SDK, and has a great self-hosted proxy server solution to fit enterprise or hybrid-cloud deployments.

## Introducing LiteLLM’s Python SDK

Why “lite”? Because **LiteLLM** is a _lightweight_ wrapper that makes working with multiple LLM providers feel as simple as working with OpenAI.

It standardizes different LLM APIs into a **single, OpenAI-compatible interface** — so you can treat any model (even local ones like Ollama) as if it were an OpenAI ChatCompletion object.

That means no new method names to learn. No specialized wrappers to write. Just plug-and-play.

```python from litellm import completiontools = [ { "type": "function", "function": { "name": "get_current_weather", "description": "Get the current weather in a given location.", "parameters": { "type": "object", "properties": { "location": { "type": "string", "description": "The city and state, e.g. San Francisco, CA", }, "unit": { "type": "string", "enum": ["celsius", "fahrenheit"], "description": "The unit of temperature.", }, }, "required": ["location"], } } }]messages = [{"role": "user", "content": "What's the weather like in Boston today?"}]response = completion( model="ollama/llama3.1", messages=messages, tools=tools)print(response.choices[0].message.tool_calls[0].function) ``` ```json Function(arguments='{"location": "Boston, MA", "unit": "fahrenheit"}', name='get_current_weather') ```

**In this example** , we used a **Llama 3.1** model deployed locally via **Ollama** — but [LiteLLM supports **100+ models**](<https://docs.litellm.ai/#call-100-llms-using-the-openai-inputoutput-format>) across cloud providers, open-source ecosystems, and self-hosted deployments.

It’s become such a foundational piece of the ecosystem that frameworks like **CrewAI** and **Giskard** rely on LiteLLM as their **default LLM abstraction**. When you define an LLM in CrewAI, you’re actually instantiating a LiteLLM class under the hood — powering all the agentic behavior.

Let’s walk through how to create an agent using LiteLLM in LlamaIndex — my favorite orchestration framework.

```python import nest_asynciofrom llama_index.llms.litellm import LiteLLMfrom llama_index.core.agent.workflow import ReActAgent, AgentStreamfrom llama_index.core.tools import FunctionToolnest_asyncio.apply()def add(a:int|float, b:int|float) -> int|float: """Adds 2 integers or floats""" return a+bllm = LiteLLM("ollama/deepseek-r1:latest")agent = ReActAgent( tools=[FunctionTool.from_defaults(add)], llm=llm)handler = agent.run("What is 21.921 + 23.21?")async for event in handler.stream_events(): if isinstance(event, AgentStream): print(event.delta, end="", flush=True) ```

The best part? You can switch models on the fly by just changing the string inside the `LiteLLM` object (or the `completion`method in the first example) — everything else stays exactly the same.

Okay, so this solves the second problem: developers reinventing the wheel by writing their own wrappers.

Truth be told, more LLM service providers (except _ahem_ AWS Bedrock 😤) are gradually adopting OpenAI-compatible APIs. So over time, this deviation from OpenAI API issue will improve — but until then, **LiteLLM offers a clean, unified interface that works today.**

## Introducing LiteLLM Proxy Server

The LiteLLM Proxy Server tackles the biggest problem head-on: managing multiple LLMs, embeddings, and guardrails across different use cases — all in one place.

The idea is simple: spin up a central proxy server to expose every model you use. Want to keep costs under control?

✅ Set request-per-minute limits per model (especially for pricier ones)

✅ Generate API keys per model, team, or user — so you know who’s using what

✅ Built-in monitoring helps you trace failed requests and debug quickly

And the best part? **Setting up your own LiteLLM proxy server is easier than you think.** It supports multiple deployment options out of the box:

🐳 **Docker** — use LiteLLM’s pre-built image or build from the pip package

☁️ **Terraform** — provision infrastructure as code

☸️ **Kubernetes** — run the server at scale

🔧 **Helm Charts** — deploy Kubernetes services using a streamlined interface

Of these, I only use Docker regularly. My Kubernetes experience is limited to what I’ve picked up from online courses — and I’ve never touched Helm Charts or Terraform.

Which is why I decided to challenge myself and spin up my own LiteLLM proxy server using **Helm Charts**.

## What are Helm Charts?

**Helm Charts** are essentially **package managers for Kubernetes,** an open-sourced container orchestration platform that handles load balancing, deployment, and scaling of containers across a cluster of machines. Instead of writing raw YAML files from scratch every time, Helm allows you to:

* 📦 Define **reusable templates** and configuration values
* 🚀 **Install, upgrade, and version-control** Kubernetes applications
* 💡 Deploy complex systems like LiteLLM Proxy with just **one command**

This makes Helm especially useful in production setups, where **consistency** , **reusability** , and **versioning** are critical.

### 🛠️ Configure your values.yaml

Before we do anything we should inspect the helm charts folder. In your folder you should see something similar to this:

What we need to do is edit the `values.yaml` file to include the LLMs that we want to host. To do this, locate the `proxy_config` section and specify the models you want to host, as well as their provider-specific connection details (for e.g. API keys) under `model_list`:

```yaml proxy_config: model_list: # At least one model must exist for the proxy to start. - model_name: llama3.1-8b litellm_params: model: ollama/llama3.1 api_base: http://host.docker.internal:11434 - model_name: qwen2.5-7b litellm_params: model: ollama/qwen2.5 api_base: http://host.docker.internal:11434 ```

> 💡 **Tip** : You can also use <http://localhost:11434> as your api_base — that’s the default Ollama endpoint.

Notice how the model references use the `{provider}/{model_name}` format — just like the LiteLLM Python SDK.

### 🔐 Add Admin Credentials

To access the LiteLLM Proxy UI and administer your proxy server, add the following environment variables under the envVars section:

```yaml envVars: PROXY_MASTER_KEY: sk-1234 UI_USERNAME: admin UI_PASSWORD: admin ```

* `PROXY_MASTER_KEY`: This is your admin key — it gives you full control over virtual keys, users, budgets, and usage tracking. Store this securely; if lost, you’ll be locked out of the admin routes.
* `UI_USERNAME` and `UI_PASSWORD`: These are the credentials you’ll use to log into the proxy dashboard.

### 🗄️ About the Database

If you scroll further in values.yaml, you’ll also see a **PostgreSQL configuration** block.

The Helm chart automatically spins up a database using the credentials defined here — no need to set up your own backend separately. ✅

## ⚠️ It’s Not All Smooth Sailing

While LiteLLM Proxy works beautifully in most use cases, I did run into some hiccups when integrating with **LangGraph** and **LlamaIndex** agents.

### 🌀 LangGraph: The Tool Loop Spiral

When I created an agent with LangGraph, the tool was called endlessly — clogging up my stdout.

Okay, not _endlessly_ — the proxy’s request-per-minute limit (5 RPM in my case) throttled it. So every minute, it would just try again another 5 times. 😅

Here’s a simplified version of my LangGraph code:

```python from langchain_core.tools import toolfrom langgraph.prebuilt import create_react_agent@tooldef get_weather(city: str) -> str: """Get weather for a given city.""" return f"It's always sunny in {city}!"agent = create_react_agent( model = langchain_llm, tools=[get_weather], prompt="""You are a helpful assistant. When you need to use a tool:1. First, call the appropriate tool2. Wait for the tool result3. Then provide a complete response using the tool resultAlways provide a text response after using any tool. Never return empty content.Example:User: "What's the weather in Singapore?"Assistant: I'll check the weather in Singapore for you.[calls get_weather tool]Tool result: "It's always sunny in Singapore!"Assistant: Based on the weather information, it's always sunny in Singapore!""")response = agent.invoke( { "messages": [ { "role": "user", "content": "What is the weather in Singapore?" } ] }, debug=True) ```

The agent calls the tool to eternity (capped at 5 requests per minute )— and beyond.

### 🤖 LlamaIndex: Returns Tool Call as Raw JSON

With **LlamaIndex** , the agent didn’t invoke the tool at all. It returned the intended tool call as a plain string — no actual execution.

* With LlamaIndex, the agent simply returns the tool call as a string without actually calling the tool:

```python from llama_index.core.agent.workflow import FunctionAgentfrom llama_index.core.tools import FunctionTooldef add(a: int | float, b: int | float) -> int|float: """Use this tool to add 2 integers or floats""" return a + bagent = FunctionAgent( llm=llamaindex_llm, tools=[FunctionTool.from_defaults(add)])response = await agent.run("What is 76+12?")print(str(response))# Output:# '{"name": "add", "arguments":{"a": 76, "b": 12}}' ```

So the agent _knew_ it needed the tool… but stopped short of actually calling it.

## 🚨 Why This Happens

To be fair, all three of these libraries — **LangGraph** , **LlamaIndex** , and **LiteLLM** — are in hyper-growth mode. Each pushes 2–3 releases **per week** on GitHub. That pace makes integration bugs inevitable.

I’ve raised these issues with the LiteLLM core team, and I’m hopeful for better interop down the line.

## 🤔 Thinking About What We Just Did

With just one solution — **LiteLLM Proxy** — we tackled two major pain points in enterprise GenAI:

* ✅ **Budget overruns**
* ✅ **Tech debt** from writing too many custom wrappers

And that’s no small feat.

### 🧩 The OpenAI API Compatibility Problem

OpenAI API compatibility might seem like a solved problem, but in reality, **it’s far from trivial**.

Even though many vendors have made their APIs _OpenAI-like_ , frameworks like **LangChain** and **LlamaIndex** still write **custom wrappers** for each provider. Why?

Because OpenAI’s API evolves rapidly — often in ways that break assumptions or behaviors.

To address this, LlamaIndex even introduced a special LLM class called `OpenAILike — `a [thin wrapper](<https://docs.llamaindex.ai/en/stable/api_reference/llms/openai_like/>) designed to work with any model that exposes OpenAI-style APIs. It’s a clever abstraction, but it still requires effort to implement and maintain.

### 🔁 Continuous Change = Continuous Breakage

Here’s just one example:

The [completions API is now deprecated](<https://platform.openai.com/docs/guides/completions>) in favor of `chat.completions.create()` — a subtle shift that broke compatibility for libraries relying on the old style.

Even the responses API is new — and isn’t supported by most wrappers yet.

It is also not uncommon to code out your own LLM deployment on FastAPI — now you’re the one [coding out OpenAI endpoints](</data-science/how-to-build-an-openai-compatible-api-87c8edea2f06>) to make the deployment OpenAI API compatible.

### 🧘 LiteLLM: Calm in the API Chaos

LiteLLM sits in the middle of all this chaos and just says:

> _“Use the OpenAI SDK. I’ll handle the differences.”_

It acts as a normalization layer so that no matter which LLM or provider you choose — Anthropic, Groq, Ollama, Fireworks, Together, DeepSeek — you write once, and route as needed. LiteLLM’s continued success in handling these changes have seen it adopted by popular frameworks like CrewAI and Giskard.

### 🛠️ The Centralized Admin Problem

Before LiteLLM, building a proper admin layer meant rolling your own:

* Proxy servers
* Virtual key systems
* Rate limiting logic
* Budget monitoring dashboards

Now? LiteLLM Proxy gives you all of that — **open-source** and ready to deploy. And thanks to its OpenAI-compatible endpoints, it even works seamlessly with your favorite SDKs (yes, **AzureOpenAI** is just a subclass of OpenAI’s SDK).
