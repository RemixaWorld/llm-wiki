Large language models (LLMs) are increasingly being applied in novel ways in areas like medical diagnosis, IT alert triaging and categorization, network operations and product support. These generically pretrained models, however, perform less favorably in such niche domains, and often suffer from hallucinations. Retrieval-Augmented Generation (RAG) is a popular and effective approach to _adapt_ LLM to one’s domain. However, this approach does not understand nor consider knowledge embedded within the vectorized documents during chunk retrieval.

On the contrary, a _knowledge graph_ is a knowledge base that uses a graph-structured data model to represent data. As per Wikipedia, knowledge graphs store interlinked descriptions of entities, like objects, events, situations or concepts, while encoding the semantics or relationships underlying these entities. With the increasing generation capability of LLMs, LlamaIndex, a popular AI framework library, took advantage of this capability to automatically generate such knowledge graphs from unstructured documents as well as provide support to efficiently query those graphs.

In this article, we will explore the generation of knowledge graphs for question-answering (QA) with module `PropertyGraphIndex`, which recently usurped the deprecated module `KnowledgeGraphIndex`, but mostly maintains the original usage pattern. This knowledge graph-inspired QA system will then be customized for the maximum paths off chunks, verbosity of the generated nodes as well as experimented using five different local LLMs to arrive at an optimal performance. With an application focus on resource-constrained devices, the chosen LLMs for our comparative experimentation will involve quantized-versions of Mistral 7B, Llama-3 8B, Phi-3 3.8B, TinyLlama 1.1B and Gemma-2 9B.

### 1.1 `PropertyGraphIndex`: How it works

A graph generated using `PropertyGraphIndex` is a knowledge collection of labeled nodes with properties (i.e. metadata), linked together by relationships resulting in structured paths [1]. `PropertyGraphIndex` provides key orchestration around:

* constructing a graph
* querying a graph

Knowledge graph construction in `LlamaIndex` works by performing extractions using one or more _kg_extractors_ on each document chunk, and attaching entities and relations as metadata to each node. Any number of extractors can be linked here, and they will get applied independently. By default, `SimpleLLMPathExtractor` with a default per-chunk maximum paths of 10, and `ImplicitPathExtractor` are adopted. The former extractor extracts short statements using an LLM with a suitable prompt, and parses single-hop paths with format (entity1, relation, entity2), also called _triplets_. It uses the following [default prompt template](<https://github.com/run-llama/llama_index/blob/4fa2d2bfd684baaf0916105850a89f7437330fb4/llama-index-core/llama_index/core/prompts/default_prompts.py#L331>), which can be customized using class parameter `extract_prompt`:

``` DEFAULT_KG_TRIPLET_EXTRACT_TMPL = ( "Some text is provided below. Given the text, extract up to " "{max_knowledge_triplets} " "knowledge triplets in the form of (subject, predicate, object). Avoid stopwords.
" "---------------------
" "Example:" "Text: Alice is Bob's mother." "Triplets:
(Alice, is mother of, Bob)
" "Text: Philz is a coffee shop founded in Berkeley in 1982.
" "Triplets:
" "(Philz, is, coffee shop)
" "(Philz, founded in, Berkeley)
" "(Philz, founded in, 1982)
" "---------------------
" "Text: {text}
" "Triplets:
") ```

Similarly, knowledge graphs can be queried in several ways to retrieve nodes and paths. Furthermore, LlamaIndex allows us to combine several node retrieval methods at once. By default, `LLMSynonymRetriever` and `VectorContextRetriever` (if embeddings are enabled) are used. `LLMSynonymRetriever` takes the query, and generates keywords and synonyms with the help of LLM and retrieves nodes along with the paths connected to those nodes. It uses the following [default prompt template](<https://github.com/run-llama/llama_index/blob/4fa2d2bfd684baaf0916105850a89f7437330fb4/llama-index-core/llama_index/core/indices/property_graph/sub_retrievers/llm_synonym.py#L19>), which can be customized using class parameter `synonym_prompt`:

``` DEFAULT_SYNONYM_EXPAND_TEMPLATE = ( "Given some initial query, generate synonyms or related keywords up to {max_keywords} in total, " "considering possible cases of capitalization, pluralization, common expressions, etc.
" "Provide all synonyms/keywords separated by '^' symbols: 'keyword1^keyword2^...'
" "Note, result should be in one-line, separated by '^' symbols." "----
" "QUERY: {query_str}
" "----
" "KEYWORDS: ") ```

`VectorContextRetriever` retrieves nodes based on their vector similarity, and then fetches the paths connected to those nodes.

We are now ready to look at employing `PropertyGraphIndex` to develop a basic QA system.

## 2.0 QA System Implementation

Let’s develop a system to read pdf documents from a local directory, generate knowledge graphs and query for chosen questions. Firstly, import all the required modules.

```python from llama_index.core import ( PropertyGraphIndex, SimpleDirectoryReader, Document, StorageContext, load_index_from_storage, Settings,)from llama_index.llms.llama_cpp import LlamaCPPfrom llama_index.embeddings.huggingface import HuggingFaceEmbeddingfrom llama_index.core.graph_stores import SimpleGraphStorefrom llama_index.core.indices.property_graph import SimpleLLMPathExtractor ```

Since LLM is central to knowledge graph generation and querying, let’s now instantiate a `LlamaCPP` object to load the required language model from local directory _./models/_. We will also instantiate the selected embeddings model. To allow this LLM to be used globally by LlamaIndex modules, assign class `Settings` property `llm` to this LLM instance and the embeddings model. Otherwise, LlamaIndex will try to reach OpenAI, by default. The following code extract summarizes these steps:

```json llm = LlamaCPP( model_path='./models/mistral-7b-instruct-v0.3.Q2_K.gguf', #model_path='./models/Llama-3-Instruct-8B-SPPO-Iter3-Q2_K.gguf', #model_path='./models/Phi-3-mini-4k-instruct-q4.gguf', #model_path='./models/tinyllama-1.1b-chat-v1.0.Q5_K_M.gguf', #model_path='./models/gemma-2-9b-it-Q2_K.gguf', temperature=0.1, max_new_tokens=256, context_window=2048, # kwargs to pass to __init__() model_kwargs={"n_gpu_layers": 1}, verbose=False)embed_model = HuggingFaceEmbedding()Settings.llm = llmSettings.embed_model = embed_modelSettings.chunk_size = 512 ```

To load the pdf documents, we will use `SimpleDirectoryReader` to read from directory _./pdf_ as well as create a `StorageContext` instance of `SimpleGraphStore`. Now, comes the real fun part. LlamaIndex makes it extremely easy to generate knowledge graphs from unstructured documents. We simply invoke `PropertyGraphIndex.from_documents` call with the loaded documents and storage context, as shown:

``` documents = SimpleDirectoryReader("./pdf/").load_data()graph_store = SimpleGraphStore() gstorage_context = StorageContext.from_defaults(graph_store=graph_store)kg_index = PropertyGraphIndex.from_documents( documents, storage_context=gstorage_context, max_triplets_per_chunk=10, include_embeddings=True,) ```

If you have a large document or many documents loaded, the graph generation is very compute-intensive and could take a long time. If you repeatedly re-run your code, there is a better way to handle it. Before attempting the graph generation, let’s attempt to load the index files from our expected directory _./storage_. Otherwise, proceed with the generation steps as well as persist the indices post generation using `gstorage_context.persist()` (by default writes to directory _./storage_), as shown below:

```yaml try: # check if index on disk gstorage_context = StorageContext.from_defaults(persist_dir='./storage') kg_index = load_index_from_storage(storage_context = gstorage_context)except FileNotFoundError: graph_store = SimpleGraphStore() gstorage_context = StorageContext.from_defaults(graph_store=graph_store) documents = SimpleDirectoryReader("./pdf/").load_data() kg_index = PropertyGraphIndex.from_documents( documents, storage_context=gstorage_context, max_triplets_per_chunk=10, include_embeddings=True, ) # save to disk gstorage_context.persist() ```

At this stage, we have the graphs ready for querying. Similar to generation, LlamaIndex makes this querying step feels like a cakewalk. Create a query engine off the graph index, which involves a key argument `include_text`. If this is set to `False`, it will return matched nodes are raw triplets. The query engine is now ready for querying!

``` kg_keyword_query_engine = kg_index.as_query_engine( # setting to false uses the raw triplets instead of adding the text from the corresponding nodes include_text=True, similarity_top_k=2,)query = "When should simplified routing be used on SteelHeads?"response = kg_keyword_query_engine.query(query)print(f'Query: {query}
Response: {response.response}') ```

### 3.1 Impact of parameter `max_paths_per_chunk`

Let’s now see how to customize the graph generation. One aspect of generation is selecting the max paths per chunk. This can be controlled using `SimpleLLMPathExtractor`. By default, this extractor uses parameter `max_paths_per_chunk` set to 10. By using argument `kg_extractors`, we can nominate a list of our chosen extractors, as part of call `PropertyGraphIndex.from_documents`. Here is the code extract with this customization:

``` kg_extractor = SimpleLLMPathExtractor( llm=llm, max_paths_per_chunk=5, num_workers=4,)# kg generationkg_index = PropertyGraphIndex.from_documents( documents, storage_context=gstorage_context, kg_extractors=[kg_extractor], max_triplets_per_chunk=10, include_embeddings=True, ) ```

Let’s now explore the impact of `max_paths_per_chunk` by varying its value from 5, 7 and 10. We will use the following query for this test:

> When should simplified routing be used on SteelHeads?

### 3.2 Impact of parameter `include_text`

As part of querying, the query engine has a boolean parameter `include_text`. This controls the returned source nodes that will be used by LLM for response generation. The query for this test will be the following:

> If you have an asymmetric setup through the SteelHead, does it have any impact on the simplified routing feature?

**Response for**`**include_text**`**True**

> **Response** : Yes, if you have an asymmetric setup through the SteelHead, it can cause undesirable results for the simplified routing feature. This is because Simplified Routing (SR) uses a per-IP address basis to gather IP to next hop MAC address mapping. If SR has no mapping for a specific IP, it will use the static routes or gateway. However, in asymmetrically routed networks, SR might cause undesirable results due to the caching of old MAC addresses even if the route to reach a server changes while the proxy table in the client-side SteelHead still has an entry for that server. This can lead to traffic being sent to the cached (old) MAC address instead of the new one, unless source gathering is turned on and there is traffic from that server coming in.

## 4.0 Final Thoughts

Retrieval-Augmented Generation (RAG) is a popular and effective approach to adapt LLM to one’s domain. However, it suffers from hallucations. The use of knowledge graphs is one attempt to deal with this predicament. LlamaIndex took advantage of the improving capability of LLMs to assist with generation of knowledge graphs from unstructured documents as well as provide support to efficiently query those graphs.

In this article, we used LlamaIndex module `PropertyGraphIndex` for this purpose. With less than 20 lines of code, we have a working knowledge-graph inspired question-answering system to query about our local documents. We tested the impact of max paths, source node verbosity as well as the choice of LLM itself affecting the response generation performance. With the help of `LlamaCPP`, we were able to test across 5 different LLMs with ease and found both Phi-3 and Mistral 7B performed the best to facilitate `PropertyGraphIndex` in generation of knowledge graphs with meaningful entities and relationships for our niche domain.
