We set out to build a Retrieval-Augmented Generation (RAG) system that was _truly_ multilingual and multimodal — one that could ingest, embed, and retrieve not just English text, but also Spanish, Chinese, and even domain-specific documents. And we wanted this all to happen _fast_ , with minimal friction for the end user. After tinkering with various frameworks, we landed on an architecture that endorse **LlamaIndex** ’s flexible agent-based approach with **Qdrant** ’s high-performance vector database. Suddenly, it felt like the lights came on: we had a pipeline that could handle everything from ingestion to retrieval with seamless cross-lingual and multimodal support.

### The Anatomy of Architecture:

### User

Every grand adventure starts with someone posing a question or making a request. In our setup, **the User** is at the helm. They interact with the system — whether they want to add new documents, retrieve information, or run a particular workflow.

### Workflow Agent

Sitting at the heart of the architecture, the **Workflow Agent** is the conductor of the orchestra. Built using `LlamaIndex`, its job is to listen to the User’s requests and decide which path to take next. Should it kick off ingestion of brand-new docs or spin up a retrieval routine? This Agent decides it all and orchestrates the overall flow.

### Documents (Docs)

These are the knowledge treasures we want to index. Think of them as the raw materials that feed into the system — whether they’re text files, PDFs, or any other form of data that you need to embed and query later on.

### Embedding Agent

After the docs arrive on the scene, the **Embedding Agent** (also powered by `LlamaIndex`) takes each document and transforms it into the mathematical magic known as “embeddings.” You can think of embeddings like fingerprints for your text. They capture the contextual essence so that later, when a user searches for something, the system can quickly figure out which documents are most relevant.

### Ingestion Agent

Once the docs are nicely embedded, the **Ingestion Agent** picks them up and handles the heavy lifting of storing them into our vector database — in this case, **Qdrant**. Think of this agent as the librarian who catalogues each newly arrived book, making sure it’s placed on the right shelf for easy retrieval later.

### Qdrant

Where do we actually keep these embeddings? In **Qdrant** , the specialized vector database. Qdrant is like our library that’s purpose-built for fast and accurate similarity search. When the system says, “I want to find all documents related to X,” Qdrant leaps into action to find the best matches.

### Retrieval Agent

When a user’s question calls for looking up existing data, the **Retrieval Agent** is summoned. It runs the queries against `Qdrant`, leverages the embedded “fingerprints,” and fetches the relevant chunks of text. This Agent’s job is to respond with the right data at the right time — no more rummaging through thousands of documents manually.

### vdr-2b-multi-v1 (Model)

This is the underlying model or “brains” used to generate embeddings. It’s where the text & images are processed into dense vectors. Think of it as the specialized engine that powers your Embedding Agent’s skills.

### Langfuse

Finally, we have **Langfuse** keeping an eye on things. It’s like a control tower that offers observability and analytics. Whenever an Agent does something — like ingest a batch of docs or perform a retrieval — Langfuse can log that activity, measure performance, and help you track what’s going on under the hood.

### **Ingestion**

The Ingestion phase is very import in the RAG workflows where there are couple of agents helping each other to make this workflow successful. `Embedding Agent` and `Ingestion Agent` These two agents will coordinate accordingly to fetch the document embed them in a predefined format and fianally ingest them to Qdrant vector store.

```python async def invoke_ingest_workflow(self): embed_agent = FunctionAgent( name="embeddings creator", description="Performs embeddings creation task", system_prompt="You are a assistant to create embeddings for the given data", tools=[ FunctionTool.from_defaults(fn=create_embeddings), ], llm=self.llm, can_handoff_to=["data ingestor"] ) ingest_agent = FunctionAgent( name="data ingestor", description="Performs data ingestion task", system_prompt="You are a assistant to ingest data into vector database", tools=[ FunctionTool.from_defaults(fn=ingest_to_vec_db), ], llm=self.llm ) # Create and run the workflow workflow = AgentWorkflow( agents=[embed_agent, ingest_agent], root_agent="embeddings creator", timeout=300 ) await workflow.run(user_msg="embed the data and then ingest it to vector database") ```

### **Retrieval (text & images)**

The next step in any RAG pipeline is all above retrieving the right context for answering the user queries. Here in our scenario the retrieval is about the retrieving Image if user asks text query and vice-versa (retrieve text if user send the path of the image).

```python async def invoke_text2img_rag_workflow(self): retrieval_agent = FunctionAgent( name="retrieval agent", description="Performs retrieval for the given user query", system_prompt="You are an assistant to perform retrival for the given user query", tools=[ FunctionTool.from_defaults(fn=retrieve_image_from_store) ], llm=self.llm ) # Create and run the workflow workflow = AgentWorkflow( agents=[retrieval_agent], root_agent="retrieval agent", timeout=300 ) await workflow.run(user_msg="user interacting with Spring AI system") async def invoke_img2text_rag_workflow(self): retrieval_agent = FunctionAgent( name="retrieval agent", description="Performs retrieval for the given user query", system_prompt="You are an assistant to perform retrival for the given user query", tools=[ FunctionTool.from_defaults(fn=retrieve_text_from_store) ], llm=self.llm ) # Create and run the workflow workflow = AgentWorkflow( agents=[retrieval_agent], root_agent="retrieval agent", timeout=300 ) await workflow.run(user_msg="images/image-2.png") ```

### The Applications:

### Industry Applications

### 1\. Internal Knowledge Discovery in Large Organizations

**Use Case** : In a big company with multiple Strategic Business Groups (SBGs), it’s easy to lose track of who has worked on what. This architecture acts like a ‘corporate memory’ system. When someone wants to build a new Proof of Concept (POC) or replicate a successful internal project, they can simply ask — using natural language — to find out if a similar project was done before, who did it, and what key lessons were learned.

**Why It Helps** :

* **Faster Research** : Rather than scrolling through document folders or emailing around, teams can quickly retrieve relevant info.
* **Avoid Duplication** : Nobody wants to reinvent the wheel. This system helps ensure you build on existing knowledge rather than starting from scratch.
* **Capture Tribal Knowledge** : Even informal notes and docs get embedded and stored, so you can locate them later — long after the original authors may have moved on.

### Medical Applications

Medical institutions handle mountains of data: clinical notes, research articles, patient records, and regulatory guidelines. Searching through these documents can be time-consuming, especially when time is critical.

### 2\. Clinical Decision Support

**Use Case** : A physician needs to quickly recall past clinical cases or reference the latest research on a particular condition. Using the architecture, all documents — journal articles, diagnostic guidelines, treatment protocols — are embedded in Qdrant, making them discoverable via natural language queries.

**Why It Helps** :

* **Rapid Diagnosis Support** : Doctors can ask, “Which antibiotics were used for X infection in past cases?” and instantly pull relevant data.
* **Evidence-Based Medicine** : Ensures that the latest research or best practices are easily accessible.
* **Reduced Cognitive Load** : Clinicians can find specific guidance without manual searching or guesswork.

### 3\. Medical Research & Literature Reviews

**Use Case** : Researchers often need to review extensive studies, clinical trial data, and meta-analyses. By embedding and indexing scientific papers, the system can surface relevant articles for a given query, even if the wording doesn’t match exactly.

**Why It Helps** :

* **Stay Current** : Quickly discover newly published studies.
* **Semantic Match** : Find papers on similar topics, not just identical keywords (e.g., synonyms for “cardiovascular disease”).
* **Collaborative** : Multiple research teams can tap into the same knowledge base, fostering synergy and preventing duplication.

## Legal Applications

Law firms, in-house legal teams, and compliance departments juggle thousands of documents: contracts, case precedents, statutes, and internal policies. Speed and precision in retrieval can be a game-changer.

### 4\. Contract Analysis & Drafting

**Use Case** : Imagine a law firm that has negotiated hundreds of similar contracts. An attorney can query, “Which previous contracts used this particular indemnity clause?” to instantly retrieve relevant sections.

**Why It Helps** :

* **Clause Reuse** : Quick access to standard clauses and language that worked in prior deals.
* **Consistency & Accuracy**: Ensures the most up-to-date and verified language is always used.
* **Faster Drafting** : Drastically cuts down the time spent searching through large contract repositories.

### 5\. Case Law & Litigation Research

**Use Case** : For litigation teams, building arguments hinges on finding the most relevant precedents. By embedding judicial opinions, legal briefs, and case summaries, the system provides a semantic search that goes beyond keywords.

**Why It Helps** :

* **Comprehensive Searches** : Surfaces cases that discuss the same legal principle, even if they use slightly different terms.
* **Better Strategy** : Quick access to relevant judgments or rulings strengthens case strategy.
* **Scalable** : As new cases and rulings come in, they’re automatically added to the index for future uses.

### The Conclusion

This architecture, with its well-defined agents for embedding, ingestion, and retrieval, fundamentally changes how organizations can store, search, and leverage their internal knowledge. Rather than sifting through disjointed folders or wikis, teams now have a powerful, unified system for turning raw text into actionable insights — all accessible through natural language. Whether you’re in a multinational corporation, a healthcare facility, or a law firm, the impact is the same: faster discovery of relevant information, more accurate decision-making, and a significant reduction in duplicated effort.

By breaking the process into specialized agents — each with its own focus on embeddings, ingestion, or retrieval — you can easily evolve or swap components without disrupting the entire pipeline. Meanwhile, tools like Qdrant and Langfuse complete the picture, offering robust storage, similarity search, and analytics to keep everything transparent and scalable. The end result? A flexible, future-proof knowledge architecture that empowers teams to do more with the data they already have.
