Developed by the **Stanford MAST team** , BLAST acts as a **high-performance serving engine** for AI applications, bringing web access through a **production-ready, OpenAI-compatible interface**.

## What Makes BLAST Different

### Built for Production, Not Just Demos

Most **_AI browsers_** you see are fine for experiments. BLAST, however, is engineered for **real-world concurrency, caching and cost management** , allowing developers to integrate web browsing into production systems with confidence.

### OpenAI-Compatible Interface

With an **OpenAI-compatible API** , developers can plug in BLAST with their existing SDKs or agents without rewriting code.
Just change the `base_url` and your LLM now browses the live web.

### Automatic Parallelisation

BLAST automatically splits tasks for concurrent browsing.

It supports:

* **Task parallelism** (multiple independent subtasks)
* **Data parallelism** (chunk-based crawling)
* **First-of-N** (cancel slower parallel tasks when one finishes)

Combined, this gives **up to 5× speed improvement** in retrieval and summarisation tasks.

### Intelligent Caching

Caching isn’t just about results anymore; BLAST also caches **plans**.
That means if an LLM knows how to browse a site, it can reuse the strategy next time — saving both time and compute.

### Real-Time Streaming

BLAST streams both **thoughts** and **screenshots** as token-like deltas.
Your UI can show what the model **_sees_** while it’s reasoning, offering a transparent and interactive experience.

## Why BLAST matters right now

1. **Production-grade web browsing for LLMs
** A lot of “AI agents that browse” demos fail to scale. BLAST focuses on serving — concurrency, resource control, streaming UX, cost caps, so we can safely expose browsing to end users.
2. **Developer-friendly: OpenAI compatibility
** You point your existing OpenAI SDK at BLAST’s `base_url` and go. This approach (OpenAI-compatible surfaces) is quickly becoming standard across providers and tools, lowering integration friction.
3. **Performance levers baked-in
** Automatic parallelism (task/data/first-of-N), prefix-aware caching for browser tasks and streamable execution give **_interactive-level_** latencies for multi-page, multi-tab crawls.

## What BLAST actually is

> A high-performance serving engine for browser-augmented LLMs… with an OpenAI-compatible API, streaming, concurrency and automatic parallelization.

## Key capabilities

* **OpenAI-compatible** endpoints (`/v1/chat/completions` and `/v1/responses`)
Works with standard OpenAI clients; you just set `base_url`.
* **Real-time streaming**
Streams _thoughts/actions_ as text and _screenshots_ as token-like “delta” events (no spaces) so UIs can render live browsing.
* **Automatic parallelism**
*  _Task parallelism_ (spawn subtasks concurrently)
* _Data parallelism_ (chunk pages; summarize with a smaller LLM)
* _First-of-N_ (take first completed copy, cancel others)
* _Nested_ with depth limits
BLAST’s docs report an **_unscientific_** ~5× speed-up from data parallelism plus ~2× by using a smaller LLM for chunk summaries.
* **Intelligent caching**
Caches not only final **results** but also **plans** (_the LLM-generated steps to get results_), with cache-control flags like `no-cache`, `no-store`, `no-cache-plan`, `no-store-plan`. Supports persistent on-disk caches you can clear programmatically.
* **Concurrency and resource control**
Multi-tenant scheduler, cost caps, memory limits, maximum concurrent browsers, headless requirements and browser reuse.

## Architecture

![image](https://miro.medium.com/v2/resize:fit:700/1*vpWLjnCsOv0QQ6Sc38Rc2g.png)

**Key Components:**

* **Client Layer:** Connects via OpenAI-compatible API.
* **Scheduler:** Manages concurrent browsing tasks.
* **Cache Manager:** Handles result and plan caching.
* **Resource Manager:** Controls memory, cost and browser usage.
* **Planner + Executors:** Use the LLM to decide and perform actions.
* **Parallel Workers:** Handle distributed browser tasks.

Together, these create a **scalable loop** of plan–execute–cache–respond, optimised for speed and cost.

## Quickstart (works locally)

**Install & serve**

```python pip install blastaiblastai serve ```

**Point your OpenAI client at BLAST**

```python from openai import OpenAIclient = OpenAI(api_key="not-needed", base_url="http://127.0.0.1:8000") ```

**Stream real-time browsing**

``` stream = client.responses.create( model="not-needed", input="Compare fried chicken reviews for top 10 fast food restaurants", stream=True)for event in stream: if event.type == "response.output_text.delta": print(event.delta if " " in event.delta else "<screenshot>", end="", flush=True) ```

For more details, please refer the official [GitHub](<https://github.com/stanford-mast/blast>) page.

**Built-in UI**
The server also launches a minimal Next.js UI on `http://localhost:3000` that consumes the streaming API (thoughts + screenshots). Handy for demos and debugging.

## Using the OpenAI-compatible surfaces

### Chat Completions

```json resp = client.chat.completions.create( model="not-needed", messages=[{"role":"user","content":"Find the 10 heaviest gorillas"}], stream=True)for chunk in resp: if chunk.choices[0].delta.content: print(chunk.choices[0].delta.content, end="") ```

_Streaming the “delta” mirrors OpenAI’s semantics; BLAST treats zero-space deltas as screenshots._

## Responses API

``` stream = client.responses.create( model="not-needed", input="Go to python.org and click Documentation", stream=True)for event in stream: # response.created, response.in_progress, response.output_text.delta, response.completed ... ```

_Use_` _previous_response_id_` _to chain multi-turn browsing sessions._

## Performance playbook

**Turn on parallelism
** Enable task/data parallelism and (optionally) first-of-N in `config.yaml`:

```yaml constraints: allow_parallelism: task: true data: true first_of_n: false max_parallelism_nesting_depth: 1 ```

**Right-size your LLMs**
Use a bigger model for planning and a small/fast model for chunk summaries:

```yaml constraints: llm_model: "openai:gpt-5" llm_model_mini: "openai:gpt-5-mini" ```

**Tip:** Use `gpt-5` for reasoning and `gpt-5-mini` for summarisation to save cost without losing quality.

**Exploit plan + result caching
** Cache defaults are on, override per request:

``` client.responses.create( model="not-needed", input="Search Python docs", cache_control="no-cache-plan" # still uses results cache) ```

Persist cache between runs if you want warm starts:

```yaml settings: persist_cache: true ```

Clear caches via API or by removing the cache directories.

**Keep it interactive with streaming
** Stream thoughts/actions and screenshots to keep users engaged during longer navigations.

## Operating it in production

* **Concurrency & resource limits**
Cap concurrent browsers, memory and cost. BLAST exposes constraints such as `max_concurrent_browsers`, `max_memory`, and budget guards like `max_cost_per_minute`.
* **Observability & logs**
Send logs to a folder, log Engine vs browser operations at different levels and poll metrics (`engine.get_metrics()`) for running tasks, browsers, memory.
* **Secrets & authenticated sites**
Put site credentials (e.g., JIRA) into a secrets file referenced by `settings.secrets_file_path` if your browsing targets need auth.
* **Headless & browser reuse**
Force headless mode and share browser processes across contexts to reduce overhead.

## How BLAST compares

* **vs. “browser-use” libraries**
Tools like _Browser Use_ focus on agent logic/APIs for controlling the browser. BLAST sits **beneath** that as a serving engine optimized for speed, caching, streaming and multi-tenant concurrency, meant for user-facing production apps.
* **vs. rolling your own Playwright + server**
You’d re-implement scheduling, cache semantics (_including plan reuse_), budget guards, streaming contracts and parallel orchestration. BLAST gives you these primitives out of the box.
* **Alignment with OpenAI-compatibility trend**
Many providers now expose OpenAI-compatible APIs (_e.g., Together, Google Gemini_), which makes BLAST’s surface area an easy drop-in for existing stacks.

## Limitations, roadmap & where it’s headed

BLAST actively prioritises **stability** , **cost optimisation** , **performance** , **human-teaming UX** and **reliability benchmarking**. It deliberately **doesn’t** try to invent a new “browser-use” stack or vision model; it focuses on serving and scaling them under constraints.
