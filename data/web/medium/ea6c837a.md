## What is DSPy

DSPy is a framework that was created by Stanford researches. I love the way that the [official docs](<https://github.com/stanfordnlp/dspy/blob/main/intro.ipynb>) explain so I’m attaching it here:

**DSPy** emphasises programming over prompting. It unifies techniques for **prompting** and **fine-tuning** LMs as well as improving them with **reasoning** and **tool/retrieval augmentation** , all expressed through a _minimalistic set of Pythonic operations that compose and learn_.

**DSPy** provides **composable and declarative modules** for instructing LMs in a familiar Pythonic syntax. On top of that, **DSPy** introduces an **automatic compiler that teaches LMs** how to conduct the declarative steps in your program. The **DSPy compiler** will internally _trace_ your program and then **craft high-quality prompts for large LMs (or train automatic finetunes for small LMs)** to teach them the steps of your task.

In my own words:

1. DSPy allows you to create LLM prompts by specifying inputs and outputs
2. DSPy allows you to optimize the task output in a supervised manner

We will deep dive into the implementation at the next sections but beforehand I wanted to show you how prompts look when implementing with DSPy.

DSPy calls this structure a signature

```python class Classification(dspy.Signature): """Classify the customer message into one of the intent labels. The output should be only the predicted class as a single intent label.""" customer_message = dspy.InputField(desc="Customer message during customer service interaction") intent_labels = dspy.InputField(desc="Labels that represent customer intent") intent_class = dspy.OutputField(desc="a label best matching customer's intent ") ```

The signature contains 3 components:

1. The main instruction: “””Classify the customer message into one of the intent labels. The output should be only the predicted class as a single intent label.”””
2. Input labels
3. Output labels

### ORM for prompts

In software engineering generally, abstractions and encapsulation allows other coders to focus on business logic rather on specifics of a certain task. This is very good when used correctly. As mentioned generally abstractions are a great thing, but not all abstractions are good (Ahm ahm, Langchain), but I digress.

To drive the point home we can compare DSPy with an ORM (object relational model). An example of an ORM that is often used in Python is SQLAlchemy. The goal of an ORM is to abstract a database, and act as an object oriented bridge between you and the data. In order to retrieve data you instantiate several methods and that’s it. You don’t need to write any line of SQL. SQL in itself can be also seen as a good analogy because the user doesn’t get to see the optimizations that are running under the hood, similarly to how we don’t “get” to see the actual prompt that’s running with DSPy (unless you choose to).

The move to an ORM allows much cleaner code that’s far easier to collaborate on rather than manipulating string based SQL queries. My take is that DSPy creates similar effects on your code base and way of thought.

### Improve prompt quality via supervised learning

Prompt engineering is the act of improving a prompt — changing the instructions to improve the result. When working on machine learning / deep learning one is used to this kind of line of thinking.

In classic machine learning / deep learning, you have a data atom that you add or subtract. For instance, pictures of cats that you can add or remove. This is what you control.

**In prompt engineering, we have different levers. Overall we control the prompt instructions. The instructions include the basics — describing the input and the output and the format. But they may include known advanced patterns as Chain Of Thought (CoT), or In Context Learning.**

> But how exactly should you phrase these patterns? It have been observed that slight changes in the prompt can lead to significant changes in the output.

DSPy lets you define these patterns programmatically by instantiating classes that will compose your prompt. You can view it as a prompt builder. You give it the main details and it will produce the prompt.

By having a small dataset (that can be small as 20 samples), you can use the framework to optimize the prompt for you against that dataset. Under the hood the framework will iterate on different directives for each of the sub components and between the samples that are possible for in context learning.

### Modularity

This framework is highly influenced by PyTorch. And PyTorch is the modalrity OG.

No, you can’t find this meme anywhere else but here.

Computational graph libraries such as Tensorflow, Keras and Pytorch allows you to create neural networks as a composition of different layers. PyTorch and Keras really simplified this process, while Keras left behind past several years, PyTorch took first place.

DSPy follows the same path, viewing a prompt as a composition of different options. You start with composing input and outputs. Do you want to add Chain Of Thoght pattern? Great, wrap your current class with a new CoT class. This allows you to swap patterns in a plug&play style, easily testing different options.

Here’s an example of adding Chain Of Thought as a component

``` predict_with_chain_of_thought = dspy.ChainOfThought(Classification) ```

Easy, right?

> Another point about computation graphs, DSPy has an analogues components for the model, loss function and the optimizer. This already makes me feel at home.

As this is an introductory blog, the first one in the series, I won’t go deeper than this, but in my next instalment expect deeper breadth.

### Evaluation as a first class citizen

Even though evaluation is a corner stone in any data-science related endeavour, in contrary prompt based projects sometimes start without any quantitative evaluation.

There are many reasons why generated text is an open problem:

1. It requires manual annotation / preference datasets / a lot of work to get the groundtruth of your task.
2. This problem currently best solved by additional LLM calls.
Shameless plug — I have written about using [deepeval for this exact task](<https://medium.com/towards-artificial-intelligence/5-cursor-ai-pro-tips-5a8d605f93fb>).
3. **LLM Frameworks mostly model the predictive / generative part without pushing you into evaluation**

Have you seen openai tutorial? Or any other framework?
They are showing you how to get things done, and that’s fine for a lot of use cases and personas.
For data-scientists personas it is not. Evaluation is key for fast iterations, comparisons and sleeping well at night.

So yeah, DSPy has evaluation baked in, increasing the chance that you will use it.

### Basics

[Link to a notebook with the all of the examples](<https://github.com/SerjSmor/open-intent-classifier/blob/main/notebooks/dspy_tutorial.ipynb>)

First define a class — or in DSPy lingo — a signature.

```python class Classification(dspy.Signature): """Classify the customer message into one of the intent labels. The output should be only the predicted class as a single intent label.""" customer_message = dspy.InputField(desc="Customer message during customer service interaction") intent_labels = dspy.InputField(desc="Labels that represent customer intent") intent_class = dspy.OutputField(desc="a label best matching customer's intent ") ```

Define the LLM you want to use

``` lm_mini = dspy.OpenAI(model='gpt-4o-mini')dspy.settings.configure(lm=mini) ```

Then create a predictor

``` predict = dspy.Predict(Classification) ```

Run prediction

``` labels = " ".join(["Cancel subscription", "Refund request"])pred = predict(customer_message=text, intent_labels=labels)# this returns: # Prediction(# intent_class='Cancel subscription'# ) ```

pred — is an actual object that has all of the members you defined in the Signature class.

It seems more complex at first, with all of these components lying around. But this makes a lot of sense once you venture in the messy reality which involves testing multiple models with multiple patterns trying to optimize performance.
