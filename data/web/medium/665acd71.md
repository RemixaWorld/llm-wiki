## Why Build a Research Digest Tool in the First Place?

Research papers are dense in information. Reading a single paper can take up 20–120 minutes of focused attention². Multiply that by the number of daily AI research releases, and staying up to date becomes your full-time job.

Research digest tools solve this problem by automating the summarization process. It distils research to the essentials and presents it in an easy-to-understand format.

These tools are widely used in academia and research institutions. Some let you upload a PDF and generate summaries or citations, such as Scispace³. Other solutions crawl research websites and email you summaries of the latest papers.

## Here’s What We’re Building

The tool that we’ll be building works as follows:

* **Retrieves** the latest research papers from arXiv, filtering them based on specific time intervals.
* **Extracts** full-text PDFs and associated metadata like title, authors, and publication date.
* **Summarizes** each paper using a structured prompt that generates both scientific and simplified insights via an LLM.
* **Displays** all output in a scrollable, interactive web feed using NiceGUI.
* **Downloads** : Optionally lets users download the full papers for further reading.

## Design Considerations That Make It Work

### Getting the Papers: The arXiv API

First, we’ll need a consistent source of research papers. [arXiv](<https://arxiv.org/>)**** is a free, research-sharing platform that covers a range of fields, including AI and computer science. It has an easy-to-use API, making it ideal for automated data pipelines.

The data is fetched through a URL and returns results in XML that we can parse⁴.

``` http://export.arxiv.org/api/{method_name}?{parameters} ```

We can manipulate the URL (as we will see later) to return research for a specific topic published in a specified period.

### Setting Up the LLM

The core mechanism of this project is uploading the full text of a research paper and passing it along with a structured prompt to the LLM.

For this, we’ll need an LLM developer key. I used the **OpenAI API.** If you don’t have one, you can get it here:

**Get your OpenAI API key here:**
👉 [https://platform.openai.com/account/api-keys](<https://platform.openai.com/api-keys>)

Once you’ve created an account and have generated a key, you can set it as an environment variable. With either the `langchain` library or direct HTTP requests, you can select and call your preferred model.

For cost efficiency and performance, selecting the right model matters. For this project, I used `gpt-4o-mini`, which offers a balance of reasoning and cost efficiency.

### Structuring the Data & Preventing Hallucinations

Whenever working with LLM’s we should always be aware that the output is non-deterministic and can be fabricated, known as AI hallucinations. To avoid misinformation, the prompt should guide the LLM to:

* Summarize only the content directly found in the paper.
* Use the standard research structure known as IMRaD (Introduction, Methods, Results, Discussion).

According to [OpenAI’s best practices](<https://platform.openai.com/docs/guides/prompt-engineering>), this reduces hallucinations. The prompt is shown in the technical section of this article.

### Optimizing with Prompt Caching

Repeatedly calling LLMs can be expensive and slow, especially when dealing with full research papers that span multiple pages. Imagine a user clicks a button and waits while the app submits and processes an entire PDF file. Not exactly a great experience.

To make things faster and more affordable, we use _prompt caching_** _—_** storing reusable responses of the LLM.

For this project, it works as follows:

* **At runtime:** Fetching and summarizing all papers upfront.
* **From that point on, everything is cached.** If the same paper is retrieved (e.g., re-run or refresh), the app loads the summary from the disk.

### Building a User-Friendly Interface

For the frontend, we’re using [NiceGUI](<https://nicegui.io/>), an open-source Python library ideal for creating interactive, browser-based interfaces. Unlike alternatives like Streamlit, it offers flexibility for custom layouts.

### 2\. Caching

This is where we save costs and latency by avoiding any redundant LLM API calls and caching previously processed summaries. The caching script contains two functions:

* `load_cache()`: Loads cached data from a JSON file.
* `save_cache(cache)`: Saves updated summaries to the cache.

These functions are called later in the data processing phase.

```python import osimport jsonCACHE_FILE = "key_findings_cache.json"def load_cache() -> dict: if os.path.exists(CACHE_FILE): with open(CACHE_FILE, "r") as f: try: return json.load(f) except json.JSONDecodeError: return {} return {}def save_cache(cache: dict): with open(CACHE_FILE, "w") as f: json.dump(cache, f, indent=2) ```

### 3\. LLM setup

The`llm_setup` contains two components:

1. The function responsible for the initialization of the Large Language Model (LLM) (e.g., `gpt-4o-mini)`by retrieving the OpenAI API key.
2. It contains a detailed prompt instructing the model to summarize research papers according to **IMRaD** and explicitly use content from the paper to **avoid hallucination**.

```python import getpassimport osfrom langchain.chat_models import init_chat_modeldef init_llm(): if not os.environ.get("OPENAI_API_KEY"): os.environ["OPENAI_API_KEY"] = getpass.getpass("Enter API key for OpenAI: ") llm = init_chat_model("gpt-4o-mini", model_provider="openai") return llm prompt = """You will be given the full text of a scientific research paper.Your task is to perform the following steps:1. **Overall Summary**: Provide a brief overall summary of the paper in 2–4 sentences, using precise and concise language.2. **IMRaD Breakdown**: Extract accurate summaries for each of the four IMRaD sections: - Introduction - Methods - Results - Discussion/Implications For each section, return: - "scientific_summary": A precise 3–5 sentence summary using the original terminology and structure found in the paper. - "simplified_explanation": A plain-language explanation that avoids jargon and could be understood by a non-technical reader. Explain clearly what the section contributes.**Important Guidelines:**- Only include content explicitly present in the paper.- Do not guess, infer, or generate content that is not directly supported by the text.- If a section is not clearly present, set both fields to an empty string: `""`.- Preserve factual accuracy, terminology, and meaning from the source.- Keep all output in the following valid Python dictionary format:{"General_summary": "...", "Introduction": { "scientific_summary": "...", "simplified_explanation": "..." }, "Methods": { "scientific_summary": "...", "simplified_explanation": "..." }, "Results": { "scientific_summary": "...", "simplified_explanation": "..." }, "Discussion": { "scientific_summary": "...", "simplified_explanation": "..." } }""" ```

## Data Processing

The `data_processing.py`file is the brain of the application. It consists of functions that extract, process, and organize the data in a format we can later insert into our user interface.

For this, we need to import the following libraries. Notice that the first two imports are the functions we had defined earlier.

```python from app.llm_setup import init_llm, promptfrom app.caching import load_cache, save_cacheimport urllib.request # Fetches data from URLs (used for arXiv API requests)import feedparser # Parses RSS/XML feeds returned by arXivfrom typing import Dict, List # For type annotations for clarityimport requests # Handles HTTP requests for downloading PDFsimport re # Regular expressions for cleaning LLM responsesimport json # Handles serialization and deserialization of JSON data (used in caching)import fitz # PyMuPDF Extracts text content from PDFsimport datetime # Handles date and time operations ```

`search_query()`: Queries the arXiv API for recent papers on the specified topic. It constructs a URL with parameters, topic, max_results, and date range (defaulting to the last 7 days). It retrieves the data in XML format.

```python TO_DATE = datetime.datetime.now().strftime("%Y%m%d")FROM_DATE = (datetime.datetime.now() - datetime.timedelta(days=7)).strftime("%Y%m%d")def search_query(topic: str, max_results: int, date_from=FROM_DATE, date_to=TO_DATE) -> str: """Returns an XML string with search results from arXiv API.""" query = f"all:{topic} AND submittedDate:[{date_from} TO {date_to}]" query_encoded = urllib.parse.quote(query) url = ( f"http://export.arxiv.org/api/query?" f"search_query={query_encoded}" f"&start=0&max_results={min(max_results, 10)}" ) data = urllib.request.urlopen(url) return data.read().decode("utf-8") ```

`parse_meta_data()`: Extracts the metadata(published, updated, title, authors, abs_link, and pdf_link) from an XML response and organizes it into a nested dictionary.

```python def parse_meta_data(xml: str) -> Dict[str, Dict]: """Parses XML from arXiv API and returns metadata as a nested dictionary keyed by arXiv ID.""" parsed_result = feedparser.parse(xml) metadata_by_id = {} for entry in parsed_result.entries: # Initialize fields abs_url = None pdf_url = None for link in entry.get("links", []): if link.get("rel") == "alternate": abs_url = link.get("href") elif link.get("title") == "pdf": pdf_url = link.get("href") if not abs_url: continue # Skip entries without an abstract URL arxiv_id = abs_url.split("/")[-1] # e.g., "2407.01234" metadata_by_id[arxiv_id] = { "published": entry.get("published"), "updated": entry.get("updated"), "title": entry.get("title"), "authors": [a.name for a in entry.get("authors", []) if hasattr(a, "name")], "abs_link": abs_url, "pdf_link": pdf_url } return metadata_by_id ```

`extract_pdf_text()`: Downloads and extracts text content from PDFs.

```python def extract_pdf_text(pdf_url:str)-> dict[list]: response = requests.get(pdf_url) response.raise_for_status() # raise error if download fails pdf_bytes = response.content document_data = fitz.open(stream=pdf_bytes, filetype='pdf') return "
".join(page.get_text() for page in document_data) ```

`generate_summaries()`: Combines the prompt and PDF text into a single input, invokes the LLM and retrieves the response, returning it as cleaned content structured in a JSON format.

```python llm = init_llm()def generate_summaries(prompt: str, pdf_text: str, llm) -> dict: full_prompt = f"{prompt}

The following contains the PDF data:

{pdf_text}" try: response = llm.invoke(full_prompt) raw_output = response.content.strip() # Remove markdown code block if present cleaned = re.sub(r"^```(?:json|python)?\s*|\s*```$", "", raw_output, flags=re.DOTALL) # Parse as JSON return json.loads(cleaned) except Exception as e: print(f"Error submitting to LLM or parsing output: {e}") return {} ```

* `main()`: Coordinates the overall data fetching, summarizing, and caching, and returns structured results including the LLM responses as a list of nested dictionaries.

```python def main(topic: str, max_results: int = 5) -> list[dict]: papers = parse_meta_data(search_query(topic, max_results)) results = [] cache = load_cache() for arxiv_id, paper in papers.items(): if not paper.get("pdf_link"): continue elif arxiv_id in cache: print(f"Using chached results for {arxiv_id}") summeries = cache[arxiv_id] else: try: print(f"Processing: {paper['title']}") pdf_text = extract_pdf_text(paper["pdf_link"]) summeries = generate_summaries(prompt, pdf_text, llm) cache[arxiv_id] = summeries save_cache(cache) except Exception as e: print(f"Skipping {arxiv_id} due to error: {e}") continue results.append({ "arxiv_id": arxiv_id, **paper, "summaries": summeries, }) if not results: print("No valid papers processed.") return results ```

## Limitations and Improvements: Build Something Even Better

Let’s discuss the limitations and improvements of this project.

### Deployment

First, I didn’t cover how to deploy this project (making it accessible through the web); it only runs locally. Deploying the app on a cloud platform such as Google Cloud Platform (GCP) or Amazon Web Services (AWS) would make it accessible online.

### **Limited Research**

The current project only focuses on extracting papers from arXiv; other websites can be included, such as PubMed, IEEE Xplore, or SpringerLink.

### Quality Research

A benefit of using arXiv is early access to research, as many researchers upload their work to the platform before getting it peer reviewed. On the other hand, this also means that the quality and reliability of the papers can vary, since they haven’t undergone formal processes.

### Improve functionality

We could consider additional features such as uploading and parsing PDF documents (like SciSpace) or add a “chat with research” functionality using a [Retrieval-Augmented Generation (RAG) pipeline](<https://medium.com/data-science-collective/talk-to-your-docs-building-a-scalable-rag-app-on-google-cloud-dd5497dae37d>).
