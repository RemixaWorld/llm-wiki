Excellent article on how to implement standard chunking techniques. However, the most effective technique we have found is to **construct the chunks after the query is submitted. This is in stark contrast to trying to determine generic chunks that will be universally effective for all possible queries.**

The basic methodology is to first assign each sentence an index number. Then process the sentences to transform them into independent statements (such as using coreference resolution). The independent statements are tagged with the corresponding index number of the original sentences (as there may be multiple independent statements for any given original sentence).

Vector embeddings are obtained for the independent statements. The index number of the original sentence is stored in the vector database (not any text).

Vector retrieval for the query now returns index numbers (not text). Chunks are constructed based on the index numbers. For example, if two index numbers are within a preset distance, a chunk is created spanning the earlier index number up through the latter index number. Pre and post padding can also be included.

**At this point, custom chunks have been created that solely contain information relevant to the query.** This weeding out of extraneous chunk information profoundly reduces hallucinations in and of itself.

We've found this, combined with eight other steps, fully eliminates hallucinations. **We've tested _thousands_ of queries without a single hallucination.**

It's important to note that standard RAG was crystalized during GPT's infancy. The standard approach is woefully broken. That's why production RAG implementations still hallucinate — even when implementing _dozens_ of "advanced RAG" techniques.

The very core of RAG, its foundation, needs to be replaced. The notion of defining chunks prior to query is but one such example.
