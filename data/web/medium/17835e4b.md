Currently, there are many open-source RAG frameworks available, which serve as experienced guides for developers, making it easier to build exceptional question-answering systems, dialogue models, and other intelligent applications. These open-source frameworks not only lower the barrier to entry but also provide a strong foundation for customization and extension. Their features, underlying mechanics, and how they drive modern AI applications are important topics worth investigating.

In this article, we’ll explore [Kotaemon](<https://github.com/Cinnamon/kotaemon>), an innovative open-source Retrieval-Augmented Generation (RAG) framework that, as of September 13, 2024, has 11.5K stars on GitHub.

To gain a deeper understanding of its core technologies, I analyzed its project structure and code, which led to the creation of this article.

Whether you’re a developer looking to build a custom RAG pipeline or an end-user seeking a seamless QA interface, kotaemon offers a powerful, flexible, and user-friendly platform. Let’s dive into how kotaemon is changing the game for document QA.

## PDF Parsing

PDF files, as a prime example of unstructured documents, are, in my view, the most critical component of the RAG pipeline’s parsing process. Therefore, this article will first focus on how kotaemon handles PDF parsing.

Press enter or click to view image in full size

Figure 2: The file upload interface. Screenshot by author.

When a PDF file is uploaded through this interface, the `[load_data](<https://github.com/Cinnamon/kotaemon/blob/cd85c4935c85afdd18416fd902e09c4a8b997d86/libs/kotaemon/kotaemon/loaders/pdf_loader.py#L65>)` function within the `[class PDFThumbnailReader(PDFReader)](<https://github.com/Cinnamon/kotaemon/blob/cd85c4935c85afdd18416fd902e09c4a8b997d86/libs/kotaemon/kotaemon/loaders/pdf_loader.py#L56>)` is triggered. The following is the code.

```python class PDFThumbnailReader(PDFReader): """PDF parser with thumbnail for each page.""" def __init__(self) -> None: """ Initialize PDFReader. """ super().__init__(return_full_document=False) def load_data( self, file: Path, extra_info: Optional[Dict] = None, fs: Optional[AbstractFileSystem] = None, ) -> List[Document]: """Parse file.""" documents = super().load_data(file, extra_info, fs) page_numbers_str = [] filtered_docs = [] is_int_page_number: dict[str, bool] = {} for doc in documents: if "page_label" in doc.metadata: page_num_str = doc.metadata["page_label"] page_numbers_str.append(page_num_str) try: _ = int(page_num_str) is_int_page_number[page_num_str] = True filtered_docs.append(doc) except ValueError: is_int_page_number[page_num_str] = False continue documents = filtered_docs page_numbers = list(range(len(page_numbers_str))) print("Page numbers:", len(page_numbers)) page_thumbnails = get_page_thumbnails(file, page_numbers) documents.extend( [ Document( text="Page thumbnail", metadata={ "image_origin": page_thumbnail, "type": "thumbnail", "page_label": page_number, **(extra_info if extra_info is not None else {}), }, ) for (page_thumbnail, page_number) in zip( page_thumbnails, page_numbers_str ) if is_int_page_number[page_number] ] ) return documents ```

The main steps are as follows:

1. **Load PDF File** : PDF text extraction is carried out through the `[load_data](<https://github.com/run-llama/llama_index/blob/v0.10.68/llama-index-integrations/readers/llama-index-readers-file/llama_index/readers/file/docs/base.py#L39>)` function in `[llama_index.readers.file.PDFReader](<https://github.com/run-llama/llama_index/blob/v0.10.68/llama-index-integrations/readers/llama-index-readers-file/llama_index/readers/file/docs/base.py#L27>)`. As noted in [my previous article](<https://pub.towardsai.net/advanced-rag-02-unveiling-pdf-parsing-b84ae866344e>), llama_index relies on [pypdf](<https://pypi.org/project/pypdf/>) for this task.
2. **Generate Thumbnails** : For each page, a thumbnail image is created using the `[get_page_thumbnails](<https://github.com/Cinnamon/kotaemon/blob/cd85c4935c85afdd18416fd902e09c4a8b997d86/libs/kotaemon/kotaemon/loaders/pdf_loader.py#L13>)` function, which utilizes [PyMuPDF (fitz)](<https://github.com/pymupdf/PyMuPDF>).
3. **Store Data** : The extracted text, generated thumbnails, and any relevant metadata (e.g., page numbers, sizes) are stored in a Python list called `documents`.
4. **Return the Data** : Finally, the `documents` list is returned.

In addition, as shown in Figure 3, the project offers several other methods for parsing PDFs.

The previously analyzed `class PDFThumbnailReader(PDFReader)` does not appear to use an OCR model. Therefore, I will introduce the `[class OCRReader](<https://github.com/Cinnamon/kotaemon/blob/cd85c4935c85afdd18416fd902e09c4a8b997d86/libs/kotaemon/kotaemon/loaders/ocr_loader.py#L35>)` .

```python class OCRReader(BaseReader): """Read PDF using OCR, with high focus on table extraction Example: ```python >> from kotaemon.loaders import OCRReader >> reader = OCRReader() >> documents = reader.load_data("path/to/pdf") ``` Args: endpoint: URL to FullOCR endpoint. If not provided, will look for environment variable `OCR_READER_ENDPOINT` or use the default `kotaemon.loaders.ocr_loader.DEFAULT_OCR_ENDPOINT` (http://127.0.0.1:8000/v2/ai/infer/) use_ocr: whether to use OCR to read text (e.g: from images, tables) in the PDF If False, only the table and text within table cells will be extracted. """ def __init__(self, endpoint: Optional[str] = None, use_ocr=True): """Init the OCR reader with OCR endpoint (FullOCR pipeline)""" super().__init__() self.ocr_endpoint = endpoint or os.getenv( "OCR_READER_ENDPOINT", DEFAULT_OCR_ENDPOINT ) self.use_ocr = use_ocr def load_data( self, file_path: Path, extra_info: Optional[dict] = None, **kwargs ) -> List[Document]: """Load data using OCR reader Args: file_path (Path): Path to PDF file debug_path (Path): Path to store debug image output artifact_path (Path): Path to OCR endpoints artifacts directory Returns: List[Document]: list of documents extracted from the PDF file """ file_path = Path(file_path).resolve() # call the API from FullOCR endpoint if "response_content" in kwargs: # overriding response content if specified ocr_results = kwargs["response_content"] else: # call original API resp = tenacious_api_post( url=self.ocr_endpoint, file_path=file_path, table_only=not self.use_ocr ) ocr_results = resp.json()["result"] debug_path = kwargs.pop("debug_path", None) artifact_path = kwargs.pop("artifact_path", None) # read PDF through normal reader (unstructured) pdf_page_items = read_pdf_unstructured(file_path) # merge PDF text output with OCR output tables, texts = parse_ocr_output( ocr_results, pdf_page_items, debug_path=debug_path, artifact_path=artifact_path, ) extra_info = extra_info or {} # create output Document with metadata from table documents = [ Document( text=strip_special_chars_markdown(table_text), metadata={ "table_origin": table_text, "type": "table", "page_label": page_id + 1, **extra_info, }, metadata_template="", metadata_seperator="", ) for page_id, table_text in tables ] # create Document from non-table text documents.extend( [ Document( text=non_table_text, metadata={"page_label": page_id + 1, **extra_info}, ) for page_id, non_table_text in texts ] ) return documents ```

The `class OCRReader` parses PDFs by first using our own `[self.ocr_endpoint](<https://github.com/Cinnamon/kotaemon/blob/cd85c4935c85afdd18416fd902e09c4a8b997d86/libs/kotaemon/kotaemon/loaders/ocr_loader.py#L84>)` for analysis, then applying `unstructured.partition.auto.partition` (via the `[read_pdf_unstructured](<https://github.com/Cinnamon/kotaemon/blob/cd85c4935c85afdd18416fd902e09c4a8b997d86/libs/kotaemon/kotaemon/loaders/ocr_loader.py#L92>)` function) for further processing. The results from both methods are then merged using `[parse_ocr_output](<https://github.com/Cinnamon/kotaemon/blob/cd85c4935c85afdd18416fd902e09c4a8b997d86/libs/kotaemon/kotaemon/loaders/ocr_loader.py#L94>)`.

It is evident that the `OCRReader` class continues to rely on the [unstructured library](<https://medium.com/@florian_algo/list/document-intelligence-and-pdf-parsing-2334780a5667>).

## Document Chunking

Once the PDF is parsed, the document should be chunked.

[By default, kotaemon uses](<https://github.com/Cinnamon/kotaemon/blob/cd85c4935c85afdd18416fd902e09c4a8b997d86/libs/ktem/ktem/index/file/pipelines.py#L677>) the `[class TokenSplitter](<https://github.com/Cinnamon/kotaemon/blob/cd85c4935c85afdd18416fd902e09c4a8b997d86/libs/kotaemon/kotaemon/indices/splitters/__init__.py#L10>)` for chunking.

```python class TokenSplitter(LlamaIndexDocTransformerMixin, BaseSplitter): def __init__( self, chunk_size: int = 1024, chunk_overlap: int = 20, separator: str = " ", **params, ): super().__init__( chunk_size=chunk_size, chunk_overlap=chunk_overlap, separator=separator, **params, ) def _get_li_class(self): from llama_index.core.text_splitter import TokenTextSplitter return TokenTextSplitter ```

We can observe that this class internally calls `[llama_index.core.text_splitter.TokenTextSplitter](<https://github.com/run-llama/llama_index/blob/v0.10.68/llama-index-core/llama_index/core/node_parser/text/token.py#L21>)`, which splits the document by specifying parameters such as `chunk_size`, `chunk_overlap`, and `separator`.

## GraphRAG

### What is GraphRAG?

[GraphRAG](<https://arxiv.org/pdf/2404.16130v1>) is a structured, hierarchical approach to RAG, contrasting with naive methods that rely on plain text snippets or simple text chunking. The process involves extracting a knowledge graph from raw text, building a community hierarchy, generating summaries for these communities, and leveraging these structures when performing RAG-based tasks.

Additionally, it was introduced in [my previous article](</advanced-rag-12-enhancing-global-understanding-b13dc9a8db39>).

### Implementation: Indexing Pipeline

First, run `pip list | grep graph` to check if GraphRAG is installed. If it isn't, install it by running `pip install graphrag`.

Press enter or click to view image in full size

Figure 7: The file upload interface of GraphRAG. Screenshot by author.

In the interface shown in Figure 7, after selecting a PDF file and clicking “Upload and Index,” the `[stream](<https://github.com/Cinnamon/kotaemon/blob/cd85c4935c85afdd18416fd902e09c4a8b997d86/libs/ktem/ktem/index/file/graph/pipelines.py#L125>)` function of the `[class GraphRAGIndexingPipeline](<https://github.com/Cinnamon/kotaemon/blob/cd85c4935c85afdd18416fd902e09c4a8b997d86/libs/ktem/ktem/index/file/graph/pipelines.py#L54>)` is triggered. The following is the code:

```python class GraphRAGIndexingPipeline(IndexDocumentPipeline): """GraphRAG specific indexing pipeline""" ... ... def call_graphrag_index(self, input_path: str): # Construct the command command = [ "python", "-m", "graphrag.index", "--root", input_path, "--reporter", "rich", "--init", ] # Run the command yield Document( channel="debug", text="[GraphRAG] Creating index... This can take a long time.", ) result = subprocess.run(command, capture_output=True, text=True) print(result.stdout) command = command[:-1] # Run the command and stream stdout with subprocess.Popen(command, stdout=subprocess.PIPE, text=True) as process: if process.stdout: for line in process.stdout: yield Document(channel="debug", text=line) def stream( self, file_paths: str | Path | list[str | Path], reindex: bool = False, **kwargs ) -> Generator[ Document, None, tuple[list[str | None], list[str | None], list[Document]] ]: file_ids, errors, all_docs = yield from super().stream( file_paths, reindex=reindex, **kwargs ) # assign graph_id to file_ids graph_id = self.store_file_id_with_graph_id(file_ids) # call GraphRAG index with docs and graph_id graph_index_path = self.write_docs_to_files(graph_id, all_docs) yield from self.call_graphrag_index(graph_index_path) return file_ids, errors, all_docs ```

The main steps of the `stream` function are as follows:

1. Execute the standard file indexing process using `yield from super().stream()`.
2. Assign the `graph_id` to `file_ids` by calling `self.store_file_id_with_graph_id(file_ids)`.
3. Finally, call [Microsoft’s GraphRAG](<https://github.com/microsoft/graphrag>) with `docs` and `graph_id` to create the graph index.

### Implementation: Retrieval Pipeline

Let’s take a look at the [retrieval process](<https://github.com/Cinnamon/kotaemon/blob/cd85c4935c85afdd18416fd902e09c4a8b997d86/libs/ktem/ktem/index/file/graph/pipelines.py#L143>) below.

```python class GraphRAGRetrieverPipeline(BaseFileIndexRetriever): """GraphRAG specific retriever pipeline""" ... ... def run( self, text: str, ) -> list[RetrievedDocument]: if not self.file_ids: return [] context_builder = self._build_graph_search() local_context_params = { "text_unit_prop": 0.5, "community_prop": 0.1, "conversation_history_max_turns": 5, "conversation_history_user_turns_only": True, "top_k_mapped_entities": 10, "top_k_relationships": 10, "include_entity_rank": False, "include_relationship_weight": False, "include_community_rank": False, "return_candidate_context": False, "embedding_vectorstore_key": EntityVectorStoreKey.ID, # set this to EntityVectorStoreKey.TITLE i # f the vectorstore uses entity title as ids "max_tokens": 12_000, # change this based on the token limit you have on your model # (if you are using a model with 8k limit, a good setting could be 5000) } context_text, context_records = context_builder.build_context( query=text, conversation_history=None, **local_context_params, ) documents = self.format_context_records(context_records) plot = self.plot_graph(context_records) return documents + [ RetrievedDocument( text="", metadata={ "file_name": "GraphRAG", "type": "plot", "data": plot, }, ), ] ```

The pipeline is illustrated in Figure 8.

Figure 8: The retrieval pipeline of kotaemon’s GraphRAG. Image by author.

Here are the main steps:

1. **Build graph search context** : It calls the `[_build_graph_search](<https://github.com/Cinnamon/kotaemon/blob/cd85c4935c85afdd18416fd902e09c4a8b997d86/libs/ktem/ktem/index/file/graph/pipelines.py#L161>)` function to construct a `context_builder` for graph search. This context builder uses the built graph index, entities, relationships, reports, and semantic embeddings to generate the context.
2. **Build context** : Uses the `context_builder.build_context` function to generate the context text and `context_records` based on the query.
3. **Format context records into documents** : Calls the `[format_context_records](<https://github.com/Cinnamon/kotaemon/blob/cd85c4935c85afdd18416fd902e09c4a8b997d86/libs/ktem/ktem/index/file/graph/pipelines.py#L268>)` function to format the `context_records` into a list of `RetrievedDocument` objects. These documents include content on entities, relationships, reports, and sources.
4. **Plot the knowledge graph** : Uses the `[plot_graph](<https://github.com/Cinnamon/kotaemon/blob/cd85c4935c85afdd18416fd902e09c4a8b997d86/libs/ktem/ktem/index/file/graph/pipelines.py#L306>)` method to extract relationships from `context_records` and generate a knowledge graph (a visual representation of the relationships).
5. **Return documents and plot** : Finally, the function returns a list of documents, which include the context documents (entities, relationships, reports, etc.) and the knowledge graph visualization.

## Reasoning

As shown in Figure 9, kotaemon primarily implements four types of reasoning methods: simple, complex, react, and rewoo.

Press enter or click to view image in full size

Figure 9: Reasoning methods supported by kotaemon: simple, complex, react, and rewoo. Screenshot by author.

The **reasoning methods** aim to enhance how the system processes and answers complex queries, especially in multi-hop question answering, where reasoning over multiple pieces of information is necessary.

The reasoning framework uses different pipelines to ensure that the system can handle both straightforward and complex tasks by breaking them down into smaller, more manageable components.

This section outlines the key principles and code of the main reasoning pipelines.

``` # Setup your new reasoning pipeline or modify existing one.KH_REASONINGS = [ "ktem.reasoning.simple.FullQAPipeline", "ktem.reasoning.simple.FullDecomposeQAPipeline", "ktem.reasoning.react.ReactAgentPipeline", "ktem.reasoning.rewoo.RewooAgentPipeline",] ```

### Simple Reasoning Pipeline

This pipeline(`[class FullQAPipeline](<https://github.com/Cinnamon/kotaemon/blob/cd85c4935c85afdd18416fd902e09c4a8b997d86/libs/ktem/ktem/reasoning/simple.py#L447>)`) is designed for straightforward question-answering tasks, where the query can be resolved with a single retrieval and response process.

It is optional to [rewrite the question](<https://github.com/Cinnamon/kotaemon/blob/cd85c4935c85afdd18416fd902e09c4a8b997d86/libs/ktem/ktem/reasoning/simple.py#L707>) using the following [prompt](<https://github.com/Cinnamon/kotaemon/blob/cd85c4935c85afdd18416fd902e09c4a8b997d86/libs/ktem/ktem/reasoning/prompt_optimization/rewrite_question.py#L6>).

``` DEFAULT_REWRITE_PROMPT = ( "Given the following question, rephrase and expand it " "to help you do better answering. Maintain all information " "in the original question. Keep the question as concise as possible. " "Give answer in {lang}
" "Original question: {question}
" "Rephrased question: ") ```

But simple reasoning pipeline doesn’t involve question decomposition.

### Complex Reasoning Pipeline

For complex questions, kotaemon uses the `[class FullDecomposeQAPipeline](<https://github.com/Cinnamon/kotaemon/blob/cd85c4935c85afdd18416fd902e09c4a8b997d86/libs/ktem/ktem/reasoning/simple.py#L810>)` . It primarily relies on the `[class DecomposeQuestionPipeline](<https://github.com/Cinnamon/kotaemon/blob/cd85c4935c85afdd18416fd902e09c4a8b997d86/libs/ktem/ktem/reasoning/prompt_optimization/decompose_question.py#L22>)` to break down a large, complex question into smaller sub-questions, each of which can be answered individually.

The prompt is shown below.

``` DECOMPOSE_SYSTEM_PROMPT_TEMPLATE = ( "You are an expert at converting user complex questions into sub questions. " "Perform query decomposition using provided function_call. " "Given a user question, break it down into the most specific sub" " questions you can (at most 3) " "which will help you answer the original question. " "Each sub question should be about a single concept/fact/idea. " "If there are acronyms or words you are not familiar with, " "do not try to rephrase them." ) ```

### **Agent-Based Reasoning**

The system supports agent-based reasoning methods such as [ReAct](<https://arxiv.org/pdf/2210.03629v3>) and [ReWOO](<https://arxiv.org/pdf/2305.18323v1>), which allow it to reason step-by-step and handle more dynamic conversations. This is useful for complex dialogues where the answer evolves as more information is gathered.

ReAct, for example, follows the classic “Thought, Action, Action Input, and Observation” model. [The corresponding prompt ](<https://github.com/Cinnamon/kotaemon/blob/cd85c4935c85afdd18416fd902e09c4a8b997d86/libs/ktem/ktem/reasoning/react.py#L126>)is shown below.

``` DEFAULT_QA_PROMPT = ( "Answer the following questions as best you can. Give answer in {lang}. " "You have access to the following tools:
" "{tool_description}
" "Use the following format:

" "Question: the input question you must answer
" "Thought: you should always think about what to do

" "Action: the action to take, should be one of [{tool_names}]

" "Action Input: the input to the action, should be different from the action input " "of the same action in previous steps.

" "Observation: the result of the action

" "... (this Thought/Action/Action Input/Observation can repeat N times)
" "#Thought: I now know the final answer
" "Final Answer: the final answer to the original input question

" "Begin! After each Action Input.

" "Question: {instruction}
" "Thought: {agent_scratchpad}
") ```

## Query Processing

In the kotaemon project, the only query processing method identified so far is query rewriting in the previously mentioned reasoning processes. Other features, such as query expansion, [classification, or refining](</advanced-rag-11-query-classification-and-refinement-2aec79f4140b>), have not been observed.

If query processing is required, [custom pipelines](<https://github.com/Cinnamon/kotaemon?tab=readme-ov-file#adding-your-own-rag-pipeline>) can be implemented.

## Prompt Compression

Currently, kotaemon does not seem to employ techniques for [prompt compression](<https://medium.com/ai-advances/advanced-rag-09-prompt-compression-95a589f7b554>), such as reducing the token count or summarizing prompts to optimize processing efficiency.

If prompt compression is needed, it could be implemented through [custom pipelines](<https://github.com/Cinnamon/kotaemon?tab=readme-ov-file#adding-your-own-rag-pipeline>) to reduce the token load sent to LLMs, especially in cases of large documents or conversation histories.

## Web Service and Frontend

Kotaemon’s web service and frontend are implemented using a combination of Gradio for the frontend UI and standard web services running on Python, including support for both local and cloud-based LLMs.

The frontend is built using Gradio UI, which provides a clean, minimalistic user interface. It allows users to upload documents, pose questions, and interact with the system.

The Gradio-based UI integrates well with Python and offers a customizable framework to display RAG results, including document previews and citations.
