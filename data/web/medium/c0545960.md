Technical guide on implementing GraphRAG architecture with FalkorDB for BFSI applications. Covers knowledge graph creation, Cypher query generation, and LLM integration for enterprise-grade AI assistants

Retrieval Augmented Generation (RAG) has come a long way since businesses started embracing it. As we’ve seen, organizations are constantly finding innovative ways to unlock more value out of it. Sure, retrieval processes and search algorithms have gotten faster and more efficient. But they still falter when it comes to handling complex tasks like multi-hop reasoning or answering those tricky questions that need connecting the dots between scattered bits of information.

Let’s explore this subject further with the help of a real-world example: “What was Christopher Columbus’s ship that sank on Christmas Day in 1492 called?”

A standard RAG system would typically follow these steps:

_Identify the Event_ : Find information about Columbus’s ships and shipwrecks.

_Confirm the Date_ : Verify which ship was involved in the Christmas Day incident.

_Determine the Name_ : Extract the specific ship’s name.

However, the first step can often pose a challenge because basic RAG systems rely on semantic similarity for text retrieval. They’re great at finding what’s similar, but not so great at connecting multiple facts to answer complex queries. When crucial information is scattered across different documents, these systems struggle to piece it together. Traditional solutions, like manually creating Q&A pairs for common queries, are not just expensive but also impractical.

To solve these limitations, Microsoft Research came up with a game-changer — [GraphRAG](<https://arxiv.org/pdf/2404.16130>). This innovative approach takes RAG to the next level by weaving knowledge graphs into both retrieval and generation. Knowledge graphs create a richer representation of your data by preserving the entities and relationships as nodes and edges. It’s like turning a messy web of information into a neatly organized map. Take a look at the knowledge graph below — you’ll instantly see how much simpler it is to answer complex queries with just a quick traversal through it. Pretty amazing, right?

## Vector Database vs Graph Database in RAG

Choosing between a vector database and a graph database for your RAG system depends entirely on the problem you’re tackling, your system architecture needs, and your performance goals. Here are some insights to help you decide.

### Vector Databases:

* Excel at multidimensional data representation and similarity searches.
* Ideal for image processing, recommendation systems, and real-time RAG.
* Scale horizontally with data volume.
* Limitations: Potential accuracy trade-offs with ANN algorithms and dimensionality issues.

### Graph Databases:

* Specialized in managing complex relationships and interconnected data.
* Best for social network analysis, fraud detection, and knowledge representation.
* Superior at relationship-based queries and traversals.
* Limitations: May face scalability challenges and latency with complex structures.

For simplicity, you can provide the required LLM to LangChain and let it handle the rest. The LLM Graph Transformer module will take care of creating the knowledge graph for you. Let me explain what’s happening behind the scenes.

The LLM Graph Transformer uses two different approaches to create the graph:

1. **Tool-Based Mode** : This is the default mode and works with any LLM that supports tool calling. In this mode, nodes and relationships are defined as classes.
2. **Prompt-Based Mode** : This is the fallback mode, used when the LLM does not support tool calling. Here, the model employs few-shot prompting to extract entities and their relationships from text. These are then parsed into JSON format to create graph nodes and connections.

```python from langchain_experimental.graph_transformers import LLMGraphTransformergraph_transformer = LLMGraphTransformer(llm=llm)data = graph_transformer.convert_to_graph_documents(docs)graph.add_graph_documents(data) ```

You can specify custom node types to restrict the graph structure. If you don’t, the LLM will automatically determine the appropriate node types based on the content. For example:

``` allowed_nodes = ["Organization", "FinancialProduct", "Feature", "Service", "Program"]graph_transformer = LLMGraphTransformer(llm=llm, allowed_nodes=allowed_nodes)data = graph_transformer.convert_to_graph_documents(docs)graph.add_graph_documents(data) ```

## Querying the Knowledge Graph

While creating a graph database is relatively straightforward, extracting meaningful information requires expertise in query languages like Cypher. Cypher is a declarative query language specifically designed for graph databases, using pattern-matching syntax to traverse nodes and relationships efficiently. FalkorDB adheres to the [OpenCypher](<https://opencypher.org/>) format.

### Automated Cypher Query Generation

We need to incorporate some prompt engineering to generate high-quality Cypher queries. Currently, our implementation uses carefully crafted prompts that combine the database schema (including nodes and relationships) with user queries. However, there’s always room for improvement. You could extend this approach by integrating tool-calling with OpenAI or leveraging fine-tuned language models for even more precise query generation.

Here’s how to define a function to refine the schema for the prompt:

```python def format_schema_for_prompt(schema: Any) -> str: """ Format the graph schema into a clear, LLM-friendly string. Args: schema: Schema object from the graph database Returns: Formatted string representation of the schema """ try: nodes = set() relationships = [] for item in schema: if hasattr(item, 'start_node'): nodes.add(item.start_node) nodes.add(item.end_node) relationships.append({ 'start': item.start_node, 'type': item.relationship_type, 'end': item.end_node }) # Format the schema information formatted_output = "Node Types:
" for node in sorted(nodes): formatted_output += f"- {node}
" formatted_output += "
Relationships:
" for rel in relationships: formatted_output += f"- {rel['start']} -[{rel['type']}]-> {rel['end']}
" return formatted_output except Exception as e: # Fallback to returning raw schema if formatting fails return str(schema) ```

The formatted schema can now be included in the prompt template.

``` current_schema = graph.schemaformatted_schema = format_schema_for_prompt(current_schema) system_prompt = f"""You are an expert at converting natural language questions into Cypher queries. The graph has the following schema: {formatted_schema} Return ONLY the Cypher query without any explanation or additional text. Make sure to use proper Cypher syntax and casing. Use the exact relationship types and node labels as shown in the schema.""" ```

### Cypher Query Output Analysis

Once the Cypher query is complete, the result needs to be passed to another LLM. This dual-LLM approach ensures that users receive clear, contextual information instead of raw database results during their chat interactions.

```python def format_results_for_llm(results: List) -> str: """ Format results in a way that's optimal for LLM analysis. Args: results: Processed query results Returns: Formatted string of results """ output = "" for i, row in enumerate(results, 1): output += f"
Item {i}:
" for item in row: if isinstance(item, dict): output += f"Type: {item['type']}
" output += "Properties:
" for key, value in item['properties'].items(): output += f" - {key}: {value}
" else: output += f"Value: {item}
" output += "---
" return output ```
