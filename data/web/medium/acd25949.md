## Building a flow

In the role of a "recruiter," your initial task is to review the requirements of the position and create a list of qualifications desired by the client. After that, you sit through a stack of CVs to identify the best potential candidates. In the tech industry, **this typically involves considering the candidate's levels of experience and their backgrounds in a bullet point list.**

To automate the recruiting process effectively, we need to build a flow that systematically handles each step from parsing the job role to evaluating the resumes. Here’s how we can structure this flow:

### 1\. Define the Open Role:

* Begin by defining the open role’s requirements on platforms like LinkedIn.
* Extract the role’s content, which includes skills, experience, and other qualifications needed.

### **2\. Collect Resumes:**

* Gather over 100 CVs from applicants who responded to the job posting on LinkedIn.

### 3\. Parse the Job Role:

* Create a contract for the job that you are using, so it can be parsed in your code. In the image is called `ProcessRole`.
* This involves identifying key attributes such as required skills (e.g., React, TypeScript), years of experience, educational background, etc.

### 4\. Process Resumes:

* Get the Resumes from your source (Linkedin), and save them into your system.

### 5\. Evaluate Candidates:

* Compare each candidate’s CV against the job requirements, `ProcessResumes`.

### 6\. Filter and Rank Candidates:

* Based on the evaluation, filter out candidates who do not meet the minimum requirements.

## Parsing the job role

The first step will be to parse the job role. The best way to do to the qualitative and quantitative categorization of a job role is to **divided into parts and set it as bullet points**. We certainly do this already, but for this process needs to be converted into a JSON. The image below describes the process:

![image](https://miro.medium.com/v2/resize:fit:700/1*vOdJF8GPjToVQVKoroTcxQ.png)

When designing this contract, we need to select specific criteria for our role and others, **such as English proficiency level, years of experience, and a college degree in the relevant field**. We can use ExtractThinker, which utilizes Pydantic and an [**instructor**](<https://github.com/jxnl/instructor>)**for the heavy lifting** , to create this contract.

```python class RoleContract(Contract): company_name: str = Field("Company name") years_of_experience: int = Field("Years of experience required. If not mention, calculate with start date and end date") is_remote: bool = Field("Is the role remote?") country: str = Field("Country of the role") city: Optional[str] = Field("City of the role") list_of_skills: List[str] = Field(""" list of strings, e.g ["5 years experience", "3 years in React", "Typescript"] Make the lists of skills to be a yes/no list, so it can be used in the LLM model as a list of true/false """) ```

We can now proceed with building our extractor for this task. In this example, we will use **PyPDF and GPT-4o** as the main components. The role contract will be extracted only once and used for all the remaining CVs, so the cost is not a factor here.

```python from extract_thinker import DocumentLoaderPyPdf, Extractor, Contractjob_role_path = "path/to/job_role.pdf"extractor_job_role = Extractor()extractor_job_role.load_document_loader( DocumentLoaderPyPdf())extractor_job_role.load_llm("gpt-4o")extractor_job_role.extract(job_role_path, RoleContract) ```

### DeepInfra and quantization

Usually, you should not trust quantized models, especially when they are already small models.

For those who were not introduced to [DeepInfra](<https://deepinfra.com>), it's a company that provides **quantized LLMs** , making AI inferences more affordable. The prices are excellent, competing with Groq even while offering scalability.

![Price comparison between Groq and deepinfra](https://miro.medium.com/v2/resize:fit:700/1*b6jvwpb3W4WVWh3Szb3GNw.png)

As long as the use case works with smaller models, it's a great alternative.

### **Limitations**

Classification and categorization can be quite limited, especially when dealing with numbers. Our results showed that while the descriptions were correctly classified, simple mistakes happen, **such as returning 9 instead of 39**. This is one of the limitations that may arise, and you can find [more information on this topic here](<https://medium.com/r?url=https%3A%2F%2Ftowardsdatascience.com%2Fintroduction-to-weight-quantization-2494701b9c0c>).

### LiteLLM — Load balancer and fallback

When leading with a high throughput of requests in LLM you will always have limitations**.** To solve this problem you can use [LiteLLM to build your infrastructure](<https://docs.litellm.ai/docs/proxy/reliability>). This code is a reflection of the image above:

```python import osfrom litellm import Routerrpm = 5000 # Rate limit in requests per minutemodel_list = [ { "model_name": "Meta-Llama-3-8B-Instruct", "litellm_params": { "model": "deepinfra/meta-llama/Meta-Llama-3-8B-Instruct", "api_key": os.getenv("DEEPINFRA_API_KEY"), "rpm": rpm, }, }, { "model_name": "Mistral-7B-Instruct-v0.2", "litellm_params": { "model": "deepinfra/mistralai/Mistral-7B-Instruct-v0.2", "api_key": os.getenv("DEEPINFRA_API_KEY"), "rpm": rpm, } }, { "model_name": "groq-llama3-8b-8192", "litellm_params": { "model": "groq/llama3-8b-8192", "api_key": os.getenv("GROQ_API_KEY"), "rpm": rpm, } },]# Adding fallback modelsfallback_models = [ { "model_name": "claude-3-haiku-20240307", "litellm_params": { "model": "claude-3-haiku-20240307", "api_key": os.getenv("CLAUDE_API_KEY"), } }, { "model_name": "azure-deployment", "litellm_params": { "model": "azure/<your-deployment-name>", "api_base": os.getenv("AZURE_API_BASE"), "api_key": os.getenv("AZURE_API_KEY"), "rpm": 1440, } }]# Combine the listsmodel_list.extend(fallback_models)# Define the router configurationrouter = Router( model_list=model_list, default_fallbacks=["claude-3-haiku-20240307", "azure/<your-deployment-name>"], context_window_fallbacks=[ {"Meta-Llama-3-8B-Instruct": ["claude-3-haiku-20240307"]}, {"groq-llama3-8b-8192": ["claude-3-haiku-20240307"]}, {"Mistral-7B-Instruct-v0.2": ["claude-3-haiku-20240307"]} ], set_verbose=True) ```

Three different situations are described in this configuration:

* **Load Balancing** : The requests rotate between the models from Groq and Deepinfra.
* **Fallback context window** : Because the LLM only takes an 8k context window for this model, and sometimes a resume contains more than 5 pages (~1000 token per page), Claude haiku model can handle this edge situation.
* **Too many requests fallback** : If the load balancing cannot take care of that many requests (e.g 50k requests per minute) the fallback will help with the extra models.

Using this in our code, we can add the router to our LLM in the Extractor object in the following way:

## **Calculations and cost — 4000 CVs per $1**

The average size of a resume is 2–5 pages; we’ll use an average of 3.5 pages per resume for our calculations. Each page typically contains around 1,000 tokens (**counting already with library overhead**), so a resume with 3.5 pages will have approximately 3,500 tokens.

Given the cost of $0.07 per million tokens, we can determine the cost to process a single CV as follows:

![image](https://miro.medium.com/v2/resize:fit:700/1*_Kp1PHDA6GsZeHaCBABewg.png)

So we can just **multiply per 1000 and we get $0.245!** So already with margin constants, you get 4000 pages/$, but in some cases can be closer to 5000!
