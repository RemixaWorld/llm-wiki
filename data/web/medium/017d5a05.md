# Custom metrics for instruction fine-tuning of LLMs

When fine-tuning large language models (LLMs) on downstream tasks, we often rely too much on generic metrics like loss/perplexity. While minimizing loss/perplexity on validation dataset helps avoid overfitting, it doesn’t guarantee the best performance on specialized tasks.

Take fine-tuning an LLM on question answering as an example, we care most that the model outputs precise answer. 91% correct and 9% absolutely incorrect answer is still better than 90% correct and 10% close enough answer. However, loss metrics only penalize text deviations from the ground truth. An increase of loss can either be contributed by a higher number of deviations, or some larger deviations. Therefore, a minimal loss does not necessarily indicate top-level accuracy.

The same issue applies in text summarization, which is another common use case of instruction fine-tuning. Here our end goal is generating high-quality summaries as measured by [ROUGE](<https://en.wikipedia.org/wiki/ROUGE_\(metric\)#:~:text=The%20metrics%20compare%20an%20automatically,produced%20summary%20and%20the%20reference.>) scores against human references. Yet the checkpoint with minimum validation loss — that best replicates the pattern of the fine-tuning data — may still achieve mediocre ROUGE, and thus subpar performance on the end summarization task.

In essence, minimum loss produces the best approximation of the fine-tuning data, rather than the best task performance. Custom metrics aligned directly with the end goals are needed to optimize instruction fine-tuning.

Luckily, the [Huggingface Trainer](<https://huggingface.co/docs/transformers/main_classes/trainer>) provides a simple way to incorporate custom validation metrics that directly reflect your end goals. By tailoring metrics capturing real-world efficacy, you can optimize your model for its final purpose rather than just its ability to fit the fine-tuning data.

In this blog post, I will demonstrate how to configure Huggingface transformer trainer to incorporate customized evaluation metrics. Monitoring these metrics during fine-tuning will enable you to pick the best model checkpoint for your end application. I will walk through the steps using an example of fine-tuning [Llama2 7B](<https://huggingface.co/meta-llama/Llama-2-7b>) on a [multi-choice medical question answering dataset](<https://huggingface.co/datasets/mamachang/medical>).

**Dataset**

I use data from the [MedQA](<https://arxiv.org/abs/2009.13081>) training set. It has 10178 multiple-choice questions. Here is one example:

Q:A 29-year-old man comes to the emergency department because of progressively worsening fatigue and shortness of breath for the past 2 weeks. His only medication is insulin. Examination shows elevated jugular venous distention and coarse crackles in both lungs. Despite appropriate life-saving measures, he dies. Gross examination of the heart at autopsy shows concentrically thickened myocardium and microscopic examination shows large cardiomyocytes with intracellular iron granules. Examination of the spinal cord shows atrophy of the lateral corticospinal tracts, spinocerebellar tracts, and dorsal columns. Which of the following is the most likely underlying cause of this patient’s condition??

‘A’: ‘SOD1 gene mutation on chromosome 21’, ‘B’: ‘CTG trinucleotide repeat expansion on chromosome 19’, ‘C’: ‘Dystrophin gene mutation on the X chromosome’, ‘D’: ‘GAA trinucleotide repeat expansion on chromosome 9’, ‘E’: ‘SMN1 gene mutation on chromosome 5’

I format the dataset into instruction dataset, and split the dataset into 64% for training, 16% for validation, and 20% for testing final model performance. The training sample of above example is

{“instruction”:“Please answer with one of the option in the bracket”,“output”:“D: GAA trinucleotide repeat expansion on chromosome 9",“input”:“Q:A 29-year-old man comes to the emergency department because of progressively worsening fatigue and shortness of breath for the past 2 weeks. His only medication is insulin. Examination shows elevated jugular venous distention and coarse crackles in both lungs. Despite appropriate life-saving measures, he dies. Gross examination of the heart at autopsy shows concentrically thickened myocardium and microscopic examination shows large cardiomyocytes with intracellular iron granules. Examination of the spinal cord shows atrophy of the lateral corticospinal tracts, spinocerebellar tracts, and dorsal columns. Which of the following is the most likely underlying cause of this patient’s condition??
{‘A’: ‘SOD1 gene mutation on chromosome 21’, ‘B’: ‘CTG trinucleotide repeat expansion on chromosome 19’, ‘C’: ‘Dystrophin gene mutation on the X chromosome’, ‘D’: ‘GAA trinucleotide repeat expansion on chromosome 9’, ‘E’: ‘SMN1 gene mutation on chromosome 5’},”}

For this dataset, I want the model to generate the exact right answer, including the answer options (D in this example) and the answer content (GAA trinucleotide repeat expansion on chromosome 9). Therefore, I would define my compute metric as the accuracy of answers.

**Define compute metric**

Huggingface transformer [Trainer](<https://huggingface.co/docs/transformers/main_classes/trainer>) uses compute_metric argument to compute metrics at evaluation. It returns a dictionary type where the key specifies metric name and the value is the metric value. If your compute metric applies on the text as in my case, you will need to decode the token ids into sentences before calculating the metric.

```python def preprocess_logits_for_metrics(logits, labels): # the actualy prediction is the first element of the tuple if isinstance(logits, tuple): logits = logits[0] return logits.argmax(dim=-1)def compute_metrics(eval_preds): preds, labels = eval_preds # preds have the same shape as the labels, after the argmax(-1) has been calculated # by preprocess_logits_for_metrics labels = labels.reshape(-1) preds = preds.reshape(-1) # -100 corresponds to tokens that should be ignored mask = labels != -100 labels = labels[mask] preds = preds[mask] # decode to obtain text that custom metric will be applied on # tokenizer can be obtained from model id decoded_preds = tokenizer.batch_decode(preds, skip_special_tokens=True) decoded_labels = tokenizer.batch_decode(labels, skip_special_tokens=True) # I define process_tokens function to extract answers from the model prediction processed_preds = process_tokens(decoded_preds) processed_labels = process_tokens(decoded_labels) # the custom_metric function is where you define your custom metric return custom_metric(processed_preds, processed_labels) ```

**Configure trainer**

Once compute metric is defined, configure trainer to use the defined compute metric.

``` trainer = Trainer( model=model, args=training_args, train_dataset=train_dataset, eval_dataset=eval_dataset, data_collator=default_data_collator, compute_metrics=compute_metrics, preprocess_logits_for_metrics = preprocess_logits_for_metrics, ) ```

**Monitor the metrics with TensorBoard**

With Huggingface transformer, it’s convenient to use TensorBoard to monitor the training job. Configure Huggingface transformer estimator as below.

```json # tensorboard logLOG_DIR="/opt/ml/output/tensorboard"tb_output_config = TensorBoardOutputConfig(s3_output_path=f"s3://{sess.default_bucket()}/tensorboard", container_local_output_path=LOG_DIR)# create the Estimator and use with SageMakerhuggingface_estimator = HuggingFace( entry_point = 'script.py', # train script source_dir = 'scripts', # directory which includes all the files needed for training instance_type = instance_type, # instances type used for the training job instance_count = 1, # the number of instances used for training base_job_name = job_name, # the name of the training job role = role, # Iam role used in training job to access AWS ressources, e.g. S3 volume_size = 300, # the size of the EBS volume in GB transformers_version = '4.28', # the transformers version used in the training job pytorch_version = '2.0', # the pytorch_version version used in the training job py_version = 'py310', # the python version used in the training job tensorboard_output_config=tb_output_config, hyperparameters = hyperparameters, # the hyperparameters passed to the training job environment = { "HUGGINGFACE_HUB_CACHE": "/tmp/.cache" }, # set env variable to cache models in /tmp) ```

Add the following two parameters in TrainingArguments used in the above trainer.

``` logging_dir=LOG_DIR,report_to='tensorboard', ```

Then you should see the added custom metric (accuracy) along with the default loss metric in the TensorBoard application. In my use case, although validation loss starts to increase from about 1K step, the evaluation accuracy still benefit from training more steps. By monitoring the right metric, I can obtain the best checkpoint when model yields the best performance on the end application.

**Summary**

The takeaway? When fine-tuning LLMs, go beyond generic loss metrics. Tailor your validation approach to the end application, using metrics that directly capture performance on the target task. This allows you to customize model selection for optimal downstream results. It’s also worth to notice the limitation: not all end applications can be quantitatively measured and hence cannot be directly used to guide training.
