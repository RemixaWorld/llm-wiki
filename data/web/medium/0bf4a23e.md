As we build increasingly capable ai agents especially ones that rely on long conversations, multi-step reasoning, and tool use we also run into a problem: the context gets _bloated_.

And when that happens, performance starts to fall apart in weird and unpredictable ways, a growing number of researchers are pointing out that bigger contexts aren’t always better , in fact .. without careful management, they can actively hurt your model.

In this post, i want to dig into three specific tactics that help prevent your agent’s context from collapsing under its own weight: **Context Pruning** , **Context Summarization** , and **Tool Loadout ,** these are simple ideas, but they make a massive difference in how well your model reasons over long trajectories.

## 1\. Context Pruning

Context pruning is exactly what it sounds like: trimming away the parts of the context that don’t matter , when an agent is making a decision or answering a question, it doesn’t need _everything_ it’s seen before it just needs what’s relevant, and if you leave too much in, the model can get distracted, fixated on the wrong thing, or even revert to memorized patterns instead of reasoning fresh.

Chroma published a great report on this called [**context rot**](<https://research.trychroma.com/context-rot>) — basically, the longer your context gets, the more surprising and inconsistent the model’s performance becomes. in other words long inputs don’t just slow things down, they _rot_ the model’s reasoning in ways that are hard to predict.

One practical tool for pruning is **Provence** ([which I’ve talked about before](</@ayoubkirouane3/stop-overfeeding-your-llm-smart-context-pruning-with-provence-3b42dcb06f4e>)). It’s a model trained specifically to clean up retrieval-augmented generation (RAG) contexts , given a question and a big blob of retrieved info, Provence strips away the noise and keeps just the parts that matter , this can save a ton of tokens and more importantly, sharpen the model’s focus.

That said, pruning isn’t without risks .. cognition labs has pointed out that compression, especially aggressive compression, can introduce new failure modes, if u cut too deep and lose key details, the model may hallucinate or reach incorrect conclusions .. so it’s all about balance…

**2 / Context Pruning Pipeline**

This block defines a custom **Context Pruning Pipeline** — a small but powerful class that helps make long contexts leaner and more focused. It uses retrieval, optional reranking, and an AI agent to trim down unneeded content before feeding it into an LLM.

The idea is to _only keep what matters_ when answering a user query.

```python from llama_index.core.schema import NodeWithScorefrom pydantic_ai import Agentfrom pydantic_ai.settings import ModelSettingsclass ContextPruningPipeline: def __init__(self, index, top_n=15, similarity_top_k=10, use_reranker=True): self.retriever = index.as_retriever(similarity_top_k=similarity_top_k) self.top_n = top_n self.use_reranker = use_reranker # Initialize Cohere reranker only if requested if use_reranker: self.reranker = CohereRerank(top_n=top_n, model="rerank-v3.5") else: self.reranker = None # Initialize the pruning agent self.pruning_agent = self._create_pruning_agent() def _create_pruning_agent(self): """Create the pruning agent with the specified configuration""" tool_pruning_prompt = """You are an expert at extracting relevant information from documents. Your task: Analyze the provided document and extract ONLY the information that directly answers or supports the user's specific request. Remove all irrelevant content. Instructions for pruning: 1. Keep information that directly addresses the user's question 2. Preserve key facts, data, and examples that support the answer 3. Remove tangential discussions, unrelated topics, and excessive background 4. Maintain the logical flow and context of relevant information 5. If multiple subtopics are discussed, focus only on those relevant to the request 6. Preserve important quotes, statistics, and research findings when relevant Return the pruned content in a clear, concise format that maintains readability while focusing solely on what's needed to answer the user's request. """ return Agent( model="google-gla:gemini-2.5-flash-lite", system_prompt=tool_pruning_prompt, output_type=str, retries=2, model_settings=ModelSettings(temperature=1.0) ) def prune_context_with_agent(self, user_request: str, context: str) -> str: """Prune a single context using the agent""" prompt = f"User's Request: {user_request}

Document to analyze:
{context}" try: result = self.pruning_agent.run_sync(prompt) return result.output if hasattr(result, 'output') else str(result) except Exception as e: print(f"Error pruning context: {e}") return context # Return original context if pruning fails def run(self, query: str) -> list[NodeWithScore]: # Step 1: Retrieve retrieved_nodes = self.retriever.retrieve(query) # Step 2: Optional reranking if self.reranker: retrieved_nodes = self.reranker.postprocess_nodes( nodes=retrieved_nodes, query_str=query ) # Step 3: Prune with agent and wrap in NodeWithScore pruned_nodes = [] for node in retrieved_nodes: original_content = node.get_content() pruned_content = self.prune_context_with_agent(query, original_content) if pruned_content and pruned_content.strip(): # Create new NodeWithScore with pruned content pruned_node = NodeWithScore( node=node.node, score=node.score, # Keep original retrieval/reranking score ) pruned_node.node.text = pruned_content.strip() pruned_nodes.append(pruned_node) return pruned_nodes ```

**3 / Run the pipeline :**

This little snippet puts the **ContextPruningPipeline** into action.

It’s a minimal working example that shows how you might use the pruning logic in a real query flow.

> **Bottom line:** Context pruning is about helping your model focus on what actually matters. When you blindly throw long chunks of retrieved text into the prompt, you’re not helping the model — you’re distracting it. Pruning cuts through that noise. It keeps the useful information and gets rid of the fluff, making answers more accurate, concise, and grounded.

## 2\. Context Summarization

Another useful trick is **context summarization** — boiling down everything the model has seen so far into a clean, concise summary. Instead of dragging around a massive chat history or sequence of tool outputs, you compress it into something smaller but still useful.

Why do this? again .. it’s about keeping the model focused , when the context gets too long, models can over-attend to that history and underweight what they actually learned during training.

> [Chroma’s context rot](<https://research.trychroma.com/context-rot>) report hits on this again — it’s not just about token limits, it’s about the model _forgetting how to think_ because it’s overwhelmed with baggage.

If you’ve played with claude code or gemini cli, u’ve probably seen summarization in action already. when the context nears its max size, the agent will auto-summarize the entire interaction to make room for more input, that’s not just for memory management — it’s actually part of how the agent keeps reasoning coherent across long sessions.

Summarization can be done in a few different ways — recursive, hierarchical, or even turn-by-turn. u might summarize at key points, like after a heavy tool call or a long back-and-forth, just like pruning, though, summarization comes with trade-offs, if your summary misses a critical detail, the model could go off track, cognition has warned about this too: compress carefully, and always test your summaries.

### Code example :

This code sets up and runs a **Context Summarization Pipeline** — a lightweight system that takes long, retrieved documents and condenses them down to their most essential ideas.

```python from llama_index.core.schema import NodeWithScorefrom pydantic_ai import Agentfrom pydantic_ai.settings import ModelSettingsclass ContextSummarizationPipeline: def __init__(self, index, top_n=15, similarity_top_k=10, use_reranker=True): self.retriever = index.as_retriever(similarity_top_k=similarity_top_k) self.top_n = top_n self.use_reranker = use_reranker # Initialize Cohere reranker only if requested if use_reranker: self.reranker = CohereRerank(top_n=top_n, model="rerank-v3.5") else: self.reranker = None # Initialize the summarization agent self.summarization_agent = self._create_summarization_agent() def _create_summarization_agent(self): """Create the summarization agent with the specified configuration""" tool_summarization_prompt = """You are an expert at condensing technical documents while preserving all critical information.Transform the provided document into a comprehensive yet concise version. Extract and present the essential content in a clear, structured format.Condensation Guidelines:1. **Preserve All Key Information**: Include every important fact, statistic, finding, and conclusion2. **Eliminate Verbosity**: Remove repetitive text, excessive explanations, and filler words3. **Maintain Logical Structure**: Keep the natural flow and relationships between concepts4. **Use Precise Language**: Replace lengthy phrases with direct, technical terminology5. **Ensure Completeness**: The condensed version should contain all necessary information to fully understand the topicCreate a comprehensive condensed version that is 50-70% shorter while retaining 100% of the essential information.""" return Agent( model="google-gla:gemini-2.5-flash-lite", system_prompt=tool_summarization_prompt, output_type=str, retries=2, model_settings=ModelSettings(temperature=1.0) ) def summarize_context_with_agent(self, user_request: str, context: str) -> str: """Summarize a single context using the agent""" prompt = f"Document to condense:
{context}" try: result = self.summarization_agent.run_sync(prompt) return result.output if hasattr(result, 'output') else str(result) except Exception as e: print(f"Error summarizing context: {e}") return context # Return original context if summarization fails def run(self, query: str) -> list[NodeWithScore]: # Step 1: Retrieve retrieved_nodes = self.retriever.retrieve(query) # Step 2: Optional reranking if self.reranker: retrieved_nodes = self.reranker.postprocess_nodes( nodes=retrieved_nodes, query_str=query ) # Step 3: Summarize with agent and wrap in NodeWithScore summarized_nodes = [] for node in retrieved_nodes: original_content = node.get_content() summarized_content = self.summarize_context_with_agent(query, original_content) if summarized_content and summarized_content.strip(): # Create new NodeWithScore with summarized content summarized_node = NodeWithScore( node=node.node, score=node.score, # Keep original retrieval/reranking score ) summarized_node.node.text = summarized_content.strip() summarized_nodes.append(summarized_node) return summarized_nodes%%timesummarization_pipeline = ContextSummarizationPipeline(index, top_n=5 , similarity_top_k=15)query = "What did the author do growing up?"summarization_results = summarization_pipeline.run(query)print([summarization_results[i].text for i in range(len(summarization_results))]) ```

It’s a simple example of how summarization can help keep your agent’s context sharp and efficient without losing important information.

> Bottom line: summarization like this helps agents _stay smart when things get long_. Instead of trying to reason over every raw detail, they get the distilled version — clean, focused, and still grounded in the original docs.

## 3\. Tool Loadout

Finally, let’s talk about **Tool Loadout** — the underrated skill of choosing which tools to show your model _before_ it acts, in multi-tool agents, it’s common to just throw the entire tool-set into the context, thinking “more options = more power.” but in practice, this can be a huge mistake.

When you overload the model with too many tool definitions — especially when they overlap in functionality — it starts to get confused, it might call the wrong tool or hesitate entirely.

> This is what they calls **Context Confusion** : the model gets lost in the menu, not knowing what to pick.

Better loadout means tighter focus.. only include the tools that are actually relevant to the task at hand , some interesting research pointed to showing that Llama 3.1 8B failed with 46 tools in context, but performance jumped significantly when that was reduced to just 19, even better, dynamically selecting tools based on the user query boosted performance by **44%**.

One counter-intuitive insight from researchers is that sometimes, _general-purpose_ tools (like a shell or python interpreter) outperform more specialized ones — because the model knows how to use them well , so instead of building a sprawling toolbox, it may be smarter to go with a few sharp, versatile tools — and make sure the model actually understands them.

### Code example :

This code is a smart way to let users ask for math operations in plain english like _“calculate arc cosine”_ and have the system automatically figure out which python function (like `math.acos`) to use. it scans all the functions in the `math` module, wraps them with tool metadata (name + description), and builds a searchable index using vector embeddings.

```python import mathimport typesimport uuidfrom langgraph_bigtool.utils import convert_positional_only_function_to_toolfrom llama_index.core import Documentfunction_nodes = []all_tools = []for function_name in dir(math): function = getattr(math, function_name) if not isinstance(function, types.BuiltinFunctionType): continue if tool := convert_positional_only_function_to_tool(function): all_tools.append(tool)tool_registry = { str(uuid.uuid4()): tool for tool in all_tools}for tool_id, tool in tool_registry.items(): function_nodes.append(Document(text = f"{tool.name}: {tool.description}" , id_=tool_id))function_index = VectorStoreIndex.from_documents(function_nodes)function_retriever = function_index.as_retriever(similarity_top_k=3)tools = []query = "Use available tools to calculate arc cosine of 0.5."tools_result = function_retriever.retrieve(query)relevant_tools = [ related.node_id for tool in tools_result for related in tool.node.relationships.values()]for tool_id in relevant_tools: tools.append(tool_registry[tool_id])print(tools) ```

So when someone asks a question like _“What’s the arc cosine of 0.5?”_ , the system doesn’t guess blindly .. it searches the index, retrieves the most relevant tools (like `acos`), and **injects only those tools into the agent on-the-fly** , just before running the original query..

This approach avoids overloading the agent with every possible tool up front , it’s like giving your code a memory of all its capabilities, then letting it look up the right ones when needed kind of like how we search google when we vaguely remember something. it’s super useful for building scalable, efficient tool-using agents , this is just one example, and there are definitely ways to improve it further.

> **Bottom line:** Instead of loading every tool up front, this approach lets your agent _search_ , _select_ , and _inject_ only the tools it needs — making it faster, smarter, and easier to scale.

Effective context management is key to building scalable, intelligent agents. whether you’re pruning, summarizing, or dynamically injecting relevant tools, smart context engineering keeps models focused and efficient , this is just one approach we will cover more advanced techniques in future posts.
