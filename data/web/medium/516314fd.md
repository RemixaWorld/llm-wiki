Recently, I’ve observed that research on multimodal RAG (Retrieval-Augmented Generation) is increasing. Therefore, I believe it’s crucial to offer a concise overview of this field. By clarifying our thoughts, we can better grasp future research directions and recognize the potential applications.

This article primarily introduces the main categories of current multimodal RAG, highlights some of the latest developments, and offers personal insights.

## Classification of Multimodal RAG

Due to the flexibility of multimodal RAG, there are various ways to classify it.

Here, we classify multimodal RAG based on **storage and retrieval modality**. It can be divided into **three categories: Image-based RAG, text-based RAG, and cross-modality-based RAG.**

As illustrated in Figure 1, (a) and (c) can be classified as **image-based RAG** , while (b) represents**text-based RAG**. The difference between Figure 1 (a) and (c) is that (a) can only process single-page documents, while (c) can handle long documents.

Previous works focus on (a) Single-page DocVQA that cannot handle many long documents or (b) Text-based RAG that ignores visual information. M3DOCRAG framework (c) retrieves relevant documents and answers questions using multi-modal retrieval and MLM components, so that it can efficiently handle many long documents while preserving visual information. Source: [M3DOCRAG](<https://arxiv.org/pdf/2411.04952v1>).

**Cross-modality-based RAG** are capable of storing and retrieving information across different modalities.

Press enter or click to view image in full size

Figure 2: Overall architecture of the multimodal RAG pipelines. For the Text-Only RAG, we only use the Text Retrieval component. Conversely, in the Image-Only RAG, we only employ the Image Retrieval component, either with multimodal embeddings or image summaries. Source: [Beyond Text](<https://arxiv.org/pdf/2410.21943v1>).

**Figure 2** illustrates two distinct configurations of the **cross-modality-based RAG pipeline** , showcasing the integration of text and image modalities into the RAG system.

* From an input source perspective, Figure 2(a) and (b) both utilize text and images extracted from PDF collections. The text undergoes embedding via a text embedding model (such as OpenAI’s text-embedding-3-small). In Figure 2(a), images are embedded using a multimodal embedding model (like CLIP). In contrast, Figure 2(b) processes images through a multimodal LLM to generate text summaries, which are then embedded using a text embedding model.
* Regarding storage, Figure 2(a) maintains separate vector stores for text and image embeddings. Figure 2(b), however, stores both text embeddings and image-generated text summary embeddings in a single vector store.
* For post-retrieval, both Figure 2(a) and (b) can feed the retrieved text and corresponding original images into a multimodal LLM to generate the final answer.

Next, let’s look at some specific examples of multimodal RAG implementation.

## ColPali: The All-Seeing Document Retrieval That Understands Both Text and Image

> ** _Open source code_** _:_[_https://github.com/illuin-tech/colpali_](<https://github.com/illuin-tech/colpali>)

### Core Idea

When developing RAG systems, we often face this challenge: **Can the system retrieve the correct document page for a given query?**

Press enter or click to view image in full size

Figure 3: Traditional retrieval systems. Image by author.

Traditional retrieval systems primarily focus on text matching, overlooking the rich visual elements in documents.

[ColPali](<https://arxiv.org/pdf/2407.01449v3>) addresses this limitation by leveraging vision language models (VLMs) to generate high-quality contextual embeddings solely from document images. Combined with a late interaction matching mechanism, ColPali not only enhances retrieval effectiveness but also speeds up processing, enabling end-to-end training.

Press enter or click to view image in full size

Figure 4: ColPali simplifies document retrieval w.r.t. standard retrieval methods while achieving stronger performances with better latencies. Source: [ColPali](<https://arxiv.org/pdf/2407.01449v3>).

ColPali extends the PaliGemma-3B model, generating multi-vector representations of text and images akin to ColBERT.

As shown in Figure 4, in contrast to traditional systems, where images or PDF documents typically undergo [text extraction and layout analysis](<https://medium.com/ai-advances/demystifying-pdf-parsing-02-pipeline-based-method-82619dbcbddf>) before encoding text blocks into vectors. However, ColPali streamlines the process. It generates embedding vectors directly from document page images, bypassing these preprocessing steps.

Furthermore, ColPali uses a **Late Interaction approach**. Each document is represented as multiple independent vectors**. During retrieval,** it computes dot products between query and document vectors to find the document with highest similarity. The overall match is determined by aggregating these maximum values, ensuring accurate retrieval.

The **training** **dataset** Consists of 127,460 query-page pairs, derived from both academic datasets and synthetic data generated from web-crawled PDF documents. Training set is entirely in English, aiming to explore zero-shot generalization to non-English content while avoiding cross-contamination in evaluations.

### Latency and Memory Usage

**Latency** : ColPali utilizes NVIDIA L4 GPUs during inference, with query encoding latency around 30ms​.

**Memory Usage** : Each page requires approximately 256KB of memory due to dimensionality reduction of the image patch embeddings​.

### Code

[The notebook](<https://github.com/weaviate/recipes/blob/c6f186476eecbc7703c60d0d4205bf8d272c5821/weaviate-features/named-vectors/ColPali-POC.ipynb>) provides a clear tutorial. It was run on an A100 with Google Colab.

The `process_pdfs_with_colpali` function divides PDF documents into images and sends them to the model for encoding.

```python def process_pdfs_with_colpali(pdf_files, output_dir, model, processor): all_embeddings = [] all_page_info = [] for pdf_file in pdf_files: pdf_images = convert_pdf_to_images(pdf_file, os.path.join(output_dir, "pdf_images")) for page_num, image in enumerate(pdf_images): image_input = processor.process_image(image).to(model.device) with torch.no_grad(): page_embedding = model(**vars(image_input)) # Average over sequence dimension if necessary if len(page_embedding.shape) == 3: page_embedding = page_embedding.mean(dim=1) all_embeddings.append(page_embedding.cpu().numpy().squeeze()) all_page_info.append({"pdf": pdf_file, "page": page_num}) embeddings_array = np.array(all_embeddings) np.save(Path(output_dir) / "embeddings.npy", embeddings_array) np.save(Path(output_dir) / "page_info.npy", all_page_info) return embeddings_array, all_page_info ```

The `answer_query_with_colpali` function identifies the most relevant document page for a given query.

```python def answer_query_with_colpali(query, embeddings_array, page_info, model, processor): query_input = processor.process_text(query).to(model.device) with torch.no_grad(): query_embedding = model(**vars(query_input)) # Reshape embeddings if necessary if len(embeddings_array.shape) == 3: embeddings_array = embeddings_array.mean(axis=1) # Average over sequence dimension if len(query_embedding.shape) == 3: query_embedding = query_embedding.mean(axis=1) # Average over sequence dimension # Ensure both embeddings are 2D embeddings_array = embeddings_array.squeeze() query_embedding = query_embedding.cpu().numpy().squeeze() # Compute similarity scores similarity_scores = np.dot(embeddings_array, query_embedding.T) K = 5 top_k_indices = np.argsort(similarity_scores.flatten())[-K:][::-1] top_results = [ {"score": similarity_scores.flatten()[i], "info": page_info[i]} for i in top_k_indices ] return top_results ```

For more details, interested readers can explore the code themselves.

### Commentary

**ColPali** addresses the limitations of traditional text retrieval methods by leveraging Visual Language Models (VLMs) for processing document visual elements. It enhances retrieval performance through **late interaction** , achieving low latency and high indexing throughput while requiring only modest hardware (such as NVIDIA L4 GPUs).

However, to deploy it as an efficient product, the following challenges need to be addressed:

1. **Further Development** : ColPali excels in retrieval, and as we’ll see below, it serves as a strong foundation for constructing multimodal RAG systems.
2. **Real-Time Needs** : In scenarios with extremely high latency requirements (such as real-time dialogue systems, financial trading decisions, or voice interaction in autonomous driving), 30ms may be slightly too high.
3. **Complex Documents** : Further tuning is needed for handwritten or unstructured data.

ColPali excels in scenarios requiring high retrieval accuracy and visual data utilization but offers little advantage in simpler text-based tasks. Despite achieving an average NDCG@5 score of 81.3, it still requires improvement for widespread industrial adoption.

## M3DOCRAG: Multi-modal Multipage Multi-Document RAG

As shown in Figure 1(a), existing models are constrained to single-page documents or rely on OCR-extracted textual data, making them inefficient for handling cross-page and multi-document scenarios.

[M3DOCRAG](<https://arxiv.org/pdf/2411.04952v1>) is a multi-modal Retrieval-Augmented Generation (RAG) framework. It supports multi-document and multi-page tasks in both open-domain and closed-domain settings while integrating various modalities such as visual and textual data.

Press enter or click to view image in full size

Figure 6. The M3DOCRAG framework consists of three stages: (1) document embedding, (2) page retrieval, and (3) question answering. Source: [M3DOCRAG](<https://arxiv.org/pdf/2411.04952v1>).

As shown in Figure 6, M3DOCRAG operates in three stages:

* **Document Embedding** : Visual embeddings are extracted (**using ColPali**) to represent each page from all PDF documents.
* **Page Retrieval** : The top-K most relevant pages are retrieved (based on MaxSim scores) using text queries. In open-domain settings, approximate page indices are created for faster searching.
* **Question Answering** : Visual question answering is performed using a multi-modal language model (e.g., Qwen2-VL) to generate the final answer.

### Commentary

Overall, M3DOCRAG offers new possibilities for multi-modal tasks in document understanding. For actual deployment, improvements are still needed in the following areas:

1. **Retrieval Efficiency** : Although Faiss is used to accelerate retrieval, scaling to even larger document repositories remains challenging.
2. **Limitations of Multi-modal Models** : The current models (e.g., Qwen2-VL 7B) have limitations in understanding complex visual relationships and handling non-English content. We can train models with diverse, multilingual, and domain-specific datasets or consider developing larger models (e.g., 16B or beyond).
3. **Semantic Alignment in Multi-modal Contexts** : Understanding complex visual content could lead to semantic errors. We can strengthen the alignment between visual and textual embeddings, and fine-tune the model with more real-world datasets.

## VisRAG: Farewell to Document Parsing

> ** _Open source code_** _:_[_https://github.com/openbmb/visrag_](<https://github.com/openbmb/visrag>)

As shown in Figure 7, traditional text-based RAG (TextRAG) relies on parsed texts for retrieval and generation, losing visual information in multimodal documents. In contrast, [Vision-based RAG (VisRAG)](<https://arxiv.org/pdf/2410.10594v1>) uses a VLM-based retriever and generator to directly process the document page’s image. This approach preserves all information from the original page.

Press enter or click to view image in full size

Figure 7: TextRAG (left) vs. VisRAG (right). Source: [VisRAG](<https://arxiv.org/pdf/2410.10594v1>).

### Retrieval Stage

* **Task** : To retrieve relevant pages from a corpus based on a user query, enabling accurate information augmentation for generation.
* **Dual-Encoder Paradigm** : Uses a VLM rather than an LLM to map the query and document page images into the same embedding space for similarity calculation.
* **Vision-Language Model (VLM)** : Encodes document pages as images directly, preserving visual and textual information without text parsing.
* **Similarity Scoring** : Computes cosine similarity between the query and page embeddings to select the most relevant pages.

### Generation Stage

* **Task** : To generate an accurate and contextually enriched response based on the user query and retrieved pages.
* **Single-Image and Multi-Image Handling** : For VLMs accepting single images, VisRAG applies **page concatenation** or **weighted selection** methods to combine information from multiple retrieved pages. For VLMs supporting multi-image input, VisRAG leverages these models directly to process all retrieved pages together.
* **Weighted Selection** : Calculates the answer confidence across multiple pages, selecting the response with the highest weighted probability.

### Commentary

VisRAG is a multi-modal RAG approach that eliminates the document parsing stage, thereby preserving comprehensive information for retrieval and generation.

While VisRAG demonstrates many advantages, it also presents challenges, particularly regarding computational resource requirements. Additionally, the approach’s dependency on model and data scale may require further adjustments for wider adoption in other domains.

## OmniSearch

> ** _Open source code_** _:_[_https://github.com/Alibaba-NLP/OmniSearch_](<https://github.com/Alibaba-NLP/OmniSearch>)

This idea is quite interesting, as it incorporates [the concept of agents](<https://medium.com/ai-in-plain-english/understanding-large-language-model-based-agents-27bee5c82cec>) into multimodal RAG. It believes that existing methods often employ fixed retrieval processes, leading to inflexible retrieval and query overload issues, as shown in Figure 8.

Press enter or click to view image in full size

Figure 8: Bottom: Heuristic mRAG based VQA. Upper: OmniSearch based VQA. Source: [OmniSearch](<https://arxiv.org/pdf/2411.02937v2>).

[OmniSearch](<https://arxiv.org/pdf/2411.02937v2>) is**** a self-adaptive planning agent that mimics human behavior by decomposing complex questions into sub-question chains and dynamically adjusting retrieval actions.

Press enter or click to view image in full size

Figure 9: Left: overall framework of OmniSearch. Right: running example of OmniSearch. Source: [OmniSearch](<https://arxiv.org/pdf/2411.02937v2>).

The framework consists of three key components: a **planning agent** for formulating sub-questions and retrieval strategies, a **retriever** for executing multimodal retrieval actions, and a **sub-question solver** for summarizing retrieved content and generating feedback. [The prompt used in OmniSearch](<https://github.com/Alibaba-NLP/OmniSearch/blob/edcc4b5f6500fb935e8644f87a2c4cb9e61982cd/src/prompt.py#L21>) is shown below.

``` sys_prompt_1 = '''You are a helpful multimodal question answering assistant. Decompose the original question into sub-questions and solve them step by step. You can use "Final Answer" to output a sentence in the answer, use "Search" to state what additional context or information is needed to provide a precise answer to the "Sub-Question". In the "Search" step, You can use "Image Retrieval with Input Image" to seek images similar to the original ones and determine their titles, "Text Retrieval" with a specific query to fetch pertinent documents and summarize their content, "Image Retrieval with Text Query" to fetch images related to the entered keywords.Use the following format strictly:<Thought>Analyse questions and answer of the sub-questions, then think about what is next sub-question.<Sub-Question>Sub-Question needs to be solved in one step, without references.<Search>One of three retrieval methods: Image Retrieval with Input Image. Text Retrieval: xxx. Image Retrieval with Text Query: xxx.... (this Thought/Sub-Question/Search can be repeated zero or more times)<Thought>Integrate retrieved information and reason to a final answer<End>Final Answer: the final answer to the original input questionExtra notes:1. Do not use you own knowledge to analyse input image or answer questions2. After you give each <Search> action, please wait for me to provide you with the answer to the sub-question, and then think about the next thought carefully.3. The answers to the questions can be found on the internet and are not privateInput Question:{}''' ```

OmniSearch supports diverse retrieval tools (e.g., web search, image search) and is compatible with various LLMs. In the experiments, it integrated GPT-4V and Qwen-VL-Chat models respectively, validating its effectiveness in various environments.

OmniSearch iteratively performs actions until it gathers sufficient knowledge to provide a final answer. This dynamic and modular design reduces the burden of single-step retrieval by dynamically planning retrieval paths and adjusting strategies, while avoiding error propagation.

### Commentary

The insight OmniSearch provides is that multimodal RAG needs to move from static to dynamic, from single-modal to multimodal, and from black box to transparency.

To better serve practical scenarios, researchers and developers should think deeply about every aspect — from system design and dataset construction to model optimization and productization.

While OmniSearch shows potential, its productization still faces challenges in performance, token cost, and generalizability. Of course, these issues are key challenges the entire AI industry needs to overcome.
