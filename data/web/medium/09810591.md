> Dynamic context discovery lets AI agents stay sharp by fetching only the information they need, exactly when they need it, reducing token waste and avoiding context rot.

![Choosing to focus over overload context, intentionally discovered.](https://miro.medium.com/v2/resize:fit:700/1*1X1XlRaE4YxEjjAAx2UL9w.png)

Bigger context windows were supposed to solve everything, but they didn’t.

As agents become more capable, they’re drowning in their own context.

Tool descriptions, chat history, file contents, terminal output, it all competes for the model’s attention, and attention is finite.

**Chroma’s research on what they call _context rot_ showed this clearly: **_across 18 frontier models, performance degrades as input length grows, even on simple retrieval tasks.
The transformer architecture demands that every token attend to every other token. As context expands, that attention budget gets stretched thin and important information gets lost._

The instinct is to cram more in the better approach is to be selective.

Cursor recently described a pattern they call **_dynamic context discovery_**. Rather than front-loading everything into the prompt, agents fetch only what they need, when they need it.
The result: nearly half the tokens, same quality output.

## The Shift: Static to Dynamic

The core insight from Cursor’s January 2026 research:

> As models have become better as agents, we’ve found success by providing fewer details up front, making it easier for the agent to pull relevant context on its own.

Instead of loading all context at startup (static), the agent fetches only what it needs, when it needs it (dynamic).

## Static vs Dynamic Context

Aspect Static Context Dynamic Context Loading Everything Upfront On-demand Token usage High (_pay for everything_) Low (_pay for what you use_) Performance Degrades with bloat Maintained via selective loading Scalability Limited by context window Scales with external storage.

## How It Works: Files as the Universal Interface

Cursor’s implementation uses files as the primitive for dynamic context. Here’s their approach:

### Long Tool Outputs → Files

Instead of truncating shell command results (_losing information_), write the full output to a file.

The agent uses `tail` or `grep` to read what it needs.

```bash # Old approach: truncate long output, lose information$ npm install 2>&1 | head -100# Dynamic approach: write to file, let agent explore$ npm install 2>&1 > /tmp/install-output.txt# Agent calls: tail /tmp/install-output.txt# Agent calls: grep "error" /tmp/install-output.txt ```

### Chat History as Files

When the context window fills up, Cursor summarizes the conversation but keeps the full history in a file.
If the agent needs details that were compressed away, it can search the history file to recover them.

### MCP Tool Descriptions → Folder

This is a key innovation for tool-heavy agents. Instead of injecting all tool descriptions into the prompt:

``` # OLD: All tool descriptions in system prompttools: - name: search_emails description: "Search through emails using various filters..." # 500 tokens of schema - name: send_email description: "Send an email with attachments..." # 400 tokens of schema # ... 50 more tools, 20,000+ tokens total ```

Cursor syncs tool descriptions to a folder and the agent receives only tool names in the prompt:

``` # NEW: Only names in prompt, descriptions in filesAvailable MCP tools: search_emails, send_email, create_calendar_event, ...# Full descriptions synced to: .cursor/mcp-tools/# - search_emails.json (full schema)# - send_email.json (full schema) ```

When the task requires a specific tool, the agent reads its description file.
The ~46.9% token reduction came specifically from this pattern.

### Terminal Sessions as Files

Cursor syncs terminal output to the filesystem. When you ask:

_why did my command fail?_

The agent greps the terminal log for relevant output, discovered dynamically rather than injected statically.

## The Three-Layer Pattern

The best implementations follow a three-layer progressive disclosure pattern:

**Layer 1: Metadata (always loaded)**

* Tool names and one-line descriptions
* Skill names and descriptions
* File paths and sizes
* ~100 tokens per item

**Layer 2: Instructions (loaded on demand)**

* Full tool schemas
* Complete skill instructions (SKILL.md)
* File contents
* Loaded when the agent decides it’s relevant

**Layer 3: Deep Resources (loaded when needed)**

* Reference documentation
* Executable scripts
* Large datasets
* Loaded only when explicitly required

This mirrors how humans work. We don’t memorize entire manuals. We maintain an index and retrieve details on demand.

## Agent Skills: Progressive Disclosure in Practice

Anthropic’s Agent Skills standard embodies this pattern.
A skill is a folder with a SKILL.md file:

``` my-skill/├── SKILL.md # Core instructions (Layer 2)├── scripts/ # Executable code (Layer 3)│ └── process.py├── references/ # Documentation (Layer 3)│ └── API.md└── assets/ # Templates, data (Layer 3) └── template.docx ```

The SKILL.md starts with YAML frontmatter:

``` \---name: pdf-processingdescription: Extract text and tables from PDF files, fill forms, merge documents.license: MIT---# PDF Processing Skill## Instructions1. Use PyPDF2 for basic text extraction2. Use pdfplumber for tables3. For form filling, run scripts/fill_form.py## When to Use- User mentions PDF, forms or document extraction- Task involves merging or splitting documentsSee [references/API.md](references/API.md) for detailed API docs. ```

**How the agent uses it:**

1. **Startup** : Only `name` and `description` loaded
2. **Task match** : Agent reads full SKILL.md into context
3. **Deep dive** : Agent reads referenced files only if needed

You can have 100 skills installed, but if a task only needs 2, only those 2 get loaded.

The Agent Skills standard is now adopted by:

* Claude (Claude.ai, Claude Code)
* OpenAI (Codex CLI)
* Microsoft (VS Code, GitHub Copilot)
* Cursor, Goose, Amp, OpenCode

## MCP: Dynamic Tool Discovery

Model Context Protocol (MCP) supports dynamic tool discovery at the protocol level:

```json // Client discovers available tools{ "jsonrpc": "2.0", "id": 1, "method": "tools/list", "params": {}}// Server returns tool definitions{ "jsonrpc": "2.0", "id": 1, "result": { "tools": [ { "name": "get_weather", "description": "Get current weather for a location", "inputSchema": { "type": "object", "properties": { "location": { "type": "string" } }, "required": ["location"] } } ] }} ```

Servers can notify clients when tools change:

```json { "jsonrpc": "2.0", "method": "notifications/tools/list_changed"} ```

This enables scenarios like:

* **Authentication state changes** : Hide tools when credentials expire
* **Feature flags** : Show different tools based on permissions
* **Context-dependent tools** : Show file operations only when a project is open

## Claude’s Context Management

Anthropic provides server-side tools for context management.

Here’s how to enable automatic tool result clearing:

```python import anthropicclient = anthropic.Anthropic()response = client.beta.messages.create( model="claude-sonnet-4-5", max_tokens=4096, betas=["context-management-2025-06-27"], messages=[ {"role": "user", "content": "Analyze this codebase..."} ], tools=[ {"type": "text_editor_20250728", "name": "str_replace_based_edit_tool"}, {"type": "web_search_20250305", "name": "web_search"} ], context_management={ "edits": [ { "type": "clear_tool_uses_20250919", "trigger": { "type": "input_tokens", "value": 50000 }, "keep": { "type": "tool_uses", "value": 5 } } ] }) ```

_When context exceeds 50,000 tokens, the oldest tool results get cleared automatically, keeping only the 5 most recent._

In Anthropic’s evaluation, this enabled agents to complete 100-turn workflows that would otherwise fail, while reducing token consumption.

## Combining with Memory

The real power comes from combining context editing with the memory tool:

```json response = client.beta.messages.create( model="claude-sonnet-4-5", max_tokens=4096, betas=["context-management-2025-06-27"], messages=[...], tools=[ {"type": "memory_20250818", "name": "memory"}, # Your other tools ], context_management={ "edits": [ {"type": "clear_tool_uses_20250919"} ] }) ```

When approaching the clearing threshold, Claude receives a warning. It can save important information to memory files before tool results get cleared. After clearing, Claude retrieves stored information from memory when needed.

This creates a two-tier system:

* **Working memory** : Active context window (_cleared automatically_)
* **Long-term memory** : Persistent files (_retrieved on demand_)

## Tool RAG: Scaling to Hundreds of Tools

When you have 50+ tools, even loading tool names becomes expensive. Enter Tool RAG: apply retrieval-augmented generation to tool selection.

The RAG-MCP paper found this approach:

* More than tripled tool-selection accuracy
* Reduced prompt tokens by over 50%

The pattern:

```python from sentence_transformers import SentenceTransformerimport numpy as np# Embed all tool descriptions oncemodel = SentenceTransformer('all-MiniLM-L6-v2')tool_embeddings = { tool.name: model.encode(tool.description) for tool in all_tools}def get_relevant_tools(query: str, top_k: int = 5): """Retrieve only the tools relevant to this query.""" query_embedding = model.encode(query) # Compute similarities similarities = { name: np.dot(query_embedding, emb) for name, emb in tool_embeddings.items() } # Return top-k tools sorted_tools = sorted(similarities.items(), key=lambda x: x[1], reverse=True) return [name for name, _ in sorted_tools[:top_k]]# Only inject relevant tools into promptrelevant = get_relevant_tools("Send an email to the team about the meeting")# Returns: ["send_email", "search_contacts", "create_calendar_event", ...] ```

The LLM only sees the tools it’s likely to need. Everything else stays in the index.

## Implementation: Claude Code’s Hybrid Approach

Claude Code demonstrates the hybrid pattern:_some context upfront, the rest discovered dynamically._

**Static context (_always loaded_):**

* CLAUDE.md file (project-specific instructions)
* Tool definitions for core tools (Read, Write, Bash, etc.)

**Dynamic context (_loaded on demand_):**

* File contents (_via_` _glob_` _,_`_grep_` _, file navigation_)
* Skill instructions (_when task matches skill description_)
* Search results (_web search tool_)

Here’s how memory works in Claude Code’s pattern:

``` # The agent maintains a NOTES.md or TODO list# This persists across compaction/summarization# When approaching context limits, Claude Code:# 1. Summarizes the conversation# 2. Preserves key decisions, errors and next steps# 3. Keeps the 5 most recently accessed files# 4. Continues with compressed context + memory files# The user sees:# "Context compacted. Key information preserved in memory." ```

## The Trade-offs

Dynamic context discovery isn’t free. There are real trade-offs:

### Latency

Exploration takes time. An agent using progressive disclosure might make 3–5 extra tool calls to discover context before starting work. For simple tasks, this overhead isn’t worth it.

### Routing Quality

Dynamic discovery only works if metadata (_names, descriptions_) are good enough for routing. Poor descriptions lead to poor tool selection and waste exploration.

### Architecture Complexity

_Static context is simple:_ load everything, send to model.

_Dynamic context requires:_

* File management
* Metadata indexes
* Discovery tools
* Memory persistence

### When NOT to Use Dynamic Discovery

* Simple, single-turn tasks
* Small tool sets (< 10 tools)
* Low-latency requirements
* Tasks requiring precise recall of early context

## Best Practices

Based on the research and implementations covered here:

**1\. Design in Layers**

``` Layer 1: Names/descriptions (~100 tokens each)Layer 2: Full instructions (~500-2000 tokens)Layer 3: Deep resources (unlimited, loaded rarely) ```

**2\. Invest in Descriptions** Your tool and skill descriptions are routing decisions. **_Sends email_** is worse than “ _Compose and send emails with attachments, CC/BCC and HTML formatting. Use when user wants to email someone._ ”

**3\. Use Files for Long Outputs** Don’t truncate. Write to files, let the agent explore with `tail`, `grep`, `head`.

**4\. Combine with Memory** Context editing alone loses information. Memory tool preserves it. Use both.

**5\. Start Hybrid, Go Dynamic** Load critical context upfront (CLAUDE.md, core tools). Let everything else be discovered.

**6\. Monitor Token Usage** Track which tools and resources actually get loaded. Prune what’s never used.

## The Bigger Picture

Dynamic context discovery represents a shift in how we think about agents. The old mental model was “ _configure everything upfront_.”
The new model is “ _provide the minimum needed for the agent to find everything else._ ”

This mirrors how intelligent systems generally work. Humans don’t memorize _encyclopedias_. They maintain indexes and retrieve on demand and Now agents can do the same.

The convergence is happening fast, Cursor’s dynamic context discovery, Anthropic’s context engineering guidance and Agent Skills, MCP’s tool discovery protocol AND They’re all pointing in the same direction.

Smarter agents need less prescriptive context. They can navigate their own information landscape.

As models continue to improve, this pattern will likely become the default. Static context will be reserved for truly critical information.

Everything else will be discovered.

The agents that win won’t be the ones with the biggest context windows. They’ll be the ones that use context most efficiently.
