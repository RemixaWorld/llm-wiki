## The Least Optimised

Let’s refer to the Dockerfile below. Isn’t it neat and easy to understand? First, we use a base Python image of version 3.12, followed by updating the package manager, and installing `git` and `build-essential`, two common libraries needed for installing Python dependencies. Then, we copy the application code and install the Python dependencies in the `requirements.txt` before setting the application startup command.

```python FROM python:3.12RUN apt-get updateRUN apt-get install -y git build-essentialCOPY . .RUN pip install -r requirements.txtCMD ["uvicorn", "app:app"] ```

Unfortunately, being simple and succinct in the programming world often does not equate to being optimised. This approach can instead result in bloated, sluggish, and potentially insecure applications.

Let’s take a look at its size, speed, and security, and see how much we can improve these by the end of this article.

## 1\. Use a Slim Base Image

Arguably, the most important consideration when building Python images is to always use the slim base image where possible.

``` FROM python:3.12-slim# instead of FROM python:3.12 ```

The slim image is a stripped-down version of the full image, but with full Python functionality. Just look at the whopping difference shown between when we switch to a slim Python image!

Press enter or click to view image in full size

Using a full Python base image (top) vs a slim Python base image (bottom). Screenshot by author.

We can even push this further by using an Alpine image. This is highly recommended if you want to achieve a zero vulnerability image due to its small number of OS libraries. However, note that you may run into issues, as many Python packages have binary wheels built for `glibc` (used by Debian), not `musl` (used by Alpine).

``` FROM python:3.12-alpine ```

Another alternative is to use `[distroless](<https://github.com/GoogleContainerTools/distroless>)`, which is significantly smaller than `python:3.12-slim` but larger than `python:3.12-alpine`. This has an advantage over the `alpine` image as it is Debian-based. However, you will need to copy your Python application using a multi-stage build since distroless does not have a package manager.

``` FROM gcr.io/distroless/static-debian12 ```

## 2\. Minimum Installation

We can optimise our `apt-get install` to exclude optional tools or libraries using the flag `--no-install-recommends`. In addition, for our Python installation using `pip`, we do not want to store any caches, hence we should always include the `--no-cache-dir` command.

```python FROM python:3.12-slimRUN apt-get updateRUN apt-get install -y --no-install-recommends git build-essentialCOPY . .RUN pip install --no-cache-dir -r requirements.txtCMD ["uvicorn", "app:app"] ```

With just two additional flags, we managed to optimise the image further.

## 3\. Layer Caching: Order

Every command in your Dockerfile is cached by Docker as a layer cache to allow efficient rebuilds of your image. For example, if you change your source code, which is at layer 4 (below), Docker will not rebuild layers 1–3 but instead use the previous caches.

Press enter or click to view image in full size

Layer caching can be further optimised if we install the requirements before copying over the source code. Image by author.

We can make the build time even faster by copying the `requirements.txt` only and installing it before copying over the rest of the source code. This is because the Python dependencies do not change often, compared to the source code, which we copy over only at the last line.

```python FROM python:3.12-slimRUN apt-get updateRUN apt-get install -y --no-install-recommends git build-essentialCOPY requirements.txt .RUN pip install --no-cache-dir -r requirements.txtCOPY project/ . ```

With this small change, upon any updates to the source code, the build time is almost immediate (2 seconds) compared to the earlier example of 9 seconds.

## 4\. Layer Cache: Single RUN

By understanding how layer caching works, we can also optimise the image by combining various layers when it makes sense to.

In the example below, after doing the `apt-get install`, we can clean up the installations by removing the caches via `apt-get clean` and removing the updated package list via `rm-rf /var/lib/apt/lists/*`.

However, since the previous `RUN` commands already stored the uncleaned directories in the last two layer caches, a new layer of `RUN` with the cleanup does not render any size reduction.

```python FROM python:3.12-slimRUN apt-get updateRUN apt-get install -y --no-install-recommends git build-essentialRUN apt-get clean && rm -rf /var/lib/apt/lists/*COPY requirements.txt .RUN pip install --no-cache-dir -r requirements.txtCOPY project/ . ```

As expected, building this image returns the same image size as before.

Press enter or click to view image in full size

There is no noticeable reduction in the image size after cleaning up the `apt` dependencies if separate runs are used. Screenshot by author.

We can optimise this effect by combining all three `RUN` commands into a single layer cache.

```python FROM python:3.12-slimRUN apt-get update && \ apt-get install -y --no-install-recommends git build-essential && \ apt-get clean && rm -rf /var/lib/apt/lists/*COPY requirements.txt .RUN pip install --no-cache-dir -r requirements.txtCOPY project/ . ```

This combination led to the efficient reduction of the image size by about 20MB.

Image size is reduced after combining the layers as a single RUN command. Screenshot by author.

## 5\. Multi-Stage Build

Earlier, I mentioned the need to install `git` and `build-essential` to enable the installation of certain Python dependencies in the subsequent step. However, this will also mean that after these Python dependencies are installed, they are no longer required and can be removed.

An efficient way to do this is by separating the Docker building process into two stages (hence a multi-stage build).

In the first stage, we first define the stage with a name `FROM python:3.12-slim AS build`. In this stage, only the dependencies are installed. A flag of `--user` is used to install the `requirements.txt` so they are installed within the directory `/root/.local` for easy migration to the subsequent stage.

In the second stage, we start a fresh new Python base image and copy over the directory where the Python libraries were installed previously from the previous stage, as evident from the command `COPY --from=build`. An `ENV` path has to be set to the directory so Python can recognise this path.

```python # ===== Build Stage =====FROM python:3.12-slim AS buildRUN apt-get update && \ apt-get install -y --no-install-recommends git build-essential && \ apt-get clean && rm -rf /var/lib/apt/lists/*COPY requirements.txt .RUN pip install --user --no-cache-dir -r requirements.txt# ===== Final Stage =====FROM python:3.12-slimCOPY --from=build /root/.local /root/.localENV PATH=/root/.local/bin:$PATHWORKDIR /appCOPY project/ .CMD ["uvicorn", "app:app"] ```

A huge reduction in the image size and the number of vulnerabilities is evident when we build this image.

## 6\. UV for Fast Python Installation

[UV](<https://github.com/astral-sh/uv>) is the latest popular Python package manager. In just a year since its release, the number of stars on GitHub has exceeded [Poetry](<https://github.com/python-poetry/poetry>), arguably the de facto Python package manager for many developers. It is developed in Rust, providing a speed boost that exceeds existing installers like pip.

In this instance, we only want to leverage UV for fast Python installations instead of a package manager.

To do that, we will first need to copy its files using `COPY — from=ghcr.io/astral-sh/uv:0.6.13 /uv /uvx /bin/` and set the path via `ENV PATH="/root/.local/bin/:$PATH"`. Installation of the requirements.txt follows the same syntax but with the command `uv` in front. A flag of `--system` is included so that UV installs the dependencies into the default `/usr/local/lib/` directory.

```python # ===== Build Stage =====FROM python:3.12-slim AS buildRUN apt-get update && \ apt-get install -y --no-install-recommends git build-essential && \ apt-get clean && rm -rf /var/lib/apt/lists/*COPY --from=ghcr.io/astral-sh/uv:0.6.13 /uv /uvx /bin/ENV PATH="/root/.local/bin/:$PATH"COPY requirements.txt .RUN uv pip install --system -r requirements.txt# ===== Final Stage =====FROM python:3.12-slimCOPY --from=build /usr/local/lib/python3.12/site-packages /usr/local/lib/python3.12/site-packagesCOPY --from=build /usr/local/bin /usr/local/binCOPY project/ .CMD ["uvicorn", "app:app"] ```

When we build this image, we can see a noticeable improvement in the build time of 17s. While this is just a few seconds, in other projects I maintained, where the Python dependencies take 5 to 10 minutes to install, UV can halve the installation time in the CI pipelines.

## Summary

I have shown six methods on how you can optimise your Dockerfiles for size, speed, and security, and the compiled results are as displayed below.

``` | Optimisation | Size | Speed | Security ||-------------------|------------------|--------------|--------------|| Least optimised | 1.09GB | 34 | 1377 || > Base image | 150MB vs 1.02GB | 5 vs 16 | 104 vs 1377 || > Install minimum | 518MB vs 576MB | 21 vs 26 | 926 vs 992 || > Layer cache 1 | - | 2 vs 9 | - || > Layer cache 2 | 465MB vs 518MB | 26 vs 35 | 926 || > Multi-stage | 183MB | 25 | 104 || > UV | 176MB vs 183MB | 17 vs 25 | - || Most optimised | 176MB | 17 | 104 | ```

The overall improvement is about **x6 smaller in size** , **x2 faster in speed** , and **x13 fewer vulnerabilities**.

Of course, these numbers will vary according to the number of dependencies you want to install, your network speed and whether new vulnerabilities are discovered, but this should serve as a useful guide for anyone to appreciate the importance of writing optimised Dockerfiles.

A side note on security is that it is absolutely essential to add a non-root user to your Dockerfile, as any amount of vulnerability reduction covered in this article is of no use if a hacker manages to enter your container with a root user role.
