# Meet the new zero-shot NER architecture

GLiNER is a Named Entity Recognition (NER) model capable of identifying any entity type using a bidirectional transformer encoder (BERT-like). It provides a practical alternative to traditional NER models, which are limited to predefined entities, and Large Language Models (LLMs) that, despite their flexibility, are costly and large for resource-constrained scenarios.

GLiNER revolutionized zero-shot NER by demonstrating that lightweight encoders can achieve excellent results. We’re excited to continue R&D with this spirit 🔥. Our new bi-encoder and poly-encoder architectures were developed to address the main limitations of the original GLiNER architecture while bringing new possibilities. But firstly let’s talk about the original GLiNER architecture.

GLiNER uses a BiLM to process entity-type prompts and input text. Entities are separated by [ENT] tokens. The BiLM outputs token representations. Entity embeddings go through a FeedForward Network, while word representations are used to compute span embeddings. Matching scores between entity and span representations are calculated using dot product and sigmoid activation. For example, the span “Alain Farley” has a high matching score with the “Person” entity embedding.

In other words, GLiNER utilizes the main power of transformer models — the attention mechanism. But with great power comes some limitations:

- Representations of entities depend on their order, which doesn’t make much more sense for NER tasks;
- Extrapolation abilities in terms number of entity types it can process are limited, most of the GLiNER model works well up to 30 entity types;
- Joint entity and text representation can create computation overhead, especially for small texts.

To address the limitations of the original GLiNER architecture, we have developed two new model types: the bi-encoder and the poly-encoder architectures.

![](https://miro.medium.com/v2/resize:fit:700/1*p2efYY1hw8RjmSBFsX6ngA.png)

The bi-encoder architecture separates the encoding of the input text and the entity types into two distinct transformer models. This allows for more efficient and scalable processing, as the entity-type encoding can be pre-computed and reused across different input texts. Additionally, the decoupling of text and entity encodings reduces the computational overhead, making the model more suitable for resource-constrained scenarios. As label encoders, we use sentence transformers, that were trained on millions and even billions of examples and have amazing semantic understanding abilities. In our experiments, we found that such a combination of sentence transformer with encoder trains faster and demonstrates better generalization abilities.

Below you can see projected entity embeddings, produced by fine-tuned labels encoder, into 2D space, as you can observe the model nicely learned semantic relations between entities and similar clusters are smoothly distributed in the vector space.

![](https://miro.medium.com/v2/resize:fit:2156/1*7jpe3f_tbKmTfpGyn4654g.png)

The poly-encoder architecture builds upon the bi-encoder approach but adds a post-fusion step to explicitly model the interactions between the input text and entity representations. At high-level poly-encoder architecture enables communication between labels and labels and text in both directions. This architecture helps address the lack of inter-label understanding that can occur in standalone bi-encoder models. The poly-encoder has shown improved performance on complex NER tasks with a large number of entity types, overcoming the extrapolation limitations of the original GLiNER model and keeping the efficiency of bi-encoder models.

To summarise the new architecture has the following advantages:

- An unlimited amount of entities can be recognized at a single time;
- Faster inference if entity embeddings are preprocessed;
- Better generalization to unseen entities;

We trained our models in two stages, the first one is massive pre-training on the NuNER dataset consisting of one million examples. The second stage was fine-tuning on more diverse and high-quality dataset consisting of 35k examples. During the first stage, we aligned the representation of entities produced by a sentence transformer and span representations produced by a transformer encoder, such as DeBERTa. During the second stage, we improve the quality of representations while preserving their generalization properties. As a result, we got efficient bi-encoder models that demonstrate better performance than GLiNER v2.1. As far as our knowledge is correct this is the first such advanced result in zero-shot NER for a bi-encoder model.

### How to run the model

First of all, we need to install the latest version of GLiNER for that run the following pip command:

`pip install gliner -U`

Then we need to initialize our model and we are ready to go:

`from gliner import GLiNER`


model = GLiNER.from_pretrained("knowledgator/gliner-bi-large-v1.0")

There are two ways of running the model, the first one inherits the original GLiNER work and can be used for the cases if you have constantly changing entity types you put into the model.

`git clone https://github.com/urchade/GLiNER.git`

But before that, we need to prepare a training dataset, which has the following format:

`[`

{“tokenized_text”: [‘your’, ‘tokenized’, ‘text’], “ner”: [[start_id, end_id, ‘Your label’], …]},

…

]

Where *start_id* is an index of the first token for a particular entity and *end_id* is an index of the last token.

You can synthetically generate such a dataset with LLMs, the example is here: https://github.com/urchade/GLiNER/blob/main/examples/synthetic_data_generation.ipynb.

After we finished with dataset preparation we needed to specify training parameters. The most important hyperparameters for us are *learning_rate* and *others_lr*, the first one specifies the learning rate for both text and entity encoders and the last one specifies the learning rate for other parts of a model, such as the LSTM layer and different fully connected layer.

We recommend setting a slightly lower learning rate for the encoder part of the model to prevent overfitting and maintain the pre-trained knowledge. Typical values for fine-tuning range between *1e-5* and* 5e-6*, which allows for subtle adjustments to the pre-trained weights without drastically altering them.

Weight decay, also known as L2 regularization, can be applied to both the encoder and other parts of the model. If preserving broad zero-shot capabilities is a priority, we suggest using larger weight decay values, such as 0.1. This helps prevent overfitting by adding a penalty term to the loss function, encouraging smaller weights and improved generalization.

Batch size selection is crucial from multiple perspectives, including available GPU resources, model generalization ability, and the confidence of the final model. Larger batch sizes can leverage GPU memory and computational power more efficiently, and produce more accurate gradients during training due to reduced stochastic noise. However, because of our sampling strategy, a training example will have more negative entity types, potentially leading to a less confident final model.

To mitigate this issue, we recommend incorporating additional loss function parameters such as *focal_loss_alpha* and *focal_loss_gamma*. The *focal_loss_alpha* parameter, typically set between 0.7 and 0.9, specifies the influence of positive and negative examples in the loss calculation. It helps address class imbalance by assigning higher weights to the minority class.

The *focal_loss_gamma* parameter controls the influence of hard examples by modulating the loss contribution of easy examples. It reduces the relative loss for well-classified examples, allowing the model to focus more on hard, misclassified examples. This is particularly helpful in our case of imbalanced data where true negative entities predominate.

The Focal Loss function, originally proposed by Lin et al. in their paper “Focal Loss for Dense Object Detection” (2017), is defined as:

FL(pt) = -α(1 — pt)ᵞ log(pt)

Where:

- pt is the model’s estimated probability for the target class
- α is the focal_loss_alpha parameter
- γ (gamma) is the focal_loss_gamma parameter

By fine-tuning these parameters, we can achieve a better balance between positive and negative examples, improving the model’s performance on imbalanced datasets and enhancing its ability to generalize across various entity types.

### Summary

The evolution of GLiNER represents a significant leap forward in zero-shot Named Entity Recognition, especially in terms of scalability. By addressing the limitations of the original architecture, the new bi-encoder and poly-encoder models offer impressive advancements in flexibility, efficiency, and performance. The bi-encoder GLiNER models have demonstrated superior performance compared to GLiNER v2.1, while having better scalability. Right now it’s possible to build an entity extraction system with hundreds and even thousands of entity categories. It opens opportunities for such tasks as entity linking, ontology construction and even RAG.
