There are several methods for post-training large language models (LLMs) to enhance their ability to follow instructions and align with human preferences. Among the most popular approaches are Reinforcement Learning with Human Feedback (RLHF), which typically relies on the PPO (Proximal Policy Optimization) algorithm, and [Direct Preference Optimization (DPO)](<https://kaitchup.substack.com/p/multi-gpu-dpo-training-with-fsdp>), a simpler yet widely used alternative.

Group Regularized Policy Optimization (GRPO), introduced one year ago with [DeepSeekMath](<https://arxiv.org/abs/2402.03300>), has also emerged as a promising alternative. GRPO has demonstrated remarkable efficiency and has been successfully used to train state-of-the-art LLMs such as Qwen2.5 and DeepSeek-R1. It is now implemented in [Hugging Face TRL](<https://github.com/huggingface/trl>) and [Unsloth](<https://github.com/unslothai/unsloth>).

In this article, we will:

  1. Explore how GRPO works and why it is a strong alternative to RLHF and DPO.

  2. Train a 14B model, Qwen2.5 Instruct, using GRPO with Unsloth on a single consumer GPU.

  3. Discuss the critical roles of the reward functions.

The following notebook provides a step-by-step guide on training an LLM with GRPO using QLoRA/LoRA.

## GRPO: Better than DPO, Cheaper than RLHF

Imagine you have a model that generates its own examples, then learns from them right away. That's the core idea behind GRPO: it's an online algorithm where the model samples completions, sees how good they are, and then updates itself.

For each batch of prompts in the training data, you get multiple completions and a reward _r i_ for each completion. You compare each reward against the group's average to get a “relative” advantage:

$$ \hat{A}_i = \frac{r_i - \bar{r}}{\sigma(r)}, $$ 

where _r̄_ is the average reward among the completions in that batch, and _σ(r)_ is the standard deviation, i.e., how much they deviate from that central value on average. This tells you whether a particular completion is better or worse than the others in the same group.

GRPO also keeps the new policy _π θ_ (the model being updated) close to a reference policy _π ref_ (a fixed model initialized by the model being updated). The measure of “closeness” is the KL divergence _DKL[π θ ∥ πref]_. If the policy drifts too far from the reference, the loss penalizes it.

Bringing it all together, the loss function looks like this:

$$ L_{\text{GRPO}}(\theta) = - \Big( \text{advantage term} \Big) \;+\; \beta \, \Big( \text{KL term} \Big), $$ 

which can be written in more detail as:

$$ L_{\text{GRPO}}(\theta) = - \sum_{i} \hat{A}_i \, \big[\pi_\theta(\text{completion}_i)\big] \;+\; \beta \, D_{\text{KL}}[\pi_\theta \,\|\, \pi_{\text{ref}}]. $$ 

where _β_ is a hyperparameter that weighs the KL penalty.

In plain language, you want to reward completions with high advantage (meaning high relative rewards) while limiting how far the new policy can move away from the reference policy (the KL penalty). That’s it.

## Training LLMs with GRPO Step-by-step

With GRPO, the model learns from the examples it generates itself. However, if implemented naively, this process can be extremely slow and memory-intensive.

During training, memory is required not only for storing gradients and optimizer states but also for generating examples. A straightforward approach would be to duplicate the model for generation, but this significantly increases memory consumption, especially when working with large models.

Additionally, using a standard inference framework like Hugging Face Transformers can lead to severe inefficiencies. For example, if we train with batches of 8 prompts and generate 8 responses per prompt, we end up generating 64 responses (8×8) per step. Given that reasoning sequences can be very long, this would drastically slow down training and require substantial memory.

#### Memory-Efficient GRPO = vLLM + LoRA

vLLM is one of the fastest inference frameworks, leveraging continuous batching and prefix caching for efficiency. The prefix caching feature is particularly beneficial when performing multiple decodings per prompt. Instead of recomputing the KV cache and re-encoding the prompt eight times, vLLM stores and reuses these computations, significantly reducing redundant processing.

To further optimize memory usage, we can avoid duplicating the model for inference by using the same frozen base model for both training and generation. Instead of modifying the full model, we train a LoRA adapter, which can be quickly swapped in and out. This allows us to generate on-policy examples efficiently with vLLM, without the need for excessive memory overhead.

#### A GRPO Adapter for Qwen2.5 14B with Unsloth

In an earlier version of this article, I attempted to use [TRL’s implementation of GRPO](<https://huggingface.co/docs/trl/main/en/grpo_trainer>). However, I encountered multiple issues related to vLLM, LoRA, and gradient checkpointing, which prevented me from publishing the results. Hugging Face is actively working to improve this implementation, aiming to create a flexible and multi-GPU-friendly GRPO pipeline.

On the other hand, Unsloth’s implementation, while less flexible and works only with a single GPU, already integrates vLLM and LoRA efficiently, making it easier to use. Additionally, it allows for quantizing the base model, reducing memory consumption by nearly 3.5x once loaded, further optimizing resource usage.

### Reward Functions for GRPO

We can guide GRPO training using a reward model or by employing a verifiable reward approach. For example, if we want the model to generate reasoning and explicitly delimit it, assuming the system prompt contains this:
    
    
    SYSTEM_PROMPT = """
    Respond in the following format:
    <reasoning>
    ...
    </reasoning>
    <answer>
    ...
    </answer>
    """

we can define a reward function like this:
    
    
    def strict_format_reward_func(completions, **kwargs) -> list[float]:
        """Reward function that checks if the completion has a specific format."""
        pattern = r"^<reasoning>\n.*?\n</reasoning>\n<answer>\n.*?\n</answer>\n$"
        responses = [completion[0]["content"] for completion in completions]
        matches = [re.match(pattern, r) for r in responses]
        return [0.5 if match else 0.0 for match in matches]

If the on-policy model generates responses that include sections delimited by `<reasoning>` and `<answer>` tags, it receives a reward of 0.5. This is a strict criterion, but Unsloth also provides a "soft" version that allows for minor formatting variations, such as ignoring newline characters (`\n`) in the pattern.

If your model fails to learn the intended behavior, it likely means your reward function is either too strict or too lenient. For example, if the system prompt does not specify the use of `<reasoning>` tags, the model may never generate them—meaning it will never recognize that including them leads to a reward.

It's important to remember that GRPO is not trained on answers directly, only on prompts and questions. It relies on feedback to understand whether its generated output is correct.

For this tutorial, we'll keep things simple by modifying the system prompt and only implementing reward functions to reward the model when the generated examples exhibit the expected format, with more or less flexibility.
    
    
    SYSTEM_PROMPT = """
    Respond in the following format:
    <reasoning>
    ...
    </reasoning>
    <answer>
    ...
    </answer>
    <aha>
    No no no, this is my real answer:
    ...
    </aha>
    """
    import re
    
    def very_loose_format_reward_func(completions, **kwargs) -> list[float]:
        """Reward function that checks if the completion has a specific format."""
        responses = [completion[0]["content"] for completion in completions]
        return [0.5 if "<reasoning>" in r and "</reasoning>" in r else 0.0 for r in responses]
    
    def strict_format_reward_func(completions, **kwargs) -> list[float]:
        """Reward function that checks if the completion has a specific format."""
        pattern = r"^<reasoning>.*?</reasoning>\s*<answer>.*?</answer>\s*<aha>.*?</aha>$"
        responses = [completion[0]["content"] for completion in completions]
        matches = [re.match(pattern, r) for r in responses]
        return [0.5 if match else 0.0 for match in matches]
    
    def aha_reward_func(completions, **kwargs) -> list[float]:
        """Reward function that checks if the completion contains "aha" times, 2 for the tags, and one more, wherever it wants."""
        responses = [completion[0]["content"] for completion in completions]
        matches = [re.findall(r'\baha\b', r, re.IGNORECASE) for r in responses]
        return [0.5 if len(match) == 3 else 0.0 for match in matches]

### Prompt Dataset 

I used the same dataset that I used for this article:

  * [cognitivecomputations/dolphin-r1](<https://huggingface.co/datasets/cognitivecomputations/dolphin-r1>) (Apache 2.0 license)

It contains many prompts and is suitable for many different types of reward functions. We only need to inject our system prompt in the “messages” column.
    
    
    from datasets import load_dataset
    import multiprocessing
    ds = load_dataset("cognitivecomputations/dolphin-r1", "reasoning-deepseek", split="train[:10000]")
    ds = ds.rename_columns({'messages':'prompt'})
    
    def process(row):
      row['prompt'][0]['content'] += '\n'+SYSTEM_PROMPT
      return row
    
    ds= ds.map(
        process,
        num_proc= multiprocessing.cpu_count(),
        load_from_cache_file=False,
    )
    
    def tokenize_with_template(example):
        """Tokenizes input text using the chat template of the tokenizer."""
        chat_template = tokenizer.apply_chat_template(example['prompt'], tokenize=False, add_generation_prompt=True)
        tokens = tokenizer(chat_template, truncation=False, add_special_tokens=True)["input_ids"]
        return {"token_length": len(tokens)}
    
    ds = ds.map(tokenize_with_template,
        #num_proc= multiprocessing.cpu_count(),
        load_from_cache_file=False)
    ds = ds.filter(lambda example: example["token_length"] <= max_seq_length)
    ds = ds.remove_columns(["token_length"])

_Note: The current Unsloth implementation appears to break when training prompts exceed the maximum sequence length. To prevent training from unexpectedly stopping, I recommend filtering out prompts that exceed this limit before training begins._

### Setting the GRPO Training Arguments

We have to set the following arguments for GRPO:
    
    
    from trl import GRPOConfig, GRPOTrainer
    training_args = GRPOConfig(
        **use_vllm** = True, # use vLLM for fast inference!
        learning_rate = 1e-6,
        warmup_ratio = 0.1,
        lr_scheduler_type = "linear",
        optim = "paged_adamw_8bit",
        logging_steps = 5,
        bf16 = True,
        per_device_train_batch_size = 1,
        gradient_accumulation_steps = 4, # Increase to 4 for smoother training
        **num_generations** = 6, # Decrease if out of memory (but avoid below 4)
        **max_prompt_length** = 256,
        **max_completion_length** = 512,
        # num_train_epochs = 1, # Set to 1 for a full training run
        max_steps = 250,
        save_steps = 250,
        report_to = "none", # Can use Weights & Biases
        output_dir = "outputs",
    )

  * `num_generations`: The number of samples generated for each training prompt. A higher value generally improves training, as seen in DeepSeek R1, where DeepSeek AI sets it to 8. However, keep in mind that increasing this value significantly increases training time and memory usage due to larger batch sizes.

  * `use_vllm`: Set this to `True` for faster inference.

  * `max_prompt_length`: This should match the length of the longest prompt in your training dataset to ensure proper handling of input sequences.

  * `max_completion_length`: This parameter has a major impact on memory consumption. Higher values improve reasoning quality, but they also increase memory requirements.

## Conclusion

In this tutorial, we explored how GRPO works and walked through a practical example of training an instruction-tuned model using QLoRA on a single GPU.

While GRPO is a powerful method, it comes with certain challenges:

  * Reward Function Design: Crafting effective reward functions can be tricky. Poorly designed rewards may lead to unproductive training dynamics or unintended behaviors.

  * Memory Overhead: Large models and multiple generations per batch can strain memory resources, requiring careful optimization.

Looking ahead, there’s significant room for improvement:

  * Exploring more sophisticated and domain-specific reward functions.

  * Investigating how LoRA rank affects RL training quality.

Additionally, Unsloth’s GRPO implementation could be easily adapted for efficient online DPO since DPO also requires on-policy response generation during training.
