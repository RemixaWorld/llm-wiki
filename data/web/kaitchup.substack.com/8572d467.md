LoRA adapters let you specialize a base LLM for specific tasks or domains by attaching low-rank weight deltas to selected layers. At inference time, the adapter must be loaded alongside the base model, and many applications benefit from serving several adapters, e.g., one for function calling and others for classification, translation, or general generation.

In a standard setup, switching tasks means unloading one adapter and loading another, which can add seconds of latency. Modern open-source servers avoid this by keeping multiple LoRA adapters resident and selecting the appropriate one per request. For example, vLLM can host several adapters simultaneously and apply them on demand with negligible switch time, subject to GPU memory limits.

This guide shows how to run vLLM with multiple LoRA adapters and a custom chat template, both offline (Python API) and online (HTTP server). As a running example, it uses two adapters fine-tuned for French and Japanese translation on a Qwen3 base model, and keeps the exact same custom chat template used during fine-tuning.

We’ll load several adapters side by side, route each request to the desired adapter, and register a custom chat template so prompts match training. The accompanying notebook contains the full, runnable code for serving multiple LoRA adapters with vLLM.

## Set Up a Custom Chat Template

Most LLM chat templates are written in Jinja, which makes non-trivial control flow hard to express clearly. Small mistakes slip in and often get discovered only after release. Unsloth, for example, routinely audits templates and finds issues. The lack of clarity (and the awkwardness of toggling behaviors via template flags) even led the Qwen team to split Qwen3 into separate Instruct and Thinking models rather than rely on a chat-template argument to enable “thinking.”

Because of this, I don’t hand-write templates. I spell out the requirements and have ChatGPT generate one, then iterate until edge cases are handled. For my translation adapters, the training text is formatted like this:
    
    
    <start>You are a professional translator that translates messages from English to French.<user>The cat is in the kitchen<translator>Le chat est dans la cuisine.<eos>

We clearly have a system prompt, a user prompt, and the model’s answer.

I simply gave this example to ChatGPT (GPT-5 Thinking) and asked it to generate a Jinja chat template based on it.

It generated:
    
    
    {# Expects: messages (list of {role, content}), add_generation_prompt (bool) #}
    {%- macro text_of(m) -%}
      {%- if m.content is string -%}{{ m.content | trim }}
      {%- else -%}{{ m.content | selectattr("type","equalto","text") | map(attribute="text") | join("\n") | trim }}
      {%- endif -%}
    {%- endmacro -%}
    
    {# Grab the first system message, if any #}
    {%- set sys = (messages | selectattr("role","equalto","system") | map(attribute="content") | list | first) -%}
    {%- if sys %}<start>{{ sys | trim }}{% endif -%}
    
    {# Render the rest #}
    {%- for m in messages if m.role != "system" -%}
      {%- if m.role == "user" -%}<user>{{ text_of(m) }}
      {%- elif m.role in ["assistant","translator"] -%}<translator>{{ text_of(m) }}
      {%- endif -%}
    {%- endfor -%}
    
    {# Open the model's turn if requested #}
    {%- if add_generation_prompt %}<translator>{% endif -%}

It’s a bit complicated, but it works. I saved the result as `chat_template.jinja`, and we’ll see how to load it in vLLM next. (You could also embed a template in `tokenizer_config.json`, but that approach is largely being phased out.)

## Offline Inference with Multiple LoRA Adapters Using vLLM

For this tutorial, I fine-tuned two adapters for translating English into French and Japanese, for [Qwen3 4B Base](<https://huggingface.co/Qwen/Qwen3-4B-Base>).

With vLLM, you can switch between LoRA adapters without reloads. That’s especially useful for translation, where each adapter can handle a specific language pair (e.g., en→fr, en→ja).

First, install vLLM:
    
    
    pip install vllm

For offline inference (no server), load the base model, e.g., `Qwen3-4B-Base`, and tell vLLM you’ll use LoRA. Set `max_lora_rank=32` to match the adapters you’ll load (all rank-32 in this example); this lets vLLM allocate the right buffers and avoid waste.

**Limitations with LoRA in vLLM**

  * Adapter rank is supported up to **512**.

  * If `max_lora_rank` exceeds the highest adapter rank you actually use, vLLM over-allocates memory and efficiency drops.

  * Adapters that bundle full modules (e.g., token embeddings, `lm_head`) aren’t supported. The safetensors must contain only the LoRA **A/B** matrices for the adapted linear layers, not full weights.

    
    
    from vllm import LLM, SamplingParams
    from vllm.lora.request import LoRARequest
    
    model_id = "Qwen/Qwen3-4B-Base"
    
    llm = LLM(model=model_id, enable_lora=True, max_lora_rank=32)

Next, create two `LoRARequest` objects, one per adapter. Each request bundles a readable name, a unique integer ID, and the local path to the adapter. You’ll pass one of these requests to `LLM.generate` to select which adapter to apply for that call.

Load the adapters like this:
    
    
    adapter_enfr_path = "/workspace/SFT-OPUS-en-fr/checkpoint-15469"
    adapter_enja_path = "/workspace/SFT-OPUS-en-ja/checkpoint-15469"
    adapter_enfr = LoRARequest("enfr", 1, adapter_enfr_path)
    adapter_enja = LoRARequest("enja", 2, adapter_enja_path)

Then, we can use them as follows:
    
    
    my_sentence_translate1 = "I'm an English teacher."
    my_sentence_translate2 = "My keyboard is broken."
    system_prompt_enxx = make_system_prompt("French") 
    prompt1 = [system_prompt_enxx,{"role": "user", "content": my_sentence_translate1}]
    prompt2 = [system_prompt_enxx,{"role": "user", "content": my_sentence_translate2}]
    
    prompts = []
    prompts.append(prompt1)
    prompts.append(prompt2)
    
    with open("/workspace/chat_template_translator.jinja", "r", encoding="utf-8") as f:
        CHAT_TEMPLATE = f.read()
    
    outputs = llm.chat(prompts, sampling_params, lora_request=adapter_enfr, chat_template=CHAT_TEMPLATE)
    
    for output in outputs:
        generated_text = output.outputs[0].text
        print(generated_text)

Pass the adapter to `llm.chat` via `lora_request`, and load your Jinja template from disk to supply as `chat_template`. This keeps formatting consistent with fine-tuning.

Only the `lora_request` (and prompt) change; the base model stays loaded, so switching adapters adds no reload latency.

For translating to Japanese, you can simply change the adapter and the system prompt:
    
    
    system_prompt_enxx = make_system_prompt("Japanese") 
    prompt1 = [system_prompt_enxx,{"role": "user", "content": my_sentence_translate1}]
    prompt2 = [system_prompt_enxx,{"role": "user", "content": my_sentence_translate2}]
    
    prompts = []
    prompts.append(prompt1)
    prompts.append(prompt2)
    outputs = llm.chat(prompts, sampling_params, lora_request=adapter_enfr, chat_template=CHAT_TEMPLATE)

## Serving Multiple Adapters with vLLM

Serving the adapters is even more straightforward and powerful.

Start the vLLM server with these two adapters and the custom chat template (just provide the file location):
    
    
    vllm serve Qwen/Qwen3-4B-Base --chat-template chat_template_translator.jinja --max-lora-rank 32 --enable-lora --lora-modules enfr=/workspace/SFT-OPUS-en-fr/checkpoint-15469/ enja=/workspace/SFT-OPUS-en-ja/checkpoint-15469/

I name the adapters `enfr` and `enja` and reuse those identifiers when routing requests.

To query the server, I use the OpenAI-compatible client: same request/response shape as the OpenAI API, pointed at the vLLM endpoint. You include the adapter name to select which LoRA runs, so prompts stay the same, only the adapter choice changes. Make sure the names match the ones you registered when launching vLLM.
    
    
    from openai import OpenAI
    
    model_id = "enfr"
    
    # Modify OpenAI's API key and API base to use vLLM's API server.
    openai_api_key = "EMPTY"
    openai_api_base = "http://localhost:8000/v1"
    client = OpenAI(
        api_key=openai_api_key,
        base_url=openai_api_base,
    )
    def make_system_prompt(language):
        system_prompt_enxx = {"role":"system", "content":"You are a professional translator that translates messages from English to "+language+"."}
        return system_prompt_enxx
    my_sentence_translate1 = "I'm an English teacher."
    my_sentence_translate2 = "My keyboard is broken."
    system_prompt_enxx = make_system_prompt("French") 
    prompt1 = [system_prompt_enxx,{"role": "user", "content": my_sentence_translate1}]
    prompt2 = [system_prompt_enxx,{"role": "user", "content": my_sentence_translate2}]
    
    prompts = []
    prompts.append(prompt1)
    prompts.append(prompt2)
    
    completion = client.chat.completions.create(
        model=model_id,
        messages=prompts[0]
    )

Replace “localhost” with the IP address of your server. 

We now have a server ready to translate user messages!

## Conclusion

LoRA adapters let you specialize a base LLM for tasks or domains by adding low-rank “delta” weights to selected layers. vLLM can keep several adapters resident and pick one per request with minimal overhead, so you can serve, say, `en→fr` and `en→ja` translators from a single base without reloads. You set a `max_lora_rank` (vLLM supports ranks up to 512) and register adapter names/paths. Avoid adapters that include full modules like `embed_tokens` or `lm_head` as those are not supported for multi-LoRA and will error out.

**About QLoRA**

QLoRA = LoRA on a 4-bit bitsandbytes base. In vLLM you enable it by loading the model with bitsandbytes quantization and pointing the engine to the QLoRA adapter repo: set `quantization="bitsandbytes"` (or `--load-format bitsandbytes`) and provide `qlora_adapter_name_or_path` (or `--qlora-adapter-name-or-path`). The engine quantizes the base to 4-bit at load time using metadata from the adapter repo, and you still select the adapter per request with `LoRARequest`, exactly as with FP16/BF16 bases. vLLM also supports LoRA on other quantized bases (AWQ, GPTQ) in the same way.
