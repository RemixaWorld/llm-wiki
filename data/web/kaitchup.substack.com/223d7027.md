2-bit quantization for LLMs can be surprisingly accurate when using state-of-the-art techniques. In a previous article, we saw how to quantize Qwen2.5 72B to 2-bit, reducing the model size to 23.8 GB while retaining 88% of its original accuracy, all with AutoRound and minimal tuning of quantization hyperparameters.

That said, some of these hyperparameters, especially at such low-bit precision, play a critical role in quantization success. In particular, group size can significantly affect model stability, accuracy, and final size.

In this article, we explore practical recipes for 2-bit quantization, with a focus on understanding and properly setting the group size. The goal is to help you anticipate its effect on model size and accuracy _before_ running the quantization.

Our best 2-bit 72B model retains 96.5% of the original 16-bit accuracy for the IFEval benchmark while being 5.3x smaller.

## What is Quantization Group Size?

Most quantization methods use the INT8, INT4, INT3, or INT2 data types depending on the precision of the quantization. To convert the original weights of the model, which are usually using FP32, FP16, or BF16 data type, we need to perform a mapping operation.

For instance, when converting FP16 parameters to INT8 parameters, we need to map the FP16 range to the INT8 range. This mapping is usually done through a scaling factor (scale) simply computed as follows:

$$ \text{scale} = \frac{\text{max}(\text{abs}(\text{min_val}), \text{abs}(\text{max_val}))}{127} $$ 

  * `min_val`, `max_val`: the range of your FP16 tensor.

  * INT8 range: `[-128, 127]`, but we map for symmetric quantization to `[-127, 127]` to keep 0 in the middle.

  * So we divide the largest absolute FP32 value by 127 to get the scaling factor.

When weights are quantized, they are mapped using scaling factors and stored as INT8 values. However, inference typically operates with FP16 or BF16 activations and key-value (KV) caches, since these formats are optimized for GPU matrix multiplications. As a result, dequantization is often necessary: INT8 weights must be mapped back to FP16 using the stored scales when they are needed.

Inference frameworks can perform partial computations directly in INT8 before dequantization, which speeds things up. But generally, we still need to store the scale in the model files to enable dequantization. This is standard in general quantization formats like GPTQ. Highly optimized frameworks designed for a specific model might fuse or compress this logic further, or even better, implement it at the hardware level.

### Quantization Example and Scale Overhead

Let’s consider quantizing weights in groups of 128 (a common default for INT8 or 4-bit quantization). Originally, 128 weights stored in FP16 take:

$$ 128 \times 2 = 256\ \text{bytes} $$ 

since 1 FP16 parameter occupies 2 bytes of memory. After quantization to INT8 (1 byte), the weights occupy:

$$ 128 \times 1 = 128\ \text{bytes} $$ 

But we also need to store one scale per group, typically as FP16 or FP32:

  * With an FP16 scale, that’s an extra 2 bytes, so the total becomes:

$$ 128 + 2 = 130\ \text{bytes} $$ 

Now, imagine applying this to a 32B parameter model:

  * At 128 weights per group, we have:

$$ 32\text{B} / 128 = 250\text{M groups} $$ 
  * Each FP16 scale takes 2 bytes, totaling:

$$ 250\text{M} \times 2 = 500\ \text{MB} $$ 

### Smaller Group Sizes: Better Accuracy, More Overhead

Smaller groups improve quantization accuracy, especially for low-bit quantization like 2-bit. For example, using a group size of 32 (common for 2-bit quantization):

  * You now have 1B groups for your 32B model, so the total scale storage (FP16) is:

$$ 1\text{B} \times 2 = 2\ \text{GB} $$ 
  * The weights themselves use:

$$ 32\text{B} \times 0.25\ (\text{2 bits}) = 8\ \text{GB} $$ 
  * Total model size becomes 10 GB, meaning scales make up 20% of the final memory footprint.

### Bits per Weight Breakdown

To reason about this more precisely, consider the effective bits per weight.

  * Quantizing to 2-bit with group size 32 and storing scales in FP32 (32 bits or 4 bytes):

    * Each scale contributes 1 bit per weight (32 bits / 32 weights).

    * So, total is:

$$ 2 + 1 = 3\ \text{bits per weight} $$ 

This means a 50% increase in memory usage, in this case, and with FP32 scales, compared to pure 2-bit quantization. In contrast, a group size of 128 results in:

$$ 2 + \frac{32}{128} = 2.25\ \text{bits per weight} $$ 

### Summary

  * Smaller group sizes yield better quantization quality but higher memory overhead.

  * The scale becomes a non-negligible contributor to model size at lower bit widths.

  * Carefully choosing the group size and scale precision is critical for balancing accuracy and efficiency.

_Note: Since quantization of the token embeddings and language modeling head is not supported by most quantization methods, we should leave these parameters in 16-bit precision for the calculation of the occupied memory._

## Optimal 2-bit Quantization

Let’s experiment with a large model like Qwen2.5-72B Instruct. I chose this model because it’s known for being highly robust to quantization, even down to 2-bit precision, with minimal loss in accuracy. _Note: achieving similar results with Llama 3 models would be significantly more challenging._

### With AutoRound

[AutoRound ](<https://github.com/intel/auto-round>)is my preferred quantization method because it’s well-maintained and capable of quantizing large models efficiently at low cost. For example, it’s possible to quantize a 70B model using a single 24 GB GPU. However, to accelerate the process and leverage better hyperparameters, I used an H100 GPU.

With AutoRound, quantization time primarily depends on the number of iterations used in the SignSGD optimization, the sequence length of the calibration dataset, and the number of calibration samples.

I used two configurations:

**Configuration A**

  * `nsamples = 512`

  * `sequence_length = 4096`

  * `iters = 512`

**Configuration B**

  * `nsamples = 256`

  * `sequence_length = 2048`

  * `iters = 256`

For both configurations, I had to set `low_gpu_memory_usage=True`, as a single H100 doesn’t have enough memory to handle a 70B model without this setting. I also enabled Torch compilation, as recommended by Intel, for improved speed and slight memory savings. However, despite using PyTorch 2.6 (the recommended version), Torch compilation threw several warnings, suggesting that its effectiveness may be limited (not sure about this, just an assumption).

Unsurprisingly, Configuration A was significantly more expensive than Configuration B:

**Configuration A**

  * Quantization Time: 11.4 hours

  * Quantization Cost: $27.25 (@ $2.39/hour)

**Configuration B**

  * Quantization Time: 3.1 hours

  * Quantization Cost: $7.41 (@ $2.39/hour)

For each configuration, I tested group sizes of 32, 64, and 128. I also tried group size 16 with Configuration B, but the results were poor enough that I didn’t bother testing it with Configuration A. While smaller group sizes like 16 should theoretically yield better accuracy, the performance issues suggest a possible bug in the GPTQ kernels with this group size.

Here is the quantization code I used:

_Note: I used PyTorch 2.6._
    
    
    from transformers import AutoModelForCausalLM, AutoTokenizer
    import torch
    
    model_name = "Qwen/Qwen2.5-72B-Instruct"
    model = AutoModelForCausalLM.from_pretrained(model_name, torch_dtype="auto")
    tokenizer = AutoTokenizer.from_pretrained(model_name)
    
    from auto_round import AutoRound
    
    def quantize_autoround(nsamples, iters, group_size, seqlen):
    
        autoround = AutoRound(model, tokenizer, nsamples=nsamples, iters=iters, low_gpu_mem_usage=True, enable_torch_compile=True, bits=2, seqlen=seqlen, group_size=group_size, sym=True)
        
        output_dir = "./Qwen2.5-72B-Instruct-autoround-2bit"
        autoround.quantize_and_save(output_dir, format='auto_gptq') 

To evaluate model quality, I used the MMLU-PRO and IFEval benchmarks, with the chat template applied for the latter. IFEval assesses whether the 2-bit models retain instruction-following capabilities comparable to the original model. The evaluation command is included in the notebook.

The 2-bit models perform remarkably well. While MMLU-PRO indicates a significant drop in accuracy, IFEval shows that the 2-bit model with a group size of 32 remains near the standard error margin of the float16 baseline. These models retain strong instruction-following capabilities, preserving up to 96.5% of the original model's accuracy.

Aside from group size 128, the more expensive quantization settings (Configuration A) provide a modest improvement, around 1 point in accuracy.

Notably, increasing the group size significantly degrades performance.

All this is achieved with a dramatically reduced model size.

![image](https://substackcdn.com/image/fetch/$s_!KO_n!,w_2400,c_limit,f_auto,q_auto:good,fl_progressive:steep/https%3A%2F%2Fsubstack-post-media.s3.amazonaws.com%2Fpublic%2Fimages%2F21cefa18-fa08-40f3-bde1-5e730b567ab8_1924x742.png) 

The smallest model fits comfortably on a 32 GB GPU, such as the RTX 5090. The largest 2-bit model that retains 96.5% of the original IFEval accuracy is 5.3x smaller than the original float16 model.

The size difference between group sizes 64 and 128 is minimal, but group size 64 offers a solid trade-off. It saves approximately 2.5 GB of memory compared to group size 32, with only a slight drop in IFEval accuracy and comparable performance on MMLU-PRO.

## Conclusion

AutoRound offers additional hyperparameters that could be tuned for potentially better results. However, given the high cost of testing numerous configurations and the likelihood of only marginal gains, I didn’t explore further optimizations.

Currently, the quantized models won’t run on a 24 GB GPU. _Can we make them smaller?_

**Yes.** AutoRound, when used with the `auto-gptq` backend, does not quantize the model’s language modeling head, leaving several billion parameters in 16-bit precision. While it's possible to quantize the head using other backends, doing so would likely lead to a noticeable drop in accuracy.

Another effective way to reduce model size is to shrink the vocabulary, which directly reduces the size of the embeddings.

_Can we “fix” the 2-bit models?_

**Absolutely.** Since QLoRA works with any quantized model, you can fine-tune an adapter on top of the 2-bit model. With this approach, you might even outperform the original model on your target tasks, while keeping the model 5× smaller. We'll explore how to do that in a future article.

### Appendix: My Failure with GPTQModel V2

I also tried 2-bit quantization with [GPTQModel V2](<https://github.com/ModelCloud/GPTQModel>). This is a new, promising algorithm that shows very good performance for 2-bit quantization of Llama 3.

I used this QuantizeConfig:
    
    
    quant_config = QuantizeConfig(bits=2, group_size=64, v2=True)

However, it breaks the model. On both MMLU-PRO and IFEval, the quantized model yields random performance. I tried with vLLM and HF backends for evaluation.

It is very possible that I missed something in the configuration. This V2 is quite new, and this was my first try with it. The [V2 paper](<https://arxiv.org/abs/2504.02692>) mentioned good results for “Quarot” or “SpinQant” + GPTQModel V2, rather than the GPTQModel V2 alone. This makes me think that a step in the process might be missing, but I didn’t have time to confirm it.
