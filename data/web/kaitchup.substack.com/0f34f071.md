The earliest large language models (LLMs) were trained and deployed using the float32 data type. Since each float32 parameter consumes 4 bytes, a 70-billion-parameter model like Llama 3 requires nearly 280 GB of memory, making large-scale deployment expensive and inefficient. 

To mitigate this, LLM developers gradually transitioned to 16-bit precision to cut memory consumption in half. Initially, they adopted mixed-precision training and inference, keeping critical modules and operations in float32 while downcasting less sensitive components to float16, a 2-byte data type. However, float16 often leads to instability during training and inference, requiring loss scaling and other mitigation strategies.

As an alternative, bfloat16 has become widely adopted due to its superior dynamic range. It matches float32 while halving memory requirements. Most modern GPUs now support bfloat16, but many deployed older GPUs lack native support. Additionally, some CUDA kernels are optimized specifically for float16 inference, leading to better performance in certain scenarios.

If a model has been trained and released in bfloat16—**like Gemma 3** —can we simply cast it to float16 without degrading its performance? In most cases, naive casting to float16 has no visible impact on model quality. However, for models with certain architectural properties and, more specifically, trained with TPUs, such as Gemma 3, converting to float16 can completely break the model, causing it to generate nonsensical output.

In this article, we will evaluate the impact of using bfloat16, float16, and float32 with Gemma 3 in its 4B, 12B, and 27B variants. We will also explore different strategies to improve the float16 version of the models and assess whether accuracy loss can be mitigated.

## The Differences Between bfloat16, float16, and float32

### Precision, Range, and Bit Allocation

The core difference between bfloat16 (BF16), float16 (FP16), and float32 (FP32) lies in how they allocate bits for the exponent and mantissa (fraction).

  * Float32 (IEEE 754 single-precision)

    * 1-bit sign, 8-bit exponent, 23-bit mantissa

    * Maximum exponent value: 127 (bias: 127)

    * Approximate range: ±(1.18 × 10⁻³⁸) to (3.4 × 10³⁸)

  * Float16 (IEEE 754 half-precision)

    * 1-bit sign, 5-bit exponent, 10-bit mantissa

    * Maximum exponent value: 15 (bias: 15)

    * Approximate range: ±(6.1 × 10⁻⁵) to (6.5 × 10⁴)

  * Bfloat16 (Brain floating point)

    * 1-bit sign, 8-bit exponent, 7-bit mantissa

    * Maximum exponent value: 127 (bias: 127)

    * Approximate range: ±(1.18 × 10⁻³⁸) to (3.4 × 10³⁸) (same as FP32)

**bfloat16 has the same exponent size as float32** , meaning it retains the same dynamic range, while float16 has a much smaller exponent, which severely limits its range.

### Impact on LLMs

#### **Numerical Stability**

Large-scale models such as LLMs require high dynamic range due to exploding or vanishing gradients. The 8-bit exponent in BF16 is a major advantage because it prevents underflows and overflows in weight updates and activations. In contrast, FP16 frequently runs into numerical issues due to its limited 5-bit exponent, which requires loss scaling techniques to prevent gradients from becoming too small to represent.

Loss scaling in FP16 works by multiplying gradients by a large factor, performing computations, and then scaling back. While this allows FP16 to function properly, it adds extra computational overhead and complexity. BF16 avoids this completely.

#### Memory Efficiency & Throughput

Both FP16 and BF16 reduce memory usage by 50% compared to FP32, which allows for larger batch sizes, more activations, and deeper models. Using lower precision formats also improves throughput by increasing the number of FLOPs per cycle in specialized hardware.

For instance:

  * NVIDIA A100 tensor cores support FP16 matrix multiplication with FP32 accumulation (TF32 mode). BF16 is also supported natively, making it comparable to FP16 in speed while being more robust to gradient scaling issues.

  * TPUs (v2, v3, v4, v5e, and v5p) are optimized for BF16, making it the default choice for Google-scale training. They trained Gemma 3 with TPUs so it is naturally a BF16 model.

  * AMD MI300 supports BF16 and FP16 equally, but hardware optimizations vary depending on software stack implementations.

## Potential Issues When Converting LLMs from BF16 to FP16

As we saw, BF16 has an 8-bit exponent (same as FP32), while FP16 has only a 5-bit exponent. This means that BF16 can represent much larger and much smaller numbers. If your BF16 model, like Gemma 3, contains very large activations or small gradients, switching to FP16 might cause overflows (NaNs) or underflows (zero values). This is especially problematic in logits and attention layers, where extreme values are common. If the model has been trained with BF16, certain weight values may exceed the FP16 maximum exponent, leading to instability during inference.

BF16 has 7 bits for the mantissa, whereas FP16 has 10 bits. This means FP16 has higher precision, which could, in theory, improve inference accuracy. However, if the model was trained with BF16, switching to FP16 does not improve accuracy but instead changes numerical behavior, which can cause minor but non-trivial discrepancies. If the model was trained with BF16, its weights and activations may assume an FP32-like exponent range, which FP16 cannot handle. If an FP16 model encounters values too large for its exponent range, it can output NaNs or Inf values.

After conversion to FP16, Clamping activations can prevent overflows by applying activation clipping to keep values within FP16’s range. Using mixed-precision inference, where some layers run in FP16 while others stay in FP32, can help avoid catastrophic numerical errors. Fine-tuning the model in FP16 for a few steps after conversion can also allow it to adjust to numerical differences.

Nothing. I didn’t encounter any errors, but the model only generates the EOS token, regardless of the prompt.

Some layers and modules in the model do not handle the conversion from BF16 to FP16 well. To address this, I manually cast the most critical components, such as the layernorms, the language modeling head, and token embeddings, to float32. However, this had no effect. It seems that key operations during inference must be executed in a data type with a larger dynamic range, like float32 or bfloat16, to function correctly.

If we want to maintain compatibility with older GPUs that lack BF16 support, our only option is to use float32. However, this comes with trade-offs: slower inference and a doubling of the model’s memory consumption. A better approach is to keep the model weights in float16 while executing computations in float32.

To achieve this, I leveraged PyTorch’s Automatic Mixed Precision (AMP) and wrapped the inference code with the following instruction:
    
    
    with torch.cuda.amp.autocast(dtype=torch.float32):

It's important to note that this is an unconventional use of AMP. By default, AMP without a specified dtype performs critical operations (such as layer normalization, softmax, and reductions) in float32, while keeping less critical ones in float16. However, this default behavior does not work for Gemma 3, as it still results in broken outputs.

To make the model function correctly, we must explicitly enforce float32 for all operations. Using autocast(dtype=torch.float32) ensures that every tensor operation inside the block runs in float32, preventing numerical instability.

While this approach increases computational overhead and slows down inference, it still maintains a significantly lower memory footprint compared to running the entire model in float32. This is because AMP performs on-the-fly, temporary conversions from float16 to float32 during inference, rather than storing the entire model in float32.

Here is the memory consumption for different data types:

  * **float16: 8.322 GB**

  * **float32: 16.426 GB**

  * **autocast(dtype=torch.float32): 11.029 GB**

  * **bfloat16: 8.254 GB**

Using AMP saves nearly 4 GB of memory compared to full float32 inference, while still requiring 3 GB more than running inference in bfloat16.

## Conclusion

Simply casting a BF16-trained model to FP16 can completely break it, as seen with Gemma 3, due to the exponent limitations of FP16. 

However, it's important to note that LLMs that fail to convert properly to FP16 are quite rare. In the case of Gemma 3, this issue may stem from Google's full utilization of TPU-optimized BF16 computations, making the model particularly sensitive to precision changes. Additionally, Gemma 3’s unique architecture, featuring global-local attention, could introduce numerical behaviors that do not translate well to FP16, further contributing to its instability when cast to this format.

Keep in mind that when using a model in a different data type than it was originally trained in, it's crucial to evaluate its performance under the new precision. While the impact may often be minimal, the model will rarely perform exactly as well as it did in its original format. Even small numerical differences can accumulate, affecting stability or output quality, so testing is essential before deployment.

_Note: The experiments I conducted for this article used the first version of Gemma 3, which was released on the Hugging Face Hub. New versions with better support for float16 might be released by Google in the future._
