Over the past six months, we've seen a steady stream of new vision-language models (VLMs). Models like Qwen2-VL, Llama 3.2 Vision, Molmo, [Pixtral](<https://kaitchup.substack.com/p/run-and-serve-faster-vlms-like-pixtral>), [Qwen2.5-VL](<https://thesalt.substack.com/p/qwen25-vl-high-resolution-vision>), [Phi-4 Multimodal](<https://kaitchup.substack.com/p/phi-4-multimodal-a-mixture-of-audio>), and Aya Expanse have all demonstrated strong performance across multimodal tasks requiring vision capabilities, such as OCR, visual understanding, image captioning, and object recognition.

A common trait among all these models is that they are built on top of large language models (LLMs). For example, Llama 3.2 Vision is derived from Llama 3.1, Qwen2.5-VL is based on Qwen2.5, and Phi-4 Multimodal originates from Phi-4 Mini. These VLMs gain their multimodal capabilities through a post-training phase, where their base LLMs are either further refined using multimodal data or enhanced with trained adapters that introduce multimodal abilities.

During this post-training process, the model is exposed to not just multimodal information but also additional textual data. This means that its language understanding capabilities continue to be trained alongside its vision capabilities, ensuring that it excels in tasks like caption generation and OCR, which require both vision and strong text generation skills.

This raises an important question: does multimodal post-training improve or degrade a model's performance on standard language generation tasks, such as creative writing, language understanding, and instruction-following?

In this article, we address this question using Qwen2.5 as a case study. We will evaluate Qwen2.5-VL on common benchmarks used for LLMs and compare its performance against its base LLM. We will see that multimodal post-training can actually enhance a model’s accuracy on language tasks, especially for larger models.

Since Qwen2.5-VL outperforms Qwen2.5 in these tasks, we will also explore how to leverage it for pure language generation tasks that do not require vision inputs. Specifically, I’ll show you how to use Qwen2.5-VL with vLLM for language inference.

## Qwen2.5-VL: Qwen2.5 Multimodal Post-Training

Building a multimodal model involves more than simply continuing the pre-training of an LLM with multimodal datasets. The model's architecture must be modified to encode multimodal information effectively. This typically involves adding a visual encoder, usually built on Vision Transformer (ViT), and integrating it with the LLM to process and interpret multimodal inputs.

For example, Qwen2.5-VL follows this architecture:

![image](https://substackcdn.com/image/fetch/$s_!gVdg!,w_2400,c_limit,f_auto,q_auto:good,fl_progressive:steep/https%3A%2F%2Fsubstack-post-media.s3.amazonaws.com%2Fpublic%2Fimages%2F8fe48677-2e8a-46f2-957f-ecef85e53086_1872x1206.png) 

The tokenizer of the LLM usually remains unchanged, as the multimodal version only needs to leverage special tokens that were already reserved in the vocabulary for such cases.

However, the method used to integrate multimodal capabilities can vary significantly between models. For instance, Microsoft enhances Phi-4 Mini with multimodal abilities by training adapters on top of the base LLM while keeping the LLM itself frozen. Meta adopts a similar approach for Llama 3.2 Vision, freezing the LLM during multimodal training. In such cases, since the LLM remains unchanged, its core language generation capabilities are unlikely to improve.

In contrast, the Qwen team, in their technical report on Qwen2.5-VL, reported that Qwen2.5-VL actually outperforms Qwen2.5 Instruct in language tasks. In this article, we will take a closer look to verify these findings, particularly for smaller models like Qwen2.5-VL 7B, and examine whether the performance gains persist when the models are quantized.

## Running VLMs for Language Generation Tasks

### VLMs with vLLM

Most VLMs accept inputs in the form of JSON objects, which include fields for both image and text inputs. For example, in the case of Qwen2.5-VL:
    
    
    messages = [
        {
            "role": "user",
            "content": [
                    {
                        "type": "image_url",
                        "image_url": {
                            "url": "qwen.png"
                        },
                    },
                    {"type": "text", "text": "What can you tell me about the best timing to plant strawberries?"},
                ] 
        },
    ]

If we want to only provide a text input, we only have to remove the image input: 
    
    
    messages = [
        {
            "role": "user",
            "content": [
                 {"type": "text", "text": "What can you tell me about the best timing to plant strawberries?"},
                ] 
        },
    ]

Now, since the prompt contains only text, the inference framework automatically handles the necessary formatting, ensuring the model processes the input correctly despite the absence of an image.

Here’s a complete example using vLLM:
    
    
    from vllm import LLM
    from vllm.sampling_params import SamplingParams
    
    model_name = "Qwen/Qwen2.5-VL-7B-Instruct"
    
    sampling_params = SamplingParams(max_tokens=8192)
    llm = LLM(
        model=model_name,
        max_model_len=1024
    )
    
    
    messages = [
        {
            "role": "user",
            "content": [
                 {"type": "text", "text": "What can you tell me about the best timing to plant strawberries?"},
                ] 
        },
    ]
    
    res = llm.chat(messages=messages, sampling_params=sampling_params)
    print(res[0].outputs[0].text)

### Inference Cost for VLMs vs LLMs for Language Generation Tasks

Now, let’s analyze how much more costly it is to run VLMs compared to LLMs. Intuitively, the cost should be higher in terms of both memory and computation time due to the following factors:

  1. **Increased Parameter Count**  
VLMs have slightly more parameters than their LLM counterparts. For example:

     * Qwen2.5 7B has 7.62B parameters, while Qwen2.5-VL 7B has 8.29B.

     * Qwen2.5 72B has 72.7B parameters, while Qwen2.5-VL 72B has 73.4B.

While these increases are relatively small, they result in higher memory consumption—adding less than 3GB in most cases.

  2. **Additional Special Tokens in Input Prompts**  
VLMs introduce vision-related special tokens into the prompt, even when no image or video is provided. This has a minor impact on KV cache size and slightly increases prefix encoding time.

To quantify these costs, we can analyze the logs generated by lm-eval when running the IFEval benchmark with vLLM. These logs provide a breakdown of memory consumption and the total processing time for each task.

For example, when running Qwen2.5-VL 72B, vLLM reports the following:
    
    
    INFO 03-09 15:14:48 worker.py:267] the current vLLM instance can use total_gpu_memory (139.72GiB) x gpu_memory_utilization (0.90) = 125.75GiB
    INFO 03-09 15:14:48 worker.py:267] model weights take 68.57GiB; non_torch_memory takes 1.82GiB; PyTorch activation peak memory takes 2.57GiB; the rest of the memory reserved for KV Cache is 52.78GiB.
     [1;36m(VllmWorkerProcess pid=21891) [0;0m INFO 03-09 15:14:48 worker.py:267] the current vLLM instance can use total_gpu_memory (139.72GiB) x gpu_memory_utilization (0.90) = 125.75GiB
     [1;36m(VllmWorkerProcess pid=21891) [0;0m INFO 03-09 15:14:48 worker.py:267] model weights take 68.57GiB; non_torch_memory takes 1.56GiB; PyTorch activation peak memory takes 2.57GiB; the rest of the memory reserved for KV Cache is 53.03GiB.

Since I used two GPUs, the memory usage is split across two workers, meaning we need to sum the memory consumption from both. The majority of GPU memory is occupied by:

  1. **Model Weights** – The parameters of the model itself.

  2. **KV Cache** – Stores key-value pairs for attention mechanisms, allowing efficient autoregressive generation. 

vLLM dynamically reserves a portion of GPU memory for the KV cache. Reducing the KV cache size can save memory, but if the cache becomes too small, the model may need to recompute it for long sequences—leading to significant slowdowns in inference.

## Conclusion

### **Should You Use an LLM or a VLM?**

It depends on your hardware and use case.

  * If you have a powerful GPU that can handle large models, such as Qwen2.5 72B, you should definitely use the VLM version instead of the LLM. The memory overhead is minimal, and there is no significant difference in inference speed. 

  * For smaller models, using a VLM for pure language generation may not be ideal.  
Smaller models have fewer parameters, making it harder to integrate multimodal knowledge while maintaining strong language generation capabilities. Retaining high accuracy in language tasks while adding vision capabilities remains a challenge at smaller scales.

  * A potential solution for small models is freezing the LLM while training a vision adapter on top of it. This approach helps preserve language generation abilities but may come at the cost of reduced multimodal performance.

In this article, we focused on Qwen2.5, but for other VLMs and LLMs, it's best to refer to their technical reports for detailed insights.

  * If the VLM only adds new parameters while freezing the LLM during multimodal post-training, stick to the LLM for language generation tasks. In this case, the VLM is unlikely to offer improvements in language-related tasks.

  * If the LLM itself has also been further trained during the multimodal post-training phase, carefully evaluate the VLM's performance on language tasks to determine whether it brings any noticeable improvements.

Understanding how a model has been trained is key to making the right choice between LLMs and VLMs for your specific needs.
