ExLlama is a framework similar to `llama.cpp`, but with a primary focus on accelerating inference using GPUs, whereas `llama.cpp` is optimized for CPU-based execution in mind. In a previous article, we explored how ExLlamaV2 handled quantization and inference to make fast and small LLMs.

When ExLlamaV2 was released, it quickly became the fastest framework for running quantized models. However, the landscape has since evolved, with strong competition emerging, notably, [highly efficient quantization formats like Marlin](<https://kaitchup.substack.com/p/marlin-nearly-ideal-inference-speed>), and ultra-fast inference frameworks such as vLLM that support them.

Despite this, the ExLlama team has continued to refine its framework, leading to the release of ExLlamaV3. This new version promises even faster inference and a significantly improved quantization algorithm.

In this article, we'll see how to use ExLlamaV3 and understand how it works under the hood. We'll check its quantization approach and how it enables very large models to run on a single GPU at impressive speeds. In short, ExLlamaV3 is blazing fast, and the development team is actively working to make it even faster. Its quantization accuracy is also among the best currently available.

## ExLlamaV3’s Quantization Algorithm Explained

ExLlamaV3 is here:

  * GitHub: [turboderp-org/exllamav3](<https://github.com/turboderp-org/exllamav3/tree/master>) (MIT license)

ExLlamaV3’s quantization algorithm is based on [QTIP](<https://github.com/Cornell-RelaxML/qtip>), which is known to provide very good accuracy, especially for low-precision quantization.

The authors didn’t publish a complete description of how it works precisely, but we can [look at the code](<https://github.com/turboderp-org/exllamav3/blob/master/exllamav3/modules/quant/exl3_lib/quantize.py>) to understand it.

It starts by regularizing the Hessian. That means slightly adjusting it to ensure it's numerically stable, adding a small constant to the diagonal, for instance. This is a common trick in optimization to prevent divisions by very small numbers or singularities.

> **Hessian in Quantization**
> 
> It provides insight into how changes in weights affect the loss. Ideally, we want to reduce the weight precision without affecting the loss.

Then comes the decomposition: using a _block-wise factorization_ of the Hessian to break it down into simpler matrices that retain its structure. This decomposition is key as it lets the system efficiently apply the Hessian's insights to batches of weight tiles during quantization.

Before the quantization happens, weights are transformed to make them more uniform. That involves flipping the signs of certain input channels and applying _Hadamard transforms_ , which are fast orthogonal transformations that spread out information across all elements. It helps ensure that no weight carries too much localized "importance" that might get lost in quantization.

Next, the weight matrix is sliced into small 16×16 tiles, which are then reshaped into 256-element vectors. These tiles are permuted into a specific layout optimized for modern GPU tensor cores. This reordering ensures that the computation can be done efficiently in parallel. Each tile is then quantized independently. After quantization, the algorithm corrects its own errors. It calculates how much information was lost and uses the decomposed Hessian to compensate for that error in the next step, adjusting future tiles accordingly. This iterative refinement helps preserve the most important aspects of the model even after significant compression.

Before finalizing, the algorithm fine-tunes a global scaling factor. It finds the scale that minimizes the mean squared quantization error across representative tiles. With this, the quantization error is further reduced, particularly for outlier values that would otherwise throw off the results.

Finally, everything gets packed into compressed representations. The quantized indices are stored in a _trellis_ format, essentially a compact, structured encoding, and the scaling factors are saved as 16-bit floats. If I understand correctly, we have scaling factors for groups of 256 weights, i.e., a group twice as large as what is normally used in GPTQ and AWQ, for instance. This means smaller quantization metadata to store and, consequently, smaller models.

## ExLlamaV3 to Quantize Large Models

ExLlamaV3 is very well optimized for reduced memory consumption and fast quantization. 

To quantize models, clone the repository locally and run:
    
    
    python exllamav3/convert.py -i {model_name} -o {model_name}-exl3-4.0bpw -w exl3_temp -b 4.0

where -i model_name is the local directory containing the model to quantize. -b is the target bit per weight.

Higher bits per weight make quantization faster. With the H100, it takes:

  * 4 hours and 6 minutes with -b 1.75

  * 3 hours and 11 minutes with -b 4.0

If you only have a consumer GPU (e.g., 24 GB of VRAM), it also works, as shown by the authors:

![image](https://substackcdn.com/image/fetch/$s_!0rhd!,w_1456,c_limit,f_auto,q_auto:good,fl_progressive:steep/https%3A%2F%2Fsubstack-post-media.s3.amazonaws.com%2Fpublic%2Fimages%2F2322d7d4-7e03-4193-b8d1-941bc3ec6740_718x492.png) 

_Note: I haven't measured it precisely, but CPU RAM usage during quantization may be quite high. Since the machine I used had over 200 GB of RAM, I didn’t encounter any issues. However, further investigation is needed to confirm memory requirements. It’s likely that having sufficient CPU RAM is essential to load the entire model during quantization, particularly for packing and serialization._

The logs generated during the quantization process are very informative and provide a clear view of each step as it progresses. It can be used to early stop the quantization in case it’s clearly failing with a very high `proxy_err`.

![image](https://substackcdn.com/image/fetch/$s_!I4ER!,w_1456,c_limit,f_auto,q_auto:good,fl_progressive:steep/https%3A%2F%2Fsubstack-post-media.s3.amazonaws.com%2Fpublic%2Fimages%2Fa283c0ee-ece1-447d-9629-a2cf94f50dfd_766x151.png) 

By default, the token embeddings are not quantized, while the language modeling head is quantized to 6-bit precision. The latter can be changed.

The models I quantized are here (Apache 2.0 license):

  * [kaitchup/Llama-3.3-70B-Instruct-exl3-1.75bpw](<https://huggingface.co/kaitchup/Llama-3.3-70B-Instruct-exl3-1.75bpw>) (17.89 GB)

  * [kaitchup/Llama-3.3-70B-Instruct-exl3-4.0bpw](<https://huggingface.co/kaitchup/Llama-3.3-70B-Instruct-exl3-4.0bpw>) (37.13 GB)

These models are remarkably small. For comparison, Llama 3.3 70B quantized with 4-bit AWQ and stable 2-bit AutoRound (group_size=32) takes up 39.77 GB and 26.1 GB, respectively. This is significantly larger than ExLlamaV3. The main reason for this difference is ExLlamaV3's use of lower-bit precision in the language modeling head (6-bit vs. 16-bit in AWQ), along with more compact metadata required for dequantization during inference.

Llama 3.3’s language modeling head has 1.07B parameters. In 16-bit, like with AWQ and many other quantization methods, it occupies 2.14 GB of memory. If quantized to 6-bit like with ExLlamaV3, it only occupies 0.8 GB, i.e., saving 1.33 GB. _Note: It’s possible to quantize the language modeling head with AutoRound. However, given that Llama 3 quantization to 2-bit is already difficult, I’ve never tried quantizing its head._

## Running Models with ExLlama V3

To run the model and get your own chat assistant running on your computer, there is this script:
    
    
    python exllamav3/examples/chat.py -m Llama-3.3-70B-Instruct-exl3-1.75bpw/ -mode llama3

![image](https://substackcdn.com/image/fetch/$s_!B9Zx!,w_2400,c_limit,f_auto,q_auto:good,fl_progressive:steep/https%3A%2F%2Fsubstack-post-media.s3.amazonaws.com%2Fpublic%2Fimages%2F08f1c4cd-885c-412a-b53a-d327c07e8a76_2134x575.png) 

It seems to work very well despite the low-precision quantization. Our quantized model only consumes 19.1 GB. It runs on an RTX4090, very fast! _Note: I didn’t try Ampere GPUs, like the RTX 3090. It may work, but the authors mentioned some issues._

This is quite impressive, especially considering that Llama 3 models are notoriously difficult to quantize.

## Conclusion

ExLlamaV3 is still in the early stages of development, but it's already capable of efficiently quantizing large models to low-bit formats for local deployment.

That said, like many frameworks at this stage, it currently supports only a limited set of models: Llama 3 (and possibly Llama 2), Gemma 2, Mistral (earlier versions), DeciLM, Phi-3, and Qwen2. Hopefully, this list will expand quickly with contributions from the open-source community. Judging by the existing model implementations in ExLlamaV3, adding support for new models doesn’t appear to be particularly difficult.

All signs point to ExLlamaV3 being on track to match, or even surpass, the success and popularity of ExLlamaV2.
