In the previous article, we explored the process of accurately quantizing Llama 3.3 70B to enable it to run on a single GPU. The resulting 4-bit model achieves significant memory savings, occupying just 40 GB of GPU RAM compared to the original model's 141 GB. However, efforts to accurately quantize the model to even lower precision were unsuccessful.

Among the robust alternatives for low-precision quantization, Half-quadratic quantization (HQQ) stands out. Another technique, [AQLM](<https://kaitchup.substack.com/p/run-a-77x-smaller-mixtral-8x7b-on>), is also accurate for low-bit quantization but is prohibitively expensive for models as large as 70 billion parameters.

While 2-bit HQQ is unlikely to cause catastrophic failures in the model, it is expected to result in significant performance degradation. To address this issue, one effective strategy is to recover the lost accuracy through fine-tuning using an adapter, similar to QLoRA-style fine-tuning.

In this article, we will see how to quantize Llama 3.3 to lower precisions using HQQ. Following this, we will explore fine-tuning the resulting quantized models. 2-bit quantization works fine, with fine-tuning being possible on a 32 GB GPU for short training sequences. 1-bit quantization was unsuccessful. We will evaluate the accuracy of the fine-tuned models and analyze the associated costs in terms of training time and memory consumption.

## Fine-Tuning a Quantized Llama 3.3 70B

For fine-tuning, we can adopt the QLoRA methodology: freeze the weights of the quantized model and fine-tune an adapter on top of it. While this approach is typically paired with bitsandbytes quantization, this quantization often yields less accurate results compared to more recent quantization algorithms.

As demonstrated [with AutoRound, we can achieve a 4-bit Llama 3.3 model that maintains the accuracy of the original](<https://kaitchup.substack.com/p/how-to-quantize-and-run-llama-33>). Fine-tuning an adapter on top of this quantized model allows us to adapt it to new tasks or domains using a single GPU. However, a notable limitation is that the fine-tuned adapter cannot be merged back into the quantized model. This limitation also applies to bitsandbytes quantization, as merging requires dequantizing the model first. Unfortunately, as we discussed in previous articles, [dequantization and merging can significantly degrade the model's](<https://kaitchup.substack.com/p/dont-merge-your-lora-adapter-into>) performance compared to simply loading the adapter alongside the quantized model.

To perform QLoRA fine-tuning on an AutoRound model, we load the quantized model and initialize an adapter on top of it—similar to standard LoRA fine-tuning. However, for better performance, it is recommended to upcast some of the most important modules to `float32`. This can be achieved with the following line of code:
    
    
    model = prepare_model_for_kbit_training(model, gradient_checkpointing_kwargs={'use_reentrant':True})

The fine-tuning code for AutoRound models is in the notebook. 

I ran it on 10k samples from [HuggingFaceH4/ultrachat_200k](<https://huggingface.co/datasets/HuggingFaceH4/ultrachat_200k>) (MIT license) which consists of prompts and their answers. Since the quantization was accurate and Llama 3.3 Instruct is already very capable for this task, I don’t expect it to be improved. This is just for demonstration purposes.

If you have access to an 80 GB GPU this method is your best option. Don’t underestimate QLoRA with AutoRound, I always get results with these techniques that would cost at least ten times more to achieve with full fine-tuning.

## Llama 3.3 70B Low-Bit Quantization with HQQ

AutoRound doesn't work well for quantizing Llama 3 models to 2-bit, though I could get good results for [Qwen2.5 72B Instruct](<https://kaitchup.substack.com/p/the-recipe-for-extremely-accurate-quantization>).

HQQ offers a solid alternative for model quantization. While it is generally less accurate than AutoRound, it rarely breaks the model under extreme compression, such as 2-bit quantization—and occasionally even 1-bit quantization works effectively.

In this section, we will evaluate the performance of HQQ on Llama 3.3 70B.

For a deeper understanding of how HQQ works, refer to this article:

In Transformers, quantization with HQQ is similar to the process used for bitsandbytes quantization. First, we define a quantization configuration and then load the model with this configuration. The quantization occurs dynamically, one module at a time, meaning the entire model is never loaded into memory at once. In other words, only the memory required for the quantized model is needed, not for the full unquantized model.

This approach is significantly more memory-efficient than AutoRound, which requires the entire model to be loaded into memory to perform optimization steps. It is also much faster. With HQQ quantization, the model loading, including the quantization, typically takes around 20 minutes, against 2.5 hours for AutoRound quantization with an H100 GPU.
    
    
    from transformers import (
        AutoModelForCausalLM,
        AutoTokenizer,
        HqqConfig
    )
    
    import torch
    
    model_id = "meta-llama/Llama-3.3-70B-Instruct"
    tokenizer = AutoTokenizer.from_pretrained(model_id, use_fast=True)
    # All linear layers will use the same quantization config
    **quant_config = HqqConfig(nbits=1, group_size=64, axis=0)**
    
    # Load and quantize
    model = AutoModelForCausalLM.from_pretrained(
        model_id,
        torch_dtype=torch.bfloat16,
        device_map="cuda",
        quantization_config=quant_config
    )

_Note: hqq must be installed: “pip install hqq”._

The **HqqConfig** is what is important:

  * `nbits`: the precision of the quantization. Lower is less accurate but further reduces the size of the model.

  * `group size`: Typically 128 for 4-bit quantization, 64 or 32 for lower-bit quantization. A lower group size produces a larger model.

  * `axis`: “1“ yields faster models for inference but is less accurate for low-bit quantization. I recommend “0” for 1-bit and 2-bit quantization.

I tried 3 different configurations. 1-bit with a group size of 32 and 2-bit quantization with group sizes of 64 and 32. I benchmarked the resulting models with MMLU:

![image](https://substackcdn.com/image/fetch/$s_!Opie!,w_1456,c_limit,f_auto,q_auto:good,fl_progressive:steep/https%3A%2F%2Fsubstack-post-media.s3.amazonaws.com%2Fpublic%2Fimages%2F0166e391-abb4-4e16-b062-2d9457bdd19e_1406x742.png) 

As we can see, the 1-bit model is essentially broken, achieving only 25% accuracy on MMLU—equivalent to a random baseline. However, the 2-bit HQQ models remain functional. While their performance is significantly lower than that of the 4-bit model produced by AutoRound, they are not entirely unusable. This leaves room to recover some of the lost performance through fine-tuning.

Let’s fine-tune adapters on top of all these models to check whether we can heal them. The fine-tuning code is the same as we would use for standard QLoRA fine-tuning, except that we define a HqqConfig instead of a BitsandBytesConfig. Moreover, note that HQQ is not compatible with FlashAttention which means that it will be much less efficient with longer training sequences and much slower than AutoRound.

It actually worked better than what I expected. The accuracy of the 2-bit model with a group size of 64 improved by 22 points. It shows that indeed the model isn’t broken. Nonetheless, it is still not good enough. Smaller models like Qwen2.5 7B Instruct yield better results on this task (71.75 points). 

The adapter fine-tuned over the model quantized with a group size of 32 achieves an accuracy of 69.6. Still lower than Qwen2.5 7B Instruct but not very far. This is also 4 points lower than Qwen2.5 72B instruct quantized to 2-bit.

The fine-tuning of the 1-bit model didn’t fix the model. Quantization damaged it too much and it is probably as good as fine-tuning an adapter on top of random tensors. 

I fine-tuned the models with an A40 GPU which has 48 GB of memory. I always used the same sequence length (512) and the same effective training batch size (32). To fully exploit the memory available, I increased the batch size per device and decreased gradient accumulation steps when possible. The total training time varied between 10 and 13 hours (excluding the validation steps). Remember that this is for 10k samples of 512 tokens. Count 20 hours for sequences of 1024 tokens. 

Under these settings, fine-tuning the 1-bit model is possible with 32 GB of GPU RAM. For the 2-bit model, a 40 GB GPU is necessary. For inference with the 2-bit HQQ models, a 32 GB GPU could be enough.

## Conclusion

Fine-tuning Llama 3.3 70B with a single GPU requires quantizing the model. With 4-bit quantization, we can do it accurately and efficiently. It significantly lowers the fine-tuning cost which would otherwise require multiple 80 GB GPUs for LoRA fine-tuning, or an entire GPU node for full fine-tuning.

Fine-tuning is feasible with a 48 GB GPU but with batch size per device of 1 and tiny sequences. I can’t recommend it for most use cases. An 80 GB GPU would be more cost-effective since it would allow large batch sizes and thus significantly accelerate fine-tuning.

2-bit HQQ is an interesting alternative but it is not competitive if we compare it with smaller models which perform better without quantization. 

This conclusion is written based on 1 fine-tuning epoch performed on 10k training samples. It might be possible to achieve a performance similar to 2-bit Qwen2.5 72B Instruct with more fine-tuning epochs. However, HQQ models remain less efficient to run, especially with Transformers. vLLM supports HQQ with Marlin, which should be more efficient but I didn’t try it and don’t know whether it can also support adapters loaded on top of HQQ models.
