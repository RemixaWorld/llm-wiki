Quantization is one of the most widely used techniques to reduce the size of large language models (LLMs). It works by lowering the precision of the model’s weights, typically from 16-bit down to 8-bit, 4-bit, or even lower. For example, a 70B model like Llama 3.3 requires around 141 GB in 16-bit precision, but this can be reduced to just 37 GB when quantized to 4-bit using ExLlamaV3. 

A variety of quantization methods exist, each with its own strengths and trade-offs, which I explore in detail in [Chapter 3 of my book ](<https://benjaminmarie.gumroad.com/l/llms-on-a-budget>)_[LLMs on a Budget](<https://benjaminmarie.gumroad.com/l/llms-on-a-budget>)_.

However, most quantization techniques focus solely on the model’s weights. During inference, many intermediate tensors, commonly referred to as _activations_ , are generated. The size of these activations largely depends on the sequence length and the model’s hidden size, and they are typically left in full precision. As a result, in scenarios involving quantized weights and long input sequences, activation memory usage can actually surpass that of the model weights!

Quantizing activations is a more complex task due to their dynamic nature. Unlike weights, which remain constant during inference, activation values vary significantly depending on the input data.

In this article, we’ll explore how to quantize activations effectively to further reduce memory consumption during inference. We’ll evaluate how activation quantization impacts memory usage, inference speed, and model accuracy. Our focus will be on llm-compressor and SmoothQuant.

You’ll also find a hands-on tutorial in the accompanying notebook, demonstrating how to apply activation quantization to LLMs in practice:

## INT8 and FP8 Quantization for Efficient LLM Inference with `llm-compressor`

For INT8 quantization with `llm-compressor`, both weights and activations are reduced to 8-bit integers. You can check llm-compressor code and documentation here:

  * GitHub: [vllm-project/llm-compressor](<https://github.com/vllm-project/llm-compressor>)

This method is particularly effective on NVIDIA GPUs with compute capability above 7.5 (such as Turing, Ampere, Ada Lovelace, and Hopper). 

> **How to know your GPU’s “compute capability”**
>     
>     
>     import torch
>     print(torch.cuda.get_device_capability(0))

The quantization pipeline involves preparing a small calibration dataset that reflects the model’s target usage, applying techniques like SmoothQuant for activation scaling and GPTQ for weight compression, and saving the result as a deployable model with vLLM. 

Calibration data is essential in this flow, especially when quantizing activations, as it helps the algorithm estimate scale ranges accurately. For instruction-tuned models, using dialogue data like Ultrachat improves quantization quality. Using calibration data that looks like the actual input seen once the model will be deployed is much more important for activation quantization than for weight quantization, for which the choice of calibration dataset often has minimal impact, as we saw in this article:

FP8 quantization targets newer GPUs (Ada Lovelace and Hopper) with compute capabilities above 8.9. Unlike INT8, this approach does not require calibration data. Instead, a simple post-training quantization (PTQ) method is applied directly, using static per-channel quantization for weights and dynamic per-token quantization for activations.

In both workflows, the final quantized model is saved in a format ready to be loaded into vLLM. For INT8, the resulting model includes both weights and activations in 8-bit integer format. For FP8, the model retains accuracy with minimal configuration, thanks to dynamic quantization strategies that adapt during inference.

At the moment, it's not practical to quantize both weights and activations to lower precision simultaneously. Technically, it is possible, but mixing data types, such as using INT4 for weights while keeping activations in INT8 or FP8, tends to make the inference process inefficient. I expect this will become much more feasible with the widespread deployment of the Blackwell architecture, which natively supports FP4 computation.

## Quantizing the Activations of Qwen2.5

Here is what we need to install for quantization and evaluation:
    
    
    pip install --upgrade transformers llmcompressor datasets lm-eval vllm langdetect immutabledict

Then, load the model you want to quantize, here, Qwen2.5 7B:
    
    
    from transformers import AutoTokenizer, AutoModelForCausalLM
    
    MODEL_ID = "Qwen/Qwen2.5-7B-Instruct"
    model = AutoModelForCausalLM.from_pretrained(
        MODEL_ID, device_map="auto", torch_dtype="auto",
    )
    tokenizer = AutoTokenizer.from_pretrained(MODEL_ID)

All the following steps can run with a 24 GB GPU. I used Google Colab’s L4, which has only 22 GB available and is capable of FP8 computation. 

#### W8A8-INT8 Quantization

We’re going to quantize the Qwen2.5 7B model to 8-bit precision, both its weights (W8) and activations (A8).

The first step is to prepare a calibration dataset. It’s important to use a dataset that closely resembles the kind of data the model will encounter in its target deployment setting.

Since we don’t have a specific task in mind, we’ll use a general-purpose chat dataset: [UltraChat 200k](<https://huggingface.co/datasets/HuggingFaceH4/ultrachat_200k>), which provides a broad and diverse sample of conversational data suitable for calibration.
    
    
    from datasets import load_dataset
    
    NUM_CALIBRATION_SAMPLES=512
    MAX_SEQUENCE_LENGTH=2048
    
    # Load dataset.
    ds = load_dataset("HuggingFaceH4/ultrachat_200k", split="train_sft")
    ds = ds.shuffle(seed=42).select(range(NUM_CALIBRATION_SAMPLES))
    
    # Preprocess the data into the format the model is trained with.
    def preprocess(example):
        return {"text": tokenizer.apply_chat_template(example["messages"], tokenize=False,)}
    ds = ds.map(preprocess)
    
    # Tokenize the data (be careful with bos tokens - we need add_special_tokens=False since the chat_template already added it).
    def tokenize(sample):
        return tokenizer(sample["text"], padding=False, max_length=MAX_SEQUENCE_LENGTH, truncation=True, add_special_tokens=False)
    ds = ds.map(tokenize, remove_columns=ds.column_names)

This step should be very quick. Then, we quantize as follows:
    
    
    from llmcompressor import oneshot
    from llmcompressor.modifiers.quantization import GPTQModifier
    from llmcompressor.modifiers.smoothquant import SmoothQuantModifier
    
    # Configure the quantization algorithms to run.
    recipe = [
        SmoothQuantModifier(smoothing_strength=0.8),
        GPTQModifier(targets="Linear", scheme="W8A8", ignore=["lm_head"]),
    ]
    
    # Apply quantization.
    oneshot(
        model=model,
        dataset=ds,
        recipe=recipe,
        max_seq_length=MAX_SEQUENCE_LENGTH,
        num_calibration_samples=NUM_CALIBRATION_SAMPLES,
    )
    
    # Save to disk compressed.
    SAVE_DIR = MODEL_ID.split("/")[1] + "-W8A8-Dynamic-Per-Token"
    model.save_pretrained(SAVE_DIR, save_compressed=True)
    tokenizer.save_pretrained(SAVE_DIR)

The quantization process took 54 minutes using a Google Colab instance with an L4 GPU.

The key component of the setup is the quantization recipe. We use the GPTQ algorithm for weight quantization, combined with SmoothQuant for activation quantization. Notably, the language modeling head is left in full precision to preserve accuracy. However, if you're working with a very large model, it might be possible to quantize the head as well with only minimal accuracy degradation.

Now, let’s evaluate the quantized model. I used the IFEval benchmark, which is particularly effective at exposing issues in quantized models; broken models often produce random scores on this benchmark.

_Note: Since IFEval generates tokens during evaluation, using the vLLM backend significantly speeds up the process. However, at the time of testing, the latest version of vLLM wasn’t fully compatible with this W8A8-INT8 model. I had to downgrade to vLLM 0.7.0 for compatibility. This is likely a temporary issue, as the vLLM team is actively developing an updated inference engine._

## W8A8-FP8 Quantization

This form of quantization is much simpler, as it doesn't require a calibration step.

However, it does require a GPU with FP8 support, such as those based on the Ada Lovelace, Hopper, or Blackwell architectures.
    
    
    from llmcompressor import oneshot
    from llmcompressor.modifiers.quantization import QuantizationModifier
    
    # Configure the simple PTQ quantization
    recipe = QuantizationModifier(
      targets="Linear", scheme="FP8_DYNAMIC", ignore=["lm_head"])
    
    # Apply the quantization algorithm.
    oneshot(model=model, recipe=recipe)
    
    # Save the model.
    SAVE_DIR = MODEL_ID.split("/")[1] + "-FP8-Dynamic"
    model.save_pretrained(SAVE_DIR)
    tokenizer.save_pretrained(SAVE_DIR)

This process is very fast, taking around 3 minutes on a Colab L4 GPU.

Unlike the INT8 version, the FP8 quantized model worked seamlessly with recent versions of vLLM, without requiring any compatibility adjustments.

If your GPU supports FP8, this version is likely the better choice in terms of both speed and simplicity.

## What About Memory Consumption?

When dealing with quantized activations, it appears that vLLM doesn’t report activation memory usage very precisely. In fact, you might notice log messages indicating that more memory is reserved for activations with the quantized model than with the original not quantized one.

In practice, the memory savings from activation quantization may not always be dramatic in typical settings, but they start to shine in the right conditions. If you're working with very long sequences, large batch sizes, or operating without FlashAttention, activation quantization can lead to notable reductions in memory usage.

## Conclusion

With llm-compressor, activation quantization is straightforward, and the resulting models are natively supported by vLLM.

When handling very large batches of queries, even saving a few hundred megabytes of memory per query can have a significant impact. This is where activation quantization makes inference far more cost-effective and scalable.

In practice, the KV cache often consumes the most memory during inference. While it can also be quantized, enabling, for instance, a fully FP8 end-to-end model, doing so naively can lead to substantial accuracy loss.

If you're interested in quantizing the KV cache properly, refer to the official vLLM documentation for detailed guidance:

[Quantized KV Cache](<https://docs.vllm.ai/en/latest/features/quantization/quantized_kvcache.html>)
