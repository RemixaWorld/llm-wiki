QLoRA fine-tuning is a highly effective and widely used parameter-efficient fine-tuning method. It works by quantizing a model to lower precision, typically 4-bit using `bitsandbytes`, and then training an adapter, which consists of a small set of new trainable parameters, on top of the quantized model.

![image](https://substackcdn.com/image/fetch/$s_!-PTG!,w_1456,c_limit,f_auto,q_auto:good,fl_progressive:steep/https%3A%2F%2Fsubstack-post-media.s3.amazonaws.com%2Fpublic%2Fimages%2F50fd3136-4f1c-40cd-b708-a2a927a56fb3_756x270.png) 

Similar to LoRA fine-tuning, QLoRA only updates the adapter, meaning optimizer states and gradients are stored exclusively for these parameters. As a result, memory consumption is significantly lower compared to full fine-tuning. Since QLoRA quantizes the model, the memory required to load it is typically reduced by approximately 3.5x.

#### What Happens to the Adapter After Fine-Tuning?

Once fine-tuning is complete, we have two main options for using the adapter:

  1. **Loading the adapter dynamically** on top of the base quantized model when needed.

  2. **Merging the adapter into the base model** permanently, eliminating the need to manage the adapter separately.

This article focuses on the second approach: merging the adapter into the base model. However, merging a QLoRA adapter is not as straightforward as many online tutorials suggest. A naive merge, similar to what is done with LoRA adapters, can severely degrade model accuracy.

We will explore the correct merging process, revisiting [an older merging approach we reviewed 18 months ago](<https://kaitchup.substack.com/p/lora-adapters-when-a-naive-merge>) to determine if it remains necessary. Additionally, we will assess merging directly into the quantized model, as implemented in Hugging Face PEFT. Furthermore, we will examine why post-merging quantization should not be performed using `bitsandbytes` and instead evaluate alternative quantization methods, comparing their effectiveness.

## Baseline: Loading the QLoRA Adapter

During QLoRA fine-tuning, the adapter is loaded on top of the base model quantized to 4-bit with `bitsandbytes`. The adapter is optimized to best work in this configuration.

For this article, I fine-tuned a QLoRA adapter for Llama 3.1 8B on [timdettmers/openassistant-guanaco](<https://huggingface.co/datasets/timdettmers/openassistant-guanaco>). This dataset has a test split that we can use to compute the perplexity of the adapter. The [fine-tuning code is very standard](<https://kaitchup.substack.com/p/fine-tuning-metas-llama-32-1b-3b>). You can find it in the notebook.

Here is the code I use to compute the perplexity:
    
    
    def compute_perplexity(model, dataset_name, dataset_split="test", text_column="text"):
    
    
        # Load dataset
        dataset = load_dataset(dataset_name, split=dataset_split)
    
        total_loss = 0.0
        total_tokens = 0
    
        for sample in tqdm(dataset, desc="Computing Perplexity"):
            text = sample[text_column]
    
            # Tokenize and ensure correct input format
            inputs = tokenizer(text, return_tensors="pt", truncation=True, max_length=2048)
            input_ids = inputs["input_ids"].to("cuda")
    
            with torch.no_grad():
                outputs = model(input_ids, labels=input_ids)
                loss = outputs.loss  # Cross-entropy loss
    
            total_loss += loss.item() * input_ids.size(1)  # Scale loss by token count
            total_tokens += input_ids.size(1)
    
        # Compute perplexity
        avg_loss = total_loss / total_tokens
        perplexity = round(math.exp(avg_loss),4)
    
        print(f"Dataset: {dataset_name} ({dataset_split} split)")
        print(f"Evaluated {total_tokens} tokens across {len(dataset)} samples")
        print(f"Perplexity: {perplexity:.2f}")
    
        return perplexity

A lower perplexity is better. 

For this task, the model quantized with bitsandbytes achieves this perplexity:
    
    
    bnb_config = BitsAndBytesConfig(

            bnb_4bit_compute_dtype=torch.bfloat16,

    )
    model = AutoModelForCausalLM.from_pretrained(
        "meta-llama/Llama-3.1-8B", quantization_config=bnb_config, device_map='cuda')
    tokenizer = AutoTokenizer.from_pretrained("meta-llama/Llama-3.1-8B")

## Why Merging a QLoRA Adapter Can Yield Unexpected Results?

Merging an adapter involves summing its parameters with those of the layer it is applied to. This is a straightforward operation, identical to what happens during inference when the adapter is loaded. Whether an adapter is merged or simply loaded, the results should be approximately the same.

Mathematically, given a model layer parameter _W_ and an adapter parameter _A_ , the merging operation can be expressed as:

$$ W_\text{merged}=W+AW $$ 

where:

  * _W_ represents the original model parameters,

  * _A_ represents the adapter parameters,

  * Wmerged is the resulting parameter after merging.

However, merging is not possible in a quantized model because they use different data types. Instead, the adapter must be merged into the original, non-quantized model. As explained in a previous article, the best approach for effective merging is:

  1. Load the model with 4-bit bitsandbytes quantization.

  2. Unquantize the model to the same compute dtype used during QLoRA fine-tuning.

  3. Merge the adapter using the equation above.

This process can be done manually, but the [PEFT package](<https://huggingface.co/docs/peft/en/index>) now automates it when merging an adapter into a bitsandbytes-quantized base model. _Note:[More information in this PR](<https://github.com/huggingface/peft/pull/851>)._
    
    
    bnb_config = BitsAndBytesConfig(
            load_in_4bit=True,
            bnb_4bit_quant_type="nf4",
            bnb_4bit_compute_dtype=torch.bfloat16,
            bnb_4bit_use_double_quant=True,
    )
    model = AutoModelForCausalLM.from_pretrained(
        "meta-llama/Llama-3.1-8B", quantization_config=bnb_config, device_map='cuda')
    adapter_model = PeftModel.from_pretrained(model, "./QLoRA_Llama3.1-8B/checkpoint-307")
    merged_model = adapter_model.merge_and_unload()
    merged_model.save_pretrained("./merged_model_4bit") # Save to avoid training again
    tokenizer = AutoTokenizer.from_pretrained("meta-llama/Llama-3.1-8B")
    
    tokenizer.save_pretrained("./merged_model_4bit") #Save tokenizer with the merged model

Under the hood, it dequantizes the layers one by one, merges the adapter, and then quantizes again the resulting model.

**The perplexity of the merged model quantized with bitsandbytes: 4.33**

The perplexity went from 3.55 to 4.33, which is **coincidently** the same as before we fine-tuned the model!**It doesn’t seem to work.**

To confirm the results, I manually applied the recipe myself: loading the model with bitsandbytes quantization, dequantize the model to the correct dtype, merging the adapter, then quantizing the model with bitsandbytes. _Note: The code is in the notebook._

**The perplexity with this custom code merging code: 4.33**

The same result. This is not a problem with the PEFT implementation.

Without quantization with bitsandbytes, after merging, the perplexity is **3.59**. This is very close to the **3.55** obtained when loading the adapter. The problem seems to come from the re-quantization with `bitsandbytes`.****_Note: This is a lot of numbers. I put a summary in the conclusion._

## **What Went Wrong?**

During the quantization-dequantization-requantization process, rounding errors inevitably occur, which can impact the adapter’s performance. However, the observed degradation is so substantial that rounding errors alone cannot fully account for it.

We have to keep in mind that**the adapter is never quantized during fine-tuning.**

Quantization always degrade. It is an approximation. So when quantizing again the model after merging, the adapter “effect” is also quantized, and thus degraded. After merging many more parameters of the model could become outliers which could be much more difficult to accurately quantize. 

We might need a better quantization method. For instance, we could use a method preserving outliers from quantization, keeping them as (b)float16. We can do this with AWQ. 

I quantized with AWQ the model obtained after merging with my custom code. It achieves this perplexity:**3.88**

There is still a significant degradation but this is much better than quantization with `bitsandbytes`. I believe we can achieve a lower perplexity with a better quantization method such as with AutoRound.

## Conclusion

The results tell us that the old custom recipe for merging QLoRA adapters is still valid. We must quantize, dequantize, and merge. _Note: The steps quantization-dequantization are not always necessary. Merging directly the adapter into the base model (not quantized) might in some cases provide optimal results. Nonetheless, since this is not always the case I recommend quantization-dequantization._

Then, if we want to quantize again the resulting model, we shouldn’t use `bitsandbytes `but AWQ or a better quantization algorithm.

Nonetheless, the fact that `bitsandbytes `quantization degrades the performance so much is surprising. I assume this is due to the presence of more outliers after merging but I didn’t formally verify it. There might be other factors at play.
