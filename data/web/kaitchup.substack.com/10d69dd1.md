To achieve this, Google developed a new architecture that improves both accuracy and efficiency. Additionally, Gemma 3 is natively multimodal, allowing it to process both text and image inputs.

## Gemma 3: A New Architecture with Global-Local Attention

Google published the technical report here:

[Gemma 3 Technical Report](<https://storage.googleapis.com/deepmind-media/gemma/Gemma3Report.pdf>)

The Gemma 3 1B, 4B, 12B, and 27B are here:

  * [Gemma 3 Release](<https://huggingface.co/collections/google/gemma-3-release-67c6c6f89c4f76621268bb6d>)

They are available in both base and instruct variants. While there is a growing trend toward fine-tuning instruct models, I recommend starting with the base model if you want the model to closely follow your data's content and format. I rather recommend to post-train instruct versions—using methods like GRPO—when the goal is to optimize performance for a specific task with a clear, verifiable objective but limited data.

### Multimodality: Image Processing with SigLIP

One of the bigger additions since Gemma 2 is image support. Gemma 3 models now integrate with a 400M SigLIP vision encoder, which converts images into soft image token sequences. Instead of processing entire images at once, the model condenses vision embeddings into 256 fixed-size vectors, reducing inference costs. The encoder works at a fixed resolution of 896 × 896 pixels, but since real-world images come in different shapes and sizes, they added a Pan & Scan (P&S) method. This allows the model to process variable resolutions by dividing images into non-overlapping crops before passing them through the encoder. The process only runs when necessary, and users can turn it off for faster inference.

Interestingly, all Gemma 3 4B, 12B, and 27B versions have the same vision encoder. The 1B version is not multimodal.

### Longer Context Support

Gemma 3 can handle 128K tokens of context (except the 1B model, which maxes out at 32K tokens). Handling long context usually leads to memory explosion due to the increasing size of the KV cache during inference. To mitigate this, Gemma 3 follows a hybrid attention mechanism: they mix local and global layers in a 5:1 ratio, meaning that five local layers are followed by one global layer. In practice, this hasn’t had a significant impact on the model performance:

![source](https://substackcdn.com/image/fetch/$s_!GtG3!,w_1456,c_limit,f_auto,q_auto:good,fl_progressive:steep/https%3A%2F%2Fsubstack-post-media.s3.amazonaws.com%2Fpublic%2Fimages%2Fc37c61b8-1510-4509-bea4-8d7b623e6336_739x324.png) 

Local layers only process short segments of 1024 tokens, while global layers take care of the full context. This keeps the memory usage in check while allowing the model to retain information across longer sequences. 

They also modified RoPE (Rotary Position Embeddings) to increase the base frequency for global layers from 10K to 1M, extending their ability to process long-range dependencies.

### Model Architecture and Training

The core structure remains decoder-only transformer, just like the previous versions. Gemma 3 continues using Grouped-Query Attention (GQA) along with RMSNorm, both pre-norm and post-norm. It will be interesting to see whether we can further improve the model with MLA.

A notable change is the removal of soft-capping, a particularity of Gemma 2, which is replaced with QK-norm, a technique borrowed from recent research that supposedly improves stability.

Instead of directly using the dot product and softmax, QK-Norm normalizes the attention scores before softmax is applied. The core idea is to normalize each row of the QK product, ensuring that attention scores are in a more controlled range.

This normalization ensures:

  1. Stable gradients during training, reducing exploding or vanishing gradients in large models.

  2. More even attention distribution, preventing certain tokens from dominating attention weights.

  3. Better long-context handling, as extreme values don’t grow uncontrollably when processing long sequences.

The models were pre-trained using knowledge distillation, where a larger model acts as a teacher to help smaller models learn more efficiently. We don’t know which model was the teacher, but we can assume it was a powerful version of Gemini. 

They used a larger dataset than Gemma 2, increasing token budgets across the board: 14T tokens for the 27B model, 12T for 12B, 4T for 4B, and 2T for 1B. A big part of this training data includes both text and image data, along with an expanded multilingual dataset that aims to improve non-English language capabilities.

The tokenizer uses SentencePiece with a vocabulary of 262K entries. It supports split digits, preserved whitespace, and byte-level encodings, improving language balance. 

This large vocabulary size makes fine-tuning more demanding on budget GPUs. The largest model’s activations, which are not "checkpointed" during fine-tuning, are directly influenced by the vocabulary size. Additionally, to maintain model accuracy, token embeddings cannot be quantized, even with state-of-the-art quantization techniques.

The embedding matrix has dimensions 2560 × 262,208, which results in 671 million parameters. Since both input and output embeddings (LM head) share the same size, the total comes to 1.34 billion parameters. This accounts for 31.2% of the total parameter count in the 4B model, which has 4.3 billion parameters in total.

### Quantization and Efficiency

To make the models smaller and more efficient, they trained quantized versions in int4, per-block int4, and switched fp8 formats. These versions are obtained using Quantization Aware Training (QAT), where models are fine-tuned for a few thousand steps after pre-training to adjust for precision loss.

Memory usage varies depending on the model size and whether KV caching is used. For example, the raw 27B model in bfloat16 takes up 54GB, but quantized versions can reduce this to as little as 14GB. When KV cache is included, memory demands increase significantly, with the 27B model requiring 72.7GB in bfloat16 but only 32.8GB in int4 quantization.

As far as I know, these models have not been released yet. Since they were trained on TPUs, they likely require conversion and adaptation for compatibility with PyTorch and GPUs. This process may also involve additional checks, and delays, to ensure proper functionality.

### Instruction-Tuning and Reinforcement Learning

After pre-training (PT), the models went through an instruction-tuning (IT) phase, which refines their ability to handle math, reasoning, chat, and multilingual tasks. They used a combination of knowledge distillation and reinforcement learning (RL), following techniques from models like BOND, WARM, and WARP.

For reward modeling, they trained weight-averaged reward models (WARM) on human feedback data and added code execution feedback to improve programming-related outputs. They also used ground-truth rewards for solving math problems, ensuring that the models improve in logical reasoning tasks.

The post-training filtering stage was meant to reduce hallucinations and improve factuality, without compromising performance in other areas. They removed training examples containing personal information, unsafe outputs, mistaken self-identifications, and duplicate examples. The final instruction-tuned models use a special formatting system with clearly defined user turns, model turns, and end-of-turn markers.

## Fine-Tuning Gemma 3

### GPU Requirements for Fine-Tuning Gemma 3

To fully fine-tune Gemma 3 on a single 80 GB GPU without quantization, only the 1B, 4B, and 12B models are feasible. However, with LoRA fine-tuning, both the 1B and 4B versions can be trained on a single 24GB GPU. The 27B model, which requires 54GB of GPU memory, can only be fine-tuned with LoRA on 80 GB GPU on short sequences.

Quantizing the 27B model to 4-bit allows fine-tuning on a 24 GB GPU, but only for very short sequences and without retraining the embeddings. This can be problematic if you need to use a chat template, as the special tokens in the template remain untrained.

The special tokens required for a chat template are not pre-trained. If standard LoRA fine-tuning is applied—targeting only the self-attention and MLP modules—these special token embeddings remain unchanged. Since the model treats untrained tokens as identical, it will be unable to differentiate them, making a chat template ineffective even if the training data follows the correct format.

If a chat template is required, training the embeddings is necessary. However, due to Gemma 3’s large vocabulary, this significantly increases memory usage during fine-tuning.

For the 1B model, this is not a concern, as it is small enough to accommodate embedding updates. However, for the 4B version, even with paging and quantized optimizer states, LoRA fine-tuning with embedding retraining fits within 24GB of memory only for sequences of 1024 tokens or fewer.

For the 12B and 27B models, quantization is required to fine-tune on a consumer GPU, making QLoRA the only viable option.

Using Unsloth can significantly reduce memory consumption, as it efficiently offloads activations and embeddings while optimizing long-context training. Unsloth doesn’t support Gemma 3 now (as of March 13th, 2025), but probably will before the end of the week.

### Specific Settings for Fine-Tuning Gemma 3

Gemma 3 is straightforward to fine-tune, as the modules targeted by LoRA use standard naming conventions.

FlashAttention does not appear to be supported yet. When I attempted to use it, I got a warning, likely due to the specific global-local attention mechanism used in Gemma 3.

The tokenizer setup is simple. Unlike many models where defining a pad token requires special handling, Gemma 3's pad token is pre-defined and even set as the default, which is uncommon. The only necessary adjustment is passing `add_bos=True` when instantiating the tokenizer, as recommended in the technical report.

Google follows the current trend of including the chat template only in the tokenizer of the instruct (`it`) versions of the models, while the pre-trained (`pt`) versions do not have it in their tokenizer. I’ve previously voiced concerns about this approach, as it introduces an unnecessary complication: 

If you want to fine-tune the pre-trained model on instruction datasets while using the official chat template, you need to load the tokenizer from the instruct model while fine-tuning the pre-trained model (as in the code shown in the next section). This setup can be confusing, especially for frameworks that load both the model and tokenizer simultaneously—which effectively loads the tokenizer of the pre-trained model, while we will also need to load the tokenizer of the instruct version to get the chat template.

In recent model releases, only the Qwen team didn’t do this and included the chat template for both instruct and base models.

A common question I receive is: _What is a good training loss value?_

If you refer to some of my previous fine-tuning experiments, such as with Llama 3.2, you'll notice that the training loss typically falls below 2.0.

This training loss is lower than that of Gemma 3, but does that mean Llama 3.2 is better or easier to train? Not at all.

**The absolute value of a loss is not inherently meaningful.**

In fact, if you fine-tune Llama 3.2 today, you will likely see a much higher loss than what I reported back in November. This is primarily due to changes in how loss is computed in the Transformers library.

Additionally, loss values are heavily influenced by model architecture and vocabulary size. Since probability distributions are assigned across all tokens, models with smaller vocabularies tend to assign higher average probabilities per token, leading to lower loss values. I explain this in more detail, with code, in _The Salt_ :

For some reason, this concept is often difficult to grasp, even for AI practitioners. Loss values should only be used to determine whether a model is learning—that is, whether the loss is decreasing.

While the loss of two models from the same family (e.g., Gemma 3 4B and Gemma 3 12B) is _somewhat_ comparable, it is generally best to avoid such comparisons. Each model has its own architecture and vocabulary size, making loss values meaningful only within the context of that specific model. It’s good practice to treat loss as a model-specific metric.

## Conclusion

Gemma 3 introduces notable architectural refinements, particularly in its multimodal capabilities and adaptation to different fine-tuning constraints. The integration of a 400M SigLIP vision encoder with a Pan & Scan method makes the model more flexible in handling images, but at the cost of additional preprocessing complexity. Additionally, the large vocabulary (262K tokens) increases memory requirements for fine-tuning, making embedding updates particularly challenging on consumer GPUs. This design choice suggests a strong focus on multilingual and diverse-token representations, but it also means that fine-tuning practitioners must carefully consider memory usage and quantization strategies, especially for larger variants like the 12B and 27B models.

Regarding quantization, most frameworks—including GPTQModel, AutoAWQ, and AutoRound—do not yet support Gemma 3. Once these frameworks are updated, I will quantize Gemma 3 and assess its performance. A key question will be whether these models quantize as effectively as Qwen2.5, maintaining strong accuracy, or if they present greater challenges, similar to Llama 3.x models, which have been more difficult to quantize without significant degradation.
