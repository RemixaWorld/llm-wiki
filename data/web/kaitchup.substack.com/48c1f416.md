When a language model generates text, it has to keep “looking back” at everything it has already produced in order to decide what comes next. To avoid doing the same work over and over, it saves some intermediate results in a small running memory called the KV cache, usually stored on the GPU.

The catch is that this cache grows with every new token the model generates. The longer the response, the more GPU memory the cache consumes. As that memory fills up, you can handle fewer requests at the same time. And if you run out of space entirely, what happens next depends on your setup: the system may stop the generation early, fall back to a much slower mode, or simply crash.

This can become an issue surprisingly fast. Take an 8B model like Qwen3 8B (36 layers, GQA with 8 KV heads and head_dim=128). With the KV cache stored in bf16/fp16 (2 bytes per value), you’re saving about:

  * ~144 KB of KV cache per generated token (K+V across all layers)

  * So ~10,000 tokens ≈ 1.5 GB of GPU memory per request, just for the KV cache

  * And 10 concurrent users ≈ 15 GB reserved for KV cache alone (before you even count model weights and other overhead)

There’s also a performance hit. Many inference workloads are limited by memory traffic, not raw compute. As the KV cache grows, the GPU has more and more data to read each step, and throughput can drop noticeably. In practice, the speed you get is often tied to the GPU’s memory bandwidth, so bigger cache → more data movement → slower generation.

The good news: the tooling here is getting much better, and modern inference frameworks can mitigate these problems in a few ways.

In this article, we’ll focus on **compressing (quantizing) the KV cache** and measuring the trade-off between speed/memory savings and model quality. This approach can improve throughput, increase the number of concurrent users you can serve, and reduce overall inference cost.

### KV-cache quantization in FP8, scales, and calibration

“KV cache quantization” means you keep the model’s attention cache (the per-layer Key and Value tensors stored for each generated token) in a lower-precision format than the compute dtype. 

KV cache grows linearly with sequence length and quickly becomes the dominant runtime memory consumer for long-context serving. With FP8 KV cache enabled, vLLM (and other engines) quantizes K/V before writing them into the cache, and (in the common path) dequantizes them back to FP16/BF16 when they’re read for attention. This reduces storage cost while keeping attention math largely in higher precision.

FP8 itself comes in a couple of hardware-supported flavors (notably E4M3 and E5M2). E4M3 has better precision but a much smaller dynamic range, so it generally relies on an accompanying FP32 scaling factor to avoid overflow/saturation, while E5M2 trades some precision for a wider range. 

vLLM exposes these via `kv_cache_dtype` (e.g., `fp8_e4m3` / `fp8_e5m2`, and `fp8` as the shorthand).

### Scale Calibration for Better Accuracy

Conceptually, for each K or V tensor, you store a scale `s` (typically FP32) and quantize values as “FP8 of (x / s)” so the FP8 numbers land in a representable range. On read you reconstruct approximately as `x ≈ s * fp8_value`. This is the typical quantization → dequantization operations.

We have two main granularities: per-tensor (one scale for an entire K or V tensor) and per-attention-head scales (a separate scale per head, which is usually better for accuracy because head distributions differ). Per-head scaling is currently tied to specific backends and the recommended calibration tooling.

Calibration is about picking “good” scales. With vLLM, we have two practical options:

  1. **No calibration** : scales default to 1.0 (or vLLM loads scales from a checkpoint if they exist). This is simplest but can cost accuracy because FP8 range/precision is unforgiving when the scale is off. However, as we will see, at 8-bit precision, no calibration is often good enough.

  2. **On-the-fly (random-token) calibration** : set `calculate_kv_scales=True` and vLLM estimates `k_scale` / `v_scale` from a single warmup batch and then keeps them fixed. 

A tiny example of enabling FP8 KV cache in vLLM (random-token calibration):
    
    
    from vllm import LLM
    llm = LLM(
        model="Qwen/Qwen3-8B",
        kv_cache_dtype="fp8",
        calculate_kv_scales=True,
    )

The analogous CLI flags exist too (`--kv-cache-dtype fp8` and `--calculate-kv-scales`).

### Quick Math on Memory Consumption Reduction with KV Cache Quantization

Let’s take Qwen3 4B and Qwen3 8B, with a maximum sequence length of 32,768 tokens.

KV cache size depends on attention geometry: `num_hidden_layers`, `num_key_value_heads` (GQA), and `head_dim`, not directly on “parameter count.” Both Qwen3-8B and Qwen3-4B use 36 layers, 8 KV heads, and head_dim 128, so their KV-cache footprints at a given context length are essentially the same.

For one 32,768-token sequence, KV elements = `2 * L * T * H_kv * D`, and bytes scale with dtype:

  * **BF16/FP16 KV cache** (2 bytes/elem): about **4.5 GiB**

  * **FP8 KV cache** (1 byte/elem): about **2.25 GiB**

These numbers apply to both Qwen3-8B and Qwen3-4B since they share the same KV geometry. 4.5 GB already sounds low, so why bother?

If you’re serving a single request with a 32k context, FP16 KV is totally fine. The issue is scale: with larger workloads, KV memory adds up fast. Just 100 concurrent 32k-token queries is ~450 GB in FP16 KV. For a 4B model, that’s a lot of memory (and cost) just to hold KV cache.

Another useful way to think about FP8 KV-cache quantization is as **HBM bandwidth relief** as much as “saving memory.” 

During autoregressive decoding, attention repeatedly reads the accumulated K/V history from GPU memory for each new token (writes are comparatively small: you only append one token’s K/V). That makes long-context decoding very often memory-bandwidth bound, so reducing KV cache from BF16/FP16 to FP8 cuts not just capacity but also the number of bytes you have to move. FP8 KV cache improves throughput for longer contexts. 

For Qwen3-8B and Qwen3-4B specifically, if you (roughly) assume each generated token streams through most of that cache once, then at 20 tok/s you’re talking on the order of ~90 GiB/s of KV reads in BF16 versus ~45 GiB/s in FP8, before multiplying by concurrent sequences. The tradeoff is a bit of extra quant/dequant work (and scale handling), but when bandwidth is the limiting factor the halved traffic is often a big win.

Let’s check whether we see this improve throughput using vLLM, and the impact on accuracy.

## FP8 KV Cache Accuracy: Everything is Fine!

_Note: sorry in advance for the slightly rough screenshots below. Substack still doesn’t offer a great way to display this kind of data cleanly, so I captured everything from a small app I “vibe-coded” with ChatGPT._

I ran the evaluation with [EvalScope](<https://github.com/modelscope/evalscope/tree/main/evalscope>) on three benchmarks:

  * **LiveCodeBench** : using only the first 256 coding problems (out of 1,055 total).

  * **AIME 2024** : repeated 8x to get more stable averages, since the benchmark has only 30 questions.

  * **GPQA Diamond** : repeated 4x, again to reduce variance and report averaged results.

To cover a range of model sizes, architectures, and generation behavior (reasoning vs. non-reasoning), I evaluated four models:

  * **Qwen3 4B Instruct (2507)** : 4B parameters, dense, non-reasoning (though it can still generate a lot of tokens, especially on AIME 2024).

  * **Qwen3 4B Thinking (2507)** : same base model, but the reasoning variant, so it tends to produce even longer outputs.

  * **Qwen3 8B** : 8B parameters. Tested with Thinking enabled (and notably, it uses the same KV-cache shape as Qwen3 4B).

  * **Nemotron 3 Nano 30B A3B** : a Mixture-of-Experts model with 30B total parameters but only ~3B active per token at inference, with a hybrid architecture we discussed earlier in this article.

KV-cache quantization is most beneficial when outputs get long, exactly what you see with reasoning models, where the cache can grow to several GB per request. For more typical instruct-style workloads, the gains are still very noticeable: lower KV memory footprint, higher concurrency, and often a clear boost in throughput because there’s simply less data to move around.

For these experiments, I mostly used KV quantization without scale calibration.

As the results above show, KV-cache quantization has only a very small effect on quality, small enough that it’s generally within the benchmarks’ natural run-to-run variation. And it’s not consistent from one benchmark to another. In other words, the differences you’re seeing don’t look statistically meaningful.

I also tried scale calibration on Qwen3 8B, but it didn’t change the picture much. On average, calibration performs slightly better than leaving scales uncalibrated, but the gap still doesn’t look clearly significant. That said, calibration is cheap, so it’s a sensible default to enable anyway.

## KV Cache Quantization: For What Inference Speed Up?

I ran these experiments on two GPUs:

  * **RTX Pro 6000** : **96 GB** of VRAM, but comparatively modest memory bandwidth (around **~1.7 TB/s**).

  * **H100 SXM** : **80 GB** of VRAM, but _much_ faster memory, with **3.35 TB/s** of bandwidth. This GPU is significantly more expensive to run, so I only collected results for Qwen3 4B Thinking and Qwen3 8B.

Let’s start with benchmark completion time. These runs are closer to real-world conditions: real prompts, real tasks, and multiple concurrent queries.

No surprises here: switching the KV cache to FP8 can speed up inference quite a bit. The effect is especially clear on the RTX Pro 6000, and that’s expected. With lower memory bandwidth, it benefits more from having to read and move less KV data each step.

For long generations, it’s realistic to cut inference cost by more than 50% in many cases. For short outputs, the benefit is much smaller (as you can see with Qwen3 4B Instruct), and may feel barely worth the effort. That said, even a ~5% improvement can add up meaningfully when you’re running at scale over weeks and months.

Nemotron 3 Nano is the exception: it doesn’t gain much from KV-cache quantization, and in some cases it can even get slightly worse because quantization/dequantization adds extra work. That’s tied to its hybrid architecture. The model already reduces attention costs, so shrinking the KV cache helps less, while the overhead remains.

One interesting consequence is that KV-cache quantization can shrink the inference-cost gap between hybrid architectures and full-attention models, while keeping accuracy essentially unchanged. For that reason, I’d argue that speed benchmarks from hybrid-architecture providers should also include comparisons against baselines that use a quantized KV cache.

The H100 is, unsurprisingly, much faster on this kind of workload.

What’s more interesting is that for long sequences, an RTX Pro 6000 with an FP8 KV cache can reach roughly the same speed as an H100 with an FP16 KV cache. Shrinking the cache reduces memory traffic enough to close a surprising part of the gap.

These results also highlight an important point: KV-cache quantization really shines when you have multiple concurrent requests. With just one query, you’re typically not memory-bound, the GPU can read the KV cache without much trouble, so the benefit is much smaller.

## Conclusion

If there’s one takeaway from this article, it’s this: quantize your KV cache. In practice, it delivers a rare combo of wins: almost no measurable accuracy drop, faster inference, lower memory usage, and therefore lower overall cost (either by increasing throughput, supporting more concurrent users, or both).

The gains are most dramatic for long generations, which is important for modern LLM use cases like reasoning-style outputs, long chats, and tool-using agents. That’s where the KV cache balloons, memory traffic dominates, and FP8 starts paying for itself quickly. On some GPUs and workloads, it can shave a meaningful fraction off your runtime and cost.

The main exception is very light workloads, like single, short queries. In that regime you’re often not memory-bound, so there’s less to gain, and the overhead can cancel out some of the benefit. But once you care about concurrency or long outputs, KV quantization quickly becomes the default choice.

Finally, about scale calibration: it can help a bit, but the effect is usually small and not consistently significant. Still, it’s cheap to enable, so it’s a good default, just don’t expect it to be the difference-maker.
