LoRA (Low-Rank Adaptation) is a parameter-efficient fine-tuning technique for large pre-trained models. Unlike standard full fine-tuning, which updates all model parameters, LoRA freezes the entire model and introduces only a small set of trainable parameters. These parameters are added to specific layers or modules of the model, which allows for efficient adaptation with minimal memory overhead.

Because LoRA only stores optimizer states and gradients for the trainable parameters, it consumes significantly less memory than full fine-tuning. However, since the other model parameters remain frozen, it cannot accommodate new tokens. Any new tokens would have untrained embeddings.

In a previous article, we explored how to use LoRA fine-tuning while fully retraining the token embeddings and the language modeling head. 

This approach enables the model to effectively handle special tokens, such as those used in a chat template and specific domains. While this method is effective, it requires significantly more memory since the embeddings and language modeling head parameters are made trainable.

In this article, we will explore a new alternative from the Hugging Face PEFT (Parameter-Efficient Fine-Tuning) library. Rather than retraining the full embeddings and language modeling head, this method focuses solely on updating the embeddings for the special tokens the model needs to learn. We will first examine how this technique works, its limitations, and its memory efficiency. Finally, we will compare its performance to full retraining.

## Trainable Tokens with LoRA: How Does It Work?

Prior to this update in the [PEFT library](<https://huggingface.co/docs/peft/en/index>), modifying token embeddings required retraining the entire embedding matrix, which could be prohibitively large. This matrix often includes hundreds of thousands of tokens, each represented by high-dimensional vectors. For example, consider the Llama 3.1 8B model: it has approximately 128k tokens (`vocab_size`) with an embedding dimension (`embed_dim`) of 4,096. This results in a total of 128k * 4,096 = 524 million parameters.

Training these parameters involves significant memory consumption:

  * **16-bit weights** : 524M * 2 bytes = 1 GB

  * **32-bit optimizer states** for these parameters: 524M * (2 * 4 bytes) = 4 GB

**Total memory usage** : 1 GB (weights) + 4 GB (optimizer states) = 5 GB

For more information on how to estimate memory consumption for the optimizer states, refer to this article:

This not only increases computational and storage requirements but also may introduce unnecessary updates to embeddings that are unrelated to the task.

“Trainable tokens” offers a more efficient alternative by introducing a sparse update mechanism. Instead of updating the full `(vocab_size, embed_dim)` embedding matrix, it creates a much smaller `(n, embed_dim)` matrix, where `n` is the number of tokens you wish to modify. These sparse embeddings are then overlaid on top of the original matrix during forward passes, such that only the specified token indices are trainable, and all others remain frozen. This design allows targeted tuning of token representations while maintaining the overall integrity of the original model and keeping memory and compute costs minimal.

There are two primary ways to integrate this capability into your model training workflow, both relying on the PEFT framework.

  1. Using `CustomTokens` PEFT method:  
This method is specifically for sparse embedding updates. You begin by defining a `CustomTokensConfig`, where you explicitly specify the `target_modules` (typically set to `['embed_tokens']`) and the `token_indices`, which is a list of token IDs (defined in the tokenizer.json) you want to fine-tune. Once the configuration is defined, you wrap your base model using `get_peft_model(model, peft_config)`. This creates a wrapper that manages the sparse embedding updates internally and ensures that only the specified tokens are trained.

    
    
    peft_config = CustomTokensConfig(target_modules=['embed_tokens'], token_indices=[0, 1, 2])
    peft_model = get_peft_model(model, peft_config)

  2. Combining with LoRA:  
If you're using LoRA to adapt linear layers in your model, you can extend its functionality to support token-level embedding updates as well. This is done via the `trainable_token_indices` argument in the `LoraConfig`. Here, you pass a dictionary mapping target module names (e.g., `'embed_tokens'`) to lists of token indices that should be trainable. It fine-tunes only the embeddings associated with the specified indices while continuing to apply LoRA to other model components.

    
    
        peft_config = LoraConfig(
                lora_alpha=16,
                lora_dropout=0.05,
                r=16,
                bias="none",
                task_type="CAUSAL_LM",
                target_modules= ['k_proj', 'q_proj', 'v_proj', 'o_proj', "gate_proj", "down_proj", "up_proj"],
                modules_to_save = ["embed_tokens", "lm_head"] if full_retrain_vocab else None,
                trainable_token_indices = {'embed_tokens':[128006, 128007, 128008, 128009], 'lm_head':[128006, 128007, 128008, 128009]},
        )

Both methods are compatible with PEFT’s save/load methods, allowing fine-tuned weights to be exported and reloaded independently of the base model. 

In the following sections, we will focus on applying this to LoRA fine-tuning.

## Trainable Tokens vs. Full Retraining of the Embeddings

In this section, we’ll explore a common scenario where we need to fine-tune a base model to use a chat template. In such cases, we must either add special tokens to the vocabulary, such as turn delimiters, or use special tokens that are already defined in the vocabulary.

Even when special tokens are already included in the vocabulary, as is the case with Llama 3.x and Qwen2.5 base models, these tokens may not be effectively pre-trained. Often, the embeddings for these tokens are so small (virtually 0.0) that they can lead to NaN (Not a Number) issues during training.

For example, let’s consider the base models of Llama 3.1 8B and Llama 3.2 3B:

  * [meta-llama/Llama-3.2-3B](<https://huggingface.co/meta-llama/Llama-3.2-3B>)

  * [meta-llama/Llama-3.1-8B](<https://huggingface.co/meta-llama/Llama-3.1-8B>)

 _Note: Llama 3.2 3B uses tied embeddings, meaning the token embeddings and the language modeling head share the same parameters._

Our goal is to train the model to effectively use a chat template. For simplicity, let’s use the chat template from the model’s instruct version. This is a convenient choice because [the vocabulary of the base model](<https://huggingface.co/meta-llama/Llama-3.1-8B/blob/main/tokenizer_config.json>) already includes the special tokens used in that chat template:
    
    
       {
          "id": 128006,
          "content": "<|start_header_id|>",
          "single_word": false,
          "lstrip": false,
          "rstrip": false,
          "normalized": false,
          "special": true
        },
        {
          "id": 128007,
          "content": "<|end_header_id|>",
          "single_word": false,
          "lstrip": false,
          "rstrip": false,
          "normalized": false,
          "special": true
        },
        {
          "id": 128008,
          "content": "<|eom_id|>",
          "single_word": false,
          "lstrip": false,
          "rstrip": false,
          "normalized": false,
          "special": true
        },
        {
          "id": 128009,
          "content": "<|eot_id|>",
          "single_word": false,
          "lstrip": false,
          "rstrip": false,
          "normalized": false,
          "special": true
        },

Although the special tokens are present in the vocabulary, the base models are not trained to use them. For these models, these special tokens are treated the same as any other reserved special tokens in the vocabulary, i.e., the embeddings of the token `128009 `might be so close to the embeddings of token `128008 `that the model might not be able to distinguish them.

The "trainable tokens" strategy is a perfect fit for this situation. Rather than retraining the full embedding matrix, we only need to retrain the embeddings of these 4 tokens.

The key questions we need to answer are:

  * How much memory is saved compared to retraining the full embedding matrices (token embeddings and language modeling head)?

  * Is this approach faster?

  * Does it perform as well?

To address these questions, I trained the models on 10k samples from the [Ultrachat dataset](<https://huggingface.co/datasets/HuggingFaceH4/ultrachat_200k>) for two epochs. The "messages" column was converted into a sequence of text by applying the chat template.

I compared four LoRA fine-tuning configurations:

  1. Frozen embeddings

  2. Trainable tokens: token embeddings and language modeling head (LM head)

  3. Trainable tokens: token embeddings only

  4. Full retraining of the embeddings

## Trainable Parameters and Memory Consumption

The "trainable tokens" strategy is designed to add only a small number of trainable parameters on top of the existing LoRA adapter parameters. This makes it a memory-efficient approach. In contrast, full retraining of the embeddings involves updating a large number of parameters, resulting in a significant increase in memory consumption.

![image](https://substackcdn.com/image/fetch/$s_!uv2y!,w_1456,c_limit,f_auto,q_auto:good,fl_progressive:steep/https%3A%2F%2Fsubstack-post-media.s3.amazonaws.com%2Fpublic%2Fimages%2F38e355f5-70e1-45b0-b65e-12196bb2207c_1200x742.png) 

As expected, training only 4 tokens adds a minimal number of trainable parameters on top of LoRA. Let’s break this down with some calculations for Llama 3.1 8B:

  * **With frozen embeddings** : 41,943,040 trainable parameters

  * **With trainable tokens (token embeddings only)** : +16,384 trainable parameters

This means there are 4,096 trainable parameters for each token being trained, as 4,096 corresponds to the model's hidden size. This is correct. Adding a trainable token introduces 4,096 trainable parameters, or 8,192 if we also train the LM head.

![image](https://substackcdn.com/image/fetch/$s_!tI0k!,w_1456,c_limit,f_auto,q_auto:good,fl_progressive:steep/https%3A%2F%2Fsubstack-post-media.s3.amazonaws.com%2Fpublic%2Fimages%2F2a4ffdb1-b6db-4d50-8165-ac91f48b21ac_1200x742.png) 

![image](https://substackcdn.com/image/fetch/$s_!l8Tu!,w_1456,c_limit,f_auto,q_auto:good,fl_progressive:steep/https%3A%2F%2Fsubstack-post-media.s3.amazonaws.com%2Fpublic%2Fimages%2F4819f98a-8e4c-4521-900e-3ed41ad95151_1200x742.png) 

When using trainable tokens to retrain the embeddings and the LM head, we observe an additional memory consumption of about 2 GB. This may seem a lot for just 16k parameters. The reason for this is that, at some point during training, we must store and materialize the entire embedding matrix in memory to update it.

If we don’t train tokens for the LM head with Llama 3.1 8B (token embeddings only), the trainable tokens only consume 16 MB more memory compared to using frozen embeddings. This isn’t observed with Llama 3.2 3B. Since the LM head and the token embeddings are shared, we need to materialize the full language modeling head. In this configuration, training only the token embeddings with or without the LM head consumes the same memory.

While the additional 2 GB for Llama 3.1 8B may seem significant compared to the original LoRA approach, it's still 5 GB less than the memory required for full retraining of both the embeddings and LM head. This is because, with trainable tokens, we only need to create optimizer states and gradients for the small number of trainable parameters.

Another question I aimed to address is: **Is training only a few tokens faster than retraining the full embeddings?**

It turns out that training only a few tokens is not faster. In fact, it is slightly slower, especially when we also train the LM head along with the trainable tokens. This slowdown is likely due to the additional complexity of updating the LM head and the need to create new matrices for the tokens being retrained. However, this process could likely be accelerated with some optimization of the code.

## What Are We Missing When Only Training Some Tokens?

When we have enough memory, fully training the embeddings and the LM head typically leads to improved results for LoRA fine-tuning. I recommend this approach, especially for fine-tuning on specific domains or specialized tasks where the base embeddings may not be well-suited.

On the other hand, full training of the embeddings can be tricky—it involves updating all the embedding parameters, and if not done carefully (e.g., with too high a learning rate), it can degrade the model's performance.

Let’s take a look at the learning curves to better understand this:

When we only train the token embeddings for the trainable tokens, the model tends to underperform, resulting in a higher validation loss. This is particularly true for Llama 3.1 8B, where LoRA with fully frozen embeddings outperforms the trainable tokens approach. However, if we also train the LM head, the results significantly improve, even surpassing the performance of full retraining of the embeddings and LM head for Llama 3.1 8B.

_Note: As mentioned in a previous article, using a lower learning rate for the embeddings can help improve the results when fully retraining the token embeddings._

These learning curves demonstrate that when we retrain the LM head for the special tokens, the model learns more effectively from the dataset.

## Conclusion

The "trainable tokens" strategy is both efficient and effective for teaching a model how to use new tokens. It works well and saves memory compared to full retraining of the embedding matrices. I highly recommend this approach!

In this article, I applied it specifically to the special tokens in the chat template. However, if you're working in a specific domain, you can adapt this strategy to target tokens related to domain-specific jargon. It can also be useful for coding tasks, where you would train tokens for special symbols and keywords specific to a target programming language.
