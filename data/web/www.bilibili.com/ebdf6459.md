# Claude Code的最佳实践（上下文管理重要性、常用技巧、项目启动流程、避免失败模式、善用探索-规划-编程-提交框架）

**核心观点：Claude Code 是一个需要精心编排的自主代理（Autonomous Agent），而非一个简单的聊天机器人。成功使用的关键在于“上下文编排（Context Orchestration）”，而非单纯的提示词工程。**

- **核心心智模型**：Claude Code 是一个在你的代码库中运行的自主代理，拥有工具、权限和执行能力，并在一个有限的上下文窗口内运作。将其视为聊天机器人是大多数失败的根源。
- **核心规则**：如果你不控制上下文，你就无法控制结果。Claude Code 奖励的是系统设计，而非聪明的提示词。

**一、 核心设计理念与配置**

- **终端优先（Terminal-First）是特性，而非限制**
    - **优势**：提供对系统环境的完全访问（如 `git`、`docker`、自定义脚本），具备脚本化能力（可通过 `-p` 标志用于 CI/CD 管道），支持并行工作（可运行多个实例处理独立任务），且不绑定于特定编辑器。
    - **取舍**：牺牲了内联代码建议和可视化差异对比，更适合复杂的、跨文件的任务（如重构、调试）。

- **自主性（Autonomy）是一个可调节的旋钮**
    - **最大安全性**：默认模式，任何操作都需手动批准。适用于不熟悉的代码库或生产环境，但会严重破坏工作流。
    - **平衡工作流**：通过 `.claude/settings.json` 配置自定义允许列表（Allowlist），允许常见的文件编辑、`git` 操作和构建命令，阻止破坏性操作。这是大多数用户的推荐设置。
    - **最大自主性**：使用 `--dangerously-skip-permissions` 标志，让 Claude 无中断运行。在**版本控制良好**的代码库中风险很低，能极大提升生产力。许多高级用户会为此设置别名（如 `alias cc="claude --dangerously-skip-permissions"`）。

- **CLAUDE.md 文件：持久化上下文，但应保持精简**
    - **作用**：Claude 在每次会话开始时自动加载此文件，其中的指令具有最高优先级。
    - **应包含的内容**：构建/测试命令、关键文件路径、项目特有的注意事项、环境设置细节。
    - **不应包含的内容**：代码风格指南（应交给 Linter）、显而易见的文件夹描述、泛泛的“最佳实践”指令。
    - **关键洞察（Chekhov‘s Gun 效应）**：模型倾向于使用所有被提供的信息，即使是不相关的。臃肿的 CLAUDE.md 文件会浪费令牌（Token）并引入干扰，从而降低性能。**保持精简（例如少于50行）**。

- **扩展能力：模型上下文协议（MCP， Model Context Protocol）**
    - **作用**：连接 Claude 到外部工具和数据源，如数据库（PostgreSQL）、GitHub、错误监控系统（Sentry）等，极大地扩展其感知和行动范围。
    - **配置建议**：仅在需要时启用 MCP 服务器，避免不必要的工具定义占用宝贵的上下文令牌。可通过 `/context` 命令检查消耗。

- **自定义斜杠命令（Slash Commands）**
    - **用途**：创建可重用的提示模板，封装复杂的工作流（如 `/project:fix-issue 1234` 来自动化修复问题）。
    - **存放位置**：个人命令放在 `~/.claude/commands/`，项目命令放在 `.claude/commands/` 并可提交到 Git 与团队共享。

**二、 关键失败模式与修复方法**

- **过早执行（Premature Execution）**：Claude 在未充分理解问题前就开始编码。
    - **修复**：采用明确的阶段性指令，如“先阅读相关文件，不要写代码”、“提出一个计划”，然后再执行。使用“仔细思考（think hard）”等词可以触发更长的推理过程。

- **上下文污染（Context Contamination）**：在不同任务间未清理上下文，导致旧任务的假设干扰新任务。
    - **修复**：频繁使用 `/clear` 命令重置会话历史，尤其是在切换任务时。

- **约20轮迭代的性能断崖（The ~15-20 Turn Degradation Cliff）**：研究表明，代理性能在经过大约15-20轮对话后会急剧下降，表现为重复、指令漂移或幻觉。
    - **修复**：将此视为硬性限制。如果接近此轮数，应主动重置上下文、将任务分解，或通过提交（Commit）、清单（Checklist）等方式将状态外部化。

- **CLAUDE.md 文件臃肿**：如前所述，包含过多无关信息。
    - **修复**：坚持精简原则。

- **权限摩擦（Permission Friction）**：持续手动批准操作，浪费时间和打断心流。
    - **修复**：根据任务和风险承受能力，合理配置允许列表或使用完全自主模式。

- **忽略终端输出（Ignoring Terminal Feedback）**：不仔细阅读 Claude 运行命令后的错误信息，而这些信息往往是解决问题的关键。
    - **修复**：主动监控命令输出，利用你对系统的了解（如路径、环境变量）来引导 Claude。

- **未使用子代理（Not Using Subagents）**：让主会话上下文充满探索性的研究和死胡同。
    - **修复**：对于复杂的研究性任务，指示 Claude “使用子代理来研究 X 是如何工作的”，子代理的结论会返回给主会话，保持主上下文清洁。

**三、 有效的工作流框架**

- **探索 → 计划 → 编码 → 提交（Explore → Plan → Code → Commit）**
    - **步骤**：1) 指示 Claude 阅读相关文件（明确说“不要写代码”）。 2) 让其提出一个计划（使用“仔细思考”）。 3) 审查并完善计划。 4) 执行计划。 5) 提交更改。
    - **适用场景**：任何非琐碎的任务。

- **测试驱动开发循环（TDD Loop）**
    - **步骤**：1) 让 Claude 为要实现的特性编写测试（先不实现）。 2) 运行测试确认失败。 3) 实现代码使测试通过，并迭代直到成功。 4) 分别提交测试和实现代码。
    - **适用场景**：成功标准可以明确用测试定义的场景（如后端逻辑、API）。为 Claude 提供了清晰的迭代目标。

- **视觉反馈循环（Visual Feedback Loop）**
    - **步骤**：1) 提供目标（截图、Figma 设计图或描述）。 2) Claude 实现。 3) Claude 获取结果截图（通过 Puppeteer MCP 或手动粘贴）。 4) 对比目标，指出差异并让其修复。 5) 迭代直到匹配。
    - **适用场景**：UI/前端开发、视觉调试。

- **并行多实例（Parallel Multi-Claude）**
    - **方法**：在多个终端标签页或使用 Git 工作树（`git worktree`）运行独立的 Claude 实例，每个处理不同的任务。
    - **适用场景**：完全独立、不共享上下文的任务，可实现多倍吞吐量。

- **编写者-审查者分离（Writer-Reviewer Split）**
    - **方法**：用一个 Claude 实例（A）编写代码，然后清除上下文或启动一个新实例（B）来审查 A 的代码。审查反馈再交给 A 或另一个实例来修复。
    - **适用场景**：对生产代码进行质量控制。分离的上下文有助于获得更客观的审查。

- **无头自动化（Headless Automation）**
    - **方法**：使用 `-p` 标志以非交互模式运行 Claude，可集成到脚本、预提交钩子（Pre-commit Hooks）或 CI/CD 管道中。
    - **适用场景**：批量处理、自动化代码审查、问题分类等。

- **清单驱动工作（Checklist-Driven Work）**
    - **方法**：对于大型任务，先让 Claude 生成一个包含所有步骤的清单（CHECKLIST.md），然后逐一完成并勾选。
    - **适用场景**：大型重构、迁移、上线清单。清单将状态外部化，便于在上下文重置后恢复进度。

**四、 实施步骤与最佳实践总结**

- **基础设置清单**：
    1.  运行 `/init` 生成 CLAUDE.md 草稿。
    2.  精简 CLAUDE.md，只保留核心信息。
    3.  在 `.claude/settings.json` 中配置权限（允许列表）。
    4.  按需添加 MCP 服务器。
    5.  为常用工作流创建几个斜杠命令。
    6.  将 `.claude/` 目录提交到 Git 以与团队共享配置。

- **核心操作命令**：
    - `/clear`：清理会话历史，保持上下文清洁。
    - `/compact`：主动压缩历史以释放令牌，建议在上下文使用率达到70%时进行。
    - `/context`：查看当前上下文窗口的消耗情况，诊断性能问题。

- **总体原则**：
    - **从提示词工程转向上下文编排**：精心管理进入上下文的信息（文件、指令、历史），比优化单个提示词更重要。
    - **拥抱终端和自主性**：理解终端优先设计的优势，并根据你的工作环境（尤其是版本控制）合理设置自主性级别。
    - **将迭代和重置视为常态**：不要害怕在遇到瓶颈时回滚到稳定状态并重新开始。频繁提交和使用清单来管理进度。
    - **设计反馈闭环**：无论是通过测试、视觉对比还是审查，为 Claude 的工作建立明确的验证和反馈机制。
