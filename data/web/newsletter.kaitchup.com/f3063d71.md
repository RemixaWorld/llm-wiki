# LLM as a Judge: Evaluate Your LLMs with Another LLM

### A good evaluation framework for quick feedback and monitoring

Evaluating large language models (LLMs) can be tricky. These models can do so many things, so it’s hard to come up with clear, simple standards to judge their responses. For example, an answer from an LLM might lack context, repeat itself, have grammar mistakes, be way too long, or even make little sense.

One effective solution is to let LLMs evaluate each other, an approach known as "LLM-as-a-judge." This approach which is used in popular benchmarks like Chatbot Arena, involves using an LLM to score or rank the responses of other models. By letting LLMs handle the judging, we can save on human effort while still getting feedback. As it's automatic, this method makes it easier to review and improve these models without relying heavily on human reviewers. LLM-as-a-judge is also a good alternative to avoid depending on old public benchmarks for evaluation like MMLU which have probably been seen by the models during training.

In this article, we will see how to use the LLM-as-a-judge framework, with examples. Using vLLM and TRL, we will see how to compare two LLMs using a third larger and better LLM as a judge and compute win rates.

## LLM-as-a-judge: How Does It Work?

The LLM-as-a-judge approach involves using an external LLM to review and “judge” an LLM’s outputs according to predefined criteria. For example, in evaluating a chatbot’s responses, the judge can assess qualities like politeness, bias, tone, sentiment, and accuracy.

#### Methods for Implementing LLM Judges

In a pairwise comparison, the LLM judge compares two responses to the same question or prompt and selects the better one. This method is especially helpful during development when comparing model versions or testing different prompts to find the most effective option. We will implement and test this method in the next sections.

Another method could be to use the LLM to review a single response based on specific qualities, like tone or clarity, without needing any additional context. This is a reference-free evaluation. Reference-based evaluation, on the other hand, involves comparing a response to a known reference, for instance, created by humans.

This method works well in applications like summarization, where developers want to ensure that the response accurately reflects the source material.

### Designing Effective LLM Judges

Creating an effective LLM judge requires a structured approach. Developers start by defining clear evaluation criteria, which may include qualities like accuracy, clarity, or politeness. Criteria should be simple and specific, so the LLM judge can focus on one aspect of quality at a time.

After defining the criteria, developers prepare a labeled dataset that serves as a ground truth. This will allow them to measure how well the LLM judge’s evaluations align with the expected results. Next, developers craft the evaluation prompt, which gives instructions to the LLM judge.

Prompts should include straightforward scoring options, like binary choices (e.g., "helpful" vs. "unhelpful"), to increase consistency and accuracy. Some prompts may also ask the LLM judge to explain its decisions, which can further improve the quality of evaluations.

Once the prompt is ready, developers test it on the labeled dataset and measure its performance using metrics such as precision and recall. Adjustments to the prompt may be necessary if the LLM judge’s evaluations do not align with the desired standards. Involving domain experts in creating and refining prompts can also improve the evaluation’s relevance and accuracy for specific product needs.

### Benefits and Limitations of LLM Judges

LLM judges offer flexible evaluation options. This flexibility is especially useful in real-time monitoring, where researchers and developers may need to quickly assess the quality of new fine-tuning, quantization, hyperparameter values, etc.

However, LLM judges are not without flaws. They may yield **inconsistent** results if the instructions are vague or overly complex, and they can carry **biases** from the data they were trained on. Additionally, using third-party LLM APIs for evaluation may raise data **privacy concerns**, particularly when handling sensitive information.

Other evaluation methods can complement LLM judges for more rigorous evaluation. Manual labeling, user feedback, traditional ML models, and rule-based checks all play a role in quality assessment. A hybrid approach often works best, where simpler issues are managed by rule-based checks, while more nuanced evaluations are handled by LLM judges and human reviewers.

If you're writing scientific papers with sections evaluating LLMs, avoid using an LLM as a judge unless it is fully transparent—meaning its pre-training data, training methodology, and model architecture are fully disclosed. This transparency is crucial to assess the extent to which the judge may overlap in training data, architecture, or vocabulary with the evaluated LLMs, which could bias the evaluation results.

### Implementing LLM-as-a-judge with Transformers and vLLM

**Use Case:** We want to find, among 2 LLMs, the one that is better to do a given task, according to a third LLM (the judge). For this use case, I want to know which tiny LLM, among SmolLM 135M and SmolLM2 135M, is the best to complete the prompts from the following dataset:

Hugging Face Dataset: fka/awesome-chatgpt-prompts


Let’s load the dataset:

```
# Load the dataset
dataset = load_dataset("fka/awesome-chatgpt-prompts", split="train")
# Extract the prompts and reference completions
prompts = dataset["prompt"]
```


Next, we run the models with vLLM for these prompts:

```
model_a = "HuggingFaceTB/SmolLM-135M-Instruct"
model_b = "HuggingFaceTB/SmolLM2-135M-Instruct"
sampling_params = SamplingParams(temperature=0.0, top_p=0.95, max_tokens=500)
llm = LLM(model=model_a, gpu_memory_utilization=0.3)
outputs = llm.generate(prompts, sampling_params)
model_a_completions = [output.outputs[0].text.strip() for output in outputs]
llm = LLM(model=model_b, gpu_memory_utilization=0.3)
outputs = llm.generate(prompts, sampling_params)
model_b_completions = [output.outputs[0].text.strip() for output in outputs]
```


*Note: Running these two models with vLLM occupies a lot of memory. You may serialize the answers into a separate file and then restart the notebook before running the second LLM.*

For the judge, I chose `nvidia/Mistral-NeMo-Minitron-8B-Instruct `

which is currently one of the best instruct LLMs of this size. If you have more GPU memory available, you may run a larger instruct model, such as Qwen2.5 14B, 32B, or 72B.

`judge_model = "nvidia/Mistral-NeMo-Minitron-8B-Instruct"`


We need a prompt to query this LLM judge to evaluate the output of SmolLM and SmolLM2. I used the default prompt template provided by TRL:

```
DEFAULT_PAIRWISE_SYSTEM_PROMPT = '''I require a leaderboard for various large language models. I'll provide you with prompts given to these models and their corresponding outputs. Your task is to assess these responses, and select the model that produces the best output from a human perspective.
## Instruction
{{
"instruction": """{prompt}""",
}}
## Model Outputs
Here are the unordered outputs from the models. Each output is associated with a specific model, identified by a unique model identifier.
{{
{{
"model_identifier": "0",
"output": """{response0}"""
}},
{{
"model_identifier": "1",
"output": """{response1}"""
}}
}}
## Task
Evaluate the models on the basis of the quality and relevance of their results, and select the model that generated the best result. Reply with the identifier of the best model. Our evaluation will only take into account the first character of your answer, so make sure it contains only one of the identifiers and nothing else (no quotation marks, no spaces, no new lines, ...).
'''
```


In a nutshell, the prompt takes three arguments: the prompt from the dataset, and the respective answer generated by the LLMs. The model is asked to return the ID of the model that provided the best answer.

You could add more models to be evaluated by incrementing "`model_identifier`

" and adding their respective outputs. However, keep in mind that this would increase the prompt length, i.e., it will increase the computational cost of the evaluation or it may become longer than the maximum length that the model can support.

I made queries for the judge using this prompt and the models’ outputs, as follows:

```
judge_prompts = []
for prompt, c0, c1 in zip(prompts,model_a_completions, model_b_completions):
judge_prompts.append([{"role":"user", "content": DEFAULT_PAIRWISE_SYSTEM_PROMPT.format(prompt=prompt, response0=c0, response1=c1)}])
```


Then, we call vLLM a third time, using the judge, for these new queries:

```
llm = LLM(model=judge_model, gpu_memory_utilization=0.5)
sampling_params = SamplingParams(temperature=0.0, max_tokens=1) # very generous max token length
outputs = llm.chat(judge_prompts, sampling_params, use_tqdm=False)
```


I set `max_tokens `

to 1 since we request the judge to only return the identifier of the model, i.e., a single token. This is why I recommend not using a smaller LLM as a judge. A model of less than 7B parameters would not strictly follow the prompt instructions and may generate more than what we requested.

I made a simple function to parse the answer of the judge:

```
def get_rank(response):
if response == "0":
return 0
elif response == "1":
return 1
else:
return -1
ranks = []
for output in outputs:
rank = get_rank(output.outputs[0].text.strip())
ranks.append(rank)
```


We expect 0 or 1 since the model_identifier is 0 and 1. If we don’t get these numbers, the function returns -1 (none of the models win).

```
model_win_rate = ranks.count(1) / len(ranks)
print(f"Model A wins: {ranks.count(0)}")
```

For this task, according to nvidia/Mistral-NeMo-Minitron-8B-Instruct, SmolLM 135M is better than SmolLM2 135M!

This is the only feedback that we get from this evaluation. It doesn’t tell us whether the generated answers are useful or even human-readable. Always manually check some of the generated responses before deciding whether a model is better.

Moreover, note that the results may vary between runs since decoding is not deterministic. To confirm your results, I suggest running the evaluation at least 3 times and randomizing the order of the evaluated outputs in the prompt (i.e., put the completion of B before the completion of A, in 50% of the evaluation samples). You may also change the model’s ID between runs.

## Conclusion

Using an LLM-as-a-judge setup can effectively streamline the evaluation of language models, reducing the reliance on human reviewers while providing feedback. By structuring evaluations with clear prompts and criteria, this approach can show strengths and weaknesses in various models.

Next steps could include fine-tuning LLM judges on specific evaluation tasks to further align them with human judgment in niche domains. Another possible extension is integrating multiple LLM judges and averaging their scores, which could mitigate the biases of a single model.

**Know your judge! **

The judge picks the answer that it judges the best, according to its own knowledge. It may also prefer models that generate answers that are close to the answer it would generate. In other words, the judge is likely biased. This bias tends to be alleviated as you pick a larger and better model. If you can, pick a 70B model or larger.
