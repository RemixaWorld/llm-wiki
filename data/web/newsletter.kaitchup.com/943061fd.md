# Train and Serve an AI Chatbot Based on Llama 3.2

### Efficient supervised fine-tuning with TRL

Creating a custom AI chatbot is now more accessible and cost-effective than ever. With parameter-efficient fine-tuning methods like LoRA and QLoRA, even small but powerful models like Llama 3.2 can be adapted to train high-quality chatbots for just a few dollars.

In this article, we will see how to format a question-answering dataset and fine-tune Llama 3.2 using supervised fine-tuning (SFT). We'll highlight common pitfalls to avoid during SFT and demonstrate how to train a chatbot with a synthetic dataset.

Each of these steps is explained in detail within the article and implemented in this notebook:

## Formatting a Synthetic Dataset of Questions and Answers for Supervised Fine-tuning

In a previous article, we saw how to generate our own synthetic dataset to train an AI chatbot. I will use this generated dataset again in this article:

Let’s see what columns we have in this dataset:

Aside from the "persona" column, the other columns in this dataset are standard for fine-tuning datasets for chatbots. Here, "supervised fine-tuning" (SFT) is a more accurate term than "training."

SFT is a "completion" task, where we provide a prompt and expect the model to generate the next sequence of tokens following the prompt. For example, if the prompt is a question, we want the model to complete it with the corresponding answer.

LLMs learn to complete prompts from examples of prompts paired with their completions. To teach a model to answer questions, we fine-tune it on pairs of questions and their answers so that these pairs appear as connected sequences. For chatbot training, we often use a chat template to format these interactions.

If you’re interested in creating custom prompts, I recommend checking out my article on chat template creation and manipulation:

It’s crucial to remember that **the chat template used during SFT must be applied consistently during inference. **If you include a system prompt—such as one that defines the chatbot's personality or specific tasks—you must use the same system prompt at inference. Otherwise, your chatbot may underperform or behave unpredictably.

To create an educational chatbot using my synthetic dataset, I’ll use Llama 3.2 Instruct's chat template, relying on only the "question" and "answer" columns from the dataset.

While it’s possible to use the "messages" format, which TRL automatically prepares for SFT, I recommend against directly passing "messages" to TRL. This is to ensure you retain control over the chat template and can add a system prompt if desired. Should TRL change its message formatting in the future, directly relying on it might lead to compatibility issues.

To apply the chat template of Llama 3.2, we’ll need to load the tokenizer for Llama 3.2 Instruct, as this model version includes the necessary chat template within its tokenizer.

This chat template supports various roles. Here we are only interested in:

system: Often used to define the task of the LLM, its style, or define safety instructions.

user: The prompt entered by the user

assistant: The answer generated by the LLM


During SFT, each training example must have user and assistant roles. The system role is optional but recommended. You might want to skip the system role if you want to speed up inference since it means fewer tokens to encode.

Then, at inference time, we only provide the system (if provided during SFT) and user prompts. The LLM task will be to complete it with the assistant’s answer.

In the dataset used for SFT, we don’t have a system prompt. I will write it and use the same one for each training example.

Then, we pack system, user, and assistant’s messages into a list:

```
messages = [
{"role": "system", "content": "You are an educational chatbot."},
{"role": "user", "content": row["question"]},
{"role": "assistant", "content": row["answer"]},
]
```


Next, we apply the chat template of Llama 3.2 Instruct.

`tokenizer.apply_chat_template(messages, tokenize=False, add_generation_prompt=False)`

The chat template automatically adds information about the cutting knowledge data.

The template also uses several special tokens. These tokens are defined in Llama 3.2 and Llama 3.2 Instruct tokenizers. However, these tokens are not trained for the base Llama 3.2 since they are only used by the Instruct version. They all have the same embeddings. If we don’t train these tokens during SFT, Llama 3.2 will never learn how to use them and will generate broken outputs with the wrong special tokens. Indeed, for instance, if `<|eot_id|>`

and `<|start_header_id|>`

both have the same embeddings, the model will consider them to be the same and can’t know when to use them.

## SFT with Special Tokens Training

In full fine-tuning, retraining or not special tokens isn’t a question, as all token embeddings are updated during training.

However, when using LoRA or QLoRA fine-tuning, we typically add adapter layers on top of the model’s linear layers and freeze everything else, including token embeddings and the language modeling head.

For effective SFT, I recommend unfreezing the token embeddings and language modeling head to help the model adapt more effectively to specific tasks and domains, especially if special tokens haven't been previously trained.

With PEFT and Transformers, you can add adapter layers to the self-attention and MLP modules while still retraining the token embeddings and language modeling head. The following LoRA configuration (LoraConfig) illustrates this approach:

```
peft_config = LoraConfig(
lora_alpha=16,
lora_dropout=0.05,
r=16,
bias="none",
task_type="CAUSAL_LM",
target_modules= ['k_proj', 'q_proj', 'v_proj', 'o_proj', "gate_proj", "down_proj", "up_proj"],
modules_to_save=['embed_tokens','lm_head'],
)
```


*Note: Be sure to spell the module names correctly as peft won’t tell you if a module doesn’t exist.*

A key drawback is the increased GPU memory consumption due to the large number of trainable parameters, primarily because the AdamW optimizer doubles the parameters by creating two for each one being trained.

With Llama 3.2, however, retraining the language modeling head is unnecessary since it uses tied embeddings. This means the language modeling head shares weights with the input embeddings and isn’t serialized separately. To verify if a model uses tied embeddings, check its configuration file:

So we can drop the "lm_head" module. The LoraConfig becomes:

```
peft_config = LoraConfig(
lora_alpha=16,
lora_dropout=0.05,
r=16,
bias="none",
task_type="CAUSAL_LM",
target_modules= ['k_proj', 'q_proj', 'v_proj', 'o_proj', "gate_proj", "down_proj", "up_proj"],
modules_to_save=['embed_tokens'],
)
```

## Testing an Adapter Fine-tuned with SFT

To test the adapter, run the following code:

```
from transformers import AutoModelForCausalLM, AutoTokenizer
from peft import PeftModel
import torch
model_name = "meta-llama/Llama-3.2-3B"
adapter="./Llama-3.2-3B-embed_tokens/checkpoint-742/"
attn_implementation = 'flash_attention_2'
model = AutoModelForCausalLM.from_pretrained(
model_name, device_map={"": 0}, torch_dtype=torch.float16, attn_implementation=attn_implementation
)
model = PeftModel.from_pretrained(model, adapter)
messages = [{"role": "system", "content": "You are an educational chatbot."},
{"role": "user", "content": "What can you tell me about muons?"}]
device = "cuda"
tokenizer = AutoTokenizer.from_pretrained(model_name+"-Instruct")
input_chat = tokenizer.apply_chat_template(messages, tokenize=False, add_generation_prompt=True)
print(input_chat)
inputs = tokenizer(input_chat, return_tensors="pt").to(device)
outputs = model.generate(**inputs, pad_token_id=tokenizer.eos_token_id, max_new_tokens=600)
print(tokenizer.decode(outputs[0]))
```


Note that this time we pass "add_generation_prompt=True" when applying the chat template. This argument tells the tokenizer to add the assistant’s tags at the end of the prompt so the model will start completing the prompt as the assistant. If we don’t set it, the LLM will complete the user prompt instead.
