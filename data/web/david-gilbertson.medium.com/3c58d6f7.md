# Text classification with vector embeddings — and no ML model

In this post I’ll show you how to classify text without training a machine learning model, using the information contained in embedding vectors.

Before I get into the explanation, you probably want to know how effective this is compared to other methods. So to save you scrolling down to find the charts, here’s one from later in the article:

![](https://miro.medium.com/v2/resize:fit:700/1*C4Q_O1XvH2Q1q6_CZ9ekZw.png)

I’ll explain the details in due time, all you need to know for now is that “SDC” is the technique I describe in this article, and that when using the right embedding model, it comes quite close to a transformer fine-tuned on the same binary classification task.

And here’s another — a comparison between SDC and a collection of ML techniques on a multi-class classification task.

![](https://miro.medium.com/v2/1*rI7FbMLzPFkJn1nEIAXVZw.png)

Let’s get started…

## An example classification task

To demonstrate the concept, I’ll need a dataset of texts and a classification task.

For the dataset, I’ll use my own history of messages to ChatGPT (exported and parsed to a CSV). This contains all my messages, a mix of initial questions/prompts and continuations of conversations.

The task will be to select all the messages where I’m telling ChatGPT that it hallucinated, failed to answer the question, provided code that errored, or did a bad job in some other way. For the sake of brevity I’ll refer to all such messages as ‘dissatisfied’ (even though that’s an imperfect label).

To put this task in context, the idea is to find instances where an LLM could be improved, regardless of whether the user hit the thumbs down button or not.

I’ve picked this dataset and task for two reasons:

- It’s a somewhat subtle concept, so we can see if embeddings contain this level of nuance.
- It’s a ‘sparse target’ problem — only about 3% of my 8,000 messages to ChatGPT express dissatisfaction. This is more difficult than a task where the classes are balanced.

In preparation, I’ve created an embedding vector for each of these messages, using OpenAI’s `text-embedding-3-large`

with the default 3,072 dimensions. (Here’s my overcomplicated helper function to embed texts with OpenAI.)

## The code

Let’s jump straight to the code and see some initial results. Then I’ll explain how it works.

First, I load the messages and their embeddings:

`import pandas as pd`

import numpy as np


df = pd.read_csv("messages.csv") # 8,000 rows, Message and Target columns

embeddings = np.load("embeddings.npy") # 8,000 rows x 3,072 dimensions

In my CSV, I’ve labelled three dissatisfied messages already, so my dataframe’s `Target`

column has three `True`

values, the rest are `False`

.

Now I’ll write the following line of code to get a score for each message:

`df["Score"] = embeddings @ (embeddings.T @ df.Target)`

And — after sorting by score — here’s the first 30 of my 8,000 messages:

![](https://miro.medium.com/v2/resize:fit:699/1*A29ZpAevzFVsQd_DhXAw9w.png)

This might seem a bit like magic, it appears to be a system that:

- Has learnt by example (and only three examples!)
- Isn’t overfitting (the positive samples aren’t the first three)
- Could classify the messages if we picked a threshold score

Yet I haven’t trained any model, it all happens in those two matrix multiplications.

Of course, there is no magic. You can think of the embedding matrix as containing the information required for *all possible classification tasks.* All we need to do is arrange that information into a score to suit the task at hand.

## How it works

To see what’s going on, let’s take a moment to explore just how much information is encoded in these embeddings.

Side note: if your brain gets warm thinking about multi-dimensional spaces, just picture the embedding matrix as a spreadsheet with one row per message and 3,072 columns. Whenever you hear the word ‘dimension’, think ‘column’.

### Single dimensions

One might wonder: of the 3,072 dimensions in the embedding matrix, do any of them happen to represent “David telling ChatGPT he’s disappointed with its response”?

As it turns out, dimension number 2,187 is pretty close. Let’s sort by that.

`indices = embeddings[:, 2187].argsort()`

df = df.iloc[indices]

And here’s the top results:

![](https://miro.medium.com/v2/resize:fit:523/1*BWh5ZGoYbFxPupzrK1qzrA.png)

You can see it doesn’t *exactly* align with the concept of ‘dissatisfied message’, but it’s in the right ballpark.

Dimension number 776 is pretty close too, and so is 520. They each express displeasure, doubt, correction, or something along those lines.

### Scaling and combining dimensions

So the information we want is in the embedding matrix. Great. But we don’t want to deal in individual dimensions, we want to combine all dimensions, giving more weight to those that better represent the semantic concept we want to classify.

So we might want to create a vector of weights, one for each dimension.

Let’s filter the embedding matrix for just the three positive samples, and calculate the mean embedding of these three.

`signature = embeddings[df.Target].mean(axis=0) # 3,072 values`

Think of this as a new embedding that represents the three messages marked as dissatisfied. The larger the magnitude of a value in `signature`

, the better that dimension represents the target. (I’m simplifying a bit here, since it’s the *relative* magnitudes of L2-normalised embeddings that capture meaning, but for understanding what’s going on you don’t need to worry about that.)

You could think of this `signature`

variable as ‘weights’, except it contains both positive and negative values, and it’s the magnitude that represents importance.

Earlier I wrote this as matrix multiplication, which gives the sum instead of the mean.

`signature = embeddings.T @ df.Target`

This is fine for sorting (and showing off with overly condensed code), but we’d like the signature on the same scale as the embeddings, so from here on in we’ll use the mean.

If we plot the 3,072 values in `signature`

, we can see that a few have significantly higher magnitude.

![](https://miro.medium.com/v2/resize:fit:700/1*ci49S0g6iqhDLDSMylwvSg.png)

I’ve marked the top 15 values with dots the colour of mandarins; you can think of these as the dimensions that are the best indicators of ‘dissatisfaction’.

Is it clear why this happens? If a dimension has nothing to do with dissatisfaction, it’s likely to have different values for each of the positive samples, so the mean will tend toward zero. When a dimension is consistently high or low across samples will it result in a high-magnitude value in the signature.

Let’s compare this to the single embedding vector for the message “That’s incorrect.”, with the same 15 dimensions marked:

![](https://miro.medium.com/v2/resize:fit:700/1*DgkGOV1p3RhSJZ7fivRTyg.png)

As you can see, this has high-magnitude values in many of the same places.

Compare that to a message that shows no signs of dissatisfaction:

![](https://miro.medium.com/v2/resize:fit:700/1*xx_30vfq3P9iKBeEk77O6Q.png)

So visually we can spot a ‘good match’, now we just need to do algorithmically what we can see in these charts.

To do this, we can multiply the embedding for an individual message by the signature embedding (element-wise) and sum the resulting values into a single value. Actually we want to do this for every message, so to do them all at once, we can matrix multiply the full embedding matrix (8,000 x 3,072) by the signature (3,072) to get 8,000 scores (one for each message).

`scores = embeddings @ signature # 8,000 scores`

If a message contains a sense of dissatisfaction, we can expect its embedding to have high magnitude values for the same dimensions that have high values in the signature embedding, so we’ll be multiplying big values by big values to get really big values. It just so happens that multiplying two negatives will result in a positive, so we can interpret the final score as ‘bigger is better’.

You might recognise this as similar to calculating covariance. Because it is.

Hey, that reminds me, the columns of our embedding matrix (the dimensions) are essentially independent features of the texts, so we should probably normalize them to each have a mean of zero and standard deviation of 1.

`embeddings = (embeddings - embeddings.mean(0)) / embeddings.std(0)`

This is important, because some dimensions will tend to have larger values or more variance than others (because my dataset is not uniformly distributed across the embedding space). Normalizing the columns first will ensure that all dimensions are treated equally and that we’re only comparing how similar an embedding is to the signature. (On this particular task, omitting this step drops the F1 score by 20 percentage points).

Fun fact: if you instead normalized each embedding (row) to have an L2 norm of 1, the scores become cosine similarity, but the results would be worse. (Stay tuned for a blog post explaining why cosine similarity isn’t ideal for similarity search over embeddings, once I’ve worked out if/when that’s true.)

OK, with all these pieces put together, the code looks like this:

`import pandas as pd`

import numpy as np


# Load the data

df = pd.read_csv("messages.csv") # 8,000 rows

embeddings = np.load("embeddings.npy") # 8,000 rows x 3,072 dimensions


# Normalize embedding values

embeddings = (embeddings - embeddings.mean(0)) / embeddings.std(0)


# Combine embeddings for all positive samples

signature = embeddings[df.Target].mean(0)


# Multiply each sample's dimension values by the signature, sum to a single value per sample

df["Score"] = embeddings @ signature


# Sort the dataframe

df = df.sort_values("Score", ascending=False)

In one sense, this technique is not particularly interesting (or complicated) and I’m quite sure I’m not the first to think of it. But in everything I’ve read about text classification, not once have I seen this put forward as a suggestion. I’d say this makes it just interesting enough to warrant a name.

Since all we’re really doing is *scaling* the *dimensions* and *combining* them, I’ll refer to this technique as **Scaled Dimension Combination (SDC) .**

## Interlude: do embeddings contain information?

I’ve been a bit loose with my language so far, suggesting that embeddings ‘contain information’ about the text. In practice this is a fine way to think about embeddings, but technically speaking, they contain no information about the meaning of the text.

To understand, let’s look at a more familiar embedding system with just two dimensions.

I could tell you that my location right now is [-33.811058, 151.268929] and that might seem informative (if you recognise them as latitude and longitude), but those numbers don’t actually contain information about my location. It’s only if you *compare* those numbers to the numbers of other places in the same space (perhaps using a ‘map’) that you can learn things about my location. So the ‘embedding’ is only useful when compared to other embeddings.

To clarify the distinction: we could look at many real world locations and find that there’s a relationship between the first dimension (latitude) and a location’s temperature. This doesn’t mean that the first dimension ‘represents’ or ‘encodes’ the temperature, and it certainly doesn’t mean that this dimension ‘contains information’ about the temperature. It just means that empirically we’ve noticed a relationship and so can infer something about a location’s temperature from the first dimension.

And so it goes with text embeddings, except there’s a lot more dimensions.

So an embedding doesn’t exactly “represent the text” that it embeds, it represents *where the text is located *in some multidimensional space. If we look at *other *examples of text, and where they reside in that same space, we can learn things like “those with lower values in dimension 2187 tend to show dissatisfaction”.

It’s a subtle difference and quite possibly irrelevant. Shall we move on? Yes, let’s.

Next up, I’ll cover a few use cases for SDC, starting with sorting results and data exploration, before moving on to binary and multi-class classification.

### Walkthrough of the process

You might be thinking that this is risky, because you’re only selecting the samples that get sorted early, and don’t know what you’re missing. So let me walk you through the actual steps I took when classifying my ‘dissatisfied’ ChatGPT messages:

- First, I found a few positive samples by searching for messages starting with ‘No’.
- Then I ran SDC and sorted.
- Then I scanned the top-ranked samples for other possible keyword searches and found “that’s wrong”, “incorrect”, “you sure?”, etc.
- I searched the dataset for each of these terms and labelled more samples as positive.
- At this stage, I’m not actually selecting samples based on the SDC sort order, rather I’m getting ideas for keyword searches, which gets me both the samples with a high SDC score and others that happen to get a low score. This ‘rounds out’ the signature so that it’s not focused on a narrow concept.
- I iterate until I’m not discovering any new keywords.
- Then I sort by score one last time and select any positive cases that don’t contain any of the identified keywords.

It’s easy enough to wrap this up in a UI where I can search, select and have the sort order update automatically. Here’s a basic one I made with Streamlit:

**Exploratory data analysis**

Let’s say you’re exploring a large dataset of texts and want to find samples that match a particular theme. String matching alone won’t be good enough, and fine-tuning a transformer is too slow.

## SDC for Classification

First, let’s look at how SDC compares with the alternatives.

### Comparison with ML models

For text classification, fine tuning a transformer model like BERT is typically going to get the best results (especially with a sparse target, like when only 3% of samples are positive).

So below I’ll compare a few variants of Scaled Dimension Combination (SDC) with Transformer Fine-Tuning (TFT) on the ‘dissatisfied messages’ classification task.

For SDC, I tested four embedding models:

- OpenAI’s
`text-embedding-3-large`

model with 3,072 dimensions - The open source Nomic v1.5 model, which produces 768 dimensions
- The open source Stella 1.5B with 8,192 dimensions
- The brand new (2025)
`voyage-3-large`

model at 1024 dimensions (which outperformed 2048 dimensions). The Voyage model was a bit disappointing because according to their tests it wipes the floor with OpenAI, but at least in this one test it’s left holding the wet end of the mop.

For TFT I tested two models:

- A 2024 ModernBERT-large
- A 2019 RoBERTa base

To repeat the graph I showed earlier, here’s how they all stack up:

![](https://miro.medium.com/v2/resize:fit:700/1*C4Q_O1XvH2Q1q6_CZ9ekZw.png)

With the right embeddings, SDC gets quite close to the fine-tuned transformers. But before you get too excited, there’s a few things to note:

- To fine-tune the BERT models I wrote some low-effort code and trained for 3 epochs. With more epochs, hyperparameter fiddling, and other tricks like SMOTE, the TFT scores would likely increase.
- You’ll recall that I selected the positive samples using mostly keyword search but some SDC. This may slightly over-inflate SDC’s score (my gut feel is not by much).
- Anecdotally, TFT false positives are more reasonable than SDC false positives, which often seem a bit odd (e.g. SDC classifies ‘yes’ as dissatisfied).

I also tested OpenAI embeddings with dimension counts from 128 up to 3,072. Here’s the relationship between dimensions and F1 score:

![](https://miro.medium.com/v2/resize:fit:700/1*l048ghBp3WpqAE5WTebW7A.png)

There appears to be improvement all the way up to 3,072 dimensions. Keep in mind that the classification task involves quite a subtle concept. On an easier task (categorising articles), scores plateaued above about 1,500 dimensions. The moral to the story: test this for your own data to find a reasonable number of dimensions to use.

In terms of run time, TFT will take thousands of times longer than SDC *if *you already have embeddings of your text. On my data, fine-tuning a transformer takes **1,800,000ms **(half an hour), while SDC takes **8ms**. To predict a batch of 2,000 samples, TFT takes about **35,500ms** while SDC takes **1ms**. If you factor embedding time into the equation, TFT training will still take hundreds of times longer than SDC (it only takes 20 seconds to get 8,000 embeddings), but prediction times are about the same (since you need to make a network request to get the embedding).

As a general rule, I think it’s safe to say that fine-tuning a transformer will likely get better results, but considering how fast and simple SDC is, there might be some scenarios where it’s the better option. Such as…

**When you won’t address all the positive cases**

Let’s say you’ve got a school chat server and a dataset of all messages. You want to identify bullying comments and have a little chat with each offending student. In one sense, this is a binary classification task. But in reality, you’ll want to sort by worst first and work through as many cases as you can before running out of time or patience. In this case, a few points difference in F1 score is immaterial.

**When humans make the call before acting on a prediction**

If positive predictions are verified by a human before any action is taken, then a few extra false positives aren’t really a problem (within reason).

**When you haven’t labelled all the positive cases**

When fine-tuning a transformer, the model learns from positive *and* negative cases, so you need to have everything labelled correctly or you’ll be teaching it the wrong thing.

But with SDC, only the positive samples are used to ‘train’ (create the signature vector), so you can select just a handful of these and get pretty good results.

This also applies when you don’t really know what the positive cases should be. E.g. you might have a vague idea that you want to classify “offensive” text, but when you sit down to look at examples, you’ll see that reasonable people disagree on what exactly deserves such a label.

**When you’re frequently updating positive cases**

With TFT, every time you identify a new positive case, you need to re-fine-tune the transformer to take that into account (this is challenging to do incrementally). But with SDC you just re-calculate the signature, which takes about one millisecond. It’s fast enough that you can update a UI in real time as a user interacts in some way with your application.

**When you want one ‘model’ per user**

With SDC, you only need to store the signature to be able to perform classification (a few KB). With TFT you would need to store a fine-tuned model per user (probably more than one GB, or several MB with LoRA).

To be clear, TFT and SDC both require a big model somewhere. The difference is that with TFT the big model is specific to a classification task, but with SDC, the big model (that generates the embeddings) is universal.

**When you don’t want to manage an ML model**

Training, deploying, serving, and maintaining an ML model ain’t easy. Since SDC can use a generic embedding model accessible via API, you can avoid a lot of complexity. This is particularly beneficial if you don’t have strong MLOps expertise at your disposal.

OK, let’s take a look at the classification code…

### A binary SDC classifier

The below code has a traditional ML-style setup with train and test splits of the data. The actual SDC logic is all contained in the `SDCBinaryClassifier`

class, the rest of the code demonstrates using it and scoring the results.

`import pandas as pd`

import numpy as np

from sklearn.metrics import f1_score

from sklearn.model_selection import train_test_split



class SDCBinaryClassifier:

def train(self, X, y):

self.signature = X[y].mean(0)

scores = X @ self.signature

self.cutoff_score = np.sort(scores)[-y.sum()]


def predict(self, X):

scores = X @ self.signature

return scores >= self.cutoff_score



df = pd.read_csv("messages.csv")

embeddings = np.load("embeddings.npy")


X_trn, X_tst, y_trn, y_tst = train_test_split(embeddings, df.Target)


sdc = SDCBinaryClassifier()

sdc.train(X_trn, y_trn)

predictions = sdc.predict(X_tst)


f1 = f1_score(y_tst, predictions)

print(f"F1: {f1:.1%}")

I’ve explained most of this already, the new thing here is that in the `train`

method, we work out what the ideal cutoff score is, then use that in the `predict`

method to convert scores into binary values.

If you value precision and recall equally, then the ideal score to split on is delightfully easy to find: if you have *n* positive samples, you should predict `True`

for *n* samples. When sorted by score, at this cutoff point the precision, recall, and F1 scores will all equal each other because any True prediction you get wrong is a false positive (FP), and must be balanced by a false negative (FN). When FP equals FN, then precision equals recall. It follows that F1 will be the same as precision and recall, since it’s just the harmonic mean of the two.

Note that if you have a massive dataset (millions of rows, too big to fit in memory), you don’t need to use it all. You can take a random sample of the embeddings and targets (as many as will fit in memory) and get an approximation of the ideal cutoff score from that.

The above code is the bare minimum required to show the concept in action. In reality you might want to accept strings and do the embedding within the class. And you might want to add `save`

and `load`

methods. You could also adjust this to expect PyTorch tensors so everything can happen on the GPU (you’ll need to adjust the `np.sort`

line).

There’s one more layer of complexity: you’ll want to normalize the dimensions so that they’re all on the same scale. In the `train`

method, we’ll calculate and store the mean and standard deviation of each embedding dimension, and use these to centre the embeddings in both the `train`

and `predict`

methods.

`class SDCBinaryClassifier:`

def train(self, X, y):

# Center the embeddings

self.mean = X.mean(0)

self.std = X.std(0)

X = (X - self.mean) / self.std


self.signature = X[y].mean(0)

scores = X @ self.signature

self.cutoff_score = np.sort(scores)[-y.sum()]

return self


def predict(self, X):

X = (X - self.mean) / self.std

scores = X @ self.signature

return scores >= self.cutoff_score

### Writing a multi-class classifier

You can do multi-class classification by calculating a signature for each label. In this case, you don’t need a cutoff score because the prediction will be whichever label gets the highest score. A minimal implementation looks something like this:

`class SDCClassifier:`

def train(self, X, y):

self.signatures = [(label, X[y == label].mean(0)) for label in set(y)]


def predict_one(self, embedding):

predicted_label, score = max(

((label, embedding @ sig) for label, sig in self.signatures),

key=lambda x: x[1],

)

return predicted_label


def predict(self, X):

return list(map(self.predict_one, X))

This works absolutely terribly on sparse binary tasks (like finding ‘dissatisfied’ messages by treating ‘True’ and ‘False’ as two class labels) because the opposite of dissatisfied doesn’t really look like anything.

It works better on regular classification tasks. For an example, I’ve borrowed from this scikit-learn page that compares a bunch of classification methods classifying the 20 newsgroups dataset.

The below chart shows the original results from the Scikit-Learn page, and how SDC compares on that same dataset and task.

![](https://miro.medium.com/v2/1*rI7FbMLzPFkJn1nEIAXVZw.png)

A few things to note:

- This is not a fair fight. SDC works on embeddings created by a massive embedding model, while the other methods all make do with TF-IDF to vectorise the text.
- SDC is much slower, if you include the embedding time (or about the same speed if you don’t).
- Then again, SDC doesn’t require any hyperparameter optimisation. So if you take into account the hours you’d spend doing HPO, SDC will get you results more quickly.

By the way, I gave Voyage embeddings another chance on this task and their 1024-dimension embeddings performed the same as OpenAI’s 3072-dimension embeddings. I suspect because this is an easier task. So I’d suggest giving them a shot too.

I also compared SDC with training `RandomForest`

and `XGBoost`

models on the embedding matrix, and the results were a mixed bag. Sometimes the ML models are much worse: with the task of finding ‘dissatisfied’ messages, SDC gets around 80% F1 while the ML models were both below 30% (not surprising for a problem with highly imbalanced class labels). But when replicating this OpenAI cookbook code classifying Amazon reviews, a `RandomForest`

trained on embeddings has an accuracy of 78% while SDC only manages 62%.

A tentative general rule to draw from all this is that you’ll probably get the best results from fine-tuning a transformer. But if you want something smaller and faster, you should try ML models like RandomForest and XGBoost as well as SDC to find the one that works best for your particular problem.

## Things to consider

### Cost

One concern with embeddings might be that the good ones cost money.

Embedding my ChatGPT messages cost a few cents. But embedding one million texts, each 500 words long, would cost about $85 (with the large OpenAI embedding model).

Now, I don’t know how you value your time, but $85, compared to fine-tuning a transformer (messing about with hyperparameters for hours on end) is probably a bargain.

### Knowledge cutoff

Embedding models only know about the world as it was when they were trained, so if your classification task involves a concept newer than that date, you might be out of luck.

Likewise, if you’re classifying articles about, say, space, an embedding model from early 2024 probably isn’t going to understand that SpaDeX falls into that category.

### Embedding storage

If you embed 100,000 texts with 3,072 dimensions and save to disk (or database), it’ll take up about 2.3 GB. We can improve on this.

Firstly, NumPy defaults to 64 bit floats, but OpenAI embeddings are only 32 bits, so we could halve this and get identical results.

Secondly, in my tests I could store the embeddings at 16 bits and see no loss in F1 score, provided I converted them to 32 bits after loading (for numerical stability in the matrix multiplications).

`# After generating the embeddings`

np.save("embeddings.npy", embeddings.astype(np.float16))


# Later...

embeddings = np.load("embeddings.npy").astype(np.float32)

So that’s only 570 MB for 100,000 texts.

When saved as 8 bit ints, the F1 score did drop, but only by 0.6%.

So if size is a concern, my suggestion is to look at reducing the precision of the stored embeddings as well as selecting a minimal number of dimensions.

By the way, if you’ve been wondering why I store my embeddings with NumPy rather than Pandas, it’s because it’s much faster both loading from disk and performing matrix multiplication.
